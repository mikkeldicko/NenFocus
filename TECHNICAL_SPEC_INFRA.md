# NenFocus — Technical Specification & Infrastructure Notes

Tactical implementation details, current build state, and platform-specific gotchas. Read this when you need to understand *how something works*, not *why it exists* (that lives in `ARCHITECT_GOVERNANCE.md` and `DOMAIN_DICTIONARY.md`).

---

## Current Implementation State

### Done

- Full domain model (Session, BlockPreset, FocusBlock, BackgroundBlock, all value objects and events)
- `Session` entity has `Rating (int?)` and `Reflection (string?)` properties; `ResumeFromBreak()`, `SetReflection(string, int)`, and `Complete()` methods
- All Application commands, queries, validators, and event handlers — fully refactored to Vertical Slice Architecture (feature folders)
- `SystemSafetyConstants.UnkillableProcesses` safety shield prevents blocking critical Windows processes (validated in command validators via normalised process name)
- EF Core + SQLite persistence (all three repositories); `BlockedAttemptTracker` uses SQLite with a 2-second debounce threshold for accurate attempt counting
- Windows enforcement: process kill loop (`p.Kill(entireProcessTree: true)`) + hosts file rewriting + DNS flush + IPv6 (`::`) entries
- `ScheduledEnforcementService`: BackgroundService heartbeat running every 5 seconds; delegates policy computation and state management to `WindowsEnforcementService`
- `WindowsEnforcementService`: exposes a local HTTP API on `http://localhost:5005` — `/check` (returns `{ "blocked": true/false }` based on active policy) and `/report` (logs web block attempts from extension); uses `SemaphoreSlim` to prevent hosts file collisions
- Browser extension (`NenFocusExtension/`): intercepts navigation, queries `/check`, redirects to `blocked.html` if blocked, calls `/report` to increment the web block counter
- Registry enforcement: disables DNS-over-HTTPS (DoH) in Chrome, Edge, and Brave via `BuiltInDnsClientEnabled = 0` registry key, preventing browsers from bypassing the hosts file
- Admin manifest (`requireAdministrator`): required for hosts file writes, registry key edits, and high-privilege process tree termination
- Windows toast notifications. Scheduled break reminders (in-process `Task.Delay`) are implemented in `WindowsNotificationService` but never wired to any caller — see Known Workarounds below and `ARCHITECT_GOVERNANCE.md` → Open Gap I.
- Session rehydration on startup: `SessionStateService.InitializeAsync()` queries DB for active/on-break sessions and maps domain entities to `SessionDto`; `SessionStateService` injects `IBlockPresetRepository` to resolve the real preset name from its ID
- Session persistence across app restarts (`%AppData%\NenFocus\active_session.json`)
- Post-session reflection: `SaveReflectionCommand` persists `Rating (1–5)` and `Reflection (string)` to the `Session` entity
- Distraction logging: app kill attempts tracked via `IBlockedAttemptTracker.RecordBlocked`; website block attempts tracked via `RecordWebBlocked(domain)`; `EndSessionCommandHandler` groups logs by `ResourceName` and `AttemptType`, serialises to a `historyData` JSON field on the session
- `ActivePolicySlice` (Domain Value Object, `NenFocus.Domain/ValueObjects/ActivePolicySlice.cs`): the canonical enforcement contract produced by `PolicyEngine.ComputeSlice()`. Carries `WebsiteFilterTypeMode` (`Blocklist`/`Allowlist`), `BlockedApps`, `BlockedSites`, `AllowedSites`, `ActiveSessionId`, and `ActiveBlockPresetType (BlockPresetType?)`. `IsEmpty` is `true` only in Blocklist mode with no blocked apps or sites. Consumed directly by `WindowsEnforcementService` and `ScheduledEnforcementService` — no DTO crosses the Application→Infrastructure enforcement boundary. Replaces the deleted `PolicySliceDto`.
- `PolicyEngine` / `IPolicyEngine` (`NenFocus.Domain/Services/`): stateless Domain service that accepts raw `BlockPreset`, `Session`, and `PlannedBlock` collections and computes the `ActivePolicySlice`. All merge logic (app union, allowlist/blocklist precedence, `ActiveBlockPresetType` priority) is encapsulated here. `ComputeActivePolicySliceQueryHandler` is now a pure orchestrator — it fetches, then delegates.
- **Blocklist mode fixed**: `PolicyEngine` correctly populates `BlockedSites` in Blocklist mode (was always an empty set in the old `ComputeActivePolicySliceQueryHandler`, causing the browser extension to block nothing)
- Ritual wizard (Ten → Zetsu → Ren → Hatsu) — fully wired end-to-end
- Main page: active session panel, countdown timer, progress bar, "USE NEN" button, end session, take a break, resume from break (auto-resume when break timer expires, restores correctly across app restarts)
- Shell navigation structure (sidebar with nav items, page switching)
- Block Presets page: full CRUD (create, edit, delete, duplicate), tabbed modal (Websites / Apps tabs), file picker for app selection (opens to `C:\Program Files`), click-to-edit preset cards
- App blocking works correctly — `NormalizeProcessName` strips only `.exe` suffix (not `Path.GetFileNameWithoutExtension`) so dotted names like `kcc_10.0.1` are preserved
- **Enforcement gap fixed**: `SessionStartedEventHandler` now injects `IEnforcementService` and `IQueryHandler<ComputeActivePolicySliceQuery, ActivePolicySlice>`; computes the current policy slice (a Domain Value Object) and calls `ApplyPolicyAsync` before sending the session-start notification. Enforcement is event-driven: `StartSessionCommandHandler` publishes `SessionStartedEvent` → `InProcessDomainEventPublisher` → `SessionStartedEventHandler` applies the policy
- Planner use cases fully refactored to Vertical Slice Architecture: `CreatePlannedBlock/`, `UpdatePlannedBlock/`, `DeletePlannedBlock/` — each with Command, Result, CommandHandler, Validator; `DeletePlannedBlock` returns `DeletePlannedBlockResult` (not `bool`); handlers apply `.ToUniversalTime()` before any DB/overlap logic
- `IActiveSessionMonitor` / `ActiveSessionMonitor`: singleton countdown engine that owns the `System.Timers.Timer`, subscribes to `ISessionStateService.SessionChanged`, auto-ends sessions and auto-resumes breaks by calling command handlers via `IServiceScopeFactory`
- `StartBreakCommandHandler` and `ResumeFromBreakCommandHandler` now call `_sessionState.SetActive(current with { ... })` after saving — break UI state propagates correctly
- `SessionStateService.MapToDto` maps `BreakSettings` domain value object to `BreakSettingsDto` (was previously always null on DB restore)
- `Session` entity stores `TemporaryBlockedApps` and `TemporaryBlockedSites` (`IReadOnlyList<string>`, JSON-serialised to TEXT columns via EF Core value converter); `PolicyEngine.ComputeSlice()` unions these into every policy computation so session-level Ren page additions are enforced immediately. Persisted to the DB so Insights can display per-session temporary additions alongside the base preset
- `StartSessionCommandHandler` now fetches `PresetName` from `IBlockPresetRepository` and includes it in the `SessionDto` passed to `ISessionStateService.SetActive`; preset name is no longer blank on the Main page after session start

- `ScheduledEnforcementService` reads `ActiveBlockPresetType` from the computed `ActivePolicySlice` (Domain Value Object) each heartbeat cycle; calls `_sessionState.SetRitualRequired(true)` when `ActiveBlockPresetType == Focus` and no session is active, triggering the Ritual overlay automatically at the Focus Block's designated start time

Also accepts `AdditionalBlockedSites` and `AdditionalBlockedApps` (raw strings from the Ren page) and writes them to `Session.TemporaryBlockedSites`/`TemporaryBlockedApps`

- **Sealed-contract enforcement guards on planned blocks (2026-08-11)**: a block whose `ContractId` resolves to a contract with `IsInEffect == true` (Scheduled or Active — a Completed/Broken contract falls back to the ordinary `HasEnded`-based protections) is now protected by its contract's `StrictnessRule`. `DeletePlannedBlockValidator` rejects any delete unconditionally, regardless of strictness. `UpdatePlannedBlockValidator` rejects any preset (`BlockPresetId`) change outright, and gates time changes through the new `NenContract.AllowsBlockTimeChange(originalDate, newStartDate, newEndDate)` — pure entity method mirroring `AllowsBlockPlacement`/`CheckRedemptionEligibility`'s shape: `Locked` rejects every edit (there is no field-by-field carve-out — `UpdatePlannedBlockCommand` has no `Title` field to begin with, and `RedemptionEntries` was already separately blocked for `Locked` via `CheckRedemptionEligibility`), `DailyFlexibility` requires the new window to stay on the block's original local calendar day, `PeriodTimeBudget` requires it to stay within `[StartDate, EndDate]`. `PlannedBlockDto.IsUnderInEffectContract` (computed once by `GetPlannedBlocksForDayQueryHandler`, same "Application computes, UI only references" discipline as `HasEnded`) drives hiding the Planner's Delete button for these blocks. `MoveOrResizeBlockAsync` now reloads the week on a rejected drag too (previously only on success), so a rejected move snaps the tile back instead of leaving it stuck at the rejected drop point — a latent bug for any rejection reason, not specific to this feature, just far more visible now that contract guards reject moves routinely.
- **Active-contract banner, week-scoped (built 2026-08-11, redesigned same day)**: closes the "active-contract visibility" gap below. `GetActiveNenContractQuery(WeekStart, WeekEnd)`/`GetActiveNenContractQueryHandler` composes the already-built `GetNenContractDeficitsQuery` and `GetNenContractCompletedFocusHoursQuery` (the established "inject a sibling `IQueryHandler`" pattern) into `ActiveNenContractDto`. The query is scoped to the Planner's *currently viewed week*, not "is any contract in effect anywhere" — `INenContractRepository.GetAllInEffectAsync()` (initially `GetInEffectAsync()`, a single pre-resolved contract; widened same day once the week-scoping requirement made a single global answer insufficient — see below) returns every Scheduled/Active contract, the handler filters to those whose `[StartDate, EndDate]` overlaps `[WeekStart, WeekEnd]` (inclusive both ends — sharing exactly one boundary day counts as overlapping), then tie-breaks (Active preferred over Scheduled, then earliest `StartDate`) — only one contract surfaces at a time. `NenContract.IsRestDay(DateOnly)` (`DailyFloorPolicy.For(date) is null`, same resolution `IsDayMet` uses) was added so the handler's days-behind count never reaches into `DailyFloorPolicy` directly; Day-X/Y and deficit figures stay relative to "today" (the clock) regardless of which week is viewed. `PlannerPageViewModel` refreshes it on init, after a successful Seal, whenever a session ends, and now on **every week navigation** — the banner disappears when the viewed week no longer overlaps the contract's range and reappears when it does. `PlannerPageView.axaml` shows it in its own persistent banner row — independent of and stackable with the pre-existing ephemeral drafting-mode banner — reading "Contract: [Name] — Day X/Y — Z of N days behind — Hh deficit", the exact format designed when Gap C2 was interrogated.
- **Contract cancellation reachable from the UI (2026-08-11)**: `NenContract.Break`/`BreakNenContractCommand` already existed fully built (Application + Infrastructure) with no UI trigger anywhere — this closes that half of the "Extend/Break UI" gap below (Extend is still unreached). - **Drafting-mode placement constraints (2026-08-11)**: while drafting (post-"Begin Scheduling", pre-Seal), a draft block must start in the future **and** fall entirely within the draft contract's `[StartDate, EndDate]` (both the block's start day and end day, mirroring `AllowsBlockTimeChange`'s DailyFlexibility check). No drag-gesture-level blocking exists anywhere in this codebase — every existing rule (Focus-overlap, Work Hours, past-date for ordinary blocks) rejects after the fact with an error message, so this follows the same shape: a new `PlannerPageViewModel.ValidateDraftPlacement(localStart, localEnd)` helper, shared by `SaveDraftBlock` (create/edit-via-form → `FormError`) and `MoveOrResizeBlockAsync`'s draft branch (drag-move/resize of an already-placed draft tile → `DragError`) — the latter previously had **zero** validation of any kind (not even the Focus-overlap check `SaveDraftBlock` already had), a real gap closed in the same pass since leaving it open would have been an immediately-discoverable loophole around the new restriction. On rejection, the draft-move branch calls `RebuildDraftTilesInPlace()` without mutating `_draftBlocks`, snapping the ghosted tile back to its true position — same "reload on failure too" fix already applied to the non-draft drag path in the sealed-contract-guards pass above.
- **Contract date-range overlap validation (2026-08-11)**: no two in-effect (Scheduled or Active) contracts may share any day — `StartDate`/`EndDate` are inclusive on both ends, so contracts sharing even one boundary day count as overlapping. ## Key Behaviours & Rules

### Session Rules

- Only one Focus session at a time (`HasActiveSessionAsync` check on start).
- Once a session starts, the preset is **locked** — it cannot be edited mid-session.
- Session-only adjustments (Ren page) are not persisted to the preset; they apply only for the duration.
- Users can **extend** the timer (make longer). Ending early is also currently possible — `MainPageViewModel.EndSession()` has no guard beyond `EndSessionCommandHandler`'s own `Status == Active || OnBreak` check, so any active or on-break session can be ended at any point (this doc previously claimed the opposite; corrected 2026-08-12, drift found and fixed against `DOMAIN_DICTIONARY.md`'s already-accurate note). Ending early stamps the originating `FocusBlock.SessionEndedAt` (closed 2026-08-12, `DESIGN_GAP_HISTORY.md` Gap 22) rather than mutating `End` — the original schedule is preserved for deficit/credited-hours accuracy, and the Planner tile is shortened only for display (`GetPlannedBlocksForDayQueryHandler`). A future Strict Mode Settings toggle (already tracked under Not Yet Built) will prevent ending early when enabled — see `DOMAIN_DICTIONARY.md`'s Session section.
- Background Blocks may overlap with anything; Ritual + Ritual overlap is rejected at creation time.

### Session Adjustment Rules (Ren page)

| Session type | Apps | Website (Blocklist preset) | Website (Allowlist preset) |
|-------------|------|---------------------------|-----------------------------|
| Spontaneous | Add or temporarily remove | Add or remove allowed | Add only; no removals |
| Planned | Add only | Add only | Apps: Add only; Websites: No changes allowed |

### Policy Computation (`ComputeActivePolicySliceQuery` + `PolicyEngine`)

The Source of Truth flow: `Database → PolicyEngine (Domain) → ActivePolicySlice (VO) → WindowsEnforcementService (OS)`

`ComputeActivePolicySliceQueryHandler` is a pure orchestrator — it fetches entities from three repositories, collects unique `BlockPresetId` values, loads the corresponding `BlockPreset` aggregates, then delegates entirely to `IPolicyEngine.ComputeSlice()`. All merge logic lives in `PolicyEngine` (Domain layer).

`PolicyEngine.ComputeSlice()` rules, given all active blocks and sessions at time `t`:
- **Apps**: union of all blocked apps across all active presets (always blocklist). Includes `TemporaryBlockedApps` from the active `Session` entity.
- **Websites**: if any active preset uses Allowlist mode → default-deny, allowed = intersection of all allowlists minus any blocklist union. Otherwise → block the union of all blocklisted sites. Includes `TemporaryBlockedSites` from the active `Session` entity.
- **Both Focus Blocks and Background Blocks are included** in the computation. A Background Block enforces at its designated time — it does not skip enforcement. The difference is that Background Blocks do not trigger the Ritual.
- **`ActiveBlockPresetType`**: set to the type of the highest-priority active planned block. `FocusBlock` takes precedence over `BackgroundBlock` (`OrderByDescending(b => b is FocusBlock)`). `null` if no planned block is currently active. This field drives the `ScheduledEnforcementService` Ritual trigger decision.

### Enforcement Implementation Details

- **App blocking**: `WindowsEnforcementService` kill loop, `p.Kill(entireProcessTree: true)`, driven by `ScheduledEnforcementService` (5s heartbeat). Process handles are disposed in a `finally` block. No browser force-kill — browser tab blocking is handled exclusively by the `NenFocusExtension` via the `/check` redirect.
- **Ritual trigger**: each heartbeat, after computing the policy slice, `ScheduledEnforcementService` checks `slice.ActiveBlockPresetType`. If it is `Focus` and `ISessionStateService.ActiveSession` is `null`, it calls `SetRitualRequired(true)`. If the block preset type is `Background` or no planned block is active, it calls `SetRitualRequired(false)`. This keeps the "should the Ritual appear?" decision in one place, driven by the domain enum.
- **Website blocking — hosts file**: writes `0.0.0.0 <domain>` and `:: <domain>` entries in `C:\Windows\System32\drivers\etc\hosts` between `# NEN_FOCUS_START` / `# NEN_FOCUS_END` markers (case-sensitive, underscores). Calls `ipconfig /flushdns` after each write. Domains are normalised (strips `https://`, `www.`, paths/ports) before insertion.
- **Website blocking — browser extension**: `NenFocusExtension` intercepts navigations, asks `WindowsEnforcementService` at `http://localhost:5005/check`, and redirects blocked tabs to `blocked.html`. Reports attempts via `/report`.
- **DoH bypass prevention**: registry keys `BuiltInDnsClientEnabled = 0` are written for Chrome, Edge, and Brave to ensure browsers cannot route around the hosts file via DNS-over-HTTPS.
- **Allowlist mode**: `ActivePolicySlice.WebsiteFilterTypeMode == Allowlist` → extension enforces default-deny; intersection of all active allowlists is the permitted set. Hosts file alone cannot enforce this.
- **Local HTTP API** (`http://localhost:5005`): hosted by `WindowsEnforcementService`. `/check` returns `{ "blocked": true/false }`. `/report` increments the blocked-attempt counter for the current domain. The API starts when enforcement is applied and shuts down when it is removed.

## Development Notes

### Platform & Admin

- **Platform**: Windows only (`net9.0-windows`). Enforcement and notification services use Windows APIs. Do not attempt to make these cross-platform without explicit instruction.
- **Admin required**: The app manifest sets `level="requireAdministrator"`. This is mandatory for hosts file writes, registry key edits, and killing high-privilege process trees.

### Database

- **SQLite via EF Core**. Add migrations: `dotnet ef migrations add <Name> --project NenFocus.Infrastructure --startup-project NenFocus`
- `HostExtensions.EnsureDatabase()` calls `context.Database.Migrate()` on startup — no bypass of migration history.
- SQLite cannot do `ORDER BY` or `>` comparisons on `DateTimeOffset` in SQL — fetch to memory first, then filter/sort in C#. **Possibly obsolete (flagged 2026-08-18):** no `DateTimeOffset` field exists anywhere in `NenFocus.Domain/Entities` today — every timestamp is a plain `DateTime` (see `ARCHITECT_GOVERNANCE.md` → Open Gap E, which independently confirmed the same for `PlannedBlock`). Kept here rather than deleted since several "fetch to memory, sort in C#" repository methods described elsewhere in this doc may still exist for other reasons (e.g. general SQLite querying limitations) even if this specific `DateTimeOffset` trigger no longer applies — worth confirming and pruning next time a repository in this area is touched.
- `BlockPreset.Tags` is stored as a serialised string in the DB. `GetByTagsAsync` filters in-memory. Known workaround.

### Known Workarounds

- **FocusBlock update**: There is no `FocusBlock.Update()` method — `UpdatePlannedBlockCommand` uses delete + recreate.
- **Hosts file markers**: must be exactly `# NEN_FOCUS_START` and `# NEN_FOCUS_END` (case-sensitive, underscores). Any deviation causes duplicate entries on next write.
- **Break reminders**: Implemented as `Task.Delay` fire-and-forget tasks tracked by `CancellationTokenSource` — but `INotificationService.ScheduleBreakReminderAsync` is never called by anything (verified against the full solution 2026-08-12), so this is currently unreachable rather than a live restart-survival risk. See `ARCHITECT_GOVERNANCE.md` → Open Gap I.
- **No index on `PlannedBlocks.Start`/`End`**: confirmed 2026-07-15 while sizing the Recurring Blocks materialization horizon (see `ARCHITECT_GOVERNANCE.md` → Open Gap E) — every range query (`GetForDayAsync`, `GetForRangeAsync`, `GetOverlappingAsync`, etc.) is currently a full table scan. Not a problem at current or foreseeable single-user scale; worth adding an index on `(Start, End)` before row counts climb into the tens of thousands, independent of any specific feature.

### DI & Registration

- **DI scope**: `InProcessDomainEventPublisher` creates a new DI scope per event handler to avoid `DbContext` concurrency issues.
- **Validator registration**: `services.AddValidatorsFromAssembly(assembly)` in `DependencyInjection.cs` auto-registers all `AbstractValidator<T>` classes in the Application assembly. Validators must be co-located inside their use-case folder (e.g. `StartSession/StartSessionValidator.cs`). The top-level `Validators/` directory has been deleted — do not recreate it.
- **Handler registration** (`Application/DependencyInjection.cs`): Scrutor has been removed. Handlers are discovered via a hand-rolled reflection scan over the Application assembly. All `ICommandHandler<,>` and `IQueryHandler<,>` implementations are registered with `AddTransient` (not `AddScoped`). Event handler types are registered with `AddTransient` as self (concrete type). This replaces the previous Scrutor `.AsImplementedInterfaces().WithScopedLifetime()` pattern.
- **Singleton + scoped pattern**: `ActiveSessionMonitor` (singleton) calls scoped command handlers by creating short-lived scopes via `IServiceScopeFactory`. This is the correct pattern; do not inject scoped services directly into singletons.
- **App startup sequence** (`Program.cs`): build host → ensure DB → `SessionStateService.InitializeAsync()` (rehydrate session from DB) → resolve `ShellViewModel` → show window.
- **NuGet alignment**: all `Microsoft.CodeAnalysis` packages pinned to `5.3.0` to avoid NU1608 version conflicts.
