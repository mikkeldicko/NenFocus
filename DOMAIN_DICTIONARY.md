# NenFocus — Domain Dictionary

This file is the canonical reference for every domain concept in NenFocus. It exists to eliminate ambiguity between conversations. When a term is used in code, comments, or a design discussion, its meaning here is authoritative.

---

## Quick Reference

| Term | One-line definition |
|------|---------------------|
| **Session** | A bounded focus period; lifecycle `NotStarted → Active → (OnBreak ↔ Active) → Completed` |
| **Ritual** | The four-step wizard (Ten → Zetsu → Ren → Hatsu) that creates a Session |
| **Block Preset** | A reusable template of blocked apps + website filter type; typed as Focus or Background at creation |
| **Planned Block** | Abstract base for `FocusBlock` and `BackgroundBlock`; carries `Start`, `End`, `BlockPresetId`, `RecurringSeriesId (Guid?)`, `IsActive()`, `OverlapsWith()` |
| **Focus Block** | A planned calendar entry that activates enforcement AND triggers the Nen Ritual at the designated time |
| **Background Block** | A planned calendar entry that activates enforcement at the designated time without triggering the Ritual |
| **Policy Slice** | The merged, computed enforcement state at a given instant; represented as `ActivePolicySlice` (Domain Value Object), produced by `PolicyEngine` |
| **PolicyEngine** | Stateless Domain service (`NenFocus.Domain/Services/`) that computes `ActivePolicySlice` from raw aggregates; sole owner of all merge rules |
| **Spontaneous Session** | A Session created by completing the Ritual manually from the Main Page; no Block entity exists; `Origin = Spontaneous` |
| **Planned Session** | A Session created via the Ritual triggered by a scheduled Focus Block; `Origin = Planned` |
| **SessionOrigin** | Enum (`Spontaneous` \| `Planned`) that tags every Session with how it was initiated |
| **Blocked Attempt** | An append-only fact recording a user's attempt to access a blocked app or site during a Session |
| **Nen Contract** | A sealed, time-bound commitment over a contiguous date range that governs allowed changes to the Focus/Background blocks within it; own aggregate root, does not own `PlannedBlock`s |
| **Seal** | The act of finalising a Nen Contract; the only way a `NenContract` comes into existence — there is no persisted draft state in the domain |
| **Strictness Rule** | Enum (`Locked` \| `DailyFlexibility` \| `PeriodTimeBudget`) — one axis of post-seal mutability; interpretation of the rule against an edit's context is an Application-layer concern |
| **Daily Floor** | The minimum completed Focus hours required per day within a Nen Contract; Focus-only, hard-checked against planned hours at Seal, soft-tracked (scored, not blocked) thereafter |
| **Change Window** | An optional daily time-of-day window during which edits to *existing* blocks are permitted, with a configured per-day use limit; the use-count itself is tracked by the Application layer |
| **Day Met** | A scoring outcome: a Nen Contract day is "met" if that day's completed Focus hours ≥ the Daily Floor — full stop. A missed or late Focus block does not fail the day directly; it only costs hours that must be made up |
| **FocusBlockOutcome** | Enum (`CompletedOnTime` \| `StartedLate` \| `Missed` \| `EndedEarly`) classifying how a single Focus block resolved; a per-block display concept, separate from the day verdict |
| **Broken** | A Nen Contract the user cancelled before its end date; only reachable if `AllowCancellation` was set true at Seal |
| **Work Hours** | A daily time-of-day window defining where Focus/Background blocks may physically exist on the calendar; blocks cannot be placed, moved, or resized outside it. Distinct from Change Window (which gates *when edits are allowed*, not *where blocks can be*) |
| **Contract Preset** | A saved, reusable template of Nen Contract rules (strictness, daily floor, work hours, allow-cancellation) — a full Domain `AggregateRoot`, not just a saved configuration row. Authored and managed on the Presets page's "Contract Presets" tab; the Contract Wizard only picks one (applied as-is, no editing mid-wizard) — see the App Structure table below |
| **Simple Contract** | A quick-seal path in the Planner wizard: pick a named preset (Lockdown, Daily Flex, Period Study), schedule blocks, seal. No tuning knobs — the floor is derived from planned hours per day |
| **Advanced Contract** | The full-configuration path: every lever exposed (strictness, work hours, custom daily floor, rest days, allow-cancellation). User can save the configuration as a Contract Preset for reuse |
| **Redemption Block** | A Focus Block explicitly linked to one or more missed/late Focus Blocks of the same preset, covering all or part of their deficit; carries `RedemptionEntries` |
| **RedemptionEntry** | A value object tying a redemption block to one missed block: `{ MissedBlockId, MinutesCovered }` |
| **Deficit** | The gap between a missed or late Focus Block's scheduled duration and actual completed minutes; tracked per missed block, not per preset |
| **Enforcement** | OS-level mechanisms (process kill, hosts file, registry, extension) that apply a Policy Slice |
| **Post-Session** | The mandatory screen shown after a Session ends; displays stats, blocked attempts, and an optional reflection |
| **Deep Module** | A module with significant functionality hidden behind a narrow, obvious API |
| **Design Gap** | The distance between visible code and what is needed to implement a feature correctly |
| **DailyUsage** | Append-only fact recording actual seconds spent on any site or app, per calendar day; the universal usage-tracking substrate, independent of ceilings, presets, or contracts |
| **UsageResourceType** | Enum (`App` \| `Website`) tagging a `DailyUsage` or `UsageCeiling` entry |
| **UsageCeiling** | An ambient, perpetual cap on daily or weekly access time for a specific site or app; created on the Presets page; deliberately independent of `BlockPreset` and `NenContract` |
| **CeilingPeriod** | Enum (`Daily` \| `Weekly`) — the aggregation window a `UsageCeiling`'s cap is measured against |
| **IUsageTracker** | Application-layer interface through which infrastructure records usage events; analogous in pattern to `IBlockedAttemptTracker` |
| **RecurrenceRule** | Value object describing a repeat schedule: interval, unit (Day/Week/Month), weekday mask, end condition — the single shape behind "Every day," "Specific weekdays," and "Custom" recurrence pickers |
| **RecurringSeries** | Entity owning a `RecurrenceRule` + block template (preset, time-of-day); generates and keeps topped-up the materialized `PlannedBlock` rows that belong to it |
| **SkippedOccurrence** | Append-only fact recording a recurring instance that couldn't be generated due to a conflict with another block; exists only while unresolved |

## Session

**Definition:** A bounded period of intentional focus, created by the user through the Ritual and enforced by the system — or, since the Missed Session amendment, a planned focus *attempt* that may have succeeded or been missed. A Session is now "a focus attempt, which may have succeeded or been missed," not only "a focus period that ran."

**Lifecycle:** `NotStarted → Active → (OnBreak ↔ Active) → Completed`, with a second terminal branch `NotStarted → Missed` reachable only by a Planned session whose originating Focus Block's window closed before the Ritual completed.

**Ubiquitous language rules:**
- A Session is *started*, not *created* or *opened*.
- A Session is *completed* or *auto-ended*, not *closed* or *finished*.
- A Session cannot be paused — only placed *on break*.
- A Session is *missed*, never *failed* or *expired* — "missed" is the only vocabulary for a Planned session whose window closed unfulfilled.

**Break behaviour:** Once a break starts, a break countdown timer replaces the session timer on the Main Page. Enforcement remains active during breaks — blocked sites and apps stay blocked. The break is a reminder only. A future Settings option will allow the user to choose whether enforcement is paused during breaks. **Breaks are currently user-initiated only** (`MainPageViewModel.TakeBreak()`) — the "reminder fires and starts a break automatically" framing this line used to have does not match shipped code; `INotificationService.ScheduleBreakReminderAsync` is fully implemented but never called anywhere. See `ARCHITECT_GOVERNANCE.md` → Open Gap I.

**Ending early:** Currently the user can end a session before the timer runs out. A future "Strict Mode" setting will prevent this.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `Session` entity (`Entities/Session.cs`) | Owns all state transitions via `Start()`, `StartBreak()`, `ResumeFromBreak()`, `Complete()`, `Miss()`; raises domain events internally; carries `Origin (SessionOrigin)` and `OriginatingBlockId (Guid?)` |
| Domain | `SessionStatus` enum | Valid states: `NotStarted`, `Active`, `OnBreak`, `Completed`, `Missed` |
| Domain | `SessionOrigin` enum | Valid values: `Spontaneous`, `Planned`; tags every Session with how it was initiated |
| Domain | `SessionGoal`, `SessionDuration`, `BreakSettings` value objects | Immutable configuration attached at creation |
| Application | `ISessionRepository` | Persistence contract; `GetActiveAsync()` is the startup rehydration entry point; `ExistsForOriginatingBlockAsync()` makes missed-session creation idempotent |
| Application | `ISessionStateService` | Singleton in-memory noticeboard; the single source of truth for the UI's view of the active session |
| Application | `IActiveSessionMonitor` | Singleton countdown engine; owns the timer, exposes `SessionTimeRemaining` / `Progress`, auto-ends via `EndSessionCommandHandler`. The auto-end/auto-resume-break calls are fire-and-forget from the timer callback; wrapped in try/catch + `ILogger` since 2026-08-21 (`DESIGN_GAP_HISTORY.md` Gap 31) — an unhandled exception previously vanished as an unobserved task exception, leaving the session stuck at `00:00:00` forever with no error surfaced anywhere. |
| Application | `StartSessionCommandHandler` | Creates and starts the session, calls `_sessionState.SetActive()`, dispatches `session.DomainEvents` via `IDomainEventPublisher`. Rejects starting against an originating block via `PlannedBlock.HasEnded(now)` (fixed 2026-08-21, `DESIGN_GAP_HISTORY.md` Gap 32) rather than an inline `now >= End`, matching the codebase's one canonical "is this past" definition. |
| Application | `EndSessionCommandHandler` | Calls `session.Complete()`, saves, dispatches `session.DomainEvents`; enforcement removal and notification are handled by `SessionEndedEventHandler`. If the session ends before its originating `FocusBlock`'s scheduled end, calls `focusBlock.MarkSessionEnded(endedAt)` — a non-destructive stamp, closed 2026-08-12 (`DESIGN_GAP_HISTORY.md` Gap 22). `block.End` is never overwritten; see `FocusBlockOutcome` below for how `SessionEndedAt` feeds classification. |
| Application | `SessionStartedEventHandler` | Computes policy slice, calls `IEnforcementService.ApplyPolicyAsync`, sends start notification |
| Application | `SessionEndedEventHandler` | Calls `IEnforcementService.RemoveEnforcementAsync`, cancels reminders, sends end notification |
| Application | `BreakStartedEventHandler` | Calls `IEnforcementService.RemoveEnforcementAsync`, sends break notification |
| UI | `MainPageViewModel` | Observer only — reads from `ISessionStateService` and `IActiveSessionMonitor`, dispatches commands. "Use Nen" button is hidden while a session is active. |

## Missed Session

**Definition:** A first-class Session, counted, filtered, and timelined in Insights alongside real sessions, produced when a planned Focus Block's scheduled window closes with the Ritual never completed. This reopens the Session aggregate: a Session is now "a focus attempt, which may have succeeded or been missed," not only "a period that ran." A missed session is essentially a planned session **frozen at "never started"** rather than progressing to `Completed` — reached via a direct `NotStarted → Missed` transition, never through `Active`.

**Only a Planned session can be missed.** A Spontaneous session is user-initiated with no scheduled commitment behind it — there is nothing to miss. `Session.Miss()` throws if `Origin != SessionOrigin.Planned`; this is defense-in-depth rather than a reachable case, since the creation path for a missed session (`MarkFocusBlockMissedCommand`) only ever originates from a `FocusBlockId`, never from an existing Spontaneous session.

**What it HAS**, inherited from the originating `FocusBlock`: a `BlockPresetId`, a `SessionDuration` (the block's scheduled length), and a scheduled `Start`/`End` — populated onto `StartedAt`/`EndedAt` at miss-time so it appears in date-range history queries exactly like a real session (`ISessionRepository.GetHistoryAsync` filters on `StartedAt`; a session that never populated it would be silently invisible to history).

**What it LACKS**, because it never ran: break settings, temporary blocked apps/sites (both simply omitted at creation — `Session.Create`'s existing optional parameters already default to `null`/`[]`), and any real elapsed runtime. Its `Goal` is the fixed placeholder `"(missed — no goal set)"` — a normal, valid `SessionGoal` (no user ever reached Zetsu to write one; validation is not loosened for this path).

**Zero completed hours, by construction:** `Session.GetElapsedTime` returns `TimeSpan.Zero` whenever `Status == Missed`, checked *before* the `StartedAt`-null check — because a missed session's `StartedAt`/`EndedAt` hold the *scheduled* window, not real elapsed time, and a naive `EndedAt − StartedAt` would wrongly report the full scheduled duration as "completed." Centralizing this on the entity (rather than in every caller that computes "completed hours") means the contract recap, `GetSessionHistoryQuery`, and any future Insights analytics are all correct for free. This is a single-entity fact ("a session that never ran has zero elapsed time"), distinct from the separate principle that *aggregating* hours across days belongs in the Application layer.

**Reflection still applies:** `SetReflection` (and `SaveReflectionCommandHandler`) accept `Completed` or `Missed` — the missed post-session screen captures a "why did I miss this?" reflection the same way a real post-session screen captures one. There is no rating field on either.

**Blocked attempts are always zero on a missed session — a known, accepted gap.** `BlockedAttempt` rows key off `SessionId`, and tracking only fires once a Session exists; during a Focus Block's active window before (or absent) Ritual completion, enforcement runs but there is no `SessionId` yet to attach an attempt to. Fixing this would mean tracking attempts against `FocusBlockId` during that window — separate future Infrastructure work, out of scope here.

**The originating block is untouched.** `FocusBlock` is not deleted or altered when its session is marked missed — it remains the schedule record (`RitualCompletedAt` stays `null`), while the Session is the attempt record. Both already agree: `FocusBlockOutcomeClassifier` independently derives `Missed` from the same `RitualCompletedAt == null` fact once the scheduled end has passed.

**Idempotent creation:** `MarkFocusBlockMissedCommand` can safely fire more than once for the same block (the expected failure mode for a heartbeat-triggered command, not a hypothetical) — `ISessionRepository.ExistsForOriginatingBlockAsync` guards against creating a second missed session for a block that already has one.

**Not built here:** any Insights UI. This amendment ensures a missed session is modeled correctly and is queryable/representable for when that UI is built.

**Two triggers call `MarkFocusBlockMissedCommand` — cold-start and live release.** A block's window can close unfulfilled while the app is closed (discovered on next launch) or while it's running and the Ritual is on screen for that exact block (discovered by the enforcement heartbeat). Both funnel through the same command; only the discovery path differs.

- **Cold-start sweep:** `SessionStateService.InitializeAsync()` calls `SweepMissedFocusBlocksCommand` after existing session rehydration. The handler queries `IPlannedBlockRepository.GetUnresolvedFocusBlocksAsync(asOf)` — Focus blocks with `End < asOf && RitualCompletedAt == null` — and calls `MarkFocusBlockMissedCommand` for each, ordered by `Start` ascending (oldest first). The resulting Missed sessions are simply persisted with `PostSessionAcknowledgedAt == null`; `ShellViewModel` discovers them itself at its own startup (see below) rather than the sweep announcing them via an event.
- **Live release:** `ScheduledEnforcementService`'s 5-second heartbeat calls `SessionStateService.SetRitualRequired(false)` when a Focus block's window closes without a session starting. `SetRitualRequired` now raises the widened `RitualRequirementChanged` event carrying a `RitualRequirementChange(bool Required, Guid? FocusBlockId)` — on the `false` transition, `FocusBlockId` is the *previously* pending block (captured into a local before `_pendingFocusBlockId` is cleared), since `ScheduledEnforcementService` itself has no memory of what was showing. `ShellViewModel` reacts by hard-closing the open Ritual overlay immediately (it can't wait — the user would be staring at a dead ritual), then calls `MarkFocusBlockMissedCommand` for that block.

**Unified with the Completed-but-undismissed case.** A Completed session whose Post-Session screen was never dismissed (app closed before clicking Done) is the same underlying problem as a Missed session nobody has seen yet — both are "a resolved session the user hasn't acknowledged." `Session.PostSessionAcknowledgedAt (DateTime?)` / `MarkPostSessionAcknowledged(DateTime)` is the one fact that answers "has the user seen this?", stamped only when `PostSessionViewModel.Done()` fires (via the new `AcknowledgePostSessionCommand`), regardless of whether a reflection was written — a blank reflection is a valid, deliberate outcome and must not be confused with "never saw the screen." `GetUnacknowledgedPostSessionsQuery` finds every `Completed` or `Missed` session with `PostSessionAcknowledgedAt == null`, ordered by `EndedAt` ascending, and is what `ShellViewModel` awaits at its own construction to replay anything pending — in the order it actually happened, oldest first, Ritual (if also pending) always enqueued last behind all of them.

**The Shell queues what it can't show immediately.** `ShellViewModel` holds a private `Queue<PendingOverlay>` (`PendingPostSession(PostSessionDto)` | `PendingRitual(Guid FocusBlockId)`) — one unified overlay type for both Missed and Completed-but-undismissed, since `PostSessionDto.Status` already distinguishes them. `TryDrainQueue()` is the single chokepoint — nothing new is shown unless `!IsRitualActive && !IsPostSessionActive && !IsTriageActive`. `ExitRitual`/`ExitRitualAndGoToMain`/`ExitPostSession` all funnel through it, and it lands on the Main page when the queue is empty.

**Triage gates a large backlog — Missed only, deliberately not unified.** If `TryDrainQueue()` is about to pop from the queue and finds more than 3 pending `PendingPostSession` items whose `Status == Missed` (checked fresh each call, not just once when discovered — so items enqueued later still trip the gate), it shows `MissedSessionsTriageViewModel` instead: "Skip All" clears every queued *Missed* post-session (any pending Completed-but-undismissed one is left untouched) and re-drains; "Review Each" sets a `_suppressTriage` flag (so the gate doesn't re-fire mid-review) and re-drains to cycle through them one by one via the normal Post-Session screen. The flag resets once the queue empties. Completed-but-undismissed is structurally excluded from ever needing batching: the overlay itself blocks starting a second session before the first is dismissed, so more than one can never accumulate.

**The Post-Session screen wears different copy for a miss.** `PostSessionDto.Status` (mirrored from the session) drives two computed `PostSessionViewModel` properties: `HeaderLabel` ("SESSION MISSED" vs "SESSION COMPLETE") and `ReflectionPrompt` ("What got in the way?" vs "How did the session go? What did you accomplish?").

## Ritual

**Definition:** The four-step wizard (Ten → Zetsu → Ren → Hatsu) through which a user consciously creates a Session. The Ritual is a design-time guardrail: it forces deliberate intent before focus begins.

**Lifecycle:** Opened by user → steps navigated → `StartSessionCommand` dispatched on Hatsu completion → Ritual closed → user returns to Main Page with active session.

**Two activation paths:**
- **Spontaneous:** User clicks "Use Nen" on the Main Page. All four steps are fully user-controlled.
- **Planned:** A scheduled Focus Block activates and pushes the user to the Ritual. The Ren and Hatsu steps are constrained (see below).

**Step meanings:**

| Step | Theme | Header Text | Purpose in UI |
|------|-------|-------------|---------------|
| **Ten** | Awareness | "Focus the mind, reflect upon the self, and determine the goal" | Greet the user; prompt internal reflection before continuing. Same for both Spontaneous and Planned. |
| **Zetsu** | Silence | "Put it into words" | User writes their session goal into a text box. Same for both Spontaneous and Planned. |
| **Ren** | Persistence | "Intensify your will" | **Spontaneous:** User selects a Focus-type Block Preset from their existing presets. **Planned:** Block Preset is pre-selected and locked (chosen when the Focus Block was scheduled); user cannot change it. User may add additional sites (Blocklist presets only) and apps for this session only — these are not saved to the preset. |
| **Hatsu** | Output | "Put it into action" | **Spontaneous:** User selects session duration (5 min – 8 hours) and optionally configures break reminders. **Planned:** Duration is pre-determined by the Focus Block's scheduled end time (displayed as "active until [time]"); user can only configure break reminders. User clicks "Start Session." |

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Application | `StartSessionCommand` / `StartSessionCommandHandler` | Final output of the Ritual; creates and starts the Session |
| UI | `RitualShellViewModel` | Hosts step navigation; owns `CurrentStep` and navigation commands |
| UI | `TenPageViewModel`, `ZetsuPageViewModel`, `RenPageViewModel`, `HatsuPageViewModel` | One ViewModel per step; collects input, validates locally |
| UI | `RitualShellView.axaml` | Full-screen overlay rendered over the Shell when `IsRitualActive = true` |

## Block Preset

**Definition:** A reusable, named configuration of blocked applications and a website filter type. A Block Preset is typed as either **Focus** or **Background** at creation time. The type can be changed later provided the preset is not currently attached to any scheduled block or active session. The type acts as a filter: Focus presets only appear during the Ren step and when scheduling a Focus Block (Planner); Background presets only appear when scheduling a Background Block (Planner).

**Lifecycle:** Created in Block Presets page (type chosen via picker at creation) → (optionally duplicated or edited; type may be changed if no active blocks reference it) → attached to Session at Ritual (Ren step, Focus-type only) or to a Planned Block in the Planner → locked for duration of Session or active Block.

**Website filter type:** Each preset carries a `WebsiteFilterType` of either `Blocklist` (block specific sites, allow everything else) or `Allowlist` (allow specific sites, block everything else). Both Ritual and Background presets can use either mode. Both can also specify blocked apps.

**Time-agnosticism:** A Block Preset is time-agnostic — it carries no schedule, no window, and no knowledge of when it is active. This allows the same preset to be reused across multiple planned blocks at different times. `BlockedSite` and `BlockedApp` are always plain hard blocks — access-time limiting is handled by the separate `UsageCeiling` feature (see `ARCHITECT_GOVERNANCE.md` → Open Gap A), which is deliberately decoupled from `BlockPreset` entirely, not a field on it.

**Ubiquitous language rules:**
- A preset is *attached* to a session or block, not *assigned* or *applied*.
- A preset is **locked** when it's in use by an active session, or referenced by any future `PlannedBlock` — whether that block is an ordinary uncommitted block or one linked to a Nen Contract (`HasFutureBlocksForPresetAsync` doesn't distinguish; both count). A locked preset can never be **deleted**.
- A locked preset can still be **updated**, but only toward being *at least as strict* (2026-07-07 revision — previously a locked preset rejected every edit outright; direction corrected 2026-08-21, `DESIGN_GAP_HISTORY.md` Gap 30 — see `BlockPreset.IsAtLeastAsStrict`): `BlockedApps` must always be a superset of the current list (apps have no allow-mode, so dropping one always weakens the preset). `Websites` depends on `WebsiteFilterType` — under `Blocklist`, the same superset (add-only) rule applies; under `Allowlist` it's the **opposite** — the new list must be a *subset* of the current one (removing an allowed site narrows access, the stricter direction; adding one widens it, the weaker direction, even though it's technically an addition). `Name`, `WebsiteFilterType`, `PresetType`, and `Tags` must all stay unchanged while locked. You can strengthen a live preset; you cannot weaken, rename, or retype it while it's committed.
- A preset is *locked* — fully, not just add-only — for `DeleteBlockPresetCommand`; deletion is never allowed while in use, regardless of what would be deleted.

**UI display:** On the Block Preset page, Focus and Background presets are displayed together in a single list with a type badge (blue = Focus, green = Background). A filter bar lets the user show All, Focus only, or Background only.

## Daily Usage *(Domain shape designed — not yet built)*

**Definition:** An append-only fact recording actual seconds of active use on a specific website or application, per calendar day. `DailyUsage` is the universal usage-tracking substrate — it records every site visited and every app used, unconditionally, not just resources with a configured `UsageCeiling`. It exists independently of `BlockPreset`, `PlannedBlock`, `Session`, and `NenContract` — it belongs to nothing but the day and the resource.

**Why it tracks everything, not just ceiling-configured entries:** The same data feeds two consumers — `UsageCeiling` enforcement (which only cares about resources someone has capped) and the future Insights page (which wants total time-per-site and time-per-app regardless of whether a cap exists). Scoping collection down to only configured entries would starve Insights of data for everything else.

**Idle detection:** Time only accrues while the user is genuinely active, not merely while a tab/app has focus. Web: `chrome.idle`, with an exception so passive media consumption (an audible or playing tab) isn't miscounted as idle. Native apps: `GetLastInputInfo`; the equivalent per-process audio-playing exception is materially harder to build (would need Windows Core Audio Session APIs) and is an open question for whenever this is built — apps may ship with plain idle-timeout and no media exception initially.

**Ubiquitous language rules:**
- Usage *accrues* on a resource; it is *recorded*, matching the existing `IBlockedAttemptTracker` vocabulary.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `DailyUsage` entity | Append-only fact, keyed by `(Date, ResourceName, UsageResourceType)`; accumulates seconds. Mirrors `BlockedAttempt`'s shape. |
| Domain | `UsageResourceType` enum | `App` \| `Website` — mirrors `BlockedAttemptType` |
| Application | `IUsageTracker` interface | Contract for recording usage events; analogous to `IBlockedAttemptTracker` |
| Infrastructure | `IUsageTracker` implementation | Persists `DailyUsage` rows, debounced/batched (same pattern as `BlockedAttemptTracker`'s 2-second debounce) rather than written per tick. **Not yet built.** |
| Infrastructure | Extension tab-focus-time tracking | `background.js` gains focus/idle tracking and calls a new `/report-time` endpoint, distinct from the existing `/report` (which only logs blocked attempts). **Not yet built.** |

## Usage Ceiling *(Domain shape designed — not yet built)*

**Definition:** An ambient, perpetual cap on how much time per day or per week a user may spend on a specific website or application. Unlike `BlockPreset`, it has no calendar involvement, no attachment to any `PlannedBlock` or `Session`, and no relationship to `NenContract` — it is created on the Presets page and stays in effect until edited, paused, or deleted.

**This supersedes the earlier "Time Budget" concept entirely.** The original design put an optional `TimeBudget` on `BlockedSite`, deriving its active window from the owning `PlannedBlock`. That conflated two unrelated things: a schedule-bound hard block (what `BlockPreset` is for) and an ambient, calendar-independent personal limit (what this is for). `BlockPreset` and `BlockedSite` remain pure hard-block only — no budget concept lives on them anymore.

**Precedence rule:** If any currently-active Focus or Background preset hard-blocks a resource, the hard block always wins — the resource is blocked regardless of remaining ceiling, and no usage accrues for it during that window. Outside of any active hard block, the resource is accessible up to its ceiling; once reached for the current period, it is blocked for the rest of that period.

**Two modes, chosen per entry (`CeilingPeriod`):**
- **Daily** — a per-weekday cap shape (e.g. Monday 3h, Tuesday 1h, Wednesday 0h), mirroring `WorkHoursPolicy`'s `{ Default, PerDayExceptions }` resolution pattern.
- **Weekly** — a single aggregate cap tracked cumulatively across the week, mirroring the idea behind `StrictnessRule.PeriodTimeBudget`, applied to resource access instead of block-editing permission.

**Why it is a Domain entity, not a value object:** `UsageCeiling` has independent identity, an independent lifecycle (created, edited, paused, and deleted through its own CRUD, not nested inside another aggregate), and is looked up and referenced by `Id` from `PolicyEngine` on every enforcement tick. This is the same justification that makes `FocusBlock`/`BackgroundBlock` entities rather than value objects — it is a separate, orthogonal question from *why* it carries a domain rule at all (that reasoning mirrors `DailyFloor.IsSatisfiedBy` — the rule belongs with its data, reused wherever exhaustion needs checking, not duplicated across callers).

**Why it stays out of `NenContract`:** `NenContract` is sealed and time-bound, governing edit permission for a committed block schedule with Daily-Floor scoring. `UsageCeiling` is perpetual, unsealed, and governs passive resource access. Coupling them would mean ceilings stop functioning between contracts or without one ever being sealed, contradicting the point of an *ambient* limit. They are sibling concepts.

**Not the same as recurring hard blocks:** "Always block Reddit" or "block Facebook 9–5 daily" is not a `UsageCeiling` — it's a permanent or repeating hard block, which is the separately-tracked **Recurring Blocks** gap (see `TECHNICAL_SPEC_INFRA.md` → Not Yet Built) applied to ordinary `BackgroundBlock`s on the Planner. No relationship between the two features.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `UsageCeiling` entity | `Id`, `ResourceName`, `ResourceType (UsageResourceType)`, `Period (CeilingPeriod)`, cap value(s), `IsPaused`. `IsExhausted(...)` — pure comparison against resolved `DailyUsage` totals for the entry's period, mirrors `DailyFloor.IsSatisfiedBy`. `Pause()` / `Resume()`. No domain events. |
| Domain | `CeilingPeriod` enum | `Daily` \| `Weekly` |
| Domain | `PolicyEngine` (extended) | `ComputeSlice()` gains inputs for active `UsageCeiling` entries and resolved usage totals; folds exhausted ceilings into `ActivePolicySlice.BlockedSites`/`BlockedApps` directly — chosen over a parallel check in `WindowsEnforcementService` specifically to preserve "`PolicyEngine` is the sole owner of all merge rules" (same principle as Gap 2/Gap 5). **Not yet built.** |
| Infrastructure | Enforcement pipeline lifecycle | `ScheduledEnforcementService`'s heartbeat and `WindowsEnforcementService`'s local HTTP API must run for the app's full lifetime rather than starting/stopping with enforcement bursts, since ceilings apply independent of any active Session or Block. **Not yet built.** |
| UI | Presets page, new tab | Working label "Usage Ceilings." Not a `BlockPreset`/`ContractPreset`-style reusable template — a ceiling isn't consumed to create another object, it's a standing, directly-enforced rule. **Not yet built.** |

**Open questions, not resolved in interrogation:**
- Whether specific resources (NenFocus's own process, `localhost`, `SystemSafetyConstants.UnkillableProcesses`) are excluded from `DailyUsage`, or truly everything is logged unconditionally.
- Day/week boundary semantics — reset time, week-start day, timezone handling.
- Exact CQRS shapes for `UsageCeiling` CRUD and usage-summation queries.
- Whether the native per-app audio-playing exception ships in v1.

See `ARCHITECT_GOVERNANCE.md` → Open Gap A for the full interrogation record.

## Recurring Blocks *(fully interrogated 2026-07-15 — not yet built)*

**Definition:** A `PlannedBlock` (Focus or Background) that repeats on a schedule instead of existing as a single one-off calendar entry — e.g. "9–5 every weekday." Type (Focus vs Background) is decided exactly the way it already is today: by which `BlockPreset` is picked when the recurring block is created. Recurrence is a Planner-only concept, deliberately independent of `NenContract` and unrelated to `UsageCeiling` (a soft ambient cap, not a hard recurring schedule).

**One recurrence shape, not three:** "Every day," "Specific weekdays," and "Custom" are all just Planner UI presets over a single `RecurrenceRule` value object — never separate domain types. This mirrors the Simple/Advanced Contract precedent (one underlying shape, simplified entry points for the common case) and avoids duplicating "does this fire on date X" logic in three places.

**Materialization is real, not lazy:** unlike Google Calendar (which expands an `RRULE` lazily, only for the date range a client is viewing), NenFocus needs concrete `PlannedBlock` rows for `ScheduledEnforcementService` to enforce against — a series can't wait to be "computed" the next time someone opens the Planner. A `RecurringSeries` therefore materializes real rows on a rolling **1-year horizon**, kept topped up by a background heartbeat (mirroring `NenContractHeartbeatService`'s pattern) plus a cold-start catch-up check at launch.

**Editing/deletion — three Google Calendar scopes:** "This event" (detaches one instance — clears its `RecurringSeriesId`), "This and following events" (splits the series: truncates the original, spawns a new `RecurringSeries` from that instance forward), "All events" (edits the series template; only propagates to instances still linked, not ones already detached).

**Conflict handling, two different moments:** at creation time (user is present) — validate the full 1-year window up front, show every conflict, let the user skip that occurrence or cancel entirely. At background top-up time (nobody's present) — the conflicting occurrence is force-skipped (can't violate the no-overlapping-Focus-Blocks rule) and recorded as a `SkippedOccurrence`; surfaced as an actionable prompt next time the app opens ("Change it" jumps to the Planner on that date; "Skip" dismisses). Once the conflicting block is cleared, the missing occurrence auto-regenerates on the next top-up pass.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `RecurrenceRule` value object | `{ IntervalValue, IntervalUnit (Day\|Week\|Month), WeekdayMask, EndCondition (Never\|OnDate\|AfterOccurrences) }`. **Not yet built.** |
| Domain | `RecurringSeries` entity | `Id`, `BlockPresetId`, `RecurrenceRule`, time-of-day template, `Title?`. Owns truncation (for "this and following" splits). **Not yet built.** |
| Domain | `PlannedBlock.RecurringSeriesId (Guid?)` | Nullable FK, mirrors `ContractId`. `null` = ordinary one-off block. **Not yet built.** |
| Domain | `SkippedOccurrence` entity | `{ Id, SeriesId, Date, ConflictingBlockId }`. No `Resolved` flag — existence means pending; deleted once regenerated. No domain events. **Not yet built.** |
| Infrastructure | Materialization heartbeat | New low-frequency `BackgroundService` (mirrors `NenContractHeartbeatService`), keeps each series' rows topped up 1 year ahead; re-scans `SkippedOccurrence` rows each pass for cleared conflicts. **Not yet built.** |
| UI | Planner block-creation form | "Repeat" toggle reveals the `RecurrenceRule` picker (Every day / Specific weekdays / Custom). Edit/delete on a recurring instance prompts for scope (This event / This and following / All events). Pending `SkippedOccurrence` rows surface as an actionable prompt on app open. **Not yet built.** |

See `ARCHITECT_GOVERNANCE.md` → Open Gap E for the full interrogation record, including verified performance facts about the `PlannedBlocks` table.

## Enforcement

**Definition:** The active OS-level mechanisms that prevent access to blocked applications and websites during a Session or Planned Block. Enforcement is a *side-effect* of a Session or Block being active — it is not a domain entity.

**Lifecycle:** Applied when a Session starts or a Planned Block activates → remains active during breaks (current behaviour) → removed when session ends or block expires.

**Mechanisms (in order of application):**
1. **Process kill loop** — kills matching process trees every 2 seconds
2. **Hosts file** — writes `0.0.0.0` / `::` entries between `# NEN_FOCUS_START` markers
3. **DNS flush** — `ipconfig /flushdns` after each hosts write
4. **Registry** — disables DoH (`BuiltInDnsClientEnabled = 0`) and sets `DnsOverHttpsMode = "off"` in Chrome, Edge, Brave
5. **Browser extension** — intercepts navigations via `chrome.webNavigation.onBeforeNavigate`, queries the local HTTP API at `localhost:5005/check`, redirects blocked sites to `blocked.html`

**Known gaps:**
- The `/report` endpoint is implemented: when the extension reports a blocked navigation, `WindowsEnforcementService` calls `IBlockedAttemptTracker.RecordWebBlockedAsync` if an active session exists. Background Block attempts (no `ActiveSessionId`) are still not tracked.
- Allowlist mode is handled by the `/check` endpoint: in Allowlist mode the endpoint returns `blocked: true` for any domain NOT in `AllowedSites`. Note that the hosts-file path cannot enforce allowlist mode (you cannot enumerate all domains); the browser extension is the sole allowlist enforcement mechanism.
- Blocked attempt tracking currently only works for app process kills during Ritual sessions (via `IBlockedAttemptTracker`). Website blocked attempts and Background Block tracking are future work.
- Usage Ceiling enforcement is not yet implemented. `PolicyEngine` does not yet read `DailyUsage`. The `/report-time` endpoint does not yet exist. See `ARCHITECT_GOVERNANCE.md` → Open Gap A.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Application | `IEnforcementService` | Contract for applying and removing enforcement; accepts `ActivePolicySlice` (Domain Value Object) |
| Domain | `IPolicyEngine` / `PolicyEngine` (`Services/`) | Computes `ActivePolicySlice` from raw domain entities; sole owner of all merge logic |
| Application | `ComputeActivePolicySliceQueryHandler` | Orchestrates data fetching across three repositories; delegates computation to `IPolicyEngine` |
| Infrastructure | `WindowsEnforcementService` | Consumes `ActivePolicySlice` directly; owns hosts file, process kill loop, registry writes, local HTTP API (`localhost:5005`). Only handles `/check` endpoint currently. |
| Infrastructure | `ScheduledEnforcementService` | `BackgroundService` heartbeat (5s); calls `ComputeActivePolicySliceQuery`, reads `ActiveBlockPresetType`, calls `IEnforcementService` |
| Extension | `background.js` | Intercepts browser navigation; queries `/check`; calls `/report` (not yet handled server-side) |

## Policy Slice

**Definition:** The computed, merged enforcement state at a given instant in time. It is the *answer* to the question "what should be blocked right now?" — derived from all currently active Sessions and Planned Blocks. Represented as `ActivePolicySlice`, a **Domain Value Object** in `NenFocus.Domain/ValueObjects/`, not a DTO.

**Computation rules** (all logic lives in `PolicyEngine.ComputeSlice()`):
- **Apps:** union of all blocked apps across all active block presets, always a blocklist. Includes `TemporaryBlockedApps` from the active `Session` entity.
- **Websites:** if *any* active preset uses `Allowlist` mode → default-deny, allowed = intersection of all allowlists minus any blocklist entries. Otherwise → block the union of all blocklisted sites. Includes `TemporaryBlockedSites` from the active `Session` entity.
- **Usage Ceilings *(not yet implemented)*:** In a future slice, `PolicyEngine.ComputeSlice()` will read `DailyUsage` against active `UsageCeiling` entries. Sites and apps whose ceiling has been exhausted for the current period (day or week) will be added to the blocked set — unless a hard-blocking preset already covers them, in which case the hard block wins and no usage accrues. See `ARCHITECT_GOVERNANCE.md` → Open Gap A.
- An `ActivePolicySlice` is considered "empty" only in `Blocklist` mode with no blocked apps or sites. It is *never* empty in `Allowlist` mode.
- **`ActiveBlockPresetType`:** set to `BlockPresetType.Focus` if any Focus Block is currently active, `BlockPresetType.Background` if only Background Blocks are active, `null` if enforcement is driven solely by an active Session with no planned block. Ritual always takes precedence over Background when both overlap.
- **"Active" is re-checked precisely inside `ComputeSlice` itself** (fixed 2026-08-20, `DESIGN_GAP_HISTORY.md` Gap 21's third addendum): `ComputeActivePolicySliceQueryHandler`'s own block query deliberately over-fetches with a ±1-second buffer around `at` (SQLite datetime-comparison slop), so `PolicyEngine` cannot simply trust every block the caller hands it — it filters through `PlannedBlock.IsActive(at)` as the final, precise authority. Before this fix, a block whose `End` fell inside that 1-second buffer could still become `ActiveFocusBlockId` even though `SweepMissedFocusBlocksCommandHandler`'s strict `End < asOf` check (using the same `at`) had already marked it `Missed` in the same heartbeat tick — re-triggering the Ritual for a block that already had a resolved Session. **`IsActive`'s own definition changed 2026-08-21 (Gap 32):** `atTime >= Start && atTime < EffectiveEnd(atTime)`, not raw `End` — a block whose session ended early now correctly stops being "active" the moment it actually ended, not at its original scheduled end (see `PlannedBlock.EffectiveEnd` below).

**Overlap rules:**
- Multiple Background Blocks can overlap freely. The net enforcement is the union of all their presets.
- A Focus Block can overlap with Background Blocks. The net enforcement is the union of all active presets. The Ritual is still triggered.
- Two Focus Blocks cannot overlap. The Planner prevents scheduling conflicts. A Spontaneous session cannot be started if it would overlap with an upcoming Focus Block.

**Why `ActiveBlockPresetType` matters:** `ScheduledEnforcementService` reads this field each heartbeat cycle. If `ActiveBlockPresetType == Ritual` and no Session is active, it calls `_sessionState.SetRitualRequired(true)` to push the user into the Ritual. If `ActiveBlockPresetType == Background`, enforcement is applied silently with no Ritual prompt. This is the correct application of the Ubiquitous Language principle — the difference between a Focus Block and a Background Block is expressed as a domain enum in the result, not as a boolean flag scattered across callers.

**Source of Truth flow:** `Database → PolicyEngine (Domain) → ActivePolicySlice (VO) → WindowsEnforcementService (OS)`

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `ActivePolicySlice` (`ValueObjects/ActivePolicySlice.cs`) | Immutable Domain Value Object; the canonical enforcement contract. Carries `BlockedApps`, `BlockedSites`, `AllowedSites`, `WebsiteFilterTypeMode`, `ActiveBlockPresetType`, `ActiveSessionId`, `IsEmpty`. |
| Domain | `IPolicyEngine` / `PolicyEngine` (`Services/`) | Stateless domain service; accepts raw `BlockPreset`, `Session`, and `PlannedBlock` collections and produces `ActivePolicySlice`. Owns all merge rules — no merge logic exists anywhere else. |
| Application | `ComputeActivePolicySliceQueryHandler` (`Queries/ComputeActivePolicySlice/`) | Pure orchestrator: fetches entities from three repositories, loads `BlockPreset` aggregates, delegates to `IPolicyEngine.ComputeSlice()`. Returns the `ActivePolicySlice` to callers. |
| Infrastructure | `WindowsEnforcementService` | Consumes `ActivePolicySlice` directly (no DTO) to drive OS-level mechanisms |
| Infrastructure | `ScheduledEnforcementService` | Reads `ActiveBlockPresetType` from the `ActivePolicySlice` each heartbeat to decide whether to trigger the Ritual |

## PolicyEngine

**Definition:** The sole Domain service responsible for computing the `ActivePolicySlice`. It is a stateless, synchronous function: given a point in time, a list of `BlockPreset` aggregates, a list of active `Session` entities, and a list of active `PlannedBlock` entities, it returns the complete enforcement state for that moment.

**Why it is a Domain Service (not an Application service):** Policy merge logic — the rules for unioning blocked apps, resolving allowlist/blocklist precedence, and assigning `ActiveBlockPresetType` — is domain logic. It expresses invariants of the domain ("an allowlist preset beats a blocklist preset", "a Focus Block takes priority over a Background Block") that must be consistent wherever policy is computed. Placing this logic in a Domain service makes it unit-testable without a database and reachable by any future consumer (e.g., a Planner "preview" query).

**Interface contract:**
```csharp
// NenFocus.Domain/Services/IPolicyEngine.cs
ActivePolicySlice ComputeSlice(
    DateTime at,
    IEnumerable<BlockPreset> presets,
    IEnumerable<Session> sessions,
    IEnumerable<PlannedBlock> blocks);
```

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `IPolicyEngine` (`Services/IPolicyEngine.cs`) | Interface; the contract Application code depends on |
| Domain | `PolicyEngine` (`Services/PolicyEngine.cs`) | Sealed implementation; all merge rules live here. Filters `blocks` through `PlannedBlock.IsActive(at)` before treating any of them as active (fixed 2026-08-20, `DESIGN_GAP_HISTORY.md` Gap 21's third addendum) — the caller's own fetch is allowed to be loose/buffered, but `PolicyEngine` is always the precise final word on "is this block active right now." `IsActive` itself now compares against `EffectiveEnd(at)`, not raw `End` (fixed 2026-08-21, Gap 32) — a block whose session ended early stopped freeing itself from `activeBlocks`, so `activeBlocks.OfType<FocusBlock>().FirstOrDefault()` could still pick a stale, already-resolved block over a genuinely new one scheduled into the freed time, permanently suppressing the new block's Ritual trigger until the stale block's raw window finally closed. |

## Planned Block

**Definition:** The abstract base class for all calendar-scheduled enforcement entries. A `PlannedBlock` has a `Start` time, an `End` time, a `BlockPresetId`, and an optional `Title`. It is never instantiated directly — only its two concrete subtypes (`FocusBlock` and `BackgroundBlock`) are created. The C# class type encodes the block preset type; there is no stored `BlockPresetType` column.

**Domain behaviour:** `PlannedBlock` carries two domain methods used by both subtypes and the query layer:
- `IsActive(DateTime atTime)` — returns `true` if `atTime` falls within `[Start, End)`.
- `OverlapsWith(PlannedBlock other)` — returns `true` if the two windows intersect; used by the planner to prevent scheduling conflicts.

**Why it exists:** `IPlannedBlockRepository` returns `IReadOnlyList<PlannedBlock>` so that the enforcement pipeline can work with all scheduled blocks polymorphically without knowing their concrete type. `ComputeActivePolicySliceQueryHandler` then pattern-matches on C# type to derive `ActiveBlockPresetType` — the distinction is made exactly once, in the one place that needs it.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `PlannedBlock` abstract class (`Entities/PlannedBlock.cs`) | Base for `FocusBlock` and `BackgroundBlock`; exposes `IsActive()` and `OverlapsWith()` |
| Application | `IPlannedBlockRepository` | Returns `IReadOnlyList<PlannedBlock>`; callers cast to concrete type when subtype behaviour is needed |
| Application | `ComputeActivePolicySliceQueryHandler` | Pattern-matches on `FocusBlock` / `BackgroundBlock` to set `ActiveBlockPresetType` on the `ActivePolicySlice` value object |

## Focus Block

**Definition:** A planned calendar entry that does two things simultaneously at its designated start time: (1) enforcement activates immediately — the block preset's rules are applied before the user has done anything, and (2) the user is pushed to the Nen Ritual page to consciously start the session. The session created via the Ritual is the *Planned Session* associated with this block. Critically, enforcement is already in place from the designated time regardless of whether the user completes the Ritual immediately. If the user never completes the Ritual, the `FocusBlock` row still exists and Insights shows it as "missed" (`RitualCompletedAt` is null). Enforcement still expires at the block's scheduled end time whether the Ritual was completed or not.

**Must use a Focus-type Block Preset.** Only presets created with the Focus type are available when scheduling a Focus Block in the Planner or selecting a preset during the Ren step.

**Overlap rules:** Two Focus Blocks cannot overlap each other. A Focus Block can overlap with one or more Background Blocks — the net enforcement is the union of all active presets.

**Ubiquitous language rules:**
- A Focus Block is *scheduled*, not *started*.
- A Focus Block *activates* and *expires* — it is not started or ended.
- Enforcement from a Focus Block is *pre-emptive* — it does not wait for the Ritual to complete.

**Activation sequence:**
1. System clock reaches the block's `Start` time
2. Enforcement applies immediately (policy slice computed, OS-level blocking begins)
3. App navigates user to the Nen Ritual (Ten → Zetsu → Ren → Hatsu)
4. User completes Ritual → `StartSessionCommand` dispatched with `Origin = Planned` and `OriginatingBlockId = <this block's Id>`
5. `StartSessionCommandHandler` calls `FocusBlock.MarkRitualCompleted(DateTime.UtcNow)` and saves the block
6. The resulting Session (with `Origin = Planned`) is linked to this Focus Block via `Session.OriginatingBlockId`

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `FocusBlock` entity (`Entities/FocusBlock.cs`) | Extends `PlannedBlock`; inherits `Id`, `BlockPresetId`, `Start`, `End`, `Title?`; own field: `RitualCompletedAt?`; block preset type derived from C# class (`FocusBlock` → `BlockPresetType.Focus` in query handler — no stored column) |
| Application | `IPlannedBlockRepository` | Retrieves blocks for overlap validation and active-state queries |
| Application | `ComputeActivePolicySliceQueryHandler` | Queries blocks covering `DateTime.UtcNow`; merges with active Session |
| Application | `StartSessionCommandHandler` | Calls `FocusBlock.MarkRitualCompleted(DateTime.UtcNow)` when `OriginatingBlockId` is provided |
| UI | `PlannerPageViewModel` | Creates, updates, deletes Focus Blocks; drag interactions and form locking implemented |
| UI | `ShellViewModel` | (Not yet built) — will detect Focus Block activation and trigger Ritual overlay |

## Background Block

**Definition:** A planned calendar entry that activates enforcement at its designated start time, exactly like a Focus Block, but does **not** trigger the Nen Ritual. The user is not prompted to start a session — the block preset's rules simply become active. There is no associated Session entity. The block expires at its `End` time and enforcement is removed. The `BackgroundBlock` row itself is the complete Insights record — it appears in the Calendar view regardless of whether the machine was on during the scheduled time.

**Must use a Background-type Block Preset.** Only presets created with the Background type are available when scheduling a Background Block in the Planner.

**Overlap rules:** Multiple Background Blocks can run simultaneously. Their presets are merged via the PolicyEngine — the net enforcement is the union of all active presets. Background Blocks can also overlap with Focus Blocks.

**Contrast with Focus Block:**

| | Focus Block | Background Block |
|---|---|---|
| Enforcement at start time | ✅ | ✅ |
| Triggers Nen Ritual | ✅ | ❌ |
| Creates a Session entity | ✅ (via Ritual) | ❌ |
| Appears in Insights Calendar | ✅ | ✅ |
| Has `RitualCompletedAt` field | ✅ | ❌ |
| Can overlap with same type | ❌ | ✅ |
| Shows on Main Page timer | ✅ (after Ritual) | ❌ |
| Has Post-Session screen | ✅ | ❌ |

**Ubiquitous language rules:**
- A Background Block is *scheduled* and *activates* — it is not *started*.
- "Background" refers to the absence of a Ritual and Session, not the absence of enforcement.

**Technical mapping:**

| Layer | Artifact | Role |
|-------|----------|------|
| Domain | `BackgroundBlock` entity (`Entities/BackgroundBlock.cs`) | Extends `PlannedBlock`; inherits `Id`, `BlockPresetId`, `Start`, `End`, `Title?`; no additional own fields; block preset type derived from C# class (`BackgroundBlock` → `BlockPresetType.Background` in query handler — no stored column) |
| Application | `ComputeActivePolicySliceQueryHandler` | **Includes** Background Blocks when computing the active policy slice |
| Infrastructure | `ScheduledEnforcementService` | Picks up the Background Block in its 5s heartbeat and applies enforcement |

**Form locking:** Completed blocks and the active session's originating block open read-only in the form. `IsBlockLocked` (= `IsEditing && (IsEditingCompleted || activeSession.OriginatingBlockId == editingId)`) disables Date, End Time, and Preset fields and hides the Save button. `IsBlockLocked` reacts live to session state changes. Note `IsEditingCompleted` is `FocusBlock.RitualCompletedAt.HasValue`-based — it answers "has a Session already been created from this exact block, making rescheduling it dangerous," which is a different, Ritual-specific question from "should this block be deletable" (see `DeletePlannedBlockCommand` below).

**Deletion protection *(built, 2026-07-07)*:** `DeletePlannedBlockCommand` rejects deleting a block if either: (a) `PlannedBlock.HasEnded(now)` is true — the block's window has fully closed, so it's a historical record (Insights depends on a past `BackgroundBlock`'s row being "the complete record," and the Missed Session feature depends on a missed `FocusBlock` never being deleted or altered), or (b) the block is the active session's `OriginatingBlockId`. Deliberately **broader** than the UI's `IsEditingCompleted`/Ritual-completion check: a Focus Block that was *missed* (window closed, Ritual never completed) and any past Background Block (which never has a Ritual at all, so `IsEditingCompleted` is always false for it) were previously deletable with no protection anywhere, UI or backend — `HasEnded` closes both, since it's defined once on the shared `PlannedBlock` base and answers the same question for either block type. Applies uniformly whether the block is an ordinary uncommitted block or one linked to a Nen Contract — `ContractId` plays no part in the check.

**`CanDeleteFromForm` references the real rule instead of deriving its own *(fixed, 2026-07-07)*:** Previously `CanDeleteFromForm => IsEditing` — the Delete button was fully clickable regardless of lock state, a real, reachable gap, not just a theoretical one (see `DESIGN_GAP_HISTORY.md` Gap 9). The fix deliberately did not just gate it on `IsBlockLocked`, since that flag answers the Ritual-completion question, not the deletion question. Instead: `PlannedBlockDto` gained a `HasEnded` field, computed once in `GetPlannedBlocksForDayQueryHandler` via `block.HasEnded(clock.UtcNow)` — the exact same domain method `DeletePlannedBlockValidator` calls. `PlannerPageViewModel.EditBlockAsync` copies it into `IsEditingBlockEnded`, and `CanDeleteFromForm` is now `IsEditing && !IsEditingBlockEnded && activeSession?.OriginatingBlockId != editingBlockId` — composing two values the ViewModel *references* (one from the DTO, one from the live `ISessionStateService` noticeboard), never deriving a business verdict from raw `Start`/`End`/session data itself. This mirrors `MODULE_STANDARDS.md`'s ViewModel Forbidden Zone principle ("a value that requires calculation is computed by the Application layer and exposed as a ready-to-bind property") — the same principle `IsBlockLocked`/`IsEditingCompleted` already followed correctly; `CanDeleteFromForm` just hadn't been brought in line with it until now.

**Block Snapshot — read-only view for a done block *(built, 2026-08-21 — see `DESIGN_GAP_HISTORY.md` Gap 28)*:** clicking a **done** block no longer opens the edit form with fields disabled — it opens a dedicated, genuinely separate read-only overlay. "Done" means: for a Focus Block, `Outcome` has resolved (`Missed`/`StartedLate`/`EndedEarly`/`CompletedOnTime` — the block is no longer open); for a Background Block, which has no `Outcome` concept at all, `HasEnded` is the only signal. The pre-existing active-session-originating-block guard (`_sessionState.ActiveSession?.OriginatingBlockId == tile.Id`) is checked first and unchanged — a block whose session is still running keeps opening nothing (matching the existing behavior the locked edit-form fields were already built for), never the snapshot.

- **Content, Focus block with a Session** (`GetSessionSnapshotForBlockQuery` returns non-null): type/outcome/redemption badges, date, time range, duration, Zetsu goal, reflection (placeholder text when blank — a session ending without a reflection is a valid, deliberate outcome per `Session.SetReflection`'s own precedent, not an error state), a full expandable list of blocked attempts (`BlockedAttemptSnapshotDto` — resource name, type, timestamp), and — when `IsRedemption` — which missed block(s) it covered and how much. The sub-minute "within grace, full credit given" note this section used to show (Gap 45) is gone — see `DESIGN_GAP_HISTORY.md` for the whole-minutes crediting redesign that removed Gap 45's forgiveness outright; an `EndedEarly` badge now always has a real, honest deficit behind it, however small.
- **Content, no Session** (Missed Focus block, or any Background block — the query returns `null`): minimal snapshot only — type, preset, date, scheduled time range, duration. No session section at all, since there is structurally nothing to show. (A Cancelled block never reaches this view, or any Planner tile — `GetPlannedBlocksForDayQueryHandler` already filters `CancelledAt.HasValue` blocks out of the tile list entirely.)
- **Delete, from the snapshot only:** enabled iff the block has never been linked to a Nen Contract (`ContractId is null`) — permanently, even after that contract concludes. This **reverses** the historical-record protection `DeletePlannedBlockValidator` has had since Gap 9 (ended blocks were previously never deletable, full stop) for the non-contract-linked case specifically, while making contract-linkage protection **stronger** than before (previously scoped to `IsInEffect`, i.e. only while the contract was still live).

## Spontaneous Session

**Definition:** A Session created by the user clicking "Use Nen" on the Main Page and completing the full Nen Ritual (Ten → Zetsu → Ren → Hatsu), outside of any scheduled Focus Block. The user has full control: they choose the Block Preset (Focus-type only), set the duration, and configure break reminders. The Session is created with `Origin = Spontaneous` and `OriginatingBlockId = null`. No Block entity of any kind is created.

**Product invariant:** A manual enforcement session cannot exist without a completed Ritual. This is a product invariant enforced by design, not by validation code. If the user abandons the Ritual at any step before clicking "Start Session" on the Hatsu page, no record is saved anywhere — no draft, no partial session, no recovery state.

**Conflict rule:** A Spontaneous Session cannot be started if it would overlap with an upcoming Focus Block. For example, if a Focus Block is scheduled at 18:00, the user cannot start a 30-minute session at 17:45.

**Contrast with Planned Session:** A Spontaneous Session is user-initiated and requires no pre-scheduled block. A Planned Session is triggered by a Focus Block at its scheduled start time. In a Spontaneous Session the user freely chooses the Block Preset and duration; in a Planned Session both are pre-determined.

**Technical mapping:** No Block entity — distinguished at the Application layer by `Session.Origin == Spontaneous`. `Session.OriginatingBlockId` is `null`.

## Planned Session

**Definition:** A Session created by the user completing the Nen Ritual after a scheduled Focus Block activated and pushed them to the Ritual overlay. The Block Preset and duration are pre-determined by the Focus Block — the user cannot change the preset (Ren step) or the end time (Hatsu step), but can configure break reminders. The Session is saved with `Origin = Planned` and `OriginatingBlockId = <the triggering FocusBlock's Id>`. `StartSessionCommandHandler` stamps `FocusBlock.RitualCompletedAt` at this moment. If the user never completes the Ritual, no Session row is created; the `FocusBlock` row remains with `RitualCompletedAt = null` and Insights shows it as "missed." Enforcement still runs until the block's scheduled end time regardless.

## SessionOrigin

**Definition:** An enum that tags every `Session` with how it was initiated. Values: `Spontaneous` (user completed the Ritual from the Main Page without a pre-scheduled block) and `Planned` (user completed the Ritual after a Focus Block pushed them to it).

**Why this is not a nullable FK check:** `Session.OriginatingBlockId` is `null` for Spontaneous sessions, but reading nullness as "origin type" is a leaky boolean. `SessionOrigin` makes the intent explicit and self-documenting. It remains unambiguous when future origin types are added.

## Nen Contract *(Domain, Application, Infrastructure, and UI all built and landed 2026-07-08–2026-08-19 — see `TECHNICAL_SPEC_INFRA.md` → Done for the full slice history. Contract Preset management UI is the one still-open piece — see below)*

**Definition:** A sealed, time-bound commitment the user makes to a schedule of Focus Blocks and Background Blocks over a contiguous date range, with self-imposed rules governing how much the schedule can be changed during the commitment period. The name is inspired by the concept of binding agreements — the user is making a contract with themselves.

**Two creation paths in the Planner wizard:**

1. **Simple Contract** — Pick from one of three named presets, schedule blocks, seal. No tuning knobs. The floor is automatically set to whatever Focus hours the user planned per day — each day's floor = that day's total scheduled Focus hours. Rest days are automatically derived (days with zero planned hours have a floor of zero). User cannot adjust strictness, work hours, or allow-cancellation individually. The three simple presets are:

| Preset | Strictness Rule | Allow Cancellation | Mental Model |
|---|---|---|---|
| **Lockdown** | `Locked` | Yes *(interim — see note below)* | "This schedule is law. I will not touch it." |
| **Daily Flex** | `DailyFlexibility` | Yes | "I can shuffle blocks around within each day." |
| **Period Study** | `PeriodTimeBudget` | Yes | "Hours can move across days, but the total must balance." |

2. **Advanced Contract** *(narrowed 2026-08-21 — see `DESIGN_GAP_HISTORY.md` Gap 27)* — no longer freeform rule entry. The user picks a saved **Contract Preset** (strictness rule, daily floor, work hours, allow-cancellation — authored and edited on the Presets page's "Contract Presets" tab, never in the wizard) and its rules apply exactly as saved, shown read-only for confirmation; there is no on-the-spot tweaking. Rest days and (future) change window remain wizard-only regardless of mode — both are date-bound to this specific contract's range, never preset material. If the user has no saved Contract Presets yet, the wizard shows an empty-state message pointing to the Presets page instead of an empty picker. Advanced is still the only path that can carry Work Hours.

**`AllowCancellation` is not enforced anywhere right now — interim, not the intended final behavior (2026-08-18, widened same day).** First pass only changed Lockdown's Simple-preset default to `true` (so newly-sealed Lockdown contracts would be cancellable), but any contract already sealed before that change — or any Advanced contract someone deliberately built with cancellation off — was still hard-blocked by `NenContract.Break()`, `BreakNenContractValidator`, and the Planner's Cancel button, all three of which checked `AllowCancellation` directly. Since the app is still in active development/testing, that meant a developer's own test contracts could get stuck un-cancellable. Confirmed with the architect: the *real* intended gate for "you can't cancel this" is a future global **Strict Mode** Settings toggle (already referenced as unbuilt in `TECHNICAL_SPEC_INFRA.md`'s Settings Page row, and in this file's own Session section re: ending early) — not this per-contract flag. So all three enforcement points were relaxed, not just the Lockdown default: `NenContract.Break()` no longer throws on `AllowCancellation == false`, `BreakNenContractValidator` dropped the matching rule, and `PlannerPageViewModel.CanCancelActiveContract` now just checks `HasActiveContract`. `AllowCancellation` itself is **not removed** — still stored on `NenContract`, still user-configurable in Advanced, still defaults per-preset — it's just not read as a gate anywhere until Strict Mode exists to become the real one. Revisit every one of these three spots (search for "interim" comments referencing this note) when Strict Mode is built.

**Contract Presets *(Domain/Application/Infrastructure built 2026-07-08; Presets-page authoring UI built 2026-08-21, superseding wizard-side creation — see `DESIGN_GAP_HISTORY.md` Gap 27)*:** A saved, reusable template of Nen Contract configuration *rules only* — `Name`, `StrictnessRule`, an optional `DailyFloor?` value (nullable since 2026-08-19 — a preset can represent "no fixed floor" the same way a contract can; see the Daily Floor entry below), a single optional `WorkHours?` value, `AllowCancellation`. `ContractPreset` is a full Domain `AggregateRoot` (`Entities/ContractPreset.cs`), consistent with every other persisted concept in this codebase. Rest days, work-hours per-day exceptions, and the date range are deliberately **not** part of a preset: all three are date-bound and can't generalize across the arbitrary future date range a preset gets applied to — they're always supplied fresh in the wizard when the user seals, regardless of which preset (if any) is picked. Applied as-is when picked in the wizard's Advanced mode — the resulting `NenContract` stores its own independent copy of every rule, not a live reference back to the preset, and there is no further tweaking once picked (unlike the old "start from preset, then edit" flow this replaced). `NenContract.ContractPresetId (Guid?)` records which preset (if any) a contract was sealed from, purely so preset deletion can check for a live commitment — see the deletion-guard row below. **Authoring and management: Presets page → "Contract Presets" tab (`ContractPresetPageViewModel`) — built.** Full CRUD (create, edit, delete, list) lives there exclusively now; the wizard's old "Save as preset" checkbox (`ContractRulesStepViewModel.SaveAsPreset`/`PresetNameToSave`) is deleted, along with `ContractReviewStepViewModel`'s `CreateContractPresetCommand` dispatch — a contract preset can no longer be created or edited mid-wizard, only picked.

**Simple vs Advanced — which contract fields are user-configured vs. derived:**

*(Table updated 2026-08-21 — Advanced's rule fields no longer come from direct entry in the wizard; they come from whichever Contract Preset is picked, applied as-is. "Fixed by preset" in the Advanced column below means the **Contract Preset** picked in the wizard, not one of the three hardcoded Simple options.)*

| Field | Simple | Advanced |
|---|---|---|
| Strictness Rule | Fixed by Simple option | Fixed by picked Contract Preset |
| Daily Floor | Derived: per-day = planned Focus hours for that day | Fixed by picked Contract Preset — a fixed whole-hour floor if the preset has one set, otherwise the same per-day-derived floor as Simple. Capped at the preset's own Work Hours window's span if both are set (enforced by `CreateContractPresetValidator`, at preset-authoring time, not in the wizard). |
| Work Hours | None (no constraint) | Fixed by picked Contract Preset (optional on the preset) |
| Rest Days | Derived: days with 0 planned hours | User explicitly designates — still wizard-only, date-bound to this contract's range, unaffected by which preset is picked |
| Allow Cancellation | Fixed by Simple option | Fixed by picked Contract Preset |

**Aggregate boundary:** `NenContract` is its own aggregate root. It does **not** own `PlannedBlock`s — blocks remain their own aggregate and legally exist outside any contract (uncommitted weeks). The link is a nullable `ContractId` on `PlannedBlock`: `null` means an ordinary, uncommitted block; set means the block is under that contract. Blocks predate contracts, are mutated directly by the existing drag/create/update paths, and the Daily Floor is a **soft, tracked** invariant after seal (flagged and scored as a miss, not hard-blocked) — there is no need for atomic multi-block invariants enforced inside the contract entity. Enforcement of Strictness Rules and Work Hours constraints is applied later by Application-layer guards that load the contract and inspect blocks separately; the domain only provides the rules and pure calculations.

**Scope:** A Nen Contract covers a single contiguous date range (`StartDate`–`EndDate`, inclusive on both ends, `DateOnly`). Contiguity is structural — a single continuous range has no gaps by construction, so no separate contiguity check exists beyond `StartDate <= EndDate`.

**No two in-effect contracts may share any day (enforced 2026-08-11):** Since both endpoints are inclusive, two contracts sharing even one boundary day (A ends the day B starts) count as overlapping — no shared days are allowed at all. Checked against every currently in-effect (Scheduled or Active) contract via `CheckNenContractDateRangeOverlapQuery`, enforced for real at Seal time by `SealNenContractValidator` and previewed live in the Contract Wizard's Basics step (UX convenience, not itself a guard). Before this, nothing prevented sealing two overlapping contracts.

**Seal:** The act of finalising a contract. There is no persisted draft state in the domain — a `NenContract` comes into existence only via `NenContract.Seal(...)`, its sole factory method. Seal hard-validates a caller-supplied `DailyFloorPolicy` against a caller-supplied per-day map of **Focus hours only** (Background block hours are never counted toward the floor — Focus-only by design). For every day in `[StartDate, EndDate]`, the policy resolves that day's floor (`DailyFloorPolicy.For(date)`); a day whose resolved floor is `null` is a rest day — **skipped entirely**, not checked against zero. A day with a resolved floor must have planned hours (from the map, defaulting to `0` if absent) that satisfy it, or Seal throws. **In Simple contracts**, the policy has no `Default` — every planned day is given its own explicit floor equal to that day's planned hours (so the check always passes by construction), and any day the caller omits from `PerDayExceptions` is a true rest day. **In Advanced contracts**, the policy typically has a fixed `Default` (e.g. "3 hours every day") applied to every day, with explicit `PerDayExceptions[date] = null` entries for user-designated rest days. On seal, `Status` becomes `Active` if the caller-supplied `sealedAt` is on or after `StartDate`, otherwise `Scheduled` — the domain never reads the clock itself; `sealedAt` is passed in, exactly like `Session.Start(DateTime startedAt)`. Raises `NenContractSealedEvent`.

**Lifecycle:**

```
Scheduled ──► Active ──► Completed
   │            │
   │            └──► Broken
   │                 ▲
   └─────────────────┘
   (Break: Scheduled or Active → Broken)
```

Transitions:
- `Scheduled → Active`: `Activate(DateTime)` — called by heartbeat when `StartDate` arrives.
- `Active → Completed`: `Complete(DateTime)` — called by heartbeat when `EndDate` passes.
- `Scheduled | Active → Broken`: `Break(DateTime)` — user cancels; only valid while `IsInEffect` (widened 2026-08-11 from Active-only, so a not-yet-started contract can be cancelled before Day 1 — see `DESIGN_GAP_HISTORY.md`) and only if `AllowCancellation` was `true` at seal. Raises `NenContractBrokenEvent`. `BreakNenContractCommandHandler` atomically breaks the contract and deletes every one of its linked blocks that hasn't ended yet (`!PlannedBlock.HasEnded(now)`) — one command, one transaction, no choice prompt (decided 2026-07-07, superseding the earlier delete-or-unlink design; see `DESIGN_GAP_HISTORY.md`). Past blocks stay linked for historical accuracy. The domain does not touch blocks — they are a separate aggregate; the handler mutates them via `IPlannedBlockRepository` directly. **UI-reachable:** a "Cancel" button on the Nen Contract popover's Active card, behind a confirmation dialog. **Relocated off the Planner's week banner entirely (2026-09-06, see `DESIGN_GAP_HISTORY.md` Gap 55)** — the banner's own "✕" was removed once the banner started reflecting a per-week *switchable* contract selection (see the Rest Days vs. the Planner's live badge entry below); Cancel now lives only in the popover's Active card, which always names the one true `NenContractStatus.Active` contract app-wide, independent of the Planner's current week or switch state. `AllowCancellation` is not currently checked at this call site (interim, 2026-08-18 — mirrors `NenContract.Break`'s own comment: every in-effect contract can be cancelled until a future Strict Mode setting exists as the real gate).

**No mid-contract extension.** A previously-built `Extend` operation (pushed `EndDate` forward on an Active contract) was removed by deliberate architect decision (2026-09-04) — it went against the product's own philosophy: a sealed contract is the commitment you made; wanting more means sealing a new one, not reopening the old one. `NenContractExtendedEvent` was deleted along with it.

**Strictness Rule (locked at seal, user-configurable):** Modelled as a single enum, not a value-object hierarchy — the three rules are points on one axis of post-seal mutability, and the logic that *interprets* a rule against an edit's context lives in Application-layer guards, not inside the rule itself. The strictness rule is immutable after seal (no mid-contract changes in v1; a future v2 feature may allow tightening only, never loosening — parked). *(Collapsed from four rules to three — see `DESIGN_GAP_HISTORY.md` for the closure record: the former `DailyTimeBudget` value was deleted because it was already 100% behaviorally identical to `DailyFlexibility` in shipped code; its "total time conserved" intent was folded into `DailyFlexibility`'s definition below instead.)*
- **Locked:** No changes allowed during the contract period. Blocks cannot be moved, removed, or shortened. New blocks can still be added.
- **DailyFlexibility:** Within each day, the user can rearrange blocks — move, resize, swap when things happen — but the total scheduled block time for that day must never drop below that day's own resolved Daily Floor; only for the current or upcoming day. **Built 2026-08-19, resolved as floor-protection rather than exact conservation** — see `DESIGN_GAP_HISTORY.md` Gap 18 for the full reasoning. `UpdatePlannedBlockValidator` re-checks the edited day's total (via `ComputePlannedFocusHoursQuery`) against `NenContract.IsDayMet(date, newTotal)` whenever a Focus block under a `DailyFlexibility` contract shrinks — the same domain rule Day-Met scoring already uses, not a re-derived comparison. A pure same-duration move never changes a day's total, so this only ever bites an actual shrink; shrinking one block while growing another on the same day still works as long as each individual edit's resulting total holds (grow-then-shrink always succeeds; shrink-then-grow can hit a false rejection mid-sequence, since there is no multi-block atomic edit in this codebase — each drag is its own commit).
- **PeriodTimeBudget:** Two distinct modes, chosen at Seal/Edit time by whether a fixed daily floor is set (built 2026-08-19 — see `DESIGN_GAP_HISTORY.md` Gap 18 for the full design history):
  - **With a fixed daily floor** (the "Advanced daily floor checkbox" is on): behaves like `DailyFlexibility`'s per-day floor-protection, except a move can land on a *different* day than it started (blocks may go anywhere within `[StartDate, EndDate]`) — so both the day being vacated and the day being landed on are re-checked against their own (possibly different) floors, not just one.
  - **Without a fixed daily floor** (the default/derived choice, and the mode that actually matches this rule's own name): no per-day obligation exists at all — `NenContract.ContractFloor (ContractFloor?)` holds a single whole-period target instead, derived at Seal as the sum of every drafted Focus block's hours, immutable after that. `NenContract.IsPeriodMet(double totalFocusHours)` mirrors `IsDayMet`'s shape, scoped to the period total instead of one day; `UpdatePlannedBlockValidator` re-checks the whole-contract total (not a single day) after any edit. Day-Met scoring, `DaysBehind`/`DaysConsidered`, and rest days don't apply to this mode at all — every day is equally "in play," none is ever individually obligated or exempt. The Planner banner instead shows total completed vs. the `ContractFloor` target (`"Xh / Yh completed"`) — the same banner format every strictness rule now uses (see `TotalFloorHours`/`TotalCompletedHours` below).
  - `ContractFloor` is deliberately a distinct value object from `DailyFloor`, not a reuse — same shape (`Hours`, `IsSatisfiedBy`), but no 24-hour cap, since a whole-period total can easily exceed a single day's realistic maximum. Mutually exclusive with a real (non-empty) `DailyFloorPolicy` — `NenContract.Seal` throws if both are set with real content, the same "illegal state prevented by a guard clause, not a type-system union" discipline used elsewhere in this aggregate.

**Sealed-contract enforcement on planned blocks (built 2026-08-11):** A `PlannedBlock` whose `ContractId` resolves to a contract with `IsInEffect == true` (Scheduled or Active — a Completed or Broken contract's blocks fall back to the ordinary `HasEnded`-based protections, the same posture the WorkHours guard already takes toward a missing/irrelevant contract) is protected by that contract's `StrictnessRule`:
- **Delete is always rejected**, regardless of `StrictnessRule` — a block under a live commitment can never be deleted; only `Break` (which explicitly requires `AllowCancellation`) can remove it, via its own atomic cleanup.
- **Update** rejects any preset (`BlockPresetId`) change outright, for every `StrictnessRule` — re-typing a committed block isn't a designed operation any more than re-parenting its `ContractId` is (the latter has no field to change on `UpdatePlannedBlockCommand` at all, by the same original design decision). Time changes (move/resize) are then gated per rule via `NenContract.AllowsBlockTimeChange(originalDate, newStartDate, newEndDate)` — a pure entity method mirroring `AllowsBlockPlacement`/`CheckRedemptionEligibility`'s shape: `Locked` rejects every time change; `DailyFlexibility` requires the new window to stay on the block's original local calendar day; `PeriodTimeBudget` requires it to stay within `[StartDate, EndDate]`. `AllowsBlockTimeChange` only compares dates — callers resolve local time before calling, same discipline the WorkHours guard already follows.
- The UI mirrors this without re-deriving it: `PlannedBlockDto.IsUnderInEffectContract` (computed once by `GetPlannedBlocksForDayQueryHandler`) hides the Planner's Delete button for these blocks, same "Application computes, UI only references" precedent `HasEnded` already established (`DESIGN_GAP_HISTORY.md` Gap 9). Drag-move/resize still runs client-side; the Application-layer guard is the actual authority and rejects the command if the drop is illegal, and the Planner now reloads the week on a rejected drag (previously only on success) so the tile snaps back to its real position.

**Split Block *(built 2026-08-19 — see `DESIGN_GAP_HISTORY.md` Gap 17)*:** The one designed exception to Delete's unconditional rejection above — splitting a sealed `DailyFlexibility` block into two. Exclusively `DailyFlexibility` (Lockdown blocks are immutable full stop; `PeriodTimeBudget` was deliberately excluded from this feature, not merely unimplemented for it) and exclusively for a block no session has touched (any session, not just an active one — checked via `ISessionRepository.GetByOriginatingBlockIdAsync`, eliminating session-migration concerns entirely). `SplitPlannedBlockCommand` takes both resulting halves' explicit `Start`/`End` — deliberately not a single cut-point — and is atomic delete-and-recreate: the original `PlannedBlock` is deleted, two new ones are created with fresh `Id`s, the same `ContractId`/`BlockPresetId`, and no parent-child relationship between them (both are "equal contract members"). `SplitPlannedBlockValidator` requires the two halves to sum to exactly the original's duration, both stay on the block's original calendar day, and neither overlaps the other or any other existing block. The command is deliberately ignorant of what happens next — dragging the resulting second half to a new time is an ordinary, separate `UpdatePlannedBlockCommand`, not part of Split at all.

**Daily Floor:** The minimum completed Focus hours required on a given day. `NenContract.DailyFloorPolicy` (a `DailyFloorPolicy` value object) resolves the floor **per day**, not as one number for the whole contract — this was a deliberate redesign (2026-07-07) from an earlier single-scalar `NenContract.DailyFloor` that could not actually support the per-day-varying behaviour described below; see `DESIGN_GAP_HISTORY.md` for the closure record. `DailyFloorPolicy` mirrors `WorkHoursPolicy`'s shape exactly: a `Default (DailyFloor?)` applied to every day plus `PerDayExceptions (IReadOnlyDictionary<DateOnly, DailyFloor?>)` that override it, resolved via `.For(date)`. The underlying pure comparison (`DailyFloor.IsSatisfiedBy(hours)`) is unchanged and still serves both the Seal-time check (against *planned* Focus hours) and the later Day Met evaluation (against *completed* Focus hours) for whatever floor `.For(date)` resolves to. **In Simple contracts**, the policy has no `Default` — every planned day gets its own explicit `PerDayExceptions` entry equal to that day's planned hours: Monday with 2 planned hours has a floor of 2, Tuesday with 3 has a floor of 3. The Application layer passes planned hours as both the "planned" and "floor" values for each day, so the Seal check always passes by construction. **In Advanced contracts**, the user sets one fixed `Default` (e.g., "3 hours every day") checked against each day's planned hours at Seal — days below the floor are rejected — with `PerDayExceptions` reserved for explicitly designated rest days (see below).

**Rest Days:** A day is a rest day when `DailyFloorPolicy.For(date)` resolves to `null` — no obligation, skipped entirely by Seal validation and trivially met by `IsDayMet`. **In Simple contracts**, rest days are derived automatically: any day the Application layer omits from `PerDayExceptions` (i.e. any day with zero planned Focus hours) is a rest day, since there is no `Default` to fall back to. **In Advanced contracts**, the user explicitly designates rest days in the Planner wizard, which the Application layer encodes as `PerDayExceptions[date] = null` — this overrides the `Default` for that specific day. Rest days are not stored as their own field on the contract entity; they are implicit from how the policy resolves each date, fixed permanently at Seal (there is no `Extend` to revisit this later — see `DESIGN_GAP_HISTORY.md` Gap 51). The user may still schedule blocks on rest days voluntarily — they just aren't required.

**Rest Days vs. the Planner's live badge (built 2026-09-04 — see `DESIGN_GAP_HISTORY.md` Gap 52):** `DailyFloorPolicy`/`IsRestDay` above are the domain's own permanent record and never change after Seal. The Planner's day-header badge is a separate, read-time-only projection that can legitimately disagree with it in one direction: a domain rest day that later receives a floor-counting block anyway (a redemption, or a committed block moved in under Period Time Budget) renders as a normal progress badge against an ad-hoc target instead of "Rest" — purely a display choice computed by `GetNenContractsForDateRangeQueryHandler` (renamed 2026-09-06 from `GetActiveNenContractQueryHandler`, see Gap 55), never written back to `DailyFloorPolicy` and never affecting `IsDayMet`/`DaysBehind`/redemption eligibility, all of which still see the same permanent rest day they always did.

**Multi-contract weeks and the banner switcher (built 2026-09-06 — see `DESIGN_GAP_HISTORY.md` Gap 55):** A viewed Planner week can straddle the boundary between two in-effect contracts (one ending, the next starting mid-week) — every day's badge is computed and shown regardless, one contract's `DayStatuses` merged with the other's (contract date ranges never overlap, so there is never a collision to resolve). The banner text and the Cover Deficit button, by contrast, only ever name **one** contract at a time (`PlannerPageViewModel.SelectedContract`) — defaulting to whichever is `Active`, else the one with the earliest `StartDate` — with a small switch button to page to the other contract touching the same week when more than one exists. Switching re-targets the banner text and Cover Deficit's target contract only; it never changes which days have badges. A day belonging to a `Scheduled` (Upcoming) contract always renders as a uniform passive grey regardless of met/unmet/rest; an `Active` contract's rest day instead uses its own teal shade, graduated by whether the day is Past/Today/Future (see `UI_UX_STANDARDS.md`).

**Work Hours *(Application-layer wired 2026-07-08 — closes Task #13; wizard UI still not built)*:** A daily time-of-day window (`TimeOnly` start/end) defining where Focus and Background blocks may physically exist on the calendar. Blocks cannot be placed, moved, or resized to any time outside the work hours window. This is distinct from Change Window — Work Hours constrains *where blocks can be*, Change Window constrains *when edits are allowed*. Advanced contracts only; Simple contracts have no work hours constraint.

Per-day exceptions are supported via an `IReadOnlyDictionary<DateOnly, WorkHours?>` — a `null` value means no constraint for that day (free placement), a non-null value overrides the default work hours for that specific date. `SealNenContractCommand` exposes only the Default-window half of this plus `NoWorkHoursDays` (an explicit-null per-day exception list) — deliberately **not** a full per-day-different-window map, even though `WorkHoursPolicy` itself supports one and the domain/EF-mapping cost is already paid (Task #11): `FixedDailyFloorHours`/`RestDays` (the analogous pair for `DailyFloorPolicy`) exposes the *exact same* asymmetry today — one fixed value plus explicit rest-day exemptions, never a different non-null floor per specific day. Matching that existing precedent was judged more consistent than exposing more for Work Hours than Daily Floor already exposes on this same command. `WorkHoursPolicy.NoConstraintExceptions(IReadOnlyCollection<DateOnly>)` mirrors `DailyFloorPolicy.RestDayExceptions` exactly, same reason (fresh-build and future-merge callers share one conversion). The Planner's drag-math (`PlannerDragMath.WouldCollide`) and CreatePlannedBlock/UpdatePlannedBlock guards (`NenContract.AllowsBlockPlacement`, built Slice 6 Step 3) are now fully live — the guard was correct all along, it just had nothing to check against until now.

Domain value object `WorkHours { TimeOnly Start, TimeOnly End }` carries one window; `ContainsRange(DateTime start, DateTime end)` checks standard interval containment (`blockStart >= Start && blockEnd <= End`) — a block ending exactly at the window's close (e.g. a 9-to-5 block against 9:00–17:00 work hours) is valid. **Fixed 2026-08-18:** the comparison anchors the window to `start`'s calendar date and compares full `DateTime`s, not `TimeOnly.FromDateTime(...)` — the earlier `TimeOnly`-based comparison discarded the date, so a block ending exactly at midnight (e.g. 19:00–24:00, represented as the next day's 00:00) wrapped to `00:00` and read as trivially before any `End`, silently passing containment no matter how far past closing time it actually ran. Regression case added to `WorkHoursTests.cs`.

**Enforced during drafting too, not just post-Seal (fixed 2026-08-18):** `NenContract.AllowsBlockPlacement`/`ContainsRange` were only ever reachable through `CreatePlannedBlock`/`UpdatePlannedBlock` validators, which require a persisted `ContractId` — but per the Seal ubiquitous-language entry above, no `NenContract` exists until Seal, so a draft Focus tile placed during the wizard's drafting phase had no contract to check against and could be dropped anywhere, only getting rejected retroactively once the contract was sealed. `PlannerPageViewModel.ValidateDraftPlacement` now also checks the in-progress `WorkHoursStart`/`WorkHoursEnd` (from `NenContractDraftRules`, reusing `WorkHours.ContainsRange` directly rather than re-deriving the comparison) for Focus draft tiles only — Background tiles remain unconstrained, matching the sealed-contract rule.

The default window and its per-day exceptions are bundled into one value object, `WorkHoursPolicy { WorkHours? Default, IReadOnlyDictionary<DateOnly, WorkHours?> PerDayExceptions }`, rather than stored as two loose fields on `NenContract` — they are always configured and consumed together (one "Work Hours" section in the Advanced wizard, one JSON blob on a Contract Preset). `WorkHoursPolicy.For(DateOnly date)` resolves the effective window for a day: an exception wins (including an explicit `null` meaning "no constraint that day"), otherwise the default applies, otherwise there is no constraint. This is the single place the exception-with-fallback lookup lives — the Planner drag-math and command handler guards will both call `contract.WorkHoursPolicy?.For(date)?.ContainsRange(start, end) ?? true` rather than reimplementing the lookup. `NenContract.WorkHoursPolicy (WorkHoursPolicy?)` is set via an optional trailing parameter on `Seal(...)`, default `null` (Simple contracts, and any Advanced contract without a work-hours constraint).

**Change Window *(parked — domain value object exists, not wired up in v1)*:** An optional daily time-of-day window (`TimeOnly` start/end) during which edits to *existing* blocks are permitted, plus a configured `UsesPerDay` limit. The domain value object (`ChangeWindow`) is built and answers `Contains(TimeOnly)`, but Application-layer use-count tracking, UI configuration, and enforcement guards are all deferred. Distinct from Work Hours (see above). If implemented later, the Change Window configuration would likely live in the Settings page as a user-wide preference rather than per-contract.

**Strictness tightening mid-contract *(parked for v2)*:** The user may want to tighten the strictness rule mid-contract (e.g., switch from `DailyFlexibility` to `Locked` because they're losing discipline). Only tightening would be allowed — never loosening. Not in v1.

**Active-contract banner text (unified 2026-08-19):** Every strictness rule shows the same format now — `"Contract: [Name] — Day X/Y — Xh / Yh completed — Zh deficit"` — replacing the earlier Day-Met-only framing (`"Z of N days behind... M of N days met"`), which read as unnecessarily different for a `PeriodTimeBudget`-without-fixed-floor contract once that mode existed. `NenContractRangeViewDto.TotalFloorHours`/`TotalCompletedHours` (renamed 2026-09-06 from `ActiveNenContractDto`, see `DESIGN_GAP_HISTORY.md` Gap 55) compute uniformly for every contract: `TotalCompletedHours` is always a straight sum of completed Focus hours across the whole contract; `TotalFloorHours` is `ContractFloor.Hours` when set, otherwise the sum of every day's resolved per-day floor across `[StartDate, EndDate]` (rest days contribute `0`) — the total minimum commitment across the whole contract, computed the same way regardless of strictness. `DaysBehind`/`DaysConsidered` are still computed (kept for any future per-day-scoring consumer, e.g. Open Gap C's streaks) but no longer read by the banner text itself. The deficit (and Bonus) figure's wording was also tightened (Gap 55): an exact-hour amount reads as `"Xh"` (not `"Xh 0m"`), a sub-hour amount spells out `"N min"`, and a mixed amount stays `"Xh Ym"` — one shared formatter (`MinutesToStringConverter.FormatMinutes`) used by the deficit text, the Bonus label, and redemption-covered displays alike.

**Day Met:** A contract day is "met" if that day's *completed* Focus hours ≥ that day's resolved Daily Floor — evaluated via `NenContract.IsDayMet(DateOnly date, double completedFocusHours)`, which resolves `DailyFloorPolicy.For(date)` and compares against it (a day with no resolved floor is trivially met — it's a rest day). A missed or late Focus block does **not** fail the day directly; it only costs hours that must be made up elsewhere. Completed hours are summed across all sources: planned-block sessions, redemption block sessions, and **spontaneous sessions** that match a contract preset (see Spontaneous Redemption below). If the hours are made up, the day is met. The missed/late information lives in the per-block `FocusBlockOutcome` classification — a separate display concern. Summing a day's actual completed Focus hours is an Application-layer computation.

**FocusBlockOutcome:** How a single Focus block resolved — `CompletedOnTime`, `StartedLate`, `Missed`, or `EndedEarly` — classified purely from its scheduled window, ritual-completion state, and (since 2026-08-12, `DESIGN_GAP_HISTORY.md` Gap 22) when the session ended, via `IFocusBlockOutcomeClassifier.Classify(scheduledStart, scheduledEnd, ritualCompletedAt, sessionEndedAt, asOf)`. Returns `null` when no verdict has been reached yet (the block is still open — in progress or future — and could still be started late right up to its scheduled end). `Classify` gives `EndedEarly` priority over `StartedLate` when a block is genuinely both — one block, one verdict — but the two facts are independent, so `PlannedBlockDto.WasStartedLate (bool)` (built 2026-08-20, `DESIGN_GAP_HISTORY.md` Gap 20) carries the lateness fact separately, letting the Planner tile show both a "STARTED LATE" and an "ENDED EARLY" badge when both are true.

**Planner tile display (built 2026-08-20, Gap 20):** a tile's `Start`/`End` are the block's *actual worked window*, not its raw scheduled window — `GetPlannedBlocksForDayQueryHandler` pulls `Start` forward to `RitualCompletedAt` once past the grace period, and `End` back to `SessionEndedAt` for an early end, so the tile visually shortens from whichever end(s) apply (both, if the block is both `StartedLate` and `EndedEarly`). A grace-period-late start is left untrimmed, matching the fact it's still credited as full duration. Tile color/badge, driven by `Outcome`: `CompletedOnTime` → green, no badge (color alone reads as "on time"); `StartedLate`/`EndedEarly` → the same amber, labeled "STARTED LATE"/"ENDED EARLY" (both, stacked, when a block is genuinely both); `Missed` → red, "MISSED," struck through (unchanged). The mapping from `Outcome` to a CSS class name/badge string lives entirely in `PlannerPageView.axaml.cs`'s code-behind, not the ViewModel — `PlannedBlockTileViewModel` only ever exposes the semantic `Outcome`/`WasStartedLate` facts, mirroring how `DayFloorStatusToBrushConverter` already keeps ViewModels ignorant of their own visual representation.

**Ritual is never opened for a block that already has a Session** (built 2026-08-20, `DESIGN_GAP_HISTORY.md` Gap 21's fourth addendum): `GetFocusBlockRitualContextQueryHandler` (called by `ShellViewModel.StartRitual` immediately before the Ritual UI opens) now also checks `ISessionRepository.ExistsForOriginatingBlockAsync` and surfaces it as `FocusBlockRitualContext.AlreadyHasSession`. If true, `StartRitual` declines to open the Ritual at all — showing it would only guarantee a rejection at Hatsu (`StartSessionCommandHandler`'s pre-existing `ExistsForOriginatingBlockAsync` check, the only place this fact was previously checked, and only at the very end of the flow). A general guard against any stale ritual-required signal, not scoped to one specific cause.

**5-minute grace period** (universal — all Focus Blocks, contracted or not) *(built, 2026-07-08 — see `DESIGN_GAP_HISTORY.md` Gap 11 for the closure record; the window was documented well before it was actually implemented in `Classify`; crediting formula rewritten 2026-09-07, `DESIGN_GAP_HISTORY.md` Gap 57)*:
- A ritual completed within 5 minutes after the scheduled start (≤ `scheduledStart + 5 min`, via `FocusBlockOutcomeClassifier.GracePeriodMinutes`) is `CompletedOnTime` — the Ritual takes a moment, and penalizing a 13:03 completion for a 13:00 block is noise. This label rule is unchanged by Gap 57.
- **Current crediting formula (`IFocusBlockOutcomeClassifier.CreditedWindow`/`CreditedFocusMinutes`), one unconditional rule, no branching on how the session ends:** grace forgives a late start **unconditionally** — credit starts counting from the block's own **scheduled start**, regardless of whether the session later runs to completion or ends early — because blocking enforcement is already active on the user's computer from `PlannedBlock.Start` onward (`PolicyEngine.ComputeSlice` keys entirely off `Start`/`End`, never `RitualCompletedAt`); crediting that setup window is honestly counting real enforcement time, not inventing work. A start **beyond** grace gets no such allowance — credit starts from the moment the Ritual actually completed. A genuine early end always counts exactly what was delivered, **however small the shortfall — no forgiveness at any grain** (Gap 45's sub-minute write-off was removed outright in Gap 57). A session that runs its course credits up to `scheduledEnd`, never beyond, whether it ended naturally or was force-ended past due (e.g. via the debug clock). The whole result — the credited *window's own End*, not just a derived minutes figure — is floored to whole minutes as the final step (`Session.GetElapsedTime` also floors at its own, independent source), so every consumer of "how much did this block earn" (the deficit ledger, completed/bonus hours, Post-Session's duration) reads a clean whole-minute value with nowhere for stray seconds to leak in. Seconds only ever matter for the Main Page's own live countdown, which never reads through either of these methods.
- **Grace-period warning notification** *(Application/Infrastructure — not yet built)*: 3 minutes past the scheduled start, if the Ritual still hasn't been completed, the app fires a toast: "You have 2 minutes to complete the Ritual or this block will be marked as a late start." At 5 minutes, if still uncompleted, the outcome becomes `StartedLate` (or `Missed` if the end passes). The notification is a one-shot — it does not repeat.
- The missed/late boundary remains the block's **scheduled end**, not its start.

**Redemption Block:** A Focus Block explicitly linked to one or more missed or late Focus Blocks, covering all or part of their deficit. The link is a collection of `RedemptionEntry` value objects on `PlannedBlock` — empty (never null) means a regular block. Redemption blocks are always Focus Blocks (Background Blocks have no sessions and cannot contribute toward a Focus-hours deficit). **Built** — see the technical mapping rows for `ComputeRedemptionAttributionQuery`, `NenContract.CheckRedemptionEligibility`, and the Create/UpdatePlannedBlock handlers below. Confirmed tiles render with a "REDEMPTION" text tag (`PlannedBlockDto.IsRedemption`, `RedemptionEntries.Count > 0`) — same color family as the block's own outcome/preset, no border treatment (a dashed-border variant was tried and removed 2026-08-21, judged not to look good).

**Redemption path — automatic attribution, no toggle *(redesigned 2026-08-21 — see `DESIGN_GAP_HISTORY.md` Gap 26, superseding the same-day toggle-based UI from Gap 25)*:** Linking is no longer a client-driven choice. Any new or edited Focus Block whose preset+date is eligible to cover an outstanding deficit is attached automatically — `CreatePlannedBlockCommandHandler`/`UpdatePlannedBlockCommandHandler` compute the attachment themselves via `ComputeRedemptionAttributionQuery`, oldest outstanding deficit first, spilling into the next if the block is longer. The block-creation form shows a passive preview notice ("This will cover 45 min of your missed Deep Work block") once eligibility is detected — informational only, no click required and nothing to opt out of. `NenContract.CheckRedemptionEligibility` now allows all three `StrictnessRule` values (see Rules 8–10 below); `RedemptionEligibility.NotAllowed` was deleted as unreachable once `Locked` stopped being a hard no. Separately, the Planner's active-contract banner gets a **"Cover Deficit"** button (`GetSuggestedRedemptionPlacementsQuery`) that creates a real tile on demand, sized to a preset's total outstanding deficit and placed at the next quarter-hour (shifted earlier, never before now, only if needed so the full amount still fits before the day's boundary — midnight or Work Hours close; searches past conflicting tiles; asks for confirmation before creating a knowingly-partial tile if even starting now can't fully cover it). More than one preset owing → a small popover (mirrors the Nen Contract popover's button+Popup shape) lets the user pick which one; exactly one → skips the popover and creates the tile directly.

**Main Page spontaneous redemption prompt — dropped (2026-07-08), not building it.** The original design: when a contract is active with an outstanding deficit, the Main Page would prompt the user to start a redemption session; the Ritual's Ren step would pre-lock to the preset with the largest deficit, Hatsu would show the deficit amount, and the resulting Spontaneous session's partial coverage would reduce the deficit ledger. Fully interrogated and deliberately dropped, not merely deferred — see `ARCHITECT_GOVERNANCE.md` Open Gap D for the full reasoning (why `Session` has no natural anchor for per-block deficit attribution, why every alternative modeling considered either leaked, over-built, or failed to deliver real redemption semantics, and what to build first if this is ever revisited). The Planner toggle above remains the only redemption mechanism.

|---|------|
| 1 | A missed or late Focus Block creates a **deficit** = `scheduledDuration − creditedMinutes` (full scheduled duration for a miss; `IFocusBlockOutcomeClassifier.CreditedFocusMinutes` for a late start or early end — **not** raw actual-elapsed minutes, see `DESIGN_GAP_HISTORY.md` Gap 24). |
| 2 | Deficit is tracked **per missed block**, not per preset — each missed block is an independent row in the deficit ledger. |

| 4 | All linked missed blocks must share the **same `BlockPresetId`** as the redemption block — `ComputeRedemptionAttributionQuery` only ever attaches a block to deficits of its own preset, computed automatically on every Create/Update, no client selection involved. |
| 4a | All linked missed blocks must also share the **same `ContractId`** as the redemption block — enforced by construction: `ComputeRedemptionAttributionQuery` only ever walks one contract's deficit ledger per block (the explicitly-scoped one, or whichever single in-effect contract it auto-discovers). |
| 5 | One redemption block can cover multiple missed blocks of the same preset (e.g., two 30-minute misses → one 60-minute redemption) — oldest outstanding deficit first, spilling into the next if the block is longer (`ComputeRedemptionAttributionQuery`). |
| 6 | A redemption block's duration can **exceed** the total selected deficit — surplus is fine and counts toward the Daily Floor, just not attributed to any specific missed block. |
| 7 | `MinutesCovered` (the ledger claim per missed block) is capped at `Min(remainingBlockDuration, remainingDeficit)` for each entry in oldest-first order — deliberately decoupled from the block's own total scheduled duration, so a block longer than any single deficit correctly spills the remainder into the next-oldest one instead of over-claiming against the first. |
| 8 | Under **`Locked`** and **`DailyFlexibility`** strictness: a missed block can only be covered on the **same calendar day** it was scheduled — for Daily Flex that's its whole model of same-day rearrangement; for Locked, new blocks can always be inserted (only editing/moving an *existing* sealed block is forbidden), so redemption is allowed but confined to that same day. |
| 9 | Under **`PeriodTimeBudget`** strictness with a real per-day floor (the Gap 18 hybrid): same rule as Rule 8 — each day has its own obligation, so coverage must land on the same day. With a pure whole-period `ContractFloor` instead (no per-day floor): a missed block can be covered on **any day** within the contract period. |
| 10 | `RedemptionEligibility.NotAllowed` does not exist — every `StrictnessRule` allows redemption in some form (Rules 8–9). There is no strictness value under which redemption categorically cannot happen. |
| 11 | A missed block's `FocusBlockOutcome` stays `Missed` (or `StartedLate`) regardless of whether it was later redeemed. Insights shows both: the original miss AND the successful redemption. |
| 12 | A redemption block gets its own `FocusBlockOutcome` (`CompletedOnTime` / `StartedLate` / `Missed`) — classified independently. |
| 13 | A redemption block that itself is missed does **not** create additional deficit. The original missed block's deficit simply remains uncovered. No "redeem the redemption" chain. **This rule was documented but not actually enforced until 2026-08-21** — `GetNenContractDeficitsQueryHandler` treated a redemption block as an ordinary Focus Block subject to becoming its own deficit source; see `FocusBlock.CanContributeOwnDeficit` below and `DESIGN_GAP_HISTORY.md` Gap 29. |
| 14 | If the user has outstanding deficits across **different presets**, each new Focus Block only ever attaches to deficits of its own preset — there is no cross-preset attribution, and no user choice involved for an ordinary block creation. The "Cover Deficit" banner button surfaces one option per preset when more than one is owing, for the user to pick which to create a tile for. |
| 15 | Every edit to an existing redemption-eligible Focus Block **recomputes its coverage from scratch**, scoped to the block's own already-known contract — an edit never re-parents a block to a different contract, and a standalone block (no contract) never auto-discovers one just by being edited. |
| 16 | Splitting a redemption block (`SplitPlannedBlockCommandHandler`) queries attribution once for the original block's whole combined span, then partitions the result across the two resulting halves by each half's own duration — an entry entirely within one half's window goes to that half only; one straddling the cut point splits into two entries against the same missed block. Never copies the same entries onto both halves (a fixed double-count bug from the toggle-era implementation). |
| 17 | The "Cover Deficit" banner button sizes each preset's tile to that preset's **total** outstanding deficit (summed across every missed block of that preset), placed at the next quarter-hour — shifted earlier (never before now) only if needed so the full amount still fits before the day's boundary (midnight, or the contract's Work Hours close for that day), searching past any conflicting tile. If even starting right now can't fully cover it, the tile is offered anyway (starting now, ending at the boundary) with a confirmation prompt before creating a knowingly-partial one. |
| 18 | A block's outcome only counts toward the deficit ledger — as a deficit source **or** as a covering block's contribution — once its session has actually ended (`Session.HasEnded`), naturally or early. A late-started session still in progress (its final credited minutes aren't knowable — it could still end early) is treated as still-open (`null`), exactly like a block that hasn't happened yet, purely within `GetNenContractDeficitsQueryHandler` — `IFocusBlockOutcomeClassifier.Classify` itself is untouched and keeps reporting live for every other consumer (Day Met's progress number, Insights, Planner badges). Deliberately **not** gated on `PostSessionAcknowledgedAt` — that fact exists for crash-recovery replay, an unrelated concern, and gating on it would leave an already-final deficit hidden until the user happens to dismiss the Post-Session screen. See `DESIGN_GAP_HISTORY.md` Gap 34. |

**Broken → blocks handling *(built; redesigned 2026-08-18 — see `DESIGN_GAP_HISTORY.md` Gap 23)*:** `BreakNenContractCommandHandler` calls `Break()`, saves, then calls `MarkCancelled(now)` on every linked block (Focus or Background alike) for which `HasEnded(now)` is false, and saves each — **no longer a delete**. `PlannedBlock.CancelledAt (DateTime?)` records the fact; `PlannedBlock` also gained `: AggregateRoot` (a prerequisite for `MarkCancelled` to raise `PlannedBlockCancelledEvent`). Enforcement stops via a `CancelledAt` filter at two layers (`ComputeActivePolicySliceQueryHandler` excludes cancelled blocks before resolving presets; `PolicyEngine.ComputeSlice()` independently filters its own `activeBlocks` input, defensively). The Planner excludes cancelled blocks from the calendar view. If the active session's `OriginatingBlockId` matches one of the contract's blocks, that session is also force-ended in the same commit (`session.Complete(now)`, mutated directly, not composed through `EndSessionCommandHandler`, to stay in the one atomic commit `TransactionalCommandHandler` provides). Blocks that have already ended (`End < now`) stay linked and untouched, for historical accuracy. This closed the original "delete-everything makes a recap of a broken contract structurally impossible" problem — a `GetNenContractRecapQuery` can now distinguish **Cancelled** (`CancelledAt.HasValue`) from **Missed/StartedLate/CompletedOnTime** (`IFocusBlockOutcomeClassifier.Classify`, untouched) among a broken contract's surviving blocks — though that query itself is still not yet built, tracked in `ARCHITECT_GOVERNANCE.md` → Open Gap G.

**Block-preset deletion guard *(not yet built)*:** A preset cannot be deleted while referenced by an active or scheduled contract, a future planned block, or an active session. This is an Application-layer concern.

**Settings integration *(future)*:** In the Settings page, the user will be able to pre-save default strictness rules automatically applied when creating a new Nen Contract. The Change Window (if implemented later) would also be configured here as a user-wide preference rather than per-contract. Work Hours configuration is per-contract (set in the Planner wizard), not a Settings-level preference — each contract can have different work hours.

## Deep Module

**Definition:** A software module (class, service, or interface) that provides *significant* functionality through a *narrow*, simple API. The term comes from John Ousterhout's *A Philosophy of Software Design* and is a core architectural principle for NenFocus.

**The test:** Can a developer understand how to use this module in under 30 seconds by reading only its interface? If yes, it is deep. If the interface requires reading the implementation to use correctly, it is shallow and should be redesigned.

**Examples in NenFocus:**

| Module | Why it is deep |
|--------|---------------|
| `IActiveSessionMonitor` | 4 properties + 2 events; hides a background timer, UTC math, break tracking, and command handler invocation |
| `ISessionStateService` | 3 methods + 2 events; hides DB rehydration, preset name resolution, and broadcast coordination |
| `IEnforcementService` | 2 methods (`ApplyPolicyAsync`, `RemoveEnforcementAsync`); hides process kill loop, hosts file, DNS flush, registry, HTTP API |

## Design Gap

**Definition:** The distance between what a developer can see (the current interfaces and existing code) and what they need to understand to implement a new feature correctly. Every new feature starts with a Design Gap; the job of the pre-implementation "Grill Me" session is to close it before any code is written.

**Related principle:** See `ARCHITECT_GOVERNANCE.md → High-Level Development Strategy → 1. Strategic Design & The Design Gap`.
