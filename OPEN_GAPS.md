### Gap 69 (A) — Usage Ceiling & Universal Usage Tracking (interrogated 2026-07-07; not yet built)

**This entirely supersedes the previous "Time Budget" framing of this gap — not a patch, a rewrite.** `BlockedSite` does **not** gain a `TimeBudget` field. `BlockPreset` (Focus and Background alike) remains pure hard-block only, permanently. The budget concept was pulled off `BlockedSite` entirely and rebuilt as an independent feature, for reasons recorded below.

**The feature, in two independent parts:**

1. **Universal usage tracking (foundation).** Every website visited and every application's foreground time is tracked unconditionally, from day one — not just resources with a configured ceiling. This is deliberately general-purpose: the same substrate feeds both Usage Ceiling enforcement and the future Insights page's time-per-site/time-per-app reporting. Scoping collection down to only configured entries would starve Insights of data for everything else.
2. **Usage Ceiling (ambient access cap).** A standing, perpetual cap on a specific site or app's access time — created and managed on the **Presets page**, not Settings, not the Planner, and explicitly not part of Nen Contract (rationale below). Always in effect once created; no calendar involvement whatsoever.

**Precedence rule (the core design decision):** If any currently-active Focus or Background preset hard-blocks a resource, that hard block always wins — the resource is blocked, full stop, and no usage accrues during that window. Outside of any active hard block, the resource is accessible up to its ceiling; once the ceiling is reached for the current period, the resource is blocked for the rest of that period. This carries forward the one rule that was already correct in the old Time Budget spec (hard block wins, budget doesn't tick during it) — unchanged by the rewrite.

**Why decoupled from `BlockPreset`/`BlockedSite`:** The original design tied a site's budget window to the owning `PlannedBlock`'s schedule, which conflated two unrelated things — a schedule-bound hard block (what presets are for) and an ambient, calendar-independent personal limit (what this is for). That conflation was the source of the original "does a time budget make sense on a Focus Block" doubt — it never did, because it was never really a preset-level concept to begin with.

**Why decoupled from Nen Contract:** `NenContract` is sealed and time-bound (`StartDate`–`EndDate`), governing edit permission for a committed block schedule with Daily-Floor scoring. A Usage Ceiling is perpetual, unsealed, and governs passive resource access — coupling them would mean ceilings stop functioning between contracts, or if no contract is ever sealed, which contradicts the point of an *ambient* limit. Sibling concepts, not dependent ones.

**Domain shape (interrogated, not yet built):**

| Concept | Shape |
|---|---|
| `DailyUsage` (entity) | Append-only fact, keyed by `(Date, ResourceName, UsageResourceType)`, accumulates seconds. Mirrors `BlockedAttempt`'s pattern exactly — no `SessionId`, no `PresetId`, no `BlockPresetId`. Belongs to nothing but the day and the resource. |
| `UsageResourceType` (enum) | `App` \| `Website` — mirrors `BlockedAttemptType`. |
| `UsageCeiling` (entity, deliberately not a value object) | `Id`, `ResourceName`, `ResourceType (UsageResourceType)`, `Period (CeilingPeriod)`, cap value(s), `IsPaused`. Entity because it has independent identity, an independent lifecycle (created/edited/paused/deleted via its own CRUD, not nested inside another aggregate), and is looked up by `Id` from `PolicyEngine` on every tick — the same justification that makes `FocusBlock`/`BackgroundBlock` entities rather than value objects. Carries a pure `IsExhausted(...)` comparison method — same justification as `DailyFloor.IsSatisfiedBy` (the rule belongs with its data, reused wherever exhaustion is checked, not duplicated across callers). That's a separate, orthogonal DDD question from the entity/value-object determination — both apply here, for different reasons. No domain events; nothing reacts to a ceiling being created or paused. |
| `CeilingPeriod` (enum) | `Daily` \| `Weekly` — chosen per entry, mirrors the multi-mode shape of `StrictnessRule`. **Daily** mode's cap is a per-weekday shape (e.g. Monday 3h, Tuesday 1h), mirroring `WorkHoursPolicy`'s `{ Default, PerDayExceptions }` resolution pattern. **Weekly** mode's cap is a single aggregate tracked cumulatively across the week, mirroring the idea behind `StrictnessRule.PeriodTimeBudget` applied to resource access instead of block-editing permission. |
| `IUsageTracker` (Application interface) | Narrow write contract for usage events, mirrors `IBlockedAttemptTracker` exactly. |

**Collection mechanisms (asymmetric cost — both required for "track everything"):**

- **Websites** — cheap; the extension already intercepts every navigation. Needs tab-focus-time accumulation added, idle detection via `chrome.idle`, and a media-playing exception (an audible/playing tab doesn't count as idle) so passive video consumption isn't misread as inactivity. Reports via a new `/report-time` endpoint, distinct from the existing `/report` (which only logs blocked *attempts*).
- **Apps** — genuinely new capability. Needs a foreground-process polling loop — cheaper than the existing 2-second kill loop, since it targets one process rather than enumerating all of them — plus idle detection via `GetLastInputInfo`. The native equivalent of the media-playing exception would need Windows Core Audio Session APIs (per-process audio output detection) and is materially harder to build than the web side. **Open question:** whether the native audio exception ships in v1, or apps launch with plain idle-timeout only.

**Enforcement wiring — a fork was considered and resolved:** `PolicyEngine.ComputeSlice()` is **extended, not bypassed**. It gains new inputs (active `UsageCeiling` entries plus resolved `DailyUsage` totals for the relevant period) and folds exhausted ceilings directly into `ActivePolicySlice.BlockedSites`/`BlockedApps`. The alternative — a second, parallel "am I blocked" check inside `WindowsEnforcementService`, OR'd together with `PolicyEngine`'s output at the enforcement layer — was explicitly rejected: it would push a domain rule (exhaustion, precedence) into Infrastructure and break "`PolicyEngine` is the sole owner of all merge rules," the same principle Gap 2 and Gap 5 already established. One authority for "what's blocked and why," not two.

**Consequence for the enforcement pipeline:** `ScheduledEnforcementService`'s heartbeat and `WindowsEnforcementService`'s local HTTP API currently start/stop with enforcement bursts. For ambient ceilings to mean anything, both must run for the app's full lifetime, independent of whether any Session or Block is active. Confirmed acceptable during interrogation — the app-side tracking loop is cheaper than the kill loop already running today, and the extension already intercepts navigation regardless of NenFocus's state, so the performance cost of "always on" is negligible.

**UI placement:** Presets page, new tab (working label "Usage Ceilings"). Not a `BlockPreset`/`ContractPreset`-style reusable template — a ceiling isn't consumed to create another object, it's a standing, directly-enforced rule. Not Settings. Not the Planner.

**Not the same feature as recurring hard blocks — do not conflate:** "Always block Reddit" or "block Facebook 9–5 daily" is not a Usage Ceiling. It's a permanent or repeating hard block — the separately-tracked **Recurring Blocks** gap (see `TECHNICAL_SPEC_INFRA.md` → Not Yet Built) applied to ordinary `BackgroundBlock`s, living on the Planner. No relationship between the two features; Recurring Blocks was not interrogated in this session and remains fully open.

**Open questions, not resolved in interrogation:**
- Whether specific resources (NenFocus's own process, `localhost`, `SystemSafetyConstants.UnkillableProcesses`) are excluded from `DailyUsage`, or truly everything is logged unconditionally.
- Day/week boundary semantics — reset time, week-start day, timezone handling.
- Exact CQRS shapes for `UsageCeiling` CRUD and usage-summation queries.
- Whether the native per-app audio-playing exception ships in v1.

**Must be closed before:** Nothing urgent — deferred until picked up. The domain shape is settled enough to start Slice 1 (entities + interfaces) whenever that happens.

### Gap 70 (B) — Crash Resilience: Session Recovery After Unexpected Shutdown

**The gap:** If the app crashes or is force-killed mid-session, the current recovery path relies entirely on `SessionStateService.InitializeAsync()` querying `ISessionRepository.GetActiveAsync()` at startup. This is sufficient for clean restarts (the session was committed to SQLite before the crash), but it does not cover two failure cases:

1. **Mid-write crash** — the session was started, OS enforcement was applied (`WindowsEnforcementService.ApplyPolicyAsync`), but the DB write had not yet committed when the process died. On restart the DB shows no active session, so enforcement is never re-applied and the user's desktop is unblocked silently.
2. **Enforcement state drift** — the hosts file and process kill timer may be in an enforcing state after a crash, but `WindowsEnforcementService._currentPolicy` is `null` on restart. `ScheduledEnforcementService` will re-apply enforcement on its next heartbeat (≤5 s), so the window is small — but it is a window.

**Why deferred:** Both failure cases require the app to be crashed in a narrow write window. The risk is low for a personal focus tool and the correct fix (a proper recovery protocol) is non-trivial to design correctly. A previous incomplete attempt (`SessionPersistenceService`, a JSON sidecar file) was deleted because it introduced a second source of truth with no active consumer, which creates a divergence risk worse than the problem it was solving.

**Direction (subject to interrogation when closed):** The correct design is to make SQLite the single durable source of truth and close the write window, rather than maintaining a sidecar file. Candidate approaches — to be interrogated before any code is written:

- Begin each session command in a DB transaction that also records an "enforcement intent" row; `ScheduledEnforcementService` reads this on startup before its first heartbeat to re-apply enforcement immediately rather than waiting up to 5 s.
- Alternatively, treat the 5-second heartbeat window as acceptable and document it; add a startup check in `HostExtensions` that calls `WindowsEnforcementService.ApplyPolicyAsync` synchronously if `GetActiveAsync` returns a live session, closing the enforcement drift window to zero.
- Do **not** reintroduce a JSON sidecar — any file-based approach must explain how it stays in sync with the DB on every write. `EfCoreUnitOfWork` already solves exactly this problem for in-process command handling (see Gap 5 in `DESIGN_GAP_HISTORY.md`); a sidecar file would have to solve it independently, with no shared transaction boundary.

**Must be closed before:** The app is used in a high-stakes environment (e.g., exam blocking, supervised study) where a crash silently removing enforcement would be a product safety failure. For personal use, the current behavior is acceptable.

**First step if recovery restores a planned session (noted 2026-09-28):** a planned session's start/end and its `FocusBlock`'s `RitualCompletedAt`/`SessionEndedAt` stamps are one story written in two places, today kept in step only by line order in `StartSessionCommandHandler`/`EndSessionCommandHandler`. A second writer is the trigger to move each pair into one Domain operation (e.g. a `PlannedSessionLifecycle` domain service) so it can never be half-done — same note on Gaps 72 and 78. Consider doing it together with grouping `RitualCompletedAt`/`SessionEndedAt` into one `SessionRun(StartedAt, EndedAt?)` value object on `FocusBlock` (null = no session, open end = running) — EF can map it onto the existing two columns (idea noted 2026-09-28, Gap 86).

### Gap 71 (C) — Nen Contract Motivation & Scoring Enhancements (three interrogated, unbuilt)

**Why deferred:** All three were fully interrogated in a design session (2026-07-07) and each has a settled interface, but none can be built until the Nen Contract Application/Infrastructure/UI layer exists at all — it is still entirely "not yet built" per `DOMAIN_DICTIONARY.md`. Specifically, all three depend on the **completed-hours-per-day summation query** (planned-block + redemption + matching-spontaneous-session hours, summed per calendar day), which is a prerequisite `IsDayMet` already needs for real use regardless of these additions — so this gap adds no new dependency, it just rides on one already owed to the feature. None of the three affect Planner, Presets, or session-start flows on their own merit; Planner is only touched because C2's streak was chosen to surface live on the already-planned active-contract banner. **That completed-hours query used to be buggy — fixed 2026-08-12, see `DESIGN_GAP_HISTORY.md` Gap 22 (closed).** `GetNenContractCompletedFocusHoursQueryHandler` used to silently under-credit any block that was ended early (`EndSessionCommandHandler`'s old `TrimEnd` call corrupted the record it read from). Gap 22 closed this before C1/C2/C3 were ever built on top of it, so none of the three inherit the bug — whenever one of them is picked up, the query it depends on is already trustworthy.

**C1 — Weighted Day Met percentage (Insights):**
- New pure domain method `DailyFloor.PercentComplete(double completedHours) -> double?` — returns `null` when `Hours == 0`, otherwise `completedHours / Hours`, uncapped (133% displays as 133%, never clamped to 100%).
- `NenContract` gains a mirroring wrapper `PercentOfFloorMet(DateOnly date, double completedFocusHours) -> double?` — resolves `DailyFloorPolicy.For(date)` and delegates to `DailyFloor.PercentComplete` if a floor exists, otherwise returns `null` (rest day) — mirrors the existing `IsDayMet(DateOnly, double)` → `IsSatisfiedBy` delegation, updated for the per-day `DailyFloorPolicy` redesign (see `DESIGN_GAP_HISTORY.md`), so the Application layer never reaches into `DailyFloorPolicy`/`DailyFloor` directly.
- `IsDayMet` stays the sole authoritative pass/fail for Redemption deficit logic and lifecycle transitions — this percentage is a purely additive display concern, computed at query time, no new persisted state.
- UI: Insights contract recap gets a day-strip (one tile per day) shaded by percentage; rest days render as "Rest," not "100%."

**C2 — In-contract streaks:**
- Consecutive Day-Met days *within a single contract's date range only*. Deliberately does not span across separate contracts or the gap between them — Day Met has no meaning outside an active contract (no floor to compare against), and extending a streak across that gap would require inventing an ungrounded rule for what "counts" on a non-contract day (rejected: a trivial spontaneous session shouldn't be able to prop up a streak meant to reflect honoring a real commitment).
- Rest days are skipped — they neither extend nor break the streak.
- Surfaces live on the Planner's active-contract banner (e.g. `"Contract: [Name] — Day X/Y — Z days behind — 5-day streak"`) and as a "best streak achieved" stat in the Insights recap after the contract ends.
- Exact query shape (bundled with the progress/deficit query vs. a separate dedicated query) deliberately left open — an implementation-time call, not a design gap.

**C3 — Deficit digest notification:**
- Proactive OS toast (same delivery mechanism as the existing grace-period warning), firing once per calendar day at a **user-configurable time** — a new Settings preference, per-user not per-contract.
- Skips entirely on days with no deficit — no "on track" toast; silence is the intended good-day behavior.
- One-shot per day, same "already fired today" guard pattern as the grace-period warning.
- Content: current deficit + days remaining, e.g. *"You're 1.5h behind on Study Month — 3 days left."*
- Was designed to coexist with the Main Page spontaneous redemption prompt — that prompt has since been dropped (see Open Gap D); C3 does not depend on it and needs no change.

**Must be closed before:** Nothing — purely additive once the Nen Contract Application layer and completed-hours summation query exist. No urgency driving closure.

**Parked, not interrogated:** Two related ideas came up in the same session and were deliberately shelved by the architect until there's a better view of the finished program — not designed in depth, listed here only so they aren't forgotten:
- **Contract templates from Insights** — a "start a new contract like this one" shortcut on a *completed* contract's Insights recap, pre-filling the Advanced wizard from that specific past instance rather than a saved Contract Preset. Distinct from Contract Presets because it copies a real past result, not a deliberately-saved template.
- **Strictness tightening mid-contract** — already tracked as a parked v2 idea in `DOMAIN_DICTIONARY.md` (Strictness Rule section); re-confirmed parked in this session, no new detail added.

### Gap 72 (D) — Spontaneous Redemption Path (interrogated 2026-07-08 and dropped; reopened 2026-09-27 with a new direction — parked, not re-interrogated)

**The original design:** When a contract is active with an outstanding deficit, the Main Page shows a prompt ("You're 1.5 hours behind on your Study Month contract. Start a redemption session?"). Clicking through pre-locks the Ritual's Ren step to the preset with the largest deficit and shows the deficit amount at Hatsu; the user picks any duration, including a partial redemption. The resulting Session is ordinary `Origin = Spontaneous`, `OriginatingBlockId = null` — no Block entity involved, matching the Ubiquitous Language definition of a Spontaneous Session.

**Why it turned out harder than the Planner-path redemption (which *is* built — see `DOMAIN_DICTIONARY.md` technical mapping):** the Planner path's deficit ledger (`GetNenContractDeficitsQuery`) is scoped **per missed block**, via `RedemptionEntry` value objects owned by the *covering* `PlannedBlock`. A Spontaneous session has no block to own an equivalent collection — its only anchor is `Session` itself, which has no `RedemptionEntries` field and, per the documented flow, is never given a specific missed block to target (only a preset). Closing that gap turned out to need real new structure, not a small addition.

**Options interrogated and rejected:**
- **`Session.RedemptionEntries`, mirroring `PlannedBlock`'s field directly, auto-allocated across missed blocks.** Rejected: the field would only ever be meaningful when `Origin == Spontaneous` — the same "nullness/relevance depends on a discriminator" smell `SessionOrigin` itself was introduced to eliminate (see `DOMAIN_DICTIONARY.md`, `SessionOrigin`).
- **Day-level only — let spontaneous sessions count toward Day Met via the already-built `GetNenContractCompletedFocusHoursQueryHandler`, no per-block attribution at all.** Rejected on closer inspection, not just complexity grounds: completed minutes are always attributed to the day the session/block actually happens on, including for the *existing, shipped* Planner-path redemption mechanism — a Friday redemption block covering a Tuesday miss credits Friday, never retroactively fixes Tuesday's Day Met. Day Met was never the currency "redemption" moves; the block-level deficit ledger is a deliberately separate mechanism that tracks "was this commitment eventually honored," independent of which day. Reusing only Day Met machinery therefore can't move the number the Planner checklist shows — it would just be "extra contract-relevant work helps today," true for any spontaneous session regardless of any deficit, dressed in redemption language without delivering redemption semantics.
- **A new independent `DeficitCoverage`-shaped entity, generalized to reference either a covering block or a covering session (nullable dual-source).** Rejected as over-built for the chosen scope: since the Planner path was never going to be migrated onto it (see next point), the block-source field would be permanently null in practice — reintroducing the same "field only sometimes meaningful" smell in a new location instead of avoiding it.
- **The same entity, but narrowed to spontaneous-only (`{Id, MissedBlockId, CoveringSessionId, MinutesCovered}`, no polymorphism) — full unification with the Planner path deferred.** This was the option the interrogation converged on as correct **if built**: additive-only change to `GetNenContractDeficitsQuery`'s existing formula (one more subtracted term), zero changes to shipped/tested Slice 6/7 code, matches the `DailyUsage`/`UsageCeiling`/`BlockedAttempt` precedent of "an entity with independent identity belonging to nothing but the fact it records." Naming it anything containing "Block" was explicitly rejected — it isn't one (no `Start`/`End`, no calendar placement, no participation in drag-math or enforcement); a name in the `RedemptionEntry` family (e.g. `SpontaneousRedemptionEntry`) was preferred instead.
- **A shared base type / inheritance between `FocusBlock` and a "SpontaneousBlock."** Rejected: `PlannedBlock`'s entire identity is a *pre-scheduled* calendar placement — that's what makes drag-math, `WorkHoursPolicy` guards, and the enforcement pipeline work. A Spontaneous session has no advance schedule; a "SpontaneousBlock" sharing that base would only ever be a retroactive shadow copy of `Session`'s own `StartedAt`/`EndedAt`, forcing an artificial is-a relationship to reuse one field, and widening `PlannedBlock`'s responsibilities to accommodate a case that doesn't share its nature (every consumer — Planner CRUD, enforcement, drag-math — would need a mental exception for it).
- **A shared `IRedemptionCapable` interface instead of a class hierarchy.** Also rejected: `FocusBlock` and `Session` always come from two separate repositories, so nothing ever holds a naturally-mixed polymorphic collection of them to justify the interface — it would have no real call site.
- **Using a shared type to help Insights distinguish Spontaneous vs Planned entries.** Unnecessary: `GetInsightsCalendarQuery` already unifies `BackgroundBlock`, `FocusBlock`, and `Session` (`Origin = Spontaneous`) into one `InsightsEntryDto` via a read-side projection — the correct DDD tool for "show heterogeneous concepts uniformly." A shared write-side base type would risk *blurring* the Spontaneous/Planned distinction Insights actually wants to preserve (e.g. Rule 11's "missed but later redeemed" labeling), not sharpen it.

**Decision:** Dropped, not deferred as a to-do. The Planner's redemption mechanism (domain/Application built Slices 6–7 2026-07-08; the UI to actually drive it — a "Redemption" toggle on the block-creation form — wasn't built until 2026-08-21, see `DESIGN_GAP_HISTORY.md` Gap 25) remains the only redemption mechanism. This also fits the app's own thesis better than the dropped feature did — NenFocus is built around *deliberate*, ritual-based intentionality; requiring the user to consciously link a specific block to a specific miss in the Planner is more consistent with that than a system silently auto-allocating coverage behind a Main Page nudge. That same standard resurfaced and was reaffirmed while building Gap 25's UI: an early design would have auto-linked a matching block silently, and was rejected for reopening exactly this reasoning.

**If ever revisited:** build the narrow, spontaneous-only entity (last rejected-options bullet above), not a shared block hierarchy, not a `Session` field, not the Day-level shortcut. All three were interrogated and found to either leak, over-build, or fail to deliver real redemption semantics.

**Must be closed before:** Nothing — this is a scope decision, not a blocked obligation.

**Reopened 2026-09-27 — "Spontaneous Redemption Block" (architect's new direction; not yet interrogated).** Raised while designing the Gap 64 follow-up that made only contract-linked blocks count toward a floor. The idea: when an active contract has a deficit, the Main Page shows a **"Cover deficit now"** button, alongside the existing Planner "Cover Deficit" path. Clicking it starts the Ritual: Ten and Zetsu as normal; **Ren** has the deficit's preset pre-selected and locked (like a planned Focus Block); **Hatsu** fixes the duration to the deficit's length (e.g. 1h deficit → 1h), with only the break schedule selectable. In the Planner it shows as a tile labelled **Spontaneous Redemption Block**.

- **Architect's definition (ubiquitous language):** it *is* spontaneous — it starts the moment Start is clicked at Hatsu, not at a pre-scheduled time — and it is a redemption block.
- **Why it doesn't hit the wall the 2026-07-08 design hit:** that design had a Spontaneous session with **no block** to own the redemption link. Here a real redemption Focus Block is created (contract link + `RedemptionEntry`s via the existing `ComputeRedemptionAttributionQuery`), so the existing deficit ledger, redemption rules and "only contract-linked blocks count toward the floor" all apply unchanged.
- **Invariant to keep:** the block and its session must be created **together, only at Hatsu Start** — abandoning the Ritual must leave no record (product invariant), and a half-made redemption block must never become a new *missed* block with its own deficit.
- **Open for the interrogation:** (1) vocabulary collision — today `SessionOrigin.Spontaneous` means "no block exists", but this is spontaneous in *timing* while having a block: a third `SessionOrigin` value, or separate "when it started" from "whether a block exists"; (2) which deficit it covers when several are outstanding (largest? oldest? the user picks?); (3) placement rules (`RedemptionPlacementPolicy`, Work Hours, overlap with an upcoming Focus Block) applied at "now"; (4) what if the deficit changes between clicking the button and Hatsu Start.
- **Depends on:** nothing built yet; compatible with the planned Spontaneous-session Planner tiles (this is a real block, so it gets an ordinary block tile with its own label).
- **First step (noted 2026-09-28):** this is a second writer of the session ↔ `FocusBlock` stamps (`RitualCompletedAt`/`SessionEndedAt`), today paired only by line order in `StartSessionCommandHandler`/`EndSessionCommandHandler`. Move each pair into one Domain operation (e.g. a `PlannedSessionLifecycle` domain service) before adding it, so the two records can never disagree — same note on Gaps 70 and 78. Consider doing it together with the `SessionRun` value object idea noted on Gap 70.

### Gap 73 (E) — Recurring Blocks (interrogated 2026-07-15; not yet built)

**The feature:** A `PlannedBlock` (Focus or Background) that repeats on a schedule — e.g. "9–5 every weekday" — instead of being a single one-off calendar entry. Distinct from Usage Ceiling (a soft ambient cap on access time) and from Nen Contract (a sealed, scored commitment) — this is purely a recurrence mechanism layered onto the existing ordinary block-scheduling flow. Type (Focus vs Background) is decided exactly as it is today: by which `BlockPreset` is picked when the block is created. Recurrence adds no new block type and has no relationship to `NenContract` — it lives entirely on the Planner, the same posture already staked out for this gap before interrogation (see Open Gap A's note distinguishing it from Usage Ceiling).

**Domain shape:**

| Concept | Shape |
|---|---|
| `RecurrenceRule` (value object) | `{ IntervalValue (int), IntervalUnit (Day \| Week \| Month), WeekdayMask (weekday flags, only meaningful when IntervalUnit = Week), EndCondition (Never \| OnDate(DateOnly) \| AfterOccurrences(int)) }`. One shape, not three parallel types — "Every day" and "Specific weekdays" are Planner UI presets that pre-fill this value object (`Every day` = `Unit=Day, Interval=1, Ends=Never`; `Specific weekdays` = `Unit=Week, Interval=1, WeekdayMask=<selection>, Ends=Never`), mirroring the existing Simple/Advanced Contract precedent — one underlying shape, simplified entry points for the common case. Chosen over three separate recurrence types specifically to avoid duplicating "does this fire on date X" logic three times, the same drift risk `DESIGN_GAP_HISTORY.md` Gap 11 and Gap 6 already caught and fixed elsewhere. |
| `RecurringSeries` (entity) | `Id`, `BlockPresetId`, `RecurrenceRule`, time-of-day template (`StartTime`/`EndTime`), `Title?`. Entity, not a value object — independent identity, independent lifecycle (created, edited, truncated, deleted on its own, not nested inside another aggregate) — same justification already used for `FocusBlock`/`BackgroundBlock`/`UsageCeiling`. |
| `PlannedBlock.RecurringSeriesId (Guid?)` | Nullable FK, mirrors `ContractId` exactly. `null` = ordinary one-off block, completely unaffected. Non-null = this row was generated from, and is still linked to, that series. |
| `SkippedOccurrence` (entity, append-only-style fact) | `{ Id, SeriesId, Date, ConflictingBlockId }`. No `Resolved` flag — deliberately avoids the "field only sometimes meaningful" smell already rejected once in Open Gap D. Existence alone means "pending, unresolved"; the row is deleted (not flagged) once the conflict clears and the occurrence is regenerated. No domain events — mirrors `SessionMissedEvent`'s "deliberately silent" precedent; surfaced by a query when the user next opens the app, not by an event handler chain. Belongs to nothing but the fact it records, same family as `BlockedAttempt`/`DailyUsage`/`UsageCeiling`. |

**Materialization — rows are real, not computed lazily:** Unlike Google Calendar (which stores one `RRULE` and expands occurrences lazily, only when a client requests a date range), NenFocus can't defer materialization — `ScheduledEnforcementService`'s heartbeat needs a concrete `PlannedBlock` row in the database to know something should be enforced today, even if nobody has opened the Planner in months. So a `RecurringSeries` materializes real rows ahead of time, on a rolling basis.

**Materialization horizon: 1 year, rolling.** A background heartbeat (mirroring `NenContractHeartbeatService`'s pattern — its own low-frequency `BackgroundService`, not the 5s enforcement loop) keeps each active series materialized 1 year ahead of "now," topping up the window as time passes, plus a cold-start catch-up check at app launch (mirroring the existing dual cold-start-sweep + live-heartbeat pattern already used for Missed Session discovery, since the heartbeat only runs while the app process is alive). The forward-looking row count for any series is constant regardless of whether its `EndCondition` is `Never` or a fixed date years out — only the current rolling window ever exists as real rows.

**Verified performance facts (checked against the live code before setting the horizon, not assumed):**
- `PlannedBlock.Start`/`End` are plain `DateTime`, not `DateTimeOffset` — the SQLite `DateTimeOffset` comparison/`ORDER BY` limitation already documented under `TECHNICAL_SPEC_INFRA.md` → Known Workarounds does **not** apply to this table.
- `PlannedBlocks` currently has **no database index** on `Start`/`End` (confirmed in `NenFocusDbContext.cs`) — every range query is a full table scan today. Not a blocker at any realistic personal-use scale (even a decade of daily-recurrence history is a few thousand rows, trivial for SQLite), but worth indexing `(Start, End)` eventually regardless of this feature — a general debt item, not specific to Recurring Blocks.

**Editing and deletion — three Google-Calendar-style scopes, identical for both operations:**
- **"This event"** — edits or deletes just that one instance. Editing clears its `RecurringSeriesId`, converting it into an ordinary standalone `PlannedBlock`; the rest of the series is untouched.
- **"This and following events"** — splits the series. The original `RecurringSeries` is truncated (its effective end moves to just before the edited/deleted instance's date). A **new** `RecurringSeries` is created starting at that instance, carrying the edited properties forward under the recurrence cadence. Already-materialized future rows from the old series, from that date onward, are replaced with rows generated from the new series.
- **"All events"** — edits the series template directly. Only propagates to instances still linked to that series (`RecurringSeriesId` matches); an instance already detached via "This event" is untouched, same as Google Calendar.

**Conflict handling — two distinct moments, deliberately different mechanics:**
- **At creation time** (user is actively in the Planner): every projected instance across the full 1-year window is validated up front against the existing "no two overlapping Focus Blocks" rule and any other existing block. Any conflicting date is shown to the user immediately, with a per-conflict choice: skip that specific occurrence (create the rest of the series with a gap there) or cancel creation entirely to adjust the pattern. Mirrors the "validate the whole operation before persisting anything" discipline `NenContract.Seal` already follows (`DESIGN_GAP_HISTORY.md` Gap 13).
- **At background top-up time** (a heartbeat running unattended, nobody watching): the conflicting occurrence cannot be created — that would violate the same overlap rule, no matter who's asked — so the skip is forced, not optional. A `SkippedOccurrence` row is written instead of silently discarding the gap. Next time the user opens the app, a query surfaces any pending `SkippedOccurrence` rows as an actionable prompt (not a passive notice): *"[Series] conflicts with [other block] on [date]. [Change it] [Skip]"*. "Change it" navigates to the Planner on that date so the user can resolve the conflicting block themselves — the system never auto-edits or auto-deletes a user's other block on their behalf. "Skip" dismisses and the gap stays.
- **Auto-fill on resolution:** once the conflicting block is cleared (edited, moved, or deleted), the missing occurrence reappears automatically on the next top-up pass — the top-up job must re-scan existing `SkippedOccurrence` rows for conflicts that have since cleared, not just extend the leading edge of the window — and its `SkippedOccurrence` row is deleted once regenerated.

**Enforcement — no new logic needed.** Materialized rows are ordinary `FocusBlock`/`BackgroundBlock` rows; `PolicyEngine`/`ScheduledEnforcementService` consume them completely unchanged. This feature only touches how rows get created and kept topped up, never how they're enforced.

**UI entry point:** a "Repeat" toggle on the existing Planner block-creation form (same tile-based creation flow as Google Calendar) — flipping it on reveals the `RecurrenceRule` picker (Every day / Specific weekdays / Custom, all three pre-filling the one underlying value object). No separate "recurring blocks" screen for v1.

**Must be closed before:** Nothing urgent — deferred until picked up. The domain shape, materialization strategy, editing/deletion scopes, and conflict-handling mechanics are all settled enough to start Slice 1 (domain entities + `RecurrenceRule`) whenever that happens.
**Interaction added 2026-09-28 (Open Gap S):** because a series materializes real `PlannedBlock` rows, contract drafting adopts its occurrences in the contract's range like any other block (keep/remove, removed ones deleted at Seal). To decide when this gap is interrogated: what happens to the **series** when an adopted occurrence is removed or edited in a draft — most likely the occurrence detaches (compare the existing `SkippedOccurrence` concept).

### Gap 75 (J) — System Clock Tampering: Detect and Nudge, Not Block (raised 2026-08-20; parked, not interrogated)

**The gap:** `ScheduledEnforcementService`'s heartbeat, and every consumer of `ISystemClock.UtcNow`, currently trusts the OS wall clock unconditionally. A user could manually set their system clock backward (before a block's `Start`, dropping enforcement entirely) or forward (skipping through a block's remaining time) to bypass a block they set for themselves. No detection or response exists today.

**Explicitly not a timezone concern.** The app is internally UTC-consistent throughout (`SystemClock.UtcNow`, `PlannedBlock.Start`/`End`, etc. — confirmed repeatedly during today's session). A timezone change alone never moves `DateTime.UtcNow`; only a manual date/time change does.

**Threat model, framed deliberately narrow:** NenFocus is a self-discipline tool — the person who might tamper with the clock and the person the app is protecting are the same user. Bulletproof anti-tamper (kernel-level clock hooks, etc.) would be disproportionate for a personal focus tool and was explicitly rejected as the goal. **The architect's own framing, which settles the intended response:** don't block further or otherwise punish — just remind the user not to cheat. A nudge, not an escalation.

**Candidate detection mechanism (sketched, not designed):** compare elapsed wall-clock time (`DateTime.UtcNow` deltas between heartbeat ticks) against elapsed monotonic time (`Environment.TickCount64`/`Stopwatch`, driven by system uptime and unaffected by manual clock changes). A large mismatch — wall clock jumped backward, or forward by far more than the ~5s tick interval could explain — is a strong signal of manual tampering. The open design problem is distinguishing that from two legitimate causes of the same kind of discontinuity: sleep/hibernate (large forward jump, expected — adjacent to Open Gap B's already-tracked territory) and ordinary NTP drift correction (small, should be tolerated, not flagged).

**Must be closed before:** Nothing — parked for later. Not yet interrogated: no decision on where the check lives (`ScheduledEnforcementService` heartbeat is the obvious candidate, already the sole per-tick observer of both `now` and elapsed time), what the nudge actually says, whether it's rate-limited (once per detected event? once per day?), or how sleep/wake and NTP-drift get reliably excluded from triggering a false nudge.

### Gap 76 (K) — Enforcement Has No Life Independent of the GUI Process (surfaced 2026-09-02; interrogated 2026-09-07; not yet built)

**Found while designing the "already-open tab" browser-enforcement fix (see `DESIGN_GAP_HISTORY.md` for that closed gap), not while looking for it.** The question that surfaced this: does killing `NenFocus.exe` (Task Manager / crash) still leave blocking in effect, the way Cold Turkey's separate background service keeps enforcing after its GUI is killed? Verified against the real code, not assumed: **no.**

**Why not, concretely:**
- `WindowsEnforcementService`'s `HttpListener` (the local `http://localhost:5005` API the extension calls for `/check` and `/report`) runs **inside** the main GUI process. Kill that process and the listener dies with it.
- `NenFocusExtension/background.js`'s `onBeforeNavigate` handler (and the `poll.js` content-script check) **fails open** on a fetch error to that endpoint (`background.js` catch block: "If the C# app is closed, this will trigger. We do nothing and let the browser load naturally.") — so once the process is dead, every subsequent navigation and every open tab's periodic check silently waves traffic through.
- The hosts-file entries `ApplyHostsRulesAsync` writes do persist on disk after the process dies (they're static file content, not actively maintained) — so DNS-level blocking nominally survives a kill. But this protection is undermined if the browser's DNS resolution bypasses the hosts file (e.g. Chrome's Secure DNS / DNS-over-HTTPS, on by default in current Chrome) — in that case there is no enforcement left at all once the app is killed.

**Why Cold Turkey doesn't have this problem:** its enforcement runs in a separate, always-on Windows Service independent of its GUI's process lifetime — killing the GUI only kills the front-end. NenFocus has no such split: `WindowsEnforcementService` and its local HTTP API are hosted entirely inside the one process a user (or the user being tempted to self-sabotage) can kill from Task Manager.

**Scope chosen at interrogation: the full architecture split, not the lighter in-process mitigation** that was also on the table (a persisted heartbeat file the extension checks staleness against, without a real second process). The architect's explicit goal — matching Cold Turkey/Freedom's resistance to force-close *and* reboot *and* casual uninstall — ruled out anything that stays inside the GUI process, since none of those three threats can be closed without a genuinely independent process.

**Settled shape (interrogated, not yet built):**

| Concept | Decision |
|---|---|
| Process split | A new `NenFocusService` (Windows Service) hosts `WindowsEnforcementService`, `ScheduledEnforcementService`, and everything that needs admin rights (hosts file, DoH-disable registry keys, process-tree kill). `NenFocus.exe` (GUI) keeps everything else — every existing command/query handler, all ViewModel-driven CRUD, the whole ritual/planner/contract flow, completely untouched. |
| DB/command ownership | The GUI keeps direct database access for all its own commands (none of them need admin rights). The Service is deliberately **restricted to read-only queries** (`ComputeActivePolicySliceQueryHandler`) **plus append-only writes only** (`IBlockedAttemptTracker`/`IUsageTracker`) — it never executes a general aggregate-mutating command. This keeps the GUI as sole authority over every core aggregate (`Session`, `PlannedBlock`, `NenContract`), avoiding two independent write models against the same store. Rationale: `NenFocus.Application`/`NenFocus.Domain` are already process-agnostic class libraries — proven today by the UI and `ScheduledEnforcementService`'s heartbeat both calling the same handlers from different call sites — so a third call site (the Service) hosting the same Application layer isn't a new pattern, as long as its write surface stays narrow. |
| GUI↔Service communication | **None, for policy.** Rejected reusing `IEnforcementService.ApplyPolicyAsync(ActivePolicySlice)` as a cross-process nudge (the GUI-side implementation would have to silently ignore its own parameter — violates the Deep Module test). Rejected a dedicated "recompute now" signal interface too. Instead, the existing immediate-sync calls in the GUI's session/break event handlers (`IEnforcementSynchronizer.SyncAsync`, Gap 62 — the synchronizer itself moves into the Service with the heartbeat) are dropped, and `ScheduledEnforcementService`'s heartbeat interval shortens from 5s to something imperceptible (exact new value, e.g. ~1s, left as an implementation-time tuning call) so the Service's own independent DB poll closes the gap on its own. GUI and Service end up needing **zero direct communication channel** — they talk purely through the shared SQLite database, the same level-triggered pattern this codebase already uses everywhere else (mirrors Gap B's "durable state, not an ephemeral signal" philosophy). The existing `localhost:5005` HTTP API (`/check`, `/report`) is untouched and stays solely for the browser extension's use — the GUI never calls it. |
| SQLite concurrency | Must move to **WAL journal mode** — confirmed via `DependencyInjection.cs` that the DB currently uses the default rollback journal (`UseSqlite($"Data Source={dbPath}")`, no journal mode configured). Once two processes access the same file concurrently, this is a required implementation detail, not an open design choice; plain rollback-journal mode risks "database is locked" errors under concurrent multi-process access. |
| Elevation | The GUI drops `requireAdministrator` entirely. Confirmed via grep that every admin-requiring operation (hosts file writes, `Registry.LocalMachine.CreateSubKey` for DoH-disable, process-tree kill) lives exclusively inside `WindowsEnforcementService` — nothing else in `NenFocus` (UI) or the rest of `NenFocus.Infrastructure` touches anything elevated. Only the Service runs elevated going forward; `NenFocus/app.manifest`'s `requestedExecutionLevel` changes accordingly. |
| Boot behavior | The Service auto-starts at Windows boot (Start type: Automatic) — confirmed **necessary, not just preferred**, given the goal of matching Cold Turkey's resistance to circumvention. Force-closing `NenFocus.exe` is already solved by the process split itself, regardless of boot behavior. What boot behavior actually decides is whether a full **reboot** is an effective bypass: under GUI-controlled start, a reboot leaves the Service stopped until the GUI reopens it, and the person a self-imposed block restrains has every incentive to just never reopen it — the same "user vs. future-self" framing already recorded in Open Gap J. Auto-start closes that loophole. |
| Distribution | A real installer (MSI/WiX), not a self-installing GUI. No installer tooling exists in this repo today (confirmed via file search) — this is new ground for the project. Chosen over the GUI silently registering the service on first run because the architect explicitly ruled out any terminal-facing step for the user: a real installer gets a familiar setup wizard, a Start Menu entry, and a standard Settings > Apps uninstall button for free; a self-install path would need its own custom in-app "remove everything" UI to reach the same terminal-free bar, which is extra work for a worse result. |
| Uninstall/stop resistance | The Service refuses a stop request only while something is actively enforcing (a live Session, or an active Focus/Background block window) — not a permanent, unconditional lock, which would also trap the architect when legitimately wanting to update or remove the app with nothing currently blocking. Validated against real precedent, not invented from scratch: Cold Turkey's "Locked Blocks" and Freedom's "Locked Mode"/"Block Task Manager"/"Block System Settings" toggles both work this way — protection tied to something actively enforcing, not always-on. **Open nuance, flagged but not fully reconciled — now with a concrete direction floated, not yet designed:** both real-world precedents gate this behind an explicit per-session opt-in (the user turns on "Locked Mode" for that specific session); what's decided here is broader — resistance applies whenever *anything* is actively enforcing, with no separate opt-in toggle. Raised while deferring this gap's build (2026-09-07): a possible **Master Locked Mode** setting (Settings page, not per-session) that would gate the broad always-on resistance behind a single deliberate toggle instead of making it unconditional — e.g., whether uninstall is blocked during *any* active enforcement (today's default direction) vs. only during a sealed `NenContract` (mirroring `StrictnessRule.Locked`/`AllowCancellation`) vs. never. Not interrogated — genuinely just an idea in the air, one of the reasons this gap's implementation was deliberately deferred rather than started now (see "Must be closed before" below). |
| Extension removal prevention | The extension is published to the Chrome Web Store as **Unlisted** (installable only via a direct link, never searchable or publicly listed) — a one-time task for the developer, not something individual users ever do. Once published, `ExtensionInstallForcelist`/`ExtensionSettings` policy (the same registry-based mechanism family already used for the existing DNS-over-HTTPS setting) force-installs it and greys out its disable/remove buttons entirely in the browser's own extensions page. **Verified via research, and it materially changed the design:** this only works for Web-Store-published extensions on an ordinary, non-domain-joined home PC — a self-hosted/off-store extension can only be force-installed this way on a domain-joined or MDM-enrolled machine, which rules out staying unpublished. Publishing is the accepted one-time cost (developer account, a review process, keeping the listing's version in sync with future extension updates) in exchange for genuine, low-maintenance prevention. |

**Fail-open vs. fail-closed — resolved as two layered defenses, not a single choice** (the original second half of this gap, revisited now that the architecture split makes it answerable). Mirrors how Freedom stacks "Locked Mode"/"Block Task Manager"/"Block System Settings" simultaneously rather than offering one master switch:
- **Layer 1 (primary, prevention, invisible to the user):** the Web Store force-install above. Stops the casual "click Remove" moment of weakness outright — there's no button that does anything, so there's nothing to react to in the first place.
- **Layer 2 (secondary, reactive backstop):** if the extension still somehow goes missing, or the Service becomes unreachable, and something *was* being actively enforced a moment before, the browser locks down **all** browsing — not just the previously-blocked sites — until the Service is confirmed reachable again. Deliberately scoped as a backstop for what Layer 1 doesn't cover (an unexpected browser update, an unusual Chromium-based browser the policy doesn't target, a brief timing window) rather than the primary mechanism. A short grace period (~10–15 seconds) before Layer 2 triggers avoids punishing an ordinary boot-timing blip or update window. If nothing was being enforced at the moment contact was lost, Layer 2 does nothing at all — browsing continues normally, since there's nothing to protect.
- **Layer 2 gets its own dedicated page, distinct from the normal per-site `blocked.html`.** A plain, non-accusatory message ("NenFocus's background protection isn't responding, so browsing is paused as a precaution. This usually clears up on its own within a few seconds. If it doesn't, try restarting your computer.") rather than assuming deliberate tampering — the extension has no way to know *why* contact was lost, so the message stays honest for both the innocent case (a genuine crash) and the deliberate one. The page polls itself (the same pattern `poll.js` already uses) and lifts automatically once the Service is reachable again — no manual refresh needed. If the GUI happens to still be open, it can also show its own small banner as a secondary nicety — not the essential communication surface, since the app may not be open at all when this happens.
- **Self-healing for the registry policy itself:** the Service periodically re-checks that its force-install registry keys are still present (piggybacking on its existing heartbeat) and rewrites them if missing, so a one-time deletion attempt gets undone within one heartbeat tick rather than permanently succeeding.
- **Honest ceiling, unchanged from the rest of this gap:** someone with enough technical persistence can still find and delete the underlying registry key themselves, since they have admin rights on their own machine. Self-healing narrows that window to a few seconds rather than closing it forever — consistent with Open Gap J's already-established position that bulletproof anti-tamper is out of scope for this app.

**Service versioning across app updates — split into two sub-questions, one resolved, one still open:**
- **Resolved: updates get a narrow, installer-authenticated exemption from stop-resistance.** Taken literally, the stop-resistance rule above would make every update fail whenever a block is active, the same way Cold Turkey's uninstaller fails during a lock — bad for an app that needs to actually ship fixes. The installer (already running elevated to perform the update at all) leaves a marker immediately before asking the Service to stop; `OnStop` allows the stop only when that marker is present, and refuses it otherwise exactly as already decided. **Why this doesn't reopen the loophole it looks like it might:** stopping the Service for a genuine update doesn't actually unblock anything — the new version starts back up and reapplies the exact same policy from the database within seconds, so there is no reward for triggering "update mode" even if someone found a way to fake the marker. The only way this exemption could ever function as a real escape route is by *also* preventing the Service from ever restarting afterward (e.g. corrupting its files post-stop) — a materially higher-effort, multi-step attack, well outside the "moment of weakness" threat this gap is built to stop. This also composes for free with the already-decided Layer 2 grace period: a normal update's brief stop-then-restart sequence, if it completes within that ~10–15 second window, never even triggers the browsing lockdown.
- **Resolved: the installer runs the database migration once, before either process starts** — not the GUI alone (today's behavior) and not both GUI and Service independently. Today, only the GUI runs migrations, once, at its own startup (`Program.cs` → `HostExtensions.EnsureDatabase()`). Once an update ships two independently-startable processes (GUI and Service) built from the same release, there's a real window where the Service could auto-start immediately after an update finishes — before the user has ever opened the GUI — and run its read/append queries against a schema that hasn't been migrated yet, risking a runtime error on anything touching a changed table. This risk didn't exist before this gap; it only arises from having two independently-launchable processes share one schema. **A real alternative was weighed and rejected:** make the Service tolerant of a stale schema instead (skip and retry on the next heartbeat tick until the GUI eventually migrates it) — rejected because it would leave the Service doing nothing at all until the user opens the GUI at least once after every update, quietly reopening the exact gap this whole feature exists to close (enforcement not truly independent of the GUI being opened). **Real cost, accepted rather than hidden:** the installer must trigger the *same* existing `EnsureDatabase()` logic rather than reimplementing migration steps natively in WiX — most likely by briefly running the app or Service in a "migrate only, then exit" mode as an installer custom action. This doesn't replace the GUI's own migration call outright; a direct dev-mode run (not through the installer) still needs it exactly as today. **Not a DDD decision** — migrations are pure Infrastructure-layer plumbing with no domain-model content — but it is consistent with a broader Clean Architecture principle already used repeatedly elsewhere in this document (a single, unambiguous owner for a piece of state rather than shared/ambiguous responsibility — the same reasoning behind `PolicyEngine` being "the sole owner of all merge rules" and the GUI being sole authority over every core aggregate earlier in this gap), just applied to schema lifecycle instead of domain writes.
- Exact WAL-mode migration mechanics, the exact new heartbeat interval value, the exact `OnStop` handler logic for the "is anything enforcing right now" check (now also checking for the update marker), the exact Layer 2 grace-period length, the self-healing registry check's own interval, the Chrome Web Store Unlisted listing setup itself, and the MSI/WiX authoring are all left as implementation-time calls — consistent with how other gaps in this document leave DTO shapes and query-bundling decisions open until Slice 1 begins.

**Relationship to Open Gap B:** adjacent but distinct. Gap B is about recovering *session state* correctly after a clean restart (was a session active when the app died, does enforcement get correctly re-applied). This gap is about enforcement having *no existence at all* between the process dying and the process (if ever) restarting — a different, larger failure mode that Gap B's candidate fixes don't address.

**Must be closed before:** Nothing urgent — deferred until picked up. Interrogation is complete — every question this gap raised has a settled answer (the last two, stop-resistance's update exemption and migration ownership, resolved 2026-09-07 in the same session as everything else above). Only implementation-time calls remain.

**Deliberately not started yet, by explicit architect decision (2026-09-07) — build sequencing, not a design gap of its own:** two reasons, distinct from "the design isn't good enough." First, the design is still visibly moving — the Master Locked Mode idea above surfaced minutes after the rest of this gap was written up, which is a live signal the uninstall/lock rules aren't done evolving, independent of anything else in the app. Second, this gap needs a genuinely different, slower testing loop than the rest of the codebase — actually installing/uninstalling a Windows Service, actually setting registry policy and restarting a browser to observe it, actually publishing to the Chrome Web Store before the force-install behavior can be tested at all — none of which has a fast inner loop the way `NenFocus.Tests`'s unit tests do. Spending that testing effort while the rules underneath are still shifting risks redoing it. **The plan:** keep building other application features in the meantime (Recurring Blocks, Usage Ceiling, Nen Contract enhancements, etc.) — none of them depend on this split existing first, since `NenFocus.Application`/`NenFocus.Domain` stay process-agnostic regardless of who's hosting them. Keep folding new ideas about this gap (like Master Locked Mode) into this write-up as they surface, cheaply, in conversation. Pick this back up once the app's feature surface has stabilized enough that the enforcement/uninstall rules feel settled — that's when the slower testing cycle actually pays for itself instead of getting redone. Ready to start Slice 1 (the new `NenFocusService` project plus `IEnforcementService`'s narrowed Service-side implementation) whenever that point is reached.

### Gap 77 (O) — Cross-Platform Suite: iOS App, Multi-Device Sync, and Desktop-Driven "Hardcore iOS Lockdown" (raised 2026-09-27; parked, not interrogated)

**Why it's here:** captured early so the idea isn't lost, not because it's close. The architect's explicit sequencing: this starts only **after the desktop app is finished**, when the iOS app is begun. **Nothing below is agreed design** — it's a record of an externally-drafted spec the architect brought in (pasted 2026-09-27), kept close to its original wording so the interrogation can start from exactly what was proposed. The architect will run the interrogation personally when the time comes; until then, nothing here should be built on, cited as settled, or used to justify a design choice elsewhere.

**The proposal, as brought in:**

- **Vision — offline-first, cross-platform focus suite.** Daily blocking runs 100% offline on each device (iOS, Android, macOS, Windows) from a local SQLite database plus native OS background APIs. When online, local changes sync to a C# ASP.NET Core Web API so laptop and phone profiles match. All internet-based blocking and network toggling were explicitly removed from the proposal in favor of local, device-level enforcement.
- **Desktop app as administrative console.** A new "Hardcore iOS Lockdown" tab in the NenFocus desktop app. Workflow: user connects iPhone over USB and taps "Trust This Computer" → desktop detects the device via `usbmuxd`/`libimobiledevice` → user is prompted to temporarily turn off Find My (required by the local backup-restore protocol) → "Lock Down Device."
- **Local backup patch sequence (proposed mechanism).** (1) Take a local USB backup of iOS preferences (`idevicebackup2`). (2) Patch the backup in-memory: `IsSupervised = true` inside `CloudConfigurationDetails.plist`. (3) Inject a generated `.mobileconfig` with `allowAppRemoval = false`, `allowScreenTimeModification = false`, `PayloadRemovalDisallowed = true`. (4) Restore the patched preferences. (5) Device reboots into Supervised Mode; user re-enables Find My. Claimed outcome: supervision without erasing apps/photos.
- **iOS app.** Native SwiftUI + Screen Time API (`FamilyControls`, `ManagedSettings`). Local SQLite holds schedules/selections for fully offline enforcement. App shields via `ManagedSettingsStore().shield.applications` using tokens from `FamilyActivityPicker`; domain blocking via `ManagedSettingsStore().webContent.blockedByFilter`. Claimed: a reinstalled blocked app is re-shielded automatically because iOS maps it back to its bundle ID.
- **In-app self-governance.** Ending a session or unlocking restricted apps requires a Master Passcode or waiting out an accountability timer inside the app.
- **Proposed bypass defense matrix:** uninstall NenFocus → blocked (`allowAppRemoval`); disable Screen Time → blocked (`allowScreenTimeModification`); remove config profile → blocked (`PayloadRemovalDisallowed`, removal needs the desktop app); reinstall a restricted app → re-shielded by bundle ID; go offline/airplane mode → irrelevant, all rules local.

**Claims flagged for verification at interrogation — not checked yet, deliberately** (per the usual rule: verify against real docs/runtime before recommending anything):
- Whether non-destructive supervision via a patched backup actually works on current iOS, and whether it's a documented path or an unofficial technique Apple could close in any update. Apple's official supervision paths (Apple Configurator, ADE/DEP) erase the device. If this is unofficial, the whole "Hardcore" tier rests on it.
- Whether shield tokens really survive an uninstall/reinstall of the blocked app (Screen Time tokens are opaque; "maps back to bundle ID" is the proposal's claim, not a verified fact).
- `libimobiledevice` on Windows — dependency on Apple Mobile Device Support / iTunes drivers, and its packaging implications for Gap K's MSI/WiX installer.
- "Runs directly on the iOS kernel" in the original wording is imprecise — `ManagedSettings` shields are enforced by the OS's Screen Time system, not by app code at kernel level. Worth restating accurately before it shapes any design discussion.

**Big questions the interrogation will have to answer (seed list, not exhaustive):**
- **Where the Domain lives across platforms.** Today `PolicyEngine`, `Session`, `NenContract`, etc. are C#. A SwiftUI app can't reuse them directly. Re-implement in Swift (two copies of every merge rule — the exact duplication the Application Handler Forbidden Zone exists to prevent), share via a cross-platform C# layer, or give mobile a deliberately thinner domain?
- **Sync model and conflict resolution.** A server and accounts are an entirely new dependency for an app that is currently fully local. What's the sync unit (presets? blocks? contracts? sessions?), and who wins on conflict — especially for sealed `NenContract`s, whose post-seal immutability rules must hold on every device.
- **Master Passcode vs. the Ritual/Nen Contract philosophy.** A passcode that unlocks everything is a bypass by design. How does it square with Strictness Rules, `AllowCancellation`, and the invariant that sessions end through the defined lifecycle?
- **Threat-model consistency.** Open Gap J settled "nudge, don't punish" for clock tampering; Open Gap K chose Cold Turkey-level resistance with a still-open **Master Locked Mode** idea. An un-deletable, supervised phone is the most escalated position yet. It should be one coherent policy across desktop and mobile — likely the same Master Locked Mode decision.
- **Reversibility.** How does a user get out of supervision cleanly and without data loss if they want to stop using NenFocus? The proposal only covers going in.
- **Scope of platforms.** Android and macOS are named in the vision but have no mechanism described. In scope for this gap, or separate gaps?
- **App Store review risk** for an iOS app whose companion tool silently supervises devices.

**Relationship to other gaps:** depends on Open Gap K's process/installer story (the lockdown tab ships inside the desktop app that K restructures), and would reopen K's Master Locked Mode question. Independent of A, C, E, G in principle, but anything they add to the Domain becomes something mobile must mirror or sync.

### Gap 78 (P) — Break Flexibility (raised 2026-09-27; parked, not interrogated)

**Why it's here:** Gap 63 made a session's breaks a stored `BreakSchedule` (offsets from `StartedAt`) that is the single source of truth, with one rule protecting history: *breaks that have started can never change; only future ones may be added or removed.* Every feature below was named during that interrogation as wanted later. None is designed — each still needs its own Design Gap interrogation — but each was checked to plug into Gap 63's model without reworking it.

**The ideas, and where each plugs in:**
- **End a break early** — the "Resume Early" button Gap 63 removed (its `ResumeFromBreakCommand` no longer existed). Would be a session method that cuts the in-progress break to end *now*: it records what actually happened, like `Complete`'s trim, so it doesn't break the history rule.
- **Skip a break** — remove a future slot from the schedule ("I'll keep working"). Same shape as ending early, one step earlier.
- **Break budget** — e.g. 15 minutes of break for a 2-hour session, taken whenever: "start a break now, 7 minutes" writes a new slot starting now. The budget itself would be a value object chosen at Start alongside the schedule and checked before a slot is added.
- **Extend the session** — `Session.Extend(newEnd)` moves `EndAt`; existing breaks stay valid because they're offsets from the start. Open question: should a preset add more cadence breaks into the extra time?
- **Adjust the schedule at Hatsu before starting** — e.g. after a late planned start, "skip my first break". Happens before Start, so it's just another way of producing the `BreakSchedule` the session receives. What a user may change would be limited by Settings, or by the rules of the contract preset the planned block is tied to.
- **Live Hatsu** — Hatsu updates as time passes: shows the block start and "late", and greys out break presets that no longer fit. ViewModels can't own timers (Forbidden Zone), so it would subscribe to an existing tick service and re-run `GetAvailableBreakTimerPresetsQuery`. Gap 63's "No breaks" fallback (a preset that stopped fitting between Hatsu and Start) stays as the safety net underneath.
- **Focus-only floor counting** — today a session's whole length, breaks included, counts toward a Nen Contract's Daily Floor (a deliberate choice, kept by Gap 63). An option to count only focus time is straightforward now that breaks are stored data: focus time = run length minus break slots.

**Mechanics any mid-session revision will need:** the revision must republish the session (`ISessionStateService.SetActive`) so `ActiveSessionMonitor` rebuilds its schedule (it already does on every `SessionChanged`), and must call `IEnforcementSynchronizer.SyncAsync` plus notify itself if the boundary it creates is at or before the monitor's last-checked time.

**Refactor to consider with the break budget:** a session now holds two break rules decided at Start — its `BreakSchedule` (Gap 63) and `KeepBlockingDuringBreaks` (Gap 64). A budget would be a third. At that point, grouping them into one `BreakPlan` value object on `Session` becomes worth it; today it would only wrap two things without adding a rule (considered and deferred in Gap 64).

**First step if "extend session" moves a planned session's end (noted 2026-09-28):** the session and its `FocusBlock` then both need to agree on the new end — a second writer of the session ↔ block stamps, today paired only by line order in `StartSessionCommandHandler`/`EndSessionCommandHandler`. Move each pair into one Domain operation (e.g. a `PlannedSessionLifecycle` domain service) first — same note on Gaps 70 and 72. Consider doing it together with the `SessionRun` value object idea noted on Gap 70.

**Must be closed before:** Nothing — parked.

### Gap 67 (R) — Contract Membership: Only Committed and Redemption Blocks Count Toward the Floor (interrogated 2026-09-28; plan agreed, not built)

**Why:** a contract's completed hours counted Spontaneous sessions whose preset matched the contract's (`GetNenContractCompletedFocusHoursQueryHandler`), including sessions from *before* the contract was sealed — a fresh contract showed 4.7 completed hours with no block done. **Architect's hard rule:** only blocks committed at Seal and redemption blocks count toward the floor; everything else in the contract's period is Bonus (display only).

**Agreed design:**
- **Membership is a fact recorded at creation**, not derived from dates — it depends on *when* something was created relative to Seal, which can't be reconstructed later. One `ContractId` plus a `ContractRole` value: **`Committed`** (drafted and sealed), **`Redemption`** (created after Seal to cover a deficit), **`Bonus`** (created after Seal inside the period, not a redemption). Rejected: two extra ids ("bonus id" + "floor id") — they'd allow contradictory combinations. Rejected: deciding Bonus by date range (`IsWithinPeriod`) — it can't exclude pre-Seal work.
- **"Counts toward the floor" = role is `Committed` or `Redemption`** — one named domain rule.
- Applies to **Focus and Background** blocks. Background blocks never count toward the floor (Focus hours only), but membership keeps the contract's strictness rules consistent across its whole period.
- **Spontaneous sessions** started while a contract is Active, inside its period, are linked as **Bonus**; their hours show as **Bonus hours** (banner running total, Post-Contract recap). A Planned session belongs wherever its block belongs.
- **Finished before Seal = outside:** blocks and sessions that ended before Seal stay non-members and count toward nothing (fixes the 4.7 h).
- **Dragging:** a **Bonus** block's membership follows the period (dragged out → non-member; a block dragged in → Bonus). **Committed and Redemption blocks can never leave their contract's period.** No block may be created or dragged so that it **crosses** a contract's start or end boundary.
- **Queries:** `GetNenContractCompletedFocusHoursQueryHandler` sums Committed + Redemption only (the Spontaneous part is deleted); `GetNenContractBonusFocusHoursQueryHandler` and the Planner's Bonus badge read the **role**, not the date range, and include Bonus Spontaneous sessions.
- **Migration:** existing `ContractId` → `Redemption` if the block has redemption entries, else `Committed`; everything else non-member. (The architect's local database was wiped 2026-09-28; the rule still has to be correct as permanent code.)
- **Tests:** a matching-preset Spontaneous session no longer counts toward completed hours (the 4.7 h regression); Bonus totals by role, including Bonus sessions; pre-Seal work counts toward nothing; drag rules; boundary crossing refused; migration mapping.

**Still to interrogate:**
1. Naming — `ContractRole` and its three values; and whether `ContractId` should be renamed now that it means "member of", not "committed to".
2. Where the assignment rule lives — likely one domain rule on `NenContract` ("which role does a block/session created at this local instant get, with or without redemption entries?"), asked by `CreatePlannedBlockCommandHandler`, `UpdatePlannedBlockCommandHandler` (drag), `SplitPlannedBlock` and `StartSessionCommandHandler`.
3. Session link shape — `Session.ContractId` alone (a Spontaneous session can only ever be Bonus) or `ContractId` + role for symmetry.
4. **Breaking a contract** — `Break` shrinks `EndDate`. Do Bonus blocks after the new end drop out (consistent with "Bonus follows the period")? Confirm Committed blocks after it are already handled by the existing Break rules.
5. **Strictness vs Bonus blocks** — do a contract's edit rules (Lockdown, Daily Flex, …) also govern Bonus blocks, or only Committed/Redemption ones?
6. How the Planner visually distinguishes Committed / Redemption / Bonus tiles (today only Bonus has a badge).

### Gap 68 (S) — Drafting Adopts the Calendar; Seal Guards (interrogated 2026-09-28, revised the same day; plan agreed, not built; depends on Gap 67)

**Agreed design:**
- **Adoption:** entering contract drafting pulls every *not-yet-finished* block (Focus and Background) already in the contract's range into the draft, next to newly drafted blocks. The user keeps or removes each. Kept → **Committed** at Seal. Removed → **deleted at Seal** (shown as "will be deleted at Seal" in the draft; cancelling the draft deletes nothing). Nothing is included or cast aside automatically. This also covers future recurring blocks (Open Gap E), which are real blocks.
- **Adopted tiles are theoretical while drafting (revision, 2026-09-28):** an adopted block that hasn't started yet does **not** activate while drafting — no enforcement, no Ritual — exactly like a newly drafted tile. Not a new loophole: such a block is outside any contract, so it can already be deleted in one click (`DeletePlannedBlockValidator` only protects contract blocks and a running session's block). Blocks already running when drafting begins stay live (the guards below). At Seal, a tile whose start has passed is refused: "This block starts in the past — move it forward" (the same rule as Gap 65's start guard). On cancel the blocks return unchanged; one whose start passed during drafting activates late under the normal rules, and one that ended during drafting is swept as Missed. Mechanism: the draft is only in the Planner's memory today, but the heartbeat must now know which real blocks are held back — a small **in-memory** Application service, never persisted (a crash mid-draft brings the blocks back, the safe default).
- **Finished blocks** in the range are not offered in the draft (they're history — Gap R).
- **Boundary rule at Seal:** an existing block that **crosses** the contract's start or end → Seal refused until the user moves, shortens or removes it in the draft (no automatic split for future blocks — the user decides).
- **Background block running at the Seal moment and kept:** **split at the Seal moment** — the part before Seal stays the original block, outside the contract (history); the rest becomes a new **Committed** block. Enforcement continues seamlessly (same preset, back to back). Builds on the existing `SplitPlannedBlock` use case.
- **"Focus time in progress" guard** — Seal refused in all three cases: a planned session running; a Spontaneous session running; an active Focus block awaiting its (late) Ritual. Checked when the user clicks **"Make Nen Contract"** (so they know before drafting) **and again at Seal** (drafting takes time; a block may start meanwhile). One named rule shared by both checks.
- **Editing a Scheduled contract** re-drafts, so adoption, removal and all guards apply again.

**Still to interrogate:**
1. Draft UI for adopted vs newly drafted tiles, and for the "crosses the boundary" error state.
2. Should an adopted block that violates the contract's Work Hours be treated like a boundary crossing (must be resolved before Seal)?
3. The split Background block: tell the user at Seal ("your running X block was split at 11:00")?
4. Exact wording of the guard messages.
5. Does a kept adopted block need any validation the draft already applies to newly drafted blocks (preset type, overlap, floor check)?

### Gap 88 — One Source for Time Slots and Block Placement (raised 2026-09-28 in the area-1 audit; interrogated 2026-09-29, plan saved; interface awaiting approval; not being built yet)

**The problem:** three rules about time are each copied into up to four places, including the UI:
1. **What does a block occupy?** Scheduled time (`Start`–`End`), real time (`Start`–`EffectiveEnd`) or display time (trimmed at both ends) — different callers use different ones.
2. **May Focus time go here?** No Focus over Focus; Background may overlap anything; a running spontaneous session also occupies time.
3. **Does it fit the contract's window?** `NenContract.AllowsBlockPlacement` → `ContractDay.Contains` (the real rule).

**Where they live today:**

| # | Where | Rule | Problem |
|---|---|---|---|
| 1 | `PlannedBlockRepository.GetOverlappingAsync` (create/move/split/seal) | 1, 2 | Focus-only is a `ritualOnly` flag each caller must pass to the repository |
| 2 | `CreatePlannedBlockCommandHandler` / `UpdatePlannedBlockCommandHandler` | 2 (running session) | Same overlap formula written twice; split and seal don't check the session at all |
| 3 | `StartSessionCommandHandler` | 1, 2 | Own inline check |
| 4 | `GetSuggestedRedemptionPlacementsQueryHandler` (Cover Deficit) | 1, 2 | Scheduled time, cancelled blocks counted as taken, running session ignored — suggestions disagree with create (the freed tail of an early end, cancelled blocks) and can land on a running session |
| 5 | `PlannedBlock.OverlapsWith` (seal: new blocks vs each other) | 1 | Correct (scheduled time for brand-new blocks); should share the formula |
| 6 | `PlannerDragMath.WouldCollide` (drag drop, form save) | 1, 2 | UI math on display times, ignores the running session, calls `ToUniversalTime()` directly |
| 7 | `PlannerPageViewModel.FindSplitOverlap` (Split form warning) | 1, 2 | ViewModel math on display times, counts Background blocks as conflicts |
| 8 | `NenContract.AllowsBlockPlacement` | 3 | ✅ the real rule |
| 9 | `PlannerPageViewModel.FindSplitWorkHoursViolation` | 3 | A ViewModel "mirror" of #8 |
| 10 | `PlannerPageViewModel.ValidateDraftPlacement` (drafting) | 3 + past + date range | Re-implements #8 — no contract exists yet while drafting |
| 11 | `SplitPlannedBlockValidator:120`, `UpdatePlannedBlockValidator:61` | "has it started?" | Written two ways; no `PlannedBlock.HasStarted` (area-1 finding D) |
| 12 | `CreditedWindow`, `WindowOn`, `PlannedFocusHoursCalculator`, `DayRangeSplitter`, several queries | — | `(DateTime Start, DateTime End)` tuples: values that travel together |

**Agreed design (interrogated 2026-09-29, by `MODULE_STANDARDS.md` → Where a Rule Lives):**
- **`TimeSlot`** (value object) — always real instants (UTC). `Overlaps`, `Contains`, `Length`, `HasStarted(asOf)`, `HasEnded(asOf)`, `StartsIn(asOf)`, `Covering(start, minutes)` (static; see below), `SplitByDay(TimeZoneInfo zone)` (replaces `DayRangeSplitter`: cuts at local midnight; each segment carries its local date, local start/end for Work Hours, and real length). **Half-open `[Start, End)` is the one boundary convention**, written only here: at exactly `End` the slot has ended and the next may start. Callers never compare `Start`/`End` themselves again.
- **`PlannedBlock.Scheduled` / `ReservedSlot(asOf)`** (entity) — named as Gap 90 will need them (`Scheduled` computed from `Start`/`End` here, stored there; factories unchanged). `IsActive`, `HasEnded`, `OverlapsWith` and `MarkersPassedBetween` are rebuilt on these slots in phase 1's first commit, full suite green before anything else switches — so no Domain question about a block's time compares raw fields. Same commit: `FocusBlock.EffectiveEnd`'s missed check (`asOf >= End`, `FocusBlock.cs:120`) and `Classify`'s Missed (`asOf >= scheduledEnd`, `FocusBlockOutcomeClassifier.cs:49`) ask `Scheduled.HasEnded(asOf)`; `IsUnresolved` already asks `HasEnded`, so its SQL mirror (`GetUnresolvedFocusBlocksAsync`) moves from `End < asOf` to `End <= asOf` — the existing parity test catches it if not. (`EffectiveEnd`'s own cancellation arithmetic computes an end, it isn't a question — it stays.) The plan vs what it really occupies (`EffectiveEnd`: early end, missed, cancelled); `ReservedSlot` null when it occupies nothing. **`HasStarted(asOf)`** next to `HasEnded`; `HasEnded` moves from `End < asOf` to `End <= asOf`. **`Session`'s slot** (`StartedAt`–`EndAt`) for every active session — a running planned session duplicates its block's slot harmlessly, so no "which kind of session" case.
- **`BlockPlacementChecker`** (the one domain service — needs blocks, sessions and a contract, owned by none):
  - `Check(slot, type, contract?, blocks, sessions, asOf, zone) → PlacementVerdict` — not in the past → inside the contract's window (`NenContract.AllowsBlockPlacement` — same rule; takes `(slot, zone)` from phase 1b) → free for Focus. `Allowed` or the **first** failure (`PlacementOutcome` + the conflicting slot when `TimeTaken`). Background skips only the "free" step; every other step applies to both types.
  - `CheckFree(slot, blocks, sessions, asOf) → PlacementVerdict` — just "is it free" (Focus blocks' `ReservedSlot`s + active sessions' slots). Replaces the draft's `FocusTimeRules`.
- **`GetBlockPlacementVerdictQuery`** (application) — fetches only: blocks around the slot, active sessions, and the contract that applies, resolved one way for every caller (including redemption attribution via `ComputeRedemptionAttributionQuery`); hands them to `BlockPlacementChecker.Check`. No rules. The repository only fetches; `ritualOnly` goes.
- **Callers:**
  - Create / Update / Split validators and the Planner drop ask `GetBlockPlacementVerdictQuery` (Split once per half) — preview and save run the same code. Split's own rules (same days as the original, halves add up, halves don't overlap each other) stay in its validator, but ask `TimeSlot` (`Length`, `Overlaps`) — today the halves-vs-each-other check is a raw formula (`SplitPlannedBlockValidator:143`), switched in phase 1. Split's halves now also get the "not in the past" check (today only the original is checked) — a small new rejection, pinned by a test.
  - Seal / Edit contract call `BlockPlacementChecker.Check` directly with the in-memory contract; `CheckFocusBlockBatchOverlapQuery` (the calendar check they use today, via `ritualOnly`) is replaced by `CheckFree` and deleted. New blocks vs each other (`ContractBlockBatchPreparer`) use `TimeSlot.Overlaps` on scheduled slots.
  - Start Session calls `BlockPlacementChecker.CheckFree`.
  - **Cover Deficit has no search (decided 2026-09-29).** The suggestion only pre-fills the block form (`PlannerPageViewModel.OpenRedemptionCreateFormAsync`), so it starts at the next quarter hour from now, length = the needed minutes rounded up (`TimeSlot.Covering`, keeping Gap 33's guarantee) — regardless of what is already there. The user places it; Save (Create → `BlockPlacementChecker.Check`) says if it overlaps or falls outside the contract. The search (shift earlier, skip conflicts, partial fallback) and `CanFullyCover` (unused by the UI) are deleted. `BlockPlacementChecker` stays pure — rules only (`Check`, `CheckFree`), no suggestion strategy; if a smarter suggestion is ever wanted, it is its own domain service that asks `CheckFree`, never a method on `BlockPlacementChecker` (it changes for UX reasons, not rule reasons). A ghost-tile placement for Cover Deficit was discussed and parked — not raised as a gap yet.
- **UI** — a query **per drop only** (as today), no cached slots, through `IQueryDispatcher` (slice folder `Queries/GetBlockPlacementVerdict/`). `WouldCollide`, `FindSplitOverlap`, `FindSplitWorkHoursViolation` deleted (ViewModel Forbidden Zone).

**Interface (proposed 2026-09-29, awaiting approval):**
```csharp
// Domain/Services/IBlockPlacementChecker.cs
public interface IBlockPlacementChecker
{
    // In order, first failure wins: slot.HasStarted(asOf) → InThePast;
    // contract?.AllowsBlockPlacement(slot, zone) false → OutsideContractHours;
    // Focus only: CheckFree. blocks/sessions = the calendar as it will be.
    PlacementVerdict Check(TimeSlot slot, BlockPresetType type, NenContract? contract,
        IEnumerable<PlannedBlock> blocks, IEnumerable<Session> sessions, DateTime asOf, TimeZoneInfo zone);

    // Allowed, or TimeTaken with the first Focus time in the way: a FocusBlock's
    // ReservedSlot(asOf) or an active Session's ReservedSlot. Background blocks never clash.
    PlacementVerdict CheckFree(TimeSlot slot,
        IEnumerable<PlannedBlock> blocks, IEnumerable<Session> sessions, DateTime asOf);
}
```
- **`PlacementVerdict`** (`ValueObjects/`) — `Outcome` + `TimeSlot? Conflict`; constructor rule: `Conflict` is set exactly when the outcome is `TimeTaken`; `static Allowed`. One result for both methods — no separate conflict type.
- **`PlacementOutcome`** (`Enums/`, agreed 2026-09-29) — `Allowed`, `InThePast`, `OutsideContractHours`, `TimeTaken`. Block-vs-session was dropped as a distinction: both mean "pick another time", a running planned session and its own block occupy the same time (so which one got reported would be arbitrary), and the conflict slot's end still gives "plan after 15:00". Start Session's two messages ("starts in N minutes" vs "active now — complete the Ritual") come from `conflict.StartsIn(now)`, not the kind.
- **`TimeSlot.HasStarted(asOf)`** (`Start <= asOf`) — the one "past" rule: `Check`'s first step and `PlannedBlock.HasStarted` (phase 0's lock) both ask it. **`TimeSlot.StartsIn(asOf)`** → `TimeSpan`, for Start Session's "a block starts in N minutes"; replaces `PlannedBlock.MinutesUntilStart`.
- **`Session.ReservedSlot`** — `StartedAt`–`EndAt` while `Active`, else null; no `asOf` (depends only on state, unlike a block's `EffectiveEnd`).
- Parameters in the `IPolicyEngine.ComputeSlice` style (raw entities, `asOf` passed in). A parameter object (blocks + sessions + contract + clock) was considered and rejected: a type with no rule of its own. Registered `AddScoped` in the Application `DependencyInjection.cs` beside `IPolicyEngine`.

**Contract resolution rule the query must keep (checked 2026-09-29):** a *new* block (Create) may pick up a contract through a deficit (`ComputeRedemptionAttributionQuery` with `ContractId` null searches); an *existing* block (Update/Split) always keeps its own — attribution is scoped to its stored `ContractId`, which the query echoes back unchanged, and nothing re-parents a block on edit. So today's validators are consistent (a suspected Update mismatch was checked and ruled out); `GetBlockPlacementVerdictQuery` must resolve the same way: candidate is new → attribution search; candidate replaces an existing block → that block's `ContractId`. So the *query's* input is richer than the checker's candidate: slot, type, preset id (attribution needs it) and the id of the block being moved/split, if any — used only to fetch (leave it out of the calendar, read its contract), never passed to the checker. **The query checks the capped slot:** Create/Update shorten a redemption block to what it covers (`FocusBlock.CapEndToRedemptionCoverage`) *before* their overlap check today — deliberately, so a long drawn block whose capped length fits isn't rejected for a clash in the part that gets cut off (`UpdatePlannedBlockCommandHandler:53-55`). Moving the check into validators would check the uncapped slot and regress that. **Decided 2026-09-29: attribution returns the final slot.** `ComputeRedemptionAttributionQuery`'s result grows to `{ ContractId, Entries, Slot, WasCapped }` — it calls `FocusBlock.CapEndToRedemptionCoverage` once (the rule stays on `FocusBlock`); `GetBlockPlacementVerdictQuery` checks `attribution.Slot` for all three steps and knows nothing about capping (one job: fetch, ask, word); Create and Update handlers use `attribution.Slot`/`WasCapped` instead of each capping themselves (two copies deleted). Removes today's small inconsistency too (the contract-hours validator checks the uncapped end, the overlap check the capped one). Rounding rule to check when moving it: `CapEndToRedemptionCoverage` does `start.AddMinutes(entries.Sum(e => e.MinutesCovered))` — a `double` from `Sum(...)` into a persisted timestamp, the exact smell `MODULE_STANDARDS.md` names. Deficits have been whole minutes since Gap 44/45, so it is probably safe today, but nothing enforces it. **Decided 2026-09-29 (phase 3, when the call moves):** failing test first (fractional `MinutesCovered` in → whole-minute end out, never past the requested end), then the fix via `TimeSlot.Covering` (below).
- **`TimeSlot.Covering(start, minutes)`** — the shortest whole-minute slot from `start` that covers at least `minutes` (`Math.Ceiling` inside). Two callers need this exact fact: Cover Deficit's suggestion (phase 2; today `Math.Ceiling` + `AddMinutes` inline in the handler, the Gap 33 fix) and `CapEndToRedemptionCoverage` (phase 3) — so by the Forbidden Zone's second-caller rule it gets a name, in the Domain, instead of two inline copies. `CapEndToRedemptionCoverage` then returns `min(requested end, Covering(start, covered).End)` — the clamp matters: rounding up alone could push the end past what the user asked for (asked 30.5 min, covers 30.2 → 31 min). Rejected: capping inside `FocusBlock.Create` — changes when "your block was shortened" is told, and validators run before any block exists, so they'd still need the final slot from somewhere.

### Gap 93 — One Source for Block Change Permissions (raised 2026-09-29 from a one-source investigation; findings recorded, not interrogated)

**The question:** "may this block be changed (moved, resized, preset changed, split) or deleted?" — the sibling of Gap 88's "may a block go here". Asked by every edit path and by the Planner before it shows a button or starts a drag.

**Where it is answered today:**

| Where | Decides |
|---|---|
| `UpdatePlannedBlockValidator` | not ended; preset fixed under an in-effect contract; `NenContract.AllowsBlockTimeChange` (the one Domain home); floor protection, branching on `StrictnessRule` |
| `SplitPlannedBlockValidator` | Focus only; contract blocks only; not Lockdown; not cancelled; future only; no session yet; floor protection, branching on `StrictnessRule` again |
| `DeletePlannedBlockValidator` | never a contract block (any status); not the active session's block |
| `PlannerPageViewModel` | `CanDeleteFromForm`, `IsBlockLocked`/`CanSaveBlock`, `CanChangePreset`, `CanSplitBlock`, `CanDeleteSnapshotBlock`, `IsTileFullyLocked`, `IsTileStartLocked` |

**Disagreements found (checked in code 2026-09-29):**
1. **Live bug:** `CanSplitBlock` (`PlannerPageViewModel.cs:709`) requires a Daily Flex contract; `SplitPlannedBlockValidator` only rejects Lockdown, so it also accepts Period Study — the Split button is hidden for a split that would succeed. The comment claims it "mirrors … exactly".
2. `CanDeleteFromForm` (`:673`, also claims "exactly"): hides Delete for an ended ordinary block the validator allows (the snapshot view's `CanDeleteSnapshotBlock` allows it); checks "in-effect contract" where the validator refuses *any* contract block — the button can show for a delete that will be rejected.
3. Drag lock (`IsTileFullyLocked`, includes ended) vs form lock (`IsBlockLocked`, doesn't) — an ended missed block can't be dragged but its form shows Save, which the validator then rejects. *(Fixed by Gap 88 phase 0 — both become `HasStarted`.)*
4. `UpdatePlannedBlockValidator:30-32` claims to mirror a Delete "ended" guard that doesn't exist. *(Rewritten in Gap 88 phase 0.)*
5. Update applies contract rules only while `IsInEffect`; Split checks `StrictnessRule` regardless of status — consistent today only because Split also requires a future block.
6. Floor protection — *which strictness needs which protection, over which days* — is a contract rule decided in two Application validators (Forbidden Zone), with different day coverage: Update (Period Study, no period floor) checks the original and new start day; Split checks every touched day. Update may miss a cross-midnight move's end day — suspected, not yet confirmed by a test.

**What Gap 88 phase 0 already removes:** every "has it started / is it running / did it complete / has it ended" variant collapses into `PlannedBlock.HasStarted` (see Gap 88). Left for this gap: findings 1, 2 (contract-status part), 5, 6.
