## Nen Contract *(Domain, Application, Infrastructure, and UI all built and landed 2026-07-08–2026-08-19 — see `TECHNICAL_SPEC_INFRA.md` → Done for the full slice history. Contract Preset management UI is the one still-open piece — see below)*

**Definition:** A sealed, time-bound commitment the user makes to a schedule of Focus Blocks and Background Blocks over a contiguous date range, with self-imposed rules governing how much the schedule can be changed during the commitment period. The name is inspired by the concept of binding agreements — the user is making a contract with themselves.

**Two creation paths in the Planner wizard:**

1. **Simple Contract** — Pick from one of three named presets, schedule blocks, seal. No tuning knobs. The floor is automatically set to whatever Focus hours the user planned per day — each day's floor = that day's total scheduled Focus hours. Rest days are automatically derived (days with zero planned hours have a floor of zero). User cannot adjust strictness, work hours, or allow-cancellation individually. The three simple presets are:

| Preset | Strictness Rule | Allow Cancellation | Mental Model |
|---|---|---|---|
| **Lockdown** | `Locked` | Yes *(interim — see note below)* | "This schedule is law. I will not touch it." |
| **Daily Flex** | `DailyFlexibility` | Yes | "I can shuffle blocks around within each day." |
| **Period Study** | `PeriodTimeBudget` | Yes | "Hours can move across days, but the total must balance." |

2. **Advanced Contract** *(narrowed 2026-08-21 — see `DESIGN_GAP_HISTORY.md` Gap 27)* — no longer freeform rule entry. The user picks a saved **Contract Preset** (strictness rule, daily floor, work hours, allow-cancellation — authored and edited on the Presets page's "Contract Presets" tab, never in the wizard) and its rules apply exactly as saved, shown read-only for confirmation; there is no on-the-spot tweaking. Rest days and (future) change window remain wizard-only regardless of mode — both are date-bound to this specific contract's range, never preset material. If the user has no saved Contract Presets yet, the wizard shows an empty-state message pointing to the Presets page instead of an empty picker. Advanced is still the only path that can carry Work Hours.

**`AllowCancellation` is not enforced anywhere right now — interim, not the intended final behavior (2026-08-18, widened same day).** First pass only changed Lockdown's Simple-preset default to `true` (so newly-sealed Lockdown contracts would be cancellable), but any contract already sealed before that change — or any Advanced contract someone deliberately built with cancellation off — was still hard-blocked by `NenContract.Break()`, `BreakNenContractValidator`, and the Planner's Cancel button, all three of which checked `AllowCancellation` directly. Since the app is still in active development/testing, that meant a developer's own test contracts could get stuck un-cancellable. Confirmed with the architect: the *real* intended gate for "you can't cancel this" is a future global **Strict Mode** Settings toggle (already referenced as unbuilt in `TECHNICAL_SPEC_INFRA.md`'s Settings Page row, and in this file's own Session section re: ending early) — not this per-contract flag. So all three enforcement points were relaxed, not just the Lockdown default: `NenContract.Break()` no longer throws on `AllowCancellation == false`, `BreakNenContractValidator` dropped the matching rule, and `PlannerPageViewModel.CanCancelActiveContract` now just checks `HasActiveContract`. `AllowCancellation` itself is **not removed** — still stored on `NenContract`, still user-configurable in Advanced, still defaults per-preset — it's just not read as a gate anywhere until Strict Mode exists to become the real one. Revisit every one of these three spots (search for "interim" comments referencing this note) when Strict Mode is built.

**Contract Presets *(Domain/Application/Infrastructure built 2026-07-08; Presets-page authoring UI built 2026-08-21, superseding wizard-side creation — see `DESIGN_GAP_HISTORY.md` Gap 27)*:** A saved, reusable template of Nen Contract configuration *rules only* — `Name`, `StrictnessRule`, an optional `DailyFloor?` value (nullable since 2026-08-19 — a preset can represent "no fixed floor" the same way a contract can; see the Daily Floor entry below), a single optional `WorkHours?` value, `AllowCancellation`. `ContractPreset` is a full Domain `AggregateRoot` (`Entities/ContractPreset.cs`), consistent with every other persisted concept in this codebase. Rest days, work-hours per-day exceptions, and the date range are deliberately **not** part of a preset: all three are date-bound and can't generalize across the arbitrary future date range a preset gets applied to — they're always supplied fresh in the wizard when the user seals, regardless of which preset (if any) is picked. Applied as-is when picked in the wizard's Advanced mode — the resulting `NenContract` stores its own independent copy of every rule, not a live reference back to the preset, and there is no further tweaking once picked (unlike the old "start from preset, then edit" flow this replaced). `NenContract.ContractPresetId (Guid?)` records which preset (if any) a contract was sealed from, purely so preset deletion can check for a live commitment — see the deletion-guard row below. **Authoring and management: Presets page → "Contract Presets" tab (`ContractPresetPageViewModel`) — built.** Full CRUD (create, edit, delete, list) lives there exclusively now; the wizard's old "Save as preset" checkbox (`ContractRulesStepViewModel.SaveAsPreset`/`PresetNameToSave`) is deleted, along with `ContractReviewStepViewModel`'s `CreateContractPresetCommand` dispatch — a contract preset can no longer be created or edited mid-wizard, only picked.

**Simple vs Advanced — which contract fields are user-configured vs. derived:**

*(Table updated 2026-08-21 — Advanced's rule fields no longer come from direct entry in the wizard; they come from whichever Contract Preset is picked, applied as-is. "Fixed by preset" in the Advanced column below means the **Contract Preset** picked in the wizard, not one of the three hardcoded Simple options.)*

| Field | Simple | Advanced |
|---|---|---|
| Strictness Rule | Fixed by Simple option | Fixed by picked Contract Preset |
| Daily Floor | Derived: per-day = planned Focus hours for that day | Fixed by picked Contract Preset — a fixed whole-hour floor if the preset has one set, otherwise the same per-day-derived floor as Simple. Capped at the preset's own Work Hours window's span if both are set (enforced by `CreateContractPresetValidator`, at preset-authoring time, not in the wizard). |
| Work Hours | None (no constraint) | Fixed by picked Contract Preset (optional on the preset) |
| Rest Days | Derived: days with 0 planned hours | User explicitly designates — still wizard-only, date-bound to this contract's range, unaffected by which preset is picked |
| Allow Cancellation | Fixed by Simple option | Fixed by picked Contract Preset |
| Change Window | None | Parked for v1 |

**Aggregate boundary:** `NenContract` is its own aggregate root. It does **not** own `PlannedBlock`s — blocks remain their own aggregate and legally exist outside any contract (uncommitted weeks). The link is a nullable `ContractId` on `PlannedBlock`: `null` means an ordinary, uncommitted block; set means the block is under that contract. Blocks predate contracts, are mutated directly by the existing drag/create/update paths, and the Daily Floor is a **soft, tracked** invariant after seal (flagged and scored as a miss, not hard-blocked) — there is no need for atomic multi-block invariants enforced inside the contract entity. Enforcement of Strictness Rules and Work Hours constraints is applied later by Application-layer guards that load the contract and inspect blocks separately; the domain only provides the rules and pure calculations.

**Scope:** A Nen Contract covers a single contiguous date range (`StartDate`–`EndDate`, inclusive on both ends, `DateOnly`). Contiguity is structural — a single continuous range has no gaps by construction, so no separate contiguity check exists beyond `StartDate <= EndDate`.

**No two in-effect contracts may share any day (enforced 2026-08-11):** Since both endpoints are inclusive, two contracts sharing even one boundary day (A ends the day B starts) count as overlapping — no shared days are allowed at all. Checked against every currently in-effect (Scheduled or Active) contract via `CheckNenContractDateRangeOverlapQuery`, enforced for real at Seal time by `SealNenContractValidator` and previewed live in the Contract Wizard's Basics step (UX convenience, not itself a guard). Before this, nothing prevented sealing two overlapping contracts.

**Seal:** The act of finalising a contract. There is no persisted draft state in the domain — a `NenContract` comes into existence only via `NenContract.Seal(...)`, its sole factory method. Seal hard-validates a caller-supplied `DailyFloorPolicy` against a caller-supplied per-day map of **Focus hours only** (Background block hours are never counted toward the floor — Focus-only by design). For every day in `[StartDate, EndDate]`, the policy resolves that day's floor (`DailyFloorPolicy.For(date)`); a day whose resolved floor is `null` is a rest day — **skipped entirely**, not checked against zero. A day with a resolved floor must have planned hours (from the map, defaulting to `0` if absent) that satisfy it, or Seal throws. **In Simple contracts**, the policy has no `Default` — every planned day is given its own explicit floor equal to that day's planned hours (so the check always passes by construction), and any day the caller omits from `PerDayExceptions` is a true rest day. **In Advanced contracts**, the policy typically has a fixed `Default` (e.g. "3 hours every day") applied to every day, with explicit `PerDayExceptions[date] = null` entries for user-designated rest days. On seal, `Status` becomes `Active` if the caller-supplied `sealedAt` is on or after `StartDate`, otherwise `Scheduled` — the domain never reads the clock itself; `sealedAt` is passed in, exactly like `Session.Start(DateTime startedAt)`. Raises `NenContractSealedEvent`.

**Lifecycle:**

```
Scheduled ──► Active ──► Completed
   │            │
   │            └──► Broken
   │                 ▲
   └─────────────────┘
   (Break: Scheduled or Active → Broken)
```

Transitions:
- `Scheduled → Active`: `Activate(DateTime)` — called by heartbeat when `StartDate` arrives.
- `Active → Completed`: `Complete(DateTime)` — called by heartbeat when `EndDate` passes.
- `Scheduled | Active → Broken`: `Break(DateTime)` — user cancels; only valid while `IsInEffect` (widened 2026-08-11 from Active-only, so a not-yet-started contract can be cancelled before Day 1 — see `DESIGN_GAP_HISTORY.md`) and only if `AllowCancellation` was `true` at seal. Raises `NenContractBrokenEvent`. `BreakNenContractCommandHandler` atomically breaks the contract and deletes every one of its linked blocks that hasn't ended yet (`!PlannedBlock.HasEnded(now)`) — one command, one transaction, no choice prompt (decided 2026-07-07, superseding the earlier delete-or-unlink design; see `DESIGN_GAP_HISTORY.md`). Past blocks stay linked for historical accuracy. The domain does not touch blocks — they are a separate aggregate; the handler mutates them via `IPlannedBlockRepository` directly. **UI-reachable:** a "Cancel" button on the Nen Contract popover's Active card, behind a confirmation dialog. **Relocated off the Planner's week banner entirely (2026-09-06, see `DESIGN_GAP_HISTORY.md` Gap 55)** — the banner's own "✕" was removed once the banner started reflecting a per-week *switchable* contract selection (see the Rest Days vs. the Planner's live badge entry below); Cancel now lives only in the popover's Active card, which always names the one true `NenContractStatus.Active` contract app-wide, independent of the Planner's current week or switch state. `AllowCancellation` is not currently checked at this call site (interim, 2026-08-18 — mirrors `NenContract.Break`'s own comment: every in-effect contract can be cancelled until a future Strict Mode setting exists as the real gate).

**No mid-contract extension.** A previously-built `Extend` operation (pushed `EndDate` forward on an Active contract) was removed by deliberate architect decision (2026-09-04) — it went against the product's own philosophy: a sealed contract is the commitment you made; wanting more means sealing a new one, not reopening the old one. `NenContractExtendedEvent` was deleted along with it.

**Strictness Rule (locked at seal, user-configurable):** Modelled as a single enum, not a value-object hierarchy — the three rules are points on one axis of post-seal mutability, and the logic that *interprets* a rule against an edit's context lives in Application-layer guards, not inside the rule itself. The strictness rule is immutable after seal (no mid-contract changes in v1; a future v2 feature may allow tightening only, never loosening — parked). *(Collapsed from four rules to three — see `DESIGN_GAP_HISTORY.md` for the closure record: the former `DailyTimeBudget` value was deleted because it was already 100% behaviorally identical to `DailyFlexibility` in shipped code; its "total time conserved" intent was folded into `DailyFlexibility`'s definition below instead.)*
- **Locked:** No changes allowed during the contract period. Blocks cannot be moved, removed, or shortened. New blocks can still be added.
- **DailyFlexibility:** Within each day, the user can rearrange blocks — move, resize, swap when things happen — but the total scheduled block time for that day must never drop below that day's own resolved Daily Floor; only for the current or upcoming day. **Built 2026-08-19, resolved as floor-protection rather than exact conservation** — see `DESIGN_GAP_HISTORY.md` Gap 18 for the full reasoning. `UpdatePlannedBlockValidator` re-checks the edited day's total (via `ComputePlannedFocusHoursQuery`) against `NenContract.IsDayMet(date, newTotal)` whenever a Focus block under a `DailyFlexibility` contract shrinks — the same domain rule Day-Met scoring already uses, not a re-derived comparison. A pure same-duration move never changes a day's total, so this only ever bites an actual shrink; shrinking one block while growing another on the same day still works as long as each individual edit's resulting total holds (grow-then-shrink always succeeds; shrink-then-grow can hit a false rejection mid-sequence, since there is no multi-block atomic edit in this codebase — each drag is its own commit).
- **PeriodTimeBudget:** Two distinct modes, chosen at Seal/Edit time by whether a fixed daily floor is set (built 2026-08-19 — see `DESIGN_GAP_HISTORY.md` Gap 18 for the full design history):
  - **With a fixed daily floor** (the "Advanced daily floor checkbox" is on): behaves like `DailyFlexibility`'s per-day floor-protection, except a move can land on a *different* day than it started (blocks may go anywhere within `[StartDate, EndDate]`) — so both the day being vacated and the day being landed on are re-checked against their own (possibly different) floors, not just one.
  - **Without a fixed daily floor** (the default/derived choice, and the mode that actually matches this rule's own name): no per-day obligation exists at all — `NenContract.ContractFloor (ContractFloor?)` holds a single whole-period target instead, derived at Seal as the sum of every drafted Focus block's hours, immutable after that. `NenContract.IsPeriodMet(double totalFocusHours)` mirrors `IsDayMet`'s shape, scoped to the period total instead of one day; `UpdatePlannedBlockValidator` re-checks the whole-contract total (not a single day) after any edit. Day-Met scoring, `DaysBehind`/`DaysConsidered`, and rest days don't apply to this mode at all — every day is equally "in play," none is ever individually obligated or exempt. The Planner banner instead shows total completed vs. the `ContractFloor` target (`"Xh / Yh completed"`) — the same banner format every strictness rule now uses (see `TotalFloorHours`/`TotalCompletedHours` below).
  - `ContractFloor` is deliberately a distinct value object from `DailyFloor`, not a reuse — same shape (`Hours`, `IsSatisfiedBy`), but no 24-hour cap, since a whole-period total can easily exceed a single day's realistic maximum. Mutually exclusive with a real (non-empty) `DailyFloorPolicy` — `NenContract.Seal` throws if both are set with real content, the same "illegal state prevented by a guard clause, not a type-system union" discipline used elsewhere in this aggregate.

**Sealed-contract enforcement on planned blocks (built 2026-08-11):** A `PlannedBlock` whose `ContractId` resolves to a contract with `IsInEffect == true` (Scheduled or Active — a Completed or Broken contract's blocks fall back to the ordinary `HasEnded`-based protections, the same posture the WorkHours guard already takes toward a missing/irrelevant contract) is protected by that contract's `StrictnessRule`:
- **Delete is always rejected**, regardless of `StrictnessRule` — a block under a live commitment can never be deleted; only `Break` (which explicitly requires `AllowCancellation`) can remove it, via its own atomic cleanup.
- **Update** rejects any preset (`BlockPresetId`) change outright, for every `StrictnessRule` — re-typing a committed block isn't a designed operation any more than re-parenting its `ContractId` is (the latter has no field to change on `UpdatePlannedBlockCommand` at all, by the same original design decision). Time changes (move/resize) are then gated per rule via `NenContract.AllowsBlockTimeChange(originalDate, newStartDate, newEndDate)` — a pure entity method mirroring `AllowsBlockPlacement`/`CheckRedemptionEligibility`'s shape: `Locked` rejects every time change; `DailyFlexibility` requires the new window to stay on the block's original local calendar day; `PeriodTimeBudget` requires it to stay within `[StartDate, EndDate]`. `AllowsBlockTimeChange` only compares dates — callers resolve local time before calling, same discipline the WorkHours guard already follows.
- The UI mirrors this without re-deriving it: `PlannedBlockDto.IsUnderInEffectContract` (computed once by `GetPlannedBlocksForDayQueryHandler`) hides the Planner's Delete button for these blocks, same "Application computes, UI only references" precedent `HasEnded` already established (`DESIGN_GAP_HISTORY.md` Gap 9). Drag-move/resize still runs client-side; the Application-layer guard is the actual authority and rejects the command if the drop is illegal, and the Planner now reloads the week on a rejected drag (previously only on success) so the tile snaps back to its real position.

**Split Block *(built 2026-08-19 — see `DESIGN_GAP_HISTORY.md` Gap 17)*:** The one designed exception to Delete's unconditional rejection above — splitting a sealed `DailyFlexibility` block into two. Exclusively `DailyFlexibility` (Lockdown blocks are immutable full stop; `PeriodTimeBudget` was deliberately excluded from this feature, not merely unimplemented for it) and exclusively for a block no session has touched (any session, not just an active one — checked via `ISessionRepository.GetByOriginatingBlockIdAsync`, eliminating session-migration concerns entirely). `SplitPlannedBlockCommand` takes both resulting halves' explicit `Start`/`End` — deliberately not a single cut-point — and is atomic delete-and-recreate: the original `PlannedBlock` is deleted, two new ones are created with fresh `Id`s, the same `ContractId`/`BlockPresetId`, and no parent-child relationship between them (both are "equal contract members"). `SplitPlannedBlockValidator` requires the two halves to sum to exactly the original's duration, both stay on the block's original calendar day, and neither overlaps the other or any other existing block. The command is deliberately ignorant of what happens next — dragging the resulting second half to a new time is an ordinary, separate `UpdatePlannedBlockCommand`, not part of Split at all.

**Daily Floor:** The minimum completed Focus hours required on a given day. `NenContract.DailyFloorPolicy` (a `DailyFloorPolicy` value object) resolves the floor **per day**, not as one number for the whole contract — this was a deliberate redesign (2026-07-07) from an earlier single-scalar `NenContract.DailyFloor` that could not actually support the per-day-varying behaviour described below; see `DESIGN_GAP_HISTORY.md` for the closure record. `DailyFloorPolicy` mirrors `WorkHoursPolicy`'s shape exactly: a `Default (DailyFloor?)` applied to every day plus `PerDayExceptions (IReadOnlyDictionary<DateOnly, DailyFloor?>)` that override it, resolved via `.For(date)`. The underlying pure comparison (`DailyFloor.IsSatisfiedBy(hours)`) is unchanged and still serves both the Seal-time check (against *planned* Focus hours) and the later Day Met evaluation (against *completed* Focus hours) for whatever floor `.For(date)` resolves to. **In Simple contracts**, the policy has no `Default` — every planned day gets its own explicit `PerDayExceptions` entry equal to that day's planned hours: Monday with 2 planned hours has a floor of 2, Tuesday with 3 has a floor of 3. The Application layer passes planned hours as both the "planned" and "floor" values for each day, so the Seal check always passes by construction. **In Advanced contracts**, the user sets one fixed `Default` (e.g., "3 hours every day") checked against each day's planned hours at Seal — days below the floor are rejected — with `PerDayExceptions` reserved for explicitly designated rest days (see below).

**Rest Days:** A day is a rest day when `DailyFloorPolicy.For(date)` resolves to `null` — no obligation, skipped entirely by Seal validation and trivially met by `IsDayMet`. **In Simple contracts**, rest days are derived automatically: any day the Application layer omits from `PerDayExceptions` (i.e. any day with zero planned Focus hours) is a rest day, since there is no `Default` to fall back to. **In Advanced contracts**, the user explicitly designates rest days in the Planner wizard, which the Application layer encodes as `PerDayExceptions[date] = null` — this overrides the `Default` for that specific day. Rest days are not stored as their own field on the contract entity; they are implicit from how the policy resolves each date, fixed permanently at Seal (there is no `Extend` to revisit this later — see `DESIGN_GAP_HISTORY.md` Gap 51). The user may still schedule blocks on rest days voluntarily — they just aren't required.

**Rest Days vs. the Planner's live badge (built 2026-09-04 — see `DESIGN_GAP_HISTORY.md` Gap 52):** `DailyFloorPolicy`/`IsRestDay` above are the domain's own permanent record and never change after Seal. The Planner's day-header badge is a separate, read-time-only projection that can legitimately disagree with it in one direction: a domain rest day that later receives a floor-counting block anyway (a redemption, or a committed block moved in under Period Time Budget) renders as a normal progress badge against an ad-hoc target instead of "Rest" — purely a display choice computed by `GetNenContractsForDateRangeQueryHandler` (renamed 2026-09-06 from `GetActiveNenContractQueryHandler`, see Gap 55), never written back to `DailyFloorPolicy` and never affecting `IsDayMet`/`DaysBehind`/redemption eligibility, all of which still see the same permanent rest day they always did.

**Multi-contract weeks and the banner switcher (built 2026-09-06 — see `DESIGN_GAP_HISTORY.md` Gap 55):** A viewed Planner week can straddle the boundary between two in-effect contracts (one ending, the next starting mid-week) — every day's badge is computed and shown regardless, one contract's `DayStatuses` merged with the other's (contract date ranges never overlap, so there is never a collision to resolve). The banner text and the Cover Deficit button, by contrast, only ever name **one** contract at a time (`PlannerPageViewModel.SelectedContract`) — defaulting to whichever is `Active`, else the one with the earliest `StartDate` — with a small switch button to page to the other contract touching the same week when more than one exists. Switching re-targets the banner text and Cover Deficit's target contract only; it never changes which days have badges. A day belonging to a `Scheduled` (Upcoming) contract always renders as a uniform passive grey regardless of met/unmet/rest; an `Active` contract's rest day instead uses its own teal shade, graduated by whether the day is Past/Today/Future (see `UI_UX_STANDARDS.md`).

**Work Hours *(Application-layer wired 2026-07-08 — closes Task #13; wizard UI still not built)*:** A daily time-of-day window (`TimeOnly` start/end) defining where Focus and Background blocks may physically exist on the calendar. Blocks cannot be placed, moved, or resized to any time outside the work hours window. This is distinct from Change Window — Work Hours constrains *where blocks can be*, Change Window constrains *when edits are allowed*. Advanced contracts only; Simple contracts have no work hours constraint.

Per-day exceptions are supported via an `IReadOnlyDictionary<DateOnly, WorkHours?>` — a `null` value means no constraint for that day (free placement), a non-null value overrides the default work hours for that specific date. `SealNenContractCommand` exposes only the Default-window half of this plus `NoWorkHoursDays` (an explicit-null per-day exception list) — deliberately **not** a full per-day-different-window map, even though `WorkHoursPolicy` itself supports one and the domain/EF-mapping cost is already paid (Task #11): `FixedDailyFloorHours`/`RestDays` (the analogous pair for `DailyFloorPolicy`) exposes the *exact same* asymmetry today — one fixed value plus explicit rest-day exemptions, never a different non-null floor per specific day. Matching that existing precedent was judged more consistent than exposing more for Work Hours than Daily Floor already exposes on this same command. `WorkHoursPolicy.NoConstraintExceptions(IReadOnlyCollection<DateOnly>)` mirrors `DailyFloorPolicy.RestDayExceptions` exactly, same reason (fresh-build and future-merge callers share one conversion). The Planner's drag-math (`PlannerDragMath.WouldCollide`) and CreatePlannedBlock/UpdatePlannedBlock guards (`NenContract.AllowsBlockPlacement`, built Slice 6 Step 3) are now fully live — the guard was correct all along, it just had nothing to check against until now.

Domain value object `WorkHours { TimeOnly Start, TimeOnly End }` carries one window; `ContainsRange(DateTime start, DateTime end)` checks standard interval containment (`blockStart >= Start && blockEnd <= End`) — a block ending exactly at the window's close (e.g. a 9-to-5 block against 9:00–17:00 work hours) is valid. **Fixed 2026-08-18:** the comparison anchors the window to `start`'s calendar date and compares full `DateTime`s, not `TimeOnly.FromDateTime(...)` — the earlier `TimeOnly`-based comparison discarded the date, so a block ending exactly at midnight (e.g. 19:00–24:00, represented as the next day's 00:00) wrapped to `00:00` and read as trivially before any `End`, silently passing containment no matter how far past closing time it actually ran. Regression case added to `WorkHoursTests.cs`.

**Enforced during drafting too, not just post-Seal (fixed 2026-08-18):** `NenContract.AllowsBlockPlacement`/`ContainsRange` were only ever reachable through `CreatePlannedBlock`/`UpdatePlannedBlock` validators, which require a persisted `ContractId` — but per the Seal ubiquitous-language entry above, no `NenContract` exists until Seal, so a draft Focus tile placed during the wizard's drafting phase had no contract to check against and could be dropped anywhere, only getting rejected retroactively once the contract was sealed. `PlannerPageViewModel.ValidateDraftPlacement` now also checks the in-progress `WorkHoursStart`/`WorkHoursEnd` (from `NenContractDraftRules`, reusing `WorkHours.ContainsRange` directly rather than re-deriving the comparison) for Focus draft tiles only — Background tiles remain unconstrained, matching the sealed-contract rule.

The default window and its per-day exceptions are bundled into one value object, `WorkHoursPolicy { WorkHours? Default, IReadOnlyDictionary<DateOnly, WorkHours?> PerDayExceptions }`, rather than stored as two loose fields on `NenContract` — they are always configured and consumed together (one "Work Hours" section in the Advanced wizard, one JSON blob on a Contract Preset). `WorkHoursPolicy.For(DateOnly date)` resolves the effective window for a day: an exception wins (including an explicit `null` meaning "no constraint that day"), otherwise the default applies, otherwise there is no constraint. This is the single place the exception-with-fallback lookup lives — the Planner drag-math and command handler guards will both call `contract.WorkHoursPolicy?.For(date)?.ContainsRange(start, end) ?? true` rather than reimplementing the lookup. `NenContract.WorkHoursPolicy (WorkHoursPolicy?)` is set via an optional trailing parameter on `Seal(...)`, default `null` (Simple contracts, and any Advanced contract without a work-hours constraint).

**Change Window *(parked — domain value object exists, not wired up in v1)*:** An optional daily time-of-day window (`TimeOnly` start/end) during which edits to *existing* blocks are permitted, plus a configured `UsesPerDay` limit. The domain value object (`ChangeWindow`) is built and answers `Contains(TimeOnly)`, but Application-layer use-count tracking, UI configuration, and enforcement guards are all deferred. Distinct from Work Hours (see above). If implemented later, the Change Window configuration would likely live in the Settings page as a user-wide preference rather than per-contract.

**Strictness tightening mid-contract *(parked for v2)*:** The user may want to tighten the strictness rule mid-contract (e.g., switch from `DailyFlexibility` to `Locked` because they're losing discipline). Only tightening would be allowed — never loosening. Not in v1.

**Active-contract banner text (unified 2026-08-19):** Every strictness rule shows the same format now — `"Contract: [Name] — Day X/Y — Xh / Yh completed — Zh deficit"` — replacing the earlier Day-Met-only framing (`"Z of N days behind... M of N days met"`), which read as unnecessarily different for a `PeriodTimeBudget`-without-fixed-floor contract once that mode existed. `NenContractRangeViewDto.TotalFloorHours`/`TotalCompletedHours` (renamed 2026-09-06 from `ActiveNenContractDto`, see `DESIGN_GAP_HISTORY.md` Gap 55) compute uniformly for every contract: `TotalCompletedHours` is always a straight sum of completed Focus hours across the whole contract; `TotalFloorHours` is `ContractFloor.Hours` when set, otherwise the sum of every day's resolved per-day floor across `[StartDate, EndDate]` (rest days contribute `0`) — the total minimum commitment across the whole contract, computed the same way regardless of strictness. `DaysBehind`/`DaysConsidered` are still computed (kept for any future per-day-scoring consumer, e.g. Open Gap C's streaks) but no longer read by the banner text itself. The deficit (and Bonus) figure's wording was also tightened (Gap 55): an exact-hour amount reads as `"Xh"` (not `"Xh 0m"`), a sub-hour amount spells out `"N min"`, and a mixed amount stays `"Xh Ym"` — one shared formatter (`MinutesToStringConverter.FormatMinutes`) used by the deficit text, the Bonus label, and redemption-covered displays alike.

**Day Met:** A contract day is "met" if that day's *completed* Focus hours ≥ that day's resolved Daily Floor — evaluated via `NenContract.IsDayMet(DateOnly date, double completedFocusHours)`, which resolves `DailyFloorPolicy.For(date)` and compares against it (a day with no resolved floor is trivially met — it's a rest day). A missed or late Focus block does **not** fail the day directly; it only costs hours that must be made up elsewhere. Completed hours are summed across all sources: planned-block sessions, redemption block sessions, and **spontaneous sessions** that match a contract preset (see Spontaneous Redemption below). If the hours are made up, the day is met. The missed/late information lives in the per-block `FocusBlockOutcome` classification — a separate display concern. Summing a day's actual completed Focus hours is an Application-layer computation.

**FocusBlockOutcome:** How a single Focus block resolved — `CompletedOnTime`, `StartedLate`, `Missed`, or `EndedEarly` — classified purely from its scheduled window, ritual-completion state, and (since 2026-08-12, `DESIGN_GAP_HISTORY.md` Gap 22) when the session ended, via `IFocusBlockOutcomeClassifier.Classify(scheduledStart, scheduledEnd, ritualCompletedAt, sessionEndedAt, asOf)`. Returns `null` when no verdict has been reached yet (the block is still open — in progress or future — and could still be started late right up to its scheduled end). `Classify` gives `EndedEarly` priority over `StartedLate` when a block is genuinely both — one block, one verdict — but the two facts are independent, so `PlannedBlockDto.WasStartedLate (bool)` (built 2026-08-20, `DESIGN_GAP_HISTORY.md` Gap 20) carries the lateness fact separately, letting the Planner tile show both a "STARTED LATE" and an "ENDED EARLY" badge when both are true.

**Planner tile display (built 2026-08-20, Gap 20):** a tile's `Start`/`End` are the block's *actual worked window*, not its raw scheduled window — `GetPlannedBlocksForDayQueryHandler` pulls `Start` forward to `RitualCompletedAt` once past the grace period, and `End` back to `SessionEndedAt` for an early end, so the tile visually shortens from whichever end(s) apply (both, if the block is both `StartedLate` and `EndedEarly`). A grace-period-late start is left untrimmed, matching the fact it's still credited as full duration. Tile color/badge, driven by `Outcome`: `CompletedOnTime` → green, no badge (color alone reads as "on time"); `StartedLate`/`EndedEarly` → the same amber, labeled "STARTED LATE"/"ENDED EARLY" (both, stacked, when a block is genuinely both); `Missed` → red, "MISSED," struck through (unchanged). The mapping from `Outcome` to a CSS class name/badge string lives entirely in `PlannerPageView.axaml.cs`'s code-behind, not the ViewModel — `PlannedBlockTileViewModel` only ever exposes the semantic `Outcome`/`WasStartedLate` facts, mirroring how `DayFloorStatusToBrushConverter` already keeps ViewModels ignorant of their own visual representation.

**Ritual is never opened for a block that already has a Session** (built 2026-08-20, `DESIGN_GAP_HISTORY.md` Gap 21's fourth addendum): `GetFocusBlockRitualContextQueryHandler` (called by `ShellViewModel.StartRitual` immediately before the Ritual UI opens) now also checks `ISessionRepository.ExistsForOriginatingBlockAsync` and surfaces it as `FocusBlockRitualContext.AlreadyHasSession`. If true, `StartRitual` declines to open the Ritual at all — showing it would only guarantee a rejection at Hatsu (`StartSessionCommandHandler`'s pre-existing `ExistsForOriginatingBlockAsync` check, the only place this fact was previously checked, and only at the very end of the flow). A general guard against any stale ritual-required signal, not scoped to one specific cause.

**5-minute grace period** (universal — all Focus Blocks, contracted or not) *(built, 2026-07-08 — see `DESIGN_GAP_HISTORY.md` Gap 11 for the closure record; the window was documented well before it was actually implemented in `Classify`; crediting formula rewritten 2026-09-07, `DESIGN_GAP_HISTORY.md` Gap 57)*:
- A ritual completed within 5 minutes after the scheduled start (≤ `scheduledStart + 5 min`, via `FocusBlockOutcomeClassifier.GracePeriodMinutes`) is `CompletedOnTime` — the Ritual takes a moment, and penalizing a 13:03 completion for a 13:00 block is noise. This label rule is unchanged by Gap 57.
- **Current crediting formula (`IFocusBlockOutcomeClassifier.CreditedWindow`/`CreditedFocusMinutes`), one unconditional rule, no branching on how the session ends:** grace forgives a late start **unconditionally** — credit starts counting from the block's own **scheduled start**, regardless of whether the session later runs to completion or ends early — because blocking enforcement is already active on the user's computer from `PlannedBlock.Start` onward (`PolicyEngine.ComputeSlice` keys entirely off `Start`/`End`, never `RitualCompletedAt`); crediting that setup window is honestly counting real enforcement time, not inventing work. A start **beyond** grace gets no such allowance — credit starts from the moment the Ritual actually completed. A genuine early end always counts exactly what was delivered, **however small the shortfall — no forgiveness at any grain** (Gap 45's sub-minute write-off was removed outright in Gap 57). A session that runs its course credits up to `scheduledEnd`, never beyond, whether it ended naturally or was force-ended past due (e.g. via the debug clock). The whole result — the credited *window's own End*, not just a derived minutes figure — is floored to whole minutes as the final step (`Session.GetElapsedTime` also floors at its own, independent source), so every consumer of "how much did this block earn" (the deficit ledger, completed/bonus hours, Post-Session's duration) reads a clean whole-minute value with nowhere for stray seconds to leak in. Seconds only ever matter for the Main Page's own live countdown, which never reads through either of these methods.
- **Grace-period warning notification** *(Application/Infrastructure — not yet built)*: 3 minutes past the scheduled start, if the Ritual still hasn't been completed, the app fires a toast: "You have 2 minutes to complete the Ritual or this block will be marked as a late start." At 5 minutes, if still uncompleted, the outcome becomes `StartedLate` (or `Missed` if the end passes). The notification is a one-shot — it does not repeat.
- The missed/late boundary remains the block's **scheduled end**, not its start.

**Redemption Block:** A Focus Block explicitly linked to one or more missed or late Focus Blocks, covering all or part of their deficit. The link is a collection of `RedemptionEntry` value objects on `PlannedBlock` — empty (never null) means a regular block. Redemption blocks are always Focus Blocks (Background Blocks have no sessions and cannot contribute toward a Focus-hours deficit). **Built** — see the technical mapping rows for `ComputeRedemptionAttributionQuery`, `NenContract.CheckRedemptionEligibility`, and the Create/UpdatePlannedBlock handlers below. Confirmed tiles render with a "REDEMPTION" text tag (`PlannedBlockDto.IsRedemption`, `RedemptionEntries.Count > 0`) — same color family as the block's own outcome/preset, no border treatment (a dashed-border variant was tried and removed 2026-08-21, judged not to look good).

**Redemption path — automatic attribution, no toggle *(redesigned 2026-08-21 — see `DESIGN_GAP_HISTORY.md` Gap 26, superseding the same-day toggle-based UI from Gap 25)*:** Linking is no longer a client-driven choice. Any new or edited Focus Block whose preset+date is eligible to cover an outstanding deficit is attached automatically — `CreatePlannedBlockCommandHandler`/`UpdatePlannedBlockCommandHandler` compute the attachment themselves via `ComputeRedemptionAttributionQuery`, oldest outstanding deficit first, spilling into the next if the block is longer. The block-creation form shows a passive preview notice ("This will cover 45 min of your missed Deep Work block") once eligibility is detected — informational only, no click required and nothing to opt out of. `NenContract.CheckRedemptionEligibility` now allows all three `StrictnessRule` values (see Rules 8–10 below); `RedemptionEligibility.NotAllowed` was deleted as unreachable once `Locked` stopped being a hard no. Separately, the Planner's active-contract banner gets a **"Cover Deficit"** button (`GetSuggestedRedemptionPlacementsQuery`) that creates a real tile on demand, sized to a preset's total outstanding deficit and placed at the next quarter-hour (shifted earlier, never before now, only if needed so the full amount still fits before the day's boundary — midnight or Work Hours close; searches past conflicting tiles; asks for confirmation before creating a knowingly-partial tile if even starting now can't fully cover it). More than one preset owing → a small popover (mirrors the Nen Contract popover's button+Popup shape) lets the user pick which one; exactly one → skips the popover and creates the tile directly.

**Main Page spontaneous redemption prompt — dropped (2026-07-08), not building it.** The original design: when a contract is active with an outstanding deficit, the Main Page would prompt the user to start a redemption session; the Ritual's Ren step would pre-lock to the preset with the largest deficit, Hatsu would show the deficit amount, and the resulting Spontaneous session's partial coverage would reduce the deficit ledger. Fully interrogated and deliberately dropped, not merely deferred — see `ARCHITECT_GOVERNANCE.md` Open Gap D for the full reasoning (why `Session` has no natural anchor for per-block deficit attribution, why every alternative modeling considered either leaked, over-built, or failed to deliver real redemption semantics, and what to build first if this is ever revisited). The Planner toggle above remains the only redemption mechanism.

**Redemption Rules (18 rules; 1–14 finalised 2026-07-07, 15 added 2026-08-21 alongside the first real UI, then 4/8/9/10/14 reworded and 15/16/17 added/replaced the same day when the toggle was replaced with automatic attribution — see `DESIGN_GAP_HISTORY.md` Gap 26; 18 added 2026-08-22, see Gap 34):**

| # | Rule |
|---|------|
| 1 | A missed or late Focus Block creates a **deficit** = `scheduledDuration − creditedMinutes` (full scheduled duration for a miss; `IFocusBlockOutcomeClassifier.CreditedFocusMinutes` for a late start or early end — **not** raw actual-elapsed minutes, see `DESIGN_GAP_HISTORY.md` Gap 24). |
| 2 | Deficit is tracked **per missed block**, not per preset — each missed block is an independent row in the deficit ledger. |
| 3 | A redemption block links to one or more missed blocks via `IReadOnlyList<RedemptionEntry> RedemptionEntries` on `PlannedBlock`. |
| 4 | All linked missed blocks must share the **same `BlockPresetId`** as the redemption block — `ComputeRedemptionAttributionQuery` only ever attaches a block to deficits of its own preset, computed automatically on every Create/Update, no client selection involved. |
| 4a | All linked missed blocks must also share the **same `ContractId`** as the redemption block — enforced by construction: `ComputeRedemptionAttributionQuery` only ever walks one contract's deficit ledger per block (the explicitly-scoped one, or whichever single in-effect contract it auto-discovers). |
| 5 | One redemption block can cover multiple missed blocks of the same preset (e.g., two 30-minute misses → one 60-minute redemption) — oldest outstanding deficit first, spilling into the next if the block is longer (`ComputeRedemptionAttributionQuery`). |
| 6 | A redemption block's duration can **exceed** the total selected deficit — surplus is fine and counts toward the Daily Floor, just not attributed to any specific missed block. |
| 7 | `MinutesCovered` (the ledger claim per missed block) is capped at `Min(remainingBlockDuration, remainingDeficit)` for each entry in oldest-first order — deliberately decoupled from the block's own total scheduled duration, so a block longer than any single deficit correctly spills the remainder into the next-oldest one instead of over-claiming against the first. |
| 8 | Under **`Locked`** and **`DailyFlexibility`** strictness: a missed block can only be covered on the **same calendar day** it was scheduled — for Daily Flex that's its whole model of same-day rearrangement; for Locked, new blocks can always be inserted (only editing/moving an *existing* sealed block is forbidden), so redemption is allowed but confined to that same day. |
| 9 | Under **`PeriodTimeBudget`** strictness with a real per-day floor (the Gap 18 hybrid): same rule as Rule 8 — each day has its own obligation, so coverage must land on the same day. With a pure whole-period `ContractFloor` instead (no per-day floor): a missed block can be covered on **any day** within the contract period. |
| 10 | `RedemptionEligibility.NotAllowed` does not exist — every `StrictnessRule` allows redemption in some form (Rules 8–9). There is no strictness value under which redemption categorically cannot happen. |
| 11 | A missed block's `FocusBlockOutcome` stays `Missed` (or `StartedLate`) regardless of whether it was later redeemed. Insights shows both: the original miss AND the successful redemption. |
| 12 | A redemption block gets its own `FocusBlockOutcome` (`CompletedOnTime` / `StartedLate` / `Missed`) — classified independently. |
| 13 | A redemption block that itself is missed does **not** create additional deficit. The original missed block's deficit simply remains uncovered. No "redeem the redemption" chain. **This rule was documented but not actually enforced until 2026-08-21** — `GetNenContractDeficitsQueryHandler` treated a redemption block as an ordinary Focus Block subject to becoming its own deficit source; see `FocusBlock.CanContributeOwnDeficit` below and `DESIGN_GAP_HISTORY.md` Gap 29. |
| 14 | If the user has outstanding deficits across **different presets**, each new Focus Block only ever attaches to deficits of its own preset — there is no cross-preset attribution, and no user choice involved for an ordinary block creation. The "Cover Deficit" banner button surfaces one option per preset when more than one is owing, for the user to pick which to create a tile for. |
| 15 | Every edit to an existing redemption-eligible Focus Block **recomputes its coverage from scratch**, scoped to the block's own already-known contract — an edit never re-parents a block to a different contract, and a standalone block (no contract) never auto-discovers one just by being edited. |
| 16 | Splitting a redemption block (`SplitPlannedBlockCommandHandler`) queries attribution once for the original block's whole combined span, then partitions the result across the two resulting halves by each half's own duration — an entry entirely within one half's window goes to that half only; one straddling the cut point splits into two entries against the same missed block. Never copies the same entries onto both halves (a fixed double-count bug from the toggle-era implementation). |
| 17 | The "Cover Deficit" banner button sizes each preset's tile to that preset's **total** outstanding deficit (summed across every missed block of that preset), placed at the next quarter-hour — shifted earlier (never before now) only if needed so the full amount still fits before the day's boundary (midnight, or the contract's Work Hours close for that day), searching past any conflicting tile. If even starting right now can't fully cover it, the tile is offered anyway (starting now, ending at the boundary) with a confirmation prompt before creating a knowingly-partial one. |
| 18 | A block's outcome only counts toward the deficit ledger — as a deficit source **or** as a covering block's contribution — once its session has actually ended (`Session.HasEnded`), naturally or early. A late-started session still in progress (its final credited minutes aren't knowable — it could still end early) is treated as still-open (`null`), exactly like a block that hasn't happened yet, purely within `GetNenContractDeficitsQueryHandler` — `IFocusBlockOutcomeClassifier.Classify` itself is untouched and keeps reporting live for every other consumer (Day Met's progress number, Insights, Planner badges). Deliberately **not** gated on `PostSessionAcknowledgedAt` — that fact exists for crash-recovery replay, an unrelated concern, and gating on it would leave an already-final deficit hidden until the user happens to dismiss the Post-Session screen. See `DESIGN_GAP_HISTORY.md` Gap 34. |

**Broken → blocks handling *(built; redesigned 2026-08-18 — see `DESIGN_GAP_HISTORY.md` Gap 23)*:** `BreakNenContractCommandHandler` calls `Break()`, saves, then calls `MarkCancelled(now)` on every linked block (Focus or Background alike) for which `HasEnded(now)` is false, and saves each — **no longer a delete**. `PlannedBlock.CancelledAt (DateTime?)` records the fact; `PlannedBlock` also gained `: AggregateRoot` (a prerequisite for `MarkCancelled` to raise `PlannedBlockCancelledEvent`). Enforcement stops via a `CancelledAt` filter at two layers (`ComputeActivePolicySliceQueryHandler` excludes cancelled blocks before resolving presets; `PolicyEngine.ComputeSlice()` independently filters its own `activeBlocks` input, defensively). The Planner excludes cancelled blocks from the calendar view. If the active session's `OriginatingBlockId` matches one of the contract's blocks, that session is also force-ended in the same commit (`session.Complete(now)`, mutated directly, not composed through `EndSessionCommandHandler`, to stay in the one atomic commit `TransactionalCommandHandler` provides). Blocks that have already ended (`End < now`) stay linked and untouched, for historical accuracy. This closed the original "delete-everything makes a recap of a broken contract structurally impossible" problem — a `GetNenContractRecapQuery` can now distinguish **Cancelled** (`CancelledAt.HasValue`) from **Missed/StartedLate/CompletedOnTime** (`IFocusBlockOutcomeClassifier.Classify`, untouched) among a broken contract's surviving blocks — though that query itself is still not yet built, tracked in `ARCHITECT_GOVERNANCE.md` → Open Gap G.

**Block-preset deletion guard *(not yet built)*:** A preset cannot be deleted while referenced by an active or scheduled contract, a future planned block, or an active session. This is an Application-layer concern.

**Settings integration *(future)*:** In the Settings page, the user will be able to pre-save default strictness rules automatically applied when creating a new Nen Contract. The Change Window (if implemented later) would also be configured here as a user-wide preference rather than per-contract. Work Hours configuration is per-contract (set in the Planner wizard), not a Settings-level preference — each contract can have different work hours.
