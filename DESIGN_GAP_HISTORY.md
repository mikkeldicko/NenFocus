# NenFocus — Design Gap Closure History

A running record of gaps that were identified, interrogated, and closed. Each entry is a concrete demonstration of the Design Gap Protocol working correctly.

**This is reference material, not constitution.** It does not need to be read at the start of every session. Consult it when:
- A new gap looks similar to a previously-closed one — check whether the same principle applies.
- You need to understand *why* the codebase looks the way it does today (e.g. why `BlockedAttempt` is a fact table and not JSON on `Session`).
- You're inducting a new collaborator on how design decisions are made on this project.

For active design tension, see the **Open Gaps** section in `ARCHITECT_GOVERNANCE.md`.

## Gap 1 — Enforcement Gap on Session Start *(closed)*

**The gap:** `StartSessionCommandHandler` saved the session and updated UI state but never applied OS-level enforcement. `SessionStartedEventHandler` had been stripped of its enforcement call and only sent a notification. Sessions could start with no blocking in effect. The bug was silent — no test caught it because `IEnforcementService` was never injected into the handler.

**The closure:** Event-driven chain restored. `Session.Start()` raises `SessionStartedEvent` internally → handler dispatches via `PublishAllAsync(session.DomainEvents)` → `SessionStartedEventHandler` computes the current policy slice via `ComputeActivePolicySliceQuery` and calls `IEnforcementService.ApplyPolicyAsync`. `IEnforcementService` remains a simple two-method interface; the orchestration complexity lives in the event handler. Three new tests in `SessionStartedEventHandlerTests` now guard this path permanently.

**Principle demonstrated:** Deep Modules — `IEnforcementService` stayed narrow. The event handler became the "orchestrator" layer, not the command handler and not the infrastructure service.

## Gap 2 — BlockPresetType Promotion: From Leaky Boolean to Domain Enum *(closed)*

**The gap:** The system could not distinguish between a Focus Block (which must trigger the Ritual) and a Background Block (which enforces silently) after computing a policy slice. A boolean `RequiresRitual` flag would have been the shallow solution — a boolean with no domain meaning that every caller must interpret differently.

**The closure:** `PolicySliceDto` now carries `ActiveBlockPresetType (BlockPresetType?)` — a domain enum from `NenFocus.Domain.Enums`. `ComputeActivePolicySliceQueryHandler` sets it to the type of the highest-priority active planned block (Ritual > Background). `ScheduledEnforcementService` reads this field and calls `SetRitualRequired(true)` only when `ActiveBlockPresetType == Ritual` with no active session. The decision is expressed once, in the domain's language, in one place.

**Principle demonstrated:** Ubiquitous Language — the difference between a Focus Block and a Background Block was already a domain concept. Promoting it to the `PolicySliceDto` made the contract self-documenting and eliminated a class of future bugs where callers would have needed to re-derive the distinction themselves.

**Side fix included:** Blocklist mode in `ComputeActivePolicySliceQueryHandler` was previously broken — `BlockedSites` was always an empty set (missing `case WebsiteFilterType.Blocklist:`). Fixed in the same slice. The browser extension was receiving an empty blocklist for all Blocklist-mode presets.

## Gap 3 — Spontaneous Sessions, Insights Architecture, and the Block Hierarchy *(closed)*

**The gap:** The domain had no way to distinguish a planned Session from a manually-started one, making the planned Insights page impossible to build correctly. Additionally, the block hierarchy was being reconsidered — a proposed `InstantFocusBlock` class and a rename to Focus Block / Background Block were both under evaluation. The `BlockedAttempt` entity was also being considered for conversion to a Value Object.

**The interrogation revealed:**
- Insights requires a unified calendar view showing Focus Blocks (completed and missed), Background Blocks, and Spontaneous Sessions
- Insights requires analytics including session quality comparison between Planned and Spontaneous sessions and block preset follow-through rates
- Background Blocks must appear in Insights using scheduled time as canonical truth regardless of machine state
- A Focus Block where the user missed the Ritual must appear in Insights as "missed" — the `FocusBlock` row is the record
- A Spontaneous Session that did not complete the Ritual must not be saved anywhere
- The ONLY manual path to enforcement is through the full Nen Ritual — this is a product invariant, not a validation rule
- Browsing time tracking on all websites is a desired future feature requiring extension changes
- Planned Period / Strict Mode is a desired future feature

**The closure:**
- `InstantFocusBlock` rejected: a Spontaneous Session is not a Block. It has no calendar identity, no life outside its Session, and no state transitions. Creating an entity to make the schema look symmetric would violate DDD and fail the Deep Module test.
- `BlockedAttempt` kept as append-only fact table: burying it in JSON would make Insights analytics queries require full in-memory deserialisation across hundreds of sessions.
- `FocusBlock` renamed to `FocusBlock`, `PassiveBlock` renamed to `BackgroundBlock`, `BlockPresetType` enum values updated to `Ritual` and `Background`. Rename is complete at every layer: entity, enum, DTO, handler, service, dictionary.
- `Session.Origin (SessionOrigin)` added: explicit `Spontaneous` / `Planned` tag. Does not rely on null-checking `OriginatingBlockId` so it remains unambiguous when future origin types are added.
- `Session.OriginatingBlockId (Guid?)` added: closes the known gap from `TECHNICAL_SPEC_INFRA.md`. Written by `StartSessionCommandHandler` when a Focus Block triggered the session.
- `FocusBlock.RitualCompletedAt (DateTime?)` added: allows Insights to detect missed blocks from the entity alone without a join to Session.
- `GetInsightsCalendarQuery` stubbed: single query handler that unifies three sources behind one interface. The ViewModel never touches the individual tables.

**Principle demonstrated:** The asymmetry between Planned and Spontaneous in the schema (Block + Session vs Session alone) is correct and intentional. It reflects a real asymmetry in the domain — a planned block exists before and independently of any Session; a spontaneous one does not. Hiding this asymmetry with a synthetic entity would be lying with code. `GetInsightsCalendarQuery` is the correct place to unify the three sources — complexity is hidden behind a narrow interface, not erased from the domain.

## Gap 4 — Domain Events Raised by Handlers, Not Entities; `BlockedAttemptsSerialized` Contradiction *(closed)*

**The gap:** Two DDD violations were found during a doc/code audit. First, domain events (`SessionStartedEvent`, `SessionEndedEvent`, `BreakStartedEvent`, `BlockPresetCreatedEvent`) were being constructed and published directly inside command handlers, not inside the entities and aggregates that own the state transitions. The governance states "domain events: raised inside entities/aggregates" — the code violated this. Second, `EndSessionCommandHandler` and `StartBreakCommandHandler` were calling `IEnforcementService` and `INotificationService` directly, bypassing the event handler chain the governance explicitly requires. Third, `Session.BlockedAttemptsSerialized` persisted blocked attempt data as a JSON blob on the Session row — contradicting the Gap 3 decision to keep `BlockedAttempt` as an append-only fact table.

**The closure:**
- `Session` and `BlockPreset` now own a private `_domainEvents` list. Each state-transition method (`Start()`, `StartBreak()`, `Complete()`) appends the appropriate event internally. Handlers call `entity.DomainEvents` and dispatch via `IDomainEventPublisher.PublishAllAsync`, then clear with `entity.ClearDomainEvents()`. The handler no longer knows which events a domain operation produces.
- `EndSessionCommandHandler` and `StartBreakCommandHandler` had their `IEnforcementService` and `INotificationService` injections removed. All enforcement and notification side-effects now flow exclusively through `SessionEndedEventHandler` and `BreakStartedEventHandler`. `BreakStartedEventHandler` also gained the missing `IEnforcementService.RemoveEnforcementAsync` call it lacked.
- `Session.BlockedAttemptsSerialized` and `Session.SetBlockedAttempts()` removed. `BlockedAttempt` rows (append-only, keyed by `SessionId`) are the sole persistence path for attempt data. Migration `20260512000001_RemoveBlockedAttemptsSerialized` drops the now-redundant `BlockedAttempts` column from the `Sessions` table.

**Principle demonstrated:** Deep Modules and the governance rule "commands do not directly call enforcement or notifications — event handlers do." The command handlers are now thin: validate → mutate domain → save → publish events → return result. All side-effects (enforcement, notifications) are encapsulated in event handlers with narrow, self-documenting interfaces.

## Gap 5 — Persistence Boundary: Per-Repository SaveChanges vs. Unit of Work *(closed)*

**The gap:** Repositories used to call `SaveChangesAsync` internally on each `SaveAsync`. `StartSessionCommandHandler` therefore performed two separate database round-trips when a Focus Block triggered a session: one to stamp `FocusBlock.RitualCompletedAt`, one to insert the new `Session` row. If the second save failed, the database would be left with a Focus Block marked completed but no corresponding Session — violating the invariant that a completed Focus Block always has an associated Planned Session. The same fragmentation pushed domain-event dispatching out to every handler, each of which had to remember to call `PublishAllAsync` and `ClearDomainEvents` in the right order relative to `SaveAsync` — a Deep Modules violation.

**The closure:** Repositories (`BlockPresetRepository`, `PlannedBlockRepository`, `SessionRepository`) no longer call `SaveChangesAsync` themselves — `SaveAsync`/`AddAsync`/`UpdateAsync` only register changes with the change tracker. `EfCoreUnitOfWork.CommitAsync()` is the sole place `SaveChangesAsync` is called: it walks the change tracker for `AggregateRoot` entries with pending `DomainEvents`, calls `SaveChangesAsync`, then publishes each aggregate's events via `IDomainEventPublisher.PublishAllAsync` and clears them. `TransactionalCommandHandler<TCommand, TResult>` wraps every command handler in DI and calls `_uow.CommitAsync()` after the inner handler returns — so a Planned Session's `FocusBlock.MarkRitualCompleted()` stamp and the new `Session` row now commit atomically in one `SaveChangesAsync` call, and no handler has to remember the "save, then publish, then clear" sequence itself.

**Confirmed via `NenFocus.Tests`:** `EfCoreUnitOfWorkTests` (persists pending changes, publishes only aggregates with pending events, clears events after publishing) and `TransactionalCommandHandlerTests` (inner handler always runs before `CommitAsync`, and `CommitAsync` still runs even when the inner handler returns a failure result).

**Principle demonstrated:** Deep Modules — the "save, then publish domain events, then clear them" rule now lives in exactly one place (`EfCoreUnitOfWork`) instead of being repeated in every command handler, and the atomicity invariant (all-or-nothing per command) is enforced structurally by the decorator rather than by convention.

## Gap 6 — NenContract's Single-Scalar Daily Floor Contradicted Its Own Documented Design *(closed)*

**The gap:** Discovered while starting the Nen Contract Application layer (2026-07-07). `DOMAIN_DICTIONARY.md` documented Simple contracts as having a *per-day* floor ("Monday with 2 planned hours has a floor of 2, Tuesday with 3 has a floor of 3") and rest days as "not floor-checked... skipped entirely." But the already-built `NenContract` aggregate stored exactly one scalar `DailyFloor` for the whole contract, and `Seal()`'s validation loop iterated *every* day in range — including days absent from the planned-hours map, which defaulted to `0` and were still checked against the single floor. Neither documented behavior was actually buildable: a Simple contract could never have a varying per-day floor, and an Advanced contract's explicitly-designated rest day would still throw at Seal if the contract's floor was above zero.

**The closure:** `NenContract.DailyFloor (DailyFloor)` replaced with `NenContract.DailyFloorPolicy (DailyFloorPolicy)` — a new value object deliberately mirroring the already-proven `WorkHoursPolicy` shape: `{ DailyFloor? Default, IReadOnlyDictionary<DateOnly, DailyFloor?> PerDayExceptions }`, resolved per day via `.For(date)`. A day resolving to `null` (no exception and no default, or an explicit `null` exception) is a true rest day. `Seal()`'s loop now resolves the floor per day and `continue`s past rest days instead of defaulting them to a zero-hour check. `IsDayMet` and `Extend` gained a `DateOnly date` parameter for the same reason — `Extend` also gained an optional `dailyFloorOverridesForNewDays` parameter so newly-added days can carry their own floors, merged into the policy's `PerDayExceptions` going forward. Simple contracts populate only `PerDayExceptions` (no `Default`); Advanced contracts set a fixed `Default` plus `PerDayExceptions` for explicit rest days — both are now real, distinct configurations rather than a single number pretending to support both.

**Confirmed via `NenFocus.Tests`:** `NenContractTests` rewritten for the new shape (39 tests, all passing), including new cases for rest-day-via-exception at Seal, per-day-varying floors at Seal, `IsDayMet` returning different verdicts for different days on the same contract, and `Extend` merging per-day floor overrides for newly added days.

**Principle demonstrated:** Surface drift, don't fix silently — the contradiction between documented behavior and shipped domain code was found before any Application-layer code was written on top of the old shape, and was brought to the architect as a choice (rebuild to per-day vs. keep the scalar and let Simple contracts lose their defining behavior) rather than resolved unilaterally. Reuse over invention — the fix is structurally identical to `WorkHoursPolicy`, an already-validated pattern for "one default, exceptions per day," rather than a new bespoke shape.

## Gap 7 — Broken Contract Cleanup: Delete-or-Unlink Choice Dropped, Event Handler Rejected in Favor of One Atomic Command *(closed)*

**The gap:** The original design (recorded when the Nen Contract domain shape was interrogated) called for `NenContractBrokenEvent` to be handled by an Application-layer event handler that would "prompt the user" with a choice — delete all upcoming blocks, or unlink them (`ContractId → null`) and keep them on the calendar ungoverned. Building the Break slice (2026-07-07) surfaced two problems with this as written: (1) an `IDomainEventHandler<NenContractBrokenEvent>` cannot literally show a UI prompt without the Application layer depending on UI types, which the architecture forbids; and (2) even once resolved into "the event handler signals a state service, the UI reacts, then dispatches a follow-up command," that shape is a four-hop pass-through chain (event → handler → state service → ViewModel → follow-up command) for something that, on inspection, has exactly one real trigger: a direct, synchronous user button click. There is no scenario in the current design where a contract breaks without the UI already knowing.

**The closure:** The architect reconsidered the underlying product decision first — does "unlink and keep the schedule" earn its complexity at all? Conclusion: a contract only reaches `Break()` if `AllowCancellation` was set at Seal, already a deliberate, rare escape hatch; someone using it is very likely abandoning the whole plan, not fine-tuning it. Delete-only was chosen, dropping the choice entirely. That in turn removed the need for a decision-relay chain: `BreakNenContractCommand` now does everything in one atomic command — calls `NenContract.Break(now)`, saves, then deletes every block linked to the contract for which the new `PlannedBlock.HasEnded(now)` returns `false`. No event handler was built for `NenContractBrokenEvent`; the event still fires (raised inside `Break()`, published automatically by `EfCoreUnitOfWork` per Gap 5) and remains available for a future non-interactive reaction, but nothing forces a consumer to exist today — the same "deliberately silent" posture already accepted for `SessionMissedEvent`.

**Two smaller reuse checks along the way:**
- `PlannedBlock.HasEnded(DateTime asOf) => End < asOf` was added as a named entity predicate — mirroring `IsActive` and the `IsDueForActivation`/`IsDueForCompletion` pair added to `NenContract` in the same work session — rather than inlining `block.End < now` ad hoc inside the handler.
- Before writing the delete loop, `DeletePlannedBlockCommandHandler` was checked for hidden business rules; it turned out to be a bare `_blocks.DeleteAsync(...)` call with no logic behind it. `BreakNenContractCommandHandler` therefore calls the repository directly rather than composing through that command — composing would have added a hop with nothing behind it, the same defect just ruled out for the rejected event-handler design.

**Principle demonstrated:** Domain events exist to decouple a fact from reactions that don't share its calling context — not to relay a signal back to the exact place that already has it. Atomicity over choice-then-follow-up: one command doing both the status transition and the related-aggregate cleanup (mirroring `StartSessionCommandHandler`'s established multi-entity commit pattern from Gap 5) means no "broken but not yet resolved" state can ever be persisted, the same reasoning already applied to Seal's atomicity. And: check whether a method you're about to compose through actually does anything before assuming composing through it is the safer choice — sometimes directness is correct, not a shortcut.

## Gap 8 — Block Preset Lock Refined to Add-Only; Contract Deletion Guard Found Already Built *(closed)*

**The gap:** Two things surfaced together while auditing protection around a `BlockPreset` that's currently in use. First, `UpdateBlockPresetValidator` rejected *any* edit outright whenever a preset was locked (in use by an active session, or referenced by a future `PlannedBlock`) — matching the documented rule at the time ("a preset is locked... no edits are permitted"). The architect judged this too blunt: you should be able to strengthen a live block (add more apps/sites) without waiting for it to free up, you just shouldn't be able to weaken it (remove entries) or change its identity (rename, retype, change filter mode) while it's committed. Second, a task on the open backlog ("Block-preset deletion guard: reject if preset referenced by active/scheduled contract or future planned block") assumed this needed building for the Nen Contract case specifically.

**The closure:** `UpdateBlockPresetValidator` was rewritten: locked + an add-only change (new `BlockedApps`/`Websites` are supersets of the current ones, and `Name`/`WebsiteFilterType`/`PresetType`/`Tags` all unchanged) → valid. Locked + anything else → invalid, with a message explaining why. Not locked → unrestricted, as before. `DeleteBlockPresetValidator` was left untouched — deletion stays fully blocked while locked, no add-only carve-out makes sense for a delete. Investigating the second item found it was **already satisfied**: `HasFutureBlocksForPresetAsync` (used by both validators) queries all `PlannedBlock`s by preset ID with `End > now` and has never filtered on `ContractId` — a block scheduled under a Nen Contract is just a `PlannedBlock` like any other in that table, so it was already covered. No separate contract-aware guard was needed; the backlog task was closed as already-done rather than built from scratch.

**Principle demonstrated:** Before implementing a backlog item, check whether the existing code already satisfies it — `HasFutureBlocksForPresetAsync`'s type-agnostic query meant the "contract case" was never actually a gap, just an unverified assumption. And: when relaxing a lock, relax exactly the dimension that was asked about (apps/sites, add-only) and leave every other dimension (name, type, filter mode, tags) under the original full lock — resist the urge to also loosen things nobody asked to loosen.

## Gap 9 — PlannedBlock Deletion Had No Application-Layer Protection At All *(closed)*

**The gap:** `DeletePlannedBlockCommandHandler` had exactly one line of logic — `await _blocks.DeleteAsync(...)` — no validation beyond "is the ID non-empty." The only thing stopping a user from deleting a currently-active or already-completed block was `PlannerPageViewModel.CanDeleteFromForm => IsEditing`, which is **not** gated by the same `IsBlockLocked` flag that already disables the Save button for that exact scenario. This was a live, reachable bug, not a hypothetical: opening a completed block or the active session's originating block in the Planner form and clicking Delete worked, with nothing stopping it, before this fix.

**A second, deeper issue surfaced while designing the fix:** the natural instinct was to mirror the UI's existing `IsEditingCompleted` flag, which is `FocusBlock.RitualCompletedAt.HasValue` — true only once a Session has actually been started from that block. Tracing what that flag actually protects (mid-session reschedule-safety, not historical-record-safety) showed it was the wrong predicate for deletion: a **missed** Focus Block (window closed, Ritual never completed) reads `RitualCompletedAt == null`, so mirroring that flag would leave missed blocks freely deletable — directly contradicting the Missed Session feature's own stated invariant that a missed block "is not deleted or altered... it remains the schedule record." Background Blocks have no Ritual concept at all, so the same flag is permanently `false` for them regardless of age, leaving every past Background Block — which Insights treats as "the complete record" for that entry — deletable forever too.

**The closure:** `DeletePlannedBlockValidator` gained two checks: the block must not be the active session's `OriginatingBlockId`, and `PlannedBlock.HasEnded(now)` must be false. `HasEnded` (added in Gap 7, for the Break slice's block cleanup) is defined once on the shared `PlannedBlock` base and answers "has this window closed" identically for both subtypes — deliberately broader than the UI's Ritual-specific flag, closing the missed-Focus-Block and past-Background-Block holes the narrower mirror would have left open. The existing `IsEditingCompleted`/Save-lock logic was left untouched — it answers a different, still-valid question (is a Session already tied to this exact block's current schedule) and was never wrong for that purpose.

**Principle demonstrated:** Don't assume the closest-looking existing flag is the right one to reuse — trace what it actually protects before mirroring it. `RitualCompletedAt` and `HasEnded` look like they'd answer the same "is this block done" question, but they're genuinely different concepts (one about Session linkage, one about time), and reusing the wrong one would have quietly moved the UI's known-narrow lock into the Application layer instead of fixing it. Business rules belong in the Application layer, not the UI: the check now lives in `DeletePlannedBlockValidator`, where no future screen or code path can bypass it by forgetting to check a ViewModel flag.

**Follow-up closure (same day):** fixing the Application layer left `CanDeleteFromForm => IsEditing` in the UI still not *referencing* the real rule — it just happened to no longer matter as much, since the backend would now reject a wrongful delete either way. Rather than leave that gap open (a disabled-looking button is much better UX than a click-then-error, and a UI-side copy of the rule is exactly the pattern that caused this whole gap), `PlannedBlockDto` gained a `HasEnded` field computed once by `GetPlannedBlocksForDayQueryHandler` via the same `PlannedBlock.HasEnded(now)` the validator calls, and `PlannerPageViewModel.CanDeleteFromForm` was rewritten to compose that referenced value with the live `ISessionStateService` comparison — never deriving the verdict itself. This is the general fix, not a one-off: enforcement lives in the Application layer; when the UI also needs to predict a rule for UX (disabling a button before the round-trip), it must reference the same computed answer, never maintain a second, independently-reasoned copy.

## Gap 10 — Where Should a Block-Spec DTO Shared by Two Slices Actually Live? *(closed, three attempts)*

**The gap:** Building the Extend slice, `SealNenContractBlockSpec` (a plain `{ PresetId, Start, End, IsFocus, Title? }` record used as a command field, not a `PlannedBlock` entity) needed to be reused by `ExtendNenContractCommand` too, rather than declaring an identical record twice. Where it should live took three attempts to get right.

**Attempt 1 — shared, wrong location:** Renamed to `NenContractBlockSpec` and moved into the parent `UseCases/NenContracts/` folder. Justified in the moment as "pure data, no behavior, no drift risk." Wrong because that justification was invented on the spot rather than checked against precedent, and it broke `MODULE_STANDARDS.md`'s "every use case lives in its own folder with exactly four files" for both `Seal/` and `Extend/` at once.

**Attempt 2 — duplicated, matching the four-file rule but nothing else:** Reverted to two independent copies, `SealNenContractBlockSpec` in `Seal/` and `ExtendNenContractBlockSpec` in `Extend/`. This restored "no shared base classes for commands or results... copy the pattern, don't abstract it" — but produced a different, equally visible problem: both slice folders now sat at *five* files instead of four, the opposite direction from Attempt 1's violation but still not matching the stated convention. Framed at the time as "vertical slices don't share command-adjacent types" — a rule this project had never actually stated that broadly.

**Attempt 3 — the actual precedent, found by checking rather than assuming:** `StartSessionCommand.BreakSettings` is typed as `BreakSettingsDto`, and that type lives in `NenFocus.Application/DTOs/BreakSettingsDto.cs` — a shared folder, not inside `UseCases/Sessions/StartSession/`. `PostSessionDto`, `SessionDto`, `PlannedBlockDto`, `RitualRequirementChange` all follow the same pattern: supporting shapes referenced by commands or queries live in `DTOs/`, kept out of any single slice's own four files. The "exactly four files" rule and "no `BaseCommand`" rule were never in tension with this — they're about not building an inheritance hierarchy for the CQRS scaffolding itself (Command/Handler/Result/Validator), not about forbidding a shared supporting DTO. `NenContractBlockSpec` moved to `NenFocus.Application/DTOs/NenContractBlockSpec.cs`; both per-slice copies deleted; both `Seal/` and `Extend/` are back to exactly four files each.

**Principle demonstrated:** Two lessons, not one. First (same as ever): ask what's actually being protected before choosing to share or not share — a business rule that could drift into disagreement is worth centralizing (see `DailyFloorPolicy.RestDayExceptions`/`PerDayExceptionsFrom`, built the same session, never reverted, because it centralizes real domain knowledge); a data-only DTO carries no such risk either way. Second, learned the hard way across two wrong attempts: when a codebase convention seems to force an awkward choice, look for existing precedent that already answers the question before inventing a resolution — `BreakSettingsDto` had been sitting in `DTOs/` the whole time, quietly demonstrating the exact pattern both earlier attempts were missing.

## Gap 11 — The 5-Minute Grace Period Was Documented, Never Implemented *(closed)*

**The gap:** Discovered while starting the deficit/completed-hours query slice (2026-07-08). `DOMAIN_DICTIONARY.md` and the Technical mapping table both describe `FocusBlockOutcomeClassifier.Classify` as treating a ritual completed within 5 minutes of `scheduledStart` as `CompletedOnTime`. The shipped code had no such window: `if (completedAt <= scheduledStart) return CompletedOnTime;` was a strict, zero-tolerance check — a ritual completed even one second late was already `StartedLate`. The existing test suite confirmed this wasn't an oversight in the tests either: no test exercised anything near the grace boundary. This was documented intent that was never built, sitting in an already-shipped domain service — unlike most gaps this session, which were caught *before* the code shipped, this one had been live (though not yet consumed by any Application-layer feature) with no test ever catching the discrepancy.

**The closure:** Added `FocusBlockOutcomeClassifier.GracePeriodMinutes` (`const int = 5`) and fixed `Classify` to check `completedAt <= scheduledStart.AddMinutes(GracePeriodMinutes)`. Also built the second half of the documented-but-missing behavior in the same pass: `IFocusBlockOutcomeClassifier` gained `CreditedFocusMinutes(scheduledStart, scheduledEnd, ritualCompletedAt, actualElapsedMinutes)` — the "completed-hours formula" the docs already described but that didn't exist as code anywhere. It returns the full scheduled duration when within grace, `actualElapsedMinutes` otherwise. Both methods share the one `GracePeriodMinutes` constant, so `Classify`'s outcome and `CreditedFocusMinutes`'s crediting can never disagree about what "within grace" means — a single source of truth for a rule now needed in two places, the same discipline as `PlannedBlock.HasEnded` and `NenContract.IsDueForActivation`/`IsDueForCompletion` earlier this session.

**Principle demonstrated:** A design gap doesn't stop being real just because the code compiles and the existing tests pass — `FocusBlockOutcomeClassifier` had shipped, with tests, missing a documented feature nobody had written a test to catch (because nobody had written the feature). Checking a domain service's actual behavior against its own documentation before building on top of it — not just before building it the first time — is what caught this. If the completed-hours query had been built against the classifier as it stood, either the grace period would have silently never applied to Daily Floor crediting, or the query would have needed to duplicate the "within grace" check itself, reintroducing the two-implementations-of-one-rule risk this session had already fixed twice elsewhere.

## Gap 12 — CreatePlannedBlock Crashed at Runtime: `INenContractRepository` Was Never Registered *(closed)*

**The gap:** The Work Hours guard (CreatePlannedBlock/UpdatePlannedBlock contract-guards slice, step 3) added `INenContractRepository` as a required constructor parameter on `CreatePlannedBlockValidator` and `UpdatePlannedBlockValidator`. At the time, this was assessed as "currently inert in the running app" — correct about behavior, wrong about reachability. `INenContractRepository` had no Infrastructure registration at all (Task #11, EF Core persistence, was and is still pending), and FluentValidation validators are constructed eagerly by DI when a command runs — every constructor parameter must resolve, whether or not the method that uses it is ever called. The result was a hard crash (`InvalidOperationException: Unable to resolve service for type 'INenContractRepository'`) on **every** `CreatePlannedBlockCommand`, including ordinary blocks with no `ContractId` at all — reported by the architect while trying to create a planned block through the running app, the first time any of this session's Nen Contract Application-layer work was actually exercised outside a test double.

**Why the earlier self-audit missed it:** "Inert" was the wrong word for what was actually true. The guard's *logic* was correctly inert (no contract ever has a non-null `WorkHoursPolicy`, so the check always passes when reached) — but *reachability* was never inert, because DI resolves the whole constructor graph up front. The distinction between "this branch never does anything" and "this dependency can never be constructed" wasn't tested, because this entire session's work had only ever been exercised through NSubstitute mocks, never through the live composition root.

**The closure:** Added `NullNenContractRepository` (`Infrastructure/Persistence/Repositories/`) — every lookup returns null/empty, every write is a no-op. This isn't a workaround masquerading as a fix: there is currently no reachable UI path that creates a `NenContract` at all, so "no contract exists" is simply true, and every caller of `INenContractRepository` across this session's work was already written to treat a missing contract as the correct non-blocking fallback (checked one by one before writing the stub, not assumed). Registered in `NenFocus.Infrastructure/DependencyInjection.cs` alongside the other repositories, with a doc comment marking it for deletion once Task #11 lands.

**Principle demonstrated:** "Inert" and "unreachable via DI" are not the same claim, and only one of them was actually verified. Application-layer work built and tested exclusively against mocks can still break the composition root the moment it's exercised for real — a gap the test suite structurally cannot catch, because the test suite never constructs the real `IServiceCollection`. This is the same category of risk `DESIGN_GAP_HISTORY.md` Gap 11 flagged for behavior ("shipped, passed tests, missing a documented feature") applied to wiring instead of logic.

## Gap 13 — Update Handlers Constructed Value Objects Unprotected; One Could Have Silently Committed Partial Mutations *(closed)*

**The gap:** Self-audit of the newly-built `CreateContractPresetCommandHandler`/`UpdateContractPresetCommandHandler` (Contract Preset CRUD slice) found both constructing `DailyFloor`/`WorkHours` and calling the entity factory/mutator unprotected — any out-of-range value would throw an uncaught `ArgumentException` instead of a clean `Result.Fail(...)`. The validators normally prevent this, but that's a runtime DI-composition guarantee, not one the type system proves; this codebase's own tests already call handlers directly, bypassing validation. Checking whether this was a new mistake or an inherited one found the same shape already present in `CreateBlockPresetCommandHandler` (unprotected `new BlockedApp(...)`/`new BlockedSite(...)` in a loop) and `DuplicateBlockPresetCommandHandler` (an explicit empty — not null — `NewName` skips the `??` default and reaches `BlockPreset.Create` unchanged). Both pre-date this session; `ContractPreset`'s handlers were written by deliberately mirroring `BlockPreset`'s CRUD shape, which is how the gap propagated forward into new code.

**The harder problem, found while designing the fix, not while looking for it:** `UpdateBlockPresetCommandHandler` couldn't be fixed with the same simple try/catch used for the three Create-shaped handlers. `TransactionalCommandHandler.HandleAsync` calls `_uow.CommitAsync(...)` **unconditionally** — it does not inspect the inner handler's `Result.Success` before committing. `UpdateBlockPresetCommandHandler`'s `preset` is loaded via `GetByIdAsync` and is therefore already tracked by the same `DbContext` instance *before* any mutation begins. The original code applied `Rename`, then looped removing and re-adding `BlockedApp`/`BlockedSite` entries — a sequence of separate mutating calls, not one atomic operation. Wrapping that whole sequence in one try/catch would not have been a fix: if entry 3 of 5 in a loop threw, entries 1 and 2 would already be mutated on the tracked entity, the handler would return `Fail`, and `CommitAsync` would persist the partial mutation anyway — turning "reports failure" into "silently corrupts data while reporting failure," strictly worse than the original uncaught crash (which at least unwound the stack before `CommitAsync` was ever reached).

**The closure:** For the three Create-shaped handlers (`CreateContractPreset`, `UpdateContractPreset` — whose `ContractPreset.Update` is a single atomic validate-then-assign method, not a sequence — `CreateBlockPreset`, `DuplicateBlockPreset`), nothing is added to the tracked `DbContext` until the final explicit `AddAsync` call, so a simple try/catch around construction is sufficient and safe. `UpdateBlockPresetCommandHandler` needed a real restructure: `BlockedApp`/`BlockedSite` instances are now constructed into local lists first, and `Rename` (itself already guard-then-assign, so safe to include) runs in the same try block — all before `preset` is touched at all. Only once every fallible construction has already succeeded do the guaranteed-safe mutations (`ChangeWebsiteFilterType`, `ChangePresetType`, the pre-validated add/remove loops) run. This mirrors a discipline `NenContract.Seal`/`Extend` already followed correctly — validate the entire operation first, mutate second, never interleaved — which turned out to be *why* their existing try/catch blocks were already safe, not an accident.

**Principle demonstrated:** A defensive try/catch around a mutating call is not automatically a fix — it can be actively worse than doing nothing, if anything under commit-on-completion semantics can partially mutate before throwing. The controlling question before wrapping any exception handler around entity mutation in this codebase is not "can this throw" but "has anything already been tracked or mutated by the time it does." Regression tests for the `Update` fix assert the entity is **completely unchanged** after a rejected command, not just that the result reports failure — asserting only `Success == false` would have let a partial-mutation regression pass silently.

## Gap 14 — SessionStateService (Singleton) Captured Scoped Repositories Directly *(closed)*

**The gap:** Found by `CompositionRootTests` (added proactively alongside Task #14, itself motivated by Gap 12's lesson that DI wiring needs to be checked against the real container, not assumed correct). Turning on `ValidateScopes = true` — a stricter check than Gap 12's fix required — failed immediately: `SessionStateService` (registered `AddSingleton`) took `ISessionRepository` and `IBlockPresetRepository` (both `AddScoped`) directly as constructor parameters. A Singleton resolves its dependencies exactly once, at first use, and holds them for the app's entire lifetime — so this would have pinned one `NenFocusDbContext` instance alive permanently, captured by a service that only ever needed it for one call (`InitializeAsync`, dispatched once at startup).

**Why this had shipped without anyone noticing:** the same reason Gap 12 did — every existing test for `SessionStateService` constructs it directly with NSubstitute mocks, never through the real `IServiceCollection`. Nothing before `CompositionRootTests` existed had ever attempted to build the real composition root at all, let alone with scope validation on.

**The closure:** `SessionStateService` already had two working siblings solving this exact problem correctly — `ActiveSessionMonitor` (`AutoEndAsync`/`AutoResumeBreakAsync`) and `ScheduledEnforcementService`'s heartbeat both take `IServiceScopeFactory` in their constructor and resolve their scoped dependencies from a fresh `CreateScope()` per operation, never capturing them directly. `SessionStateService` was the one service in this family that didn't follow its own codebase's already-established pattern. Fixed by bringing it in line: constructor now takes only `IServiceScopeFactory`; `InitializeAsync` creates one scope, resolves `ISessionRepository`, `IBlockPresetRepository`, and the sweep command handler from it, and disposes the scope when the method returns. `ISessionStateService`'s public interface — `InitializeAsync()`, `ActiveSession`, `SetActive`, `SetRitualRequired`, `Clear`, all three events — is completely unchanged; every calling ViewModel is unaffected. The test file was updated to build a real minimal `ServiceCollection`/`ServiceProvider` from the same NSubstitute mocks (registered as singleton instances) to obtain a genuine `IServiceScopeFactory`, rather than hand-mocking the `IServiceScope`/`IServiceProvider` resolution chain.

**Principle demonstrated:** When a lifetime mismatch is found, check whether the codebase has already solved it correctly somewhere else before designing a new fix — `ActiveSessionMonitor` and `ScheduledEnforcementService` had already established the right pattern; the fix was to make `SessionStateService` consistent with its own siblings, not to invent anything new. Also: `ValidateScopes = true` is a strictly stronger check than `ValidateOnBuild` alone, and costs nothing extra to enable in a smoke test — there is no reason to leave it off once nothing in the graph fails it.
