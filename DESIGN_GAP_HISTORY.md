# NenFocus — Design Gap Closure History

A running record of gaps that were identified, interrogated, and closed. Each entry is a concrete demonstration of the Design Gap Protocol working correctly.

**This is reference material, not constitution.** It does not need to be read at the start of every session. Consult it when:
- A new gap looks similar to a previously-closed one — check whether the same principle applies.
- You need to understand *why* the codebase looks the way it does today (e.g. why `BlockedAttempt` is a fact table and not JSON on `Session`).
- You're inducting a new collaborator on how design decisions are made on this project.

For active design tension, see the **Open Gaps** section in `ARCHITECT_GOVERNANCE.md`.

## Gap 1 — Enforcement Gap on Session Start *(closed)*

**The gap:** `StartSessionCommandHandler` saved the session and updated UI state but never applied OS-level enforcement. `SessionStartedEventHandler` had been stripped of its enforcement call and only sent a notification. Sessions could start with no blocking in effect. The bug was silent — no test caught it because `IEnforcementService` was never injected into the handler.

**The closure:** Event-driven chain restored. `Session.Start()` raises `SessionStartedEvent` internally → handler dispatches via `PublishAllAsync(session.DomainEvents)` → `SessionStartedEventHandler` computes the current policy slice via `ComputeActivePolicySliceQuery` and calls `IEnforcementService.ApplyPolicyAsync`. `IEnforcementService` remains a simple two-method interface; the orchestration complexity lives in the event handler. Three new tests in `SessionStartedEventHandlerTests` now guard this path permanently.

**Principle demonstrated:** Deep Modules — `IEnforcementService` stayed narrow. The event handler became the "orchestrator" layer, not the command handler and not the infrastructure service.

## Gap 2 — BlockPresetType Promotion: From Leaky Boolean to Domain Enum *(closed)*

**The gap:** The system could not distinguish between a Focus Block (which must trigger the Ritual) and a Background Block (which enforces silently) after computing a policy slice. A boolean `RequiresRitual` flag would have been the shallow solution — a boolean with no domain meaning that every caller must interpret differently.

**The closure:** `PolicySliceDto` now carries `ActiveBlockPresetType (BlockPresetType?)` — a domain enum from `NenFocus.Domain.Enums`. `ComputeActivePolicySliceQueryHandler` sets it to the type of the highest-priority active planned block (Ritual > Background). `ScheduledEnforcementService` reads this field and calls `SetRitualRequired(true)` only when `ActiveBlockPresetType == Ritual` with no active session. The decision is expressed once, in the domain's language, in one place.

**Principle demonstrated:** Ubiquitous Language — the difference between a Focus Block and a Background Block was already a domain concept. Promoting it to the `PolicySliceDto` made the contract self-documenting and eliminated a class of future bugs where callers would have needed to re-derive the distinction themselves.

**Side fix included:** Blocklist mode in `ComputeActivePolicySliceQueryHandler` was previously broken — `BlockedSites` was always an empty set (missing `case WebsiteFilterType.Blocklist:`). Fixed in the same slice. The browser extension was receiving an empty blocklist for all Blocklist-mode presets.

## Gap 3 — Spontaneous Sessions, Insights Architecture, and the Block Hierarchy *(closed)*

**The gap:** The domain had no way to distinguish a planned Session from a manually-started one, making the planned Insights page impossible to build correctly. Additionally, the block hierarchy was being reconsidered — a proposed `InstantFocusBlock` class and a rename to Focus Block / Background Block were both under evaluation. The `BlockedAttempt` entity was also being considered for conversion to a Value Object.

**The interrogation revealed:**
- Insights requires a unified calendar view showing Focus Blocks (completed and missed), Background Blocks, and Spontaneous Sessions
- Insights requires analytics including session quality comparison between Planned and Spontaneous sessions and block preset follow-through rates
- Background Blocks must appear in Insights using scheduled time as canonical truth regardless of machine state
- A Focus Block where the user missed the Ritual must appear in Insights as "missed" — the `FocusBlock` row is the record
- A Spontaneous Session that did not complete the Ritual must not be saved anywhere
- The ONLY manual path to enforcement is through the full Nen Ritual — this is a product invariant, not a validation rule
- Browsing time tracking on all websites is a desired future feature requiring extension changes
- Planned Period / Strict Mode is a desired future feature

**The closure:**
- `InstantFocusBlock` rejected: a Spontaneous Session is not a Block. It has no calendar identity, no life outside its Session, and no state transitions. Creating an entity to make the schema look symmetric would violate DDD and fail the Deep Module test.
- `BlockedAttempt` kept as append-only fact table: burying it in JSON would make Insights analytics queries require full in-memory deserialisation across hundreds of sessions.
- `FocusBlock` renamed to `FocusBlock`, `PassiveBlock` renamed to `BackgroundBlock`, `BlockPresetType` enum values updated to `Ritual` and `Background`. Rename is complete at every layer: entity, enum, DTO, handler, service, dictionary. **Correction (2026-08-18):** the `Focus`→`Ritual` half of this rename does not match the live codebase — `BlockPresetType` is `{ Focus, Background }` today, confirmed directly against `NenFocus.Domain/Enums/BlockPresetType.cs`. Either it was reverted after this gap closed or never fully landed; this entry is kept as-written for historical accuracy (the closure record reflects what was decided/attempted at the time) but should not be trusted as a description of current code — see `TECHNICAL_SPEC_INFRA.md`'s Done list for the corrected, current enum shape.
- `Session.Origin (SessionOrigin)` added: explicit `Spontaneous` / `Planned` tag. Does not rely on null-checking `OriginatingBlockId` so it remains unambiguous when future origin types are added.
- `Session.OriginatingBlockId (Guid?)` added: closes the known gap from `TECHNICAL_SPEC_INFRA.md`. Written by `StartSessionCommandHandler` when a Focus Block triggered the session.
- `FocusBlock.RitualCompletedAt (DateTime?)` added: allows Insights to detect missed blocks from the entity alone without a join to Session.
- `GetInsightsCalendarQuery` stubbed: single query handler that unifies three sources behind one interface. The ViewModel never touches the individual tables. **Correction (2026-08-18):** no such query, handler, or DTO exists in the codebase today — the Insights page is currently a static "Coming soon" placeholder with no Application-layer code behind it. Whatever stub existed at closure time has since been removed; see `TECHNICAL_SPEC_INFRA.md`'s Not Yet Built table for current status.

**Principle demonstrated:** The asymmetry between Planned and Spontaneous in the schema (Block + Session vs Session alone) is correct and intentional. It reflects a real asymmetry in the domain — a planned block exists before and independently of any Session; a spontaneous one does not. Hiding this asymmetry with a synthetic entity would be lying with code. `GetInsightsCalendarQuery` is the correct place to unify the three sources — complexity is hidden behind a narrow interface, not erased from the domain.

## Gap 4 — Domain Events Raised by Handlers, Not Entities; `BlockedAttemptsSerialized` Contradiction *(closed)*

**The gap:** Two DDD violations were found during a doc/code audit. First, domain events (`SessionStartedEvent`, `SessionEndedEvent`, `BreakStartedEvent`, `BlockPresetCreatedEvent`) were being constructed and published directly inside command handlers, not inside the entities and aggregates that own the state transitions. The governance states "domain events: raised inside entities/aggregates" — the code violated this. Second, `EndSessionCommandHandler` and `StartBreakCommandHandler` were calling `IEnforcementService` and `INotificationService` directly, bypassing the event handler chain the governance explicitly requires. Third, `Session.BlockedAttemptsSerialized` persisted blocked attempt data as a JSON blob on the Session row — contradicting the Gap 3 decision to keep `BlockedAttempt` as an append-only fact table.

**The closure:**
- `Session` and `BlockPreset` now own a private `_domainEvents` list. Each state-transition method (`Start()`, `StartBreak()`, `Complete()`) appends the appropriate event internally. Handlers call `entity.DomainEvents` and dispatch via `IDomainEventPublisher.PublishAllAsync`, then clear with `entity.ClearDomainEvents()`. The handler no longer knows which events a domain operation produces.
- `EndSessionCommandHandler` and `StartBreakCommandHandler` had their `IEnforcementService` and `INotificationService` injections removed. All enforcement and notification side-effects now flow exclusively through `SessionEndedEventHandler` and `BreakStartedEventHandler`. `BreakStartedEventHandler` also gained the missing `IEnforcementService.RemoveEnforcementAsync` call it lacked.
- `Session.BlockedAttemptsSerialized` and `Session.SetBlockedAttempts()` removed. `BlockedAttempt` rows (append-only, keyed by `SessionId`) are the sole persistence path for attempt data. Migration `20260512000001_RemoveBlockedAttemptsSerialized` drops the now-redundant `BlockedAttempts` column from the `Sessions` table.

**Principle demonstrated:** Deep Modules and the governance rule "commands do not directly call enforcement or notifications — event handlers do." The command handlers are now thin: validate → mutate domain → save → publish events → return result. All side-effects (enforcement, notifications) are encapsulated in event handlers with narrow, self-documenting interfaces.

## Gap 5 — Persistence Boundary: Per-Repository SaveChanges vs. Unit of Work *(closed)*

**The gap:** Repositories used to call `SaveChangesAsync` internally on each `SaveAsync`. `StartSessionCommandHandler` therefore performed two separate database round-trips when a Focus Block triggered a session: one to stamp `FocusBlock.RitualCompletedAt`, one to insert the new `Session` row. If the second save failed, the database would be left with a Focus Block marked completed but no corresponding Session — violating the invariant that a completed Focus Block always has an associated Planned Session. The same fragmentation pushed domain-event dispatching out to every handler, each of which had to remember to call `PublishAllAsync` and `ClearDomainEvents` in the right order relative to `SaveAsync` — a Deep Modules violation.

**The closure:** Repositories (`BlockPresetRepository`, `PlannedBlockRepository`, `SessionRepository`) no longer call `SaveChangesAsync` themselves — `SaveAsync`/`AddAsync`/`UpdateAsync` only register changes with the change tracker. `EfCoreUnitOfWork.CommitAsync()` is the sole place `SaveChangesAsync` is called: it walks the change tracker for `AggregateRoot` entries with pending `DomainEvents`, calls `SaveChangesAsync`, then publishes each aggregate's events via `IDomainEventPublisher.PublishAllAsync` and clears them. `TransactionalCommandHandler<TCommand, TResult>` wraps every command handler in DI and calls `_uow.CommitAsync()` after the inner handler returns — so a Planned Session's `FocusBlock.MarkRitualCompleted()` stamp and the new `Session` row now commit atomically in one `SaveChangesAsync` call, and no handler has to remember the "save, then publish, then clear" sequence itself.

**Confirmed via `NenFocus.Tests`:** `EfCoreUnitOfWorkTests` (persists pending changes, publishes only aggregates with pending events, clears events after publishing) and `TransactionalCommandHandlerTests` (inner handler always runs before `CommitAsync`, and `CommitAsync` still runs even when the inner handler returns a failure result).

**Principle demonstrated:** Deep Modules — the "save, then publish domain events, then clear them" rule now lives in exactly one place (`EfCoreUnitOfWork`) instead of being repeated in every command handler, and the atomicity invariant (all-or-nothing per command) is enforced structurally by the decorator rather than by convention.

## Gap 6 — NenContract's Single-Scalar Daily Floor Contradicted Its Own Documented Design *(closed)*

**The gap:** Discovered while starting the Nen Contract Application layer (2026-07-07). `DOMAIN_DICTIONARY.md` documented Simple contracts as having a *per-day* floor ("Monday with 2 planned hours has a floor of 2, Tuesday with 3 has a floor of 3") and rest days as "not floor-checked... skipped entirely." But the already-built `NenContract` aggregate stored exactly one scalar `DailyFloor` for the whole contract, and `Seal()`'s validation loop iterated *every* day in range — including days absent from the planned-hours map, which defaulted to `0` and were still checked against the single floor. Neither documented behavior was actually buildable: a Simple contract could never have a varying per-day floor, and an Advanced contract's explicitly-designated rest day would still throw at Seal if the contract's floor was above zero.

**The closure:** `NenContract.DailyFloor (DailyFloor)` replaced with `NenContract.DailyFloorPolicy (DailyFloorPolicy)` — a new value object deliberately mirroring the already-proven `WorkHoursPolicy` shape: `{ DailyFloor? Default, IReadOnlyDictionary<DateOnly, DailyFloor?> PerDayExceptions }`, resolved per day via `.For(date)`. A day resolving to `null` (no exception and no default, or an explicit `null` exception) is a true rest day. `Seal()`'s loop now resolves the floor per day and `continue`s past rest days instead of defaulting them to a zero-hour check. `IsDayMet` and `Extend` gained a `DateOnly date` parameter for the same reason — `Extend` also gained an optional `dailyFloorOverridesForNewDays` parameter so newly-added days can carry their own floors, merged into the policy's `PerDayExceptions` going forward. Simple contracts populate only `PerDayExceptions` (no `Default`); Advanced contracts set a fixed `Default` plus `PerDayExceptions` for explicit rest days — both are now real, distinct configurations rather than a single number pretending to support both.

**Confirmed via `NenFocus.Tests`:** `NenContractTests` rewritten for the new shape (39 tests, all passing), including new cases for rest-day-via-exception at Seal, per-day-varying floors at Seal, `IsDayMet` returning different verdicts for different days on the same contract, and `Extend` merging per-day floor overrides for newly added days.

**Principle demonstrated:** Surface drift, don't fix silently — the contradiction between documented behavior and shipped domain code was found before any Application-layer code was written on top of the old shape, and was brought to the architect as a choice (rebuild to per-day vs. keep the scalar and let Simple contracts lose their defining behavior) rather than resolved unilaterally. Reuse over invention — the fix is structurally identical to `WorkHoursPolicy`, an already-validated pattern for "one default, exceptions per day," rather than a new bespoke shape.

## Gap 7 — Broken Contract Cleanup: Delete-or-Unlink Choice Dropped, Event Handler Rejected in Favor of One Atomic Command *(closed)*

**The gap:** The original design (recorded when the Nen Contract domain shape was interrogated) called for `NenContractBrokenEvent` to be handled by an Application-layer event handler that would "prompt the user" with a choice — delete all upcoming blocks, or unlink them (`ContractId → null`) and keep them on the calendar ungoverned. Building the Break slice (2026-07-07) surfaced two problems with this as written: (1) an `IDomainEventHandler<NenContractBrokenEvent>` cannot literally show a UI prompt without the Application layer depending on UI types, which the architecture forbids; and (2) even once resolved into "the event handler signals a state service, the UI reacts, then dispatches a follow-up command," that shape is a four-hop pass-through chain (event → handler → state service → ViewModel → follow-up command) for something that, on inspection, has exactly one real trigger: a direct, synchronous user button click. There is no scenario in the current design where a contract breaks without the UI already knowing.

**The closure:** The architect reconsidered the underlying product decision first — does "unlink and keep the schedule" earn its complexity at all? Conclusion: a contract only reaches `Break()` if `AllowCancellation` was set at Seal, already a deliberate, rare escape hatch; someone using it is very likely abandoning the whole plan, not fine-tuning it. Delete-only was chosen, dropping the choice entirely. That in turn removed the need for a decision-relay chain: `BreakNenContractCommand` now does everything in one atomic command — calls `NenContract.Break(now)`, saves, then deletes every block linked to the contract for which the new `PlannedBlock.HasEnded(now)` returns `false`. No event handler was built for `NenContractBrokenEvent`; the event still fires (raised inside `Break()`, published automatically by `EfCoreUnitOfWork` per Gap 5) and remains available for a future non-interactive reaction, but nothing forces a consumer to exist today — the same "deliberately silent" posture already accepted for `SessionMissedEvent`.

**Two smaller reuse checks along the way:**
- `PlannedBlock.HasEnded(DateTime asOf) => End < asOf` was added as a named entity predicate — mirroring `IsActive` and the `IsDueForActivation`/`IsDueForCompletion` pair added to `NenContract` in the same work session — rather than inlining `block.End < now` ad hoc inside the handler.
- Before writing the delete loop, `DeletePlannedBlockCommandHandler` was checked for hidden business rules; it turned out to be a bare `_blocks.DeleteAsync(...)` call with no logic behind it. `BreakNenContractCommandHandler` therefore calls the repository directly rather than composing through that command — composing would have added a hop with nothing behind it, the same defect just ruled out for the rejected event-handler design.

**Principle demonstrated:** Domain events exist to decouple a fact from reactions that don't share its calling context — not to relay a signal back to the exact place that already has it. Atomicity over choice-then-follow-up: one command doing both the status transition and the related-aggregate cleanup (mirroring `StartSessionCommandHandler`'s established multi-entity commit pattern from Gap 5) means no "broken but not yet resolved" state can ever be persisted, the same reasoning already applied to Seal's atomicity. And: check whether a method you're about to compose through actually does anything before assuming composing through it is the safer choice — sometimes directness is correct, not a shortcut.

## Gap 8 — Block Preset Lock Refined to Add-Only; Contract Deletion Guard Found Already Built *(closed)*

**The gap:** Two things surfaced together while auditing protection around a `BlockPreset` that's currently in use. First, `UpdateBlockPresetValidator` rejected *any* edit outright whenever a preset was locked (in use by an active session, or referenced by a future `PlannedBlock`) — matching the documented rule at the time ("a preset is locked... no edits are permitted"). The architect judged this too blunt: you should be able to strengthen a live block (add more apps/sites) without waiting for it to free up, you just shouldn't be able to weaken it (remove entries) or change its identity (rename, retype, change filter mode) while it's committed. Second, a task on the open backlog ("Block-preset deletion guard: reject if preset referenced by active/scheduled contract or future planned block") assumed this needed building for the Nen Contract case specifically.

**The closure:** `UpdateBlockPresetValidator` was rewritten: locked + an add-only change (new `BlockedApps`/`Websites` are supersets of the current ones, and `Name`/`WebsiteFilterType`/`PresetType`/`Tags` all unchanged) → valid. Locked + anything else → invalid, with a message explaining why. Not locked → unrestricted, as before. `DeleteBlockPresetValidator` was left untouched — deletion stays fully blocked while locked, no add-only carve-out makes sense for a delete. Investigating the second item found it was **already satisfied**: `HasFutureBlocksForPresetAsync` (used by both validators) queries all `PlannedBlock`s by preset ID with `End > now` and has never filtered on `ContractId` — a block scheduled under a Nen Contract is just a `PlannedBlock` like any other in that table, so it was already covered. No separate contract-aware guard was needed; the backlog task was closed as already-done rather than built from scratch.

**Principle demonstrated:** Before implementing a backlog item, check whether the existing code already satisfies it — `HasFutureBlocksForPresetAsync`'s type-agnostic query meant the "contract case" was never actually a gap, just an unverified assumption. And: when relaxing a lock, relax exactly the dimension that was asked about (apps/sites, add-only) and leave every other dimension (name, type, filter mode, tags) under the original full lock — resist the urge to also loosen things nobody asked to loosen.

## Gap 9 — PlannedBlock Deletion Had No Application-Layer Protection At All *(closed)*

**The gap:** `DeletePlannedBlockCommandHandler` had exactly one line of logic — `await _blocks.DeleteAsync(...)` — no validation beyond "is the ID non-empty." The only thing stopping a user from deleting a currently-active or already-completed block was `PlannerPageViewModel.CanDeleteFromForm => IsEditing`, which is **not** gated by the same `IsBlockLocked` flag that already disables the Save button for that exact scenario. This was a live, reachable bug, not a hypothetical: opening a completed block or the active session's originating block in the Planner form and clicking Delete worked, with nothing stopping it, before this fix.

**A second, deeper issue surfaced while designing the fix:** the natural instinct was to mirror the UI's existing `IsEditingCompleted` flag, which is `FocusBlock.RitualCompletedAt.HasValue` — true only once a Session has actually been started from that block. Tracing what that flag actually protects (mid-session reschedule-safety, not historical-record-safety) showed it was the wrong predicate for deletion: a **missed** Focus Block (window closed, Ritual never completed) reads `RitualCompletedAt == null`, so mirroring that flag would leave missed blocks freely deletable — directly contradicting the Missed Session feature's own stated invariant that a missed block "is not deleted or altered... it remains the schedule record." Background Blocks have no Ritual concept at all, so the same flag is permanently `false` for them regardless of age, leaving every past Background Block — which Insights treats as "the complete record" for that entry — deletable forever too.

**The closure:** `DeletePlannedBlockValidator` gained two checks: the block must not be the active session's `OriginatingBlockId`, and `PlannedBlock.HasEnded(now)` must be false. `HasEnded` (added in Gap 7, for the Break slice's block cleanup) is defined once on the shared `PlannedBlock` base and answers "has this window closed" identically for both subtypes — deliberately broader than the UI's Ritual-specific flag, closing the missed-Focus-Block and past-Background-Block holes the narrower mirror would have left open. The existing `IsEditingCompleted`/Save-lock logic was left untouched — it answers a different, still-valid question (is a Session already tied to this exact block's current schedule) and was never wrong for that purpose.

**Principle demonstrated:** Don't assume the closest-looking existing flag is the right one to reuse — trace what it actually protects before mirroring it. `RitualCompletedAt` and `HasEnded` look like they'd answer the same "is this block done" question, but they're genuinely different concepts (one about Session linkage, one about time), and reusing the wrong one would have quietly moved the UI's known-narrow lock into the Application layer instead of fixing it. Business rules belong in the Application layer, not the UI: the check now lives in `DeletePlannedBlockValidator`, where no future screen or code path can bypass it by forgetting to check a ViewModel flag.

**Follow-up closure (same day):** fixing the Application layer left `CanDeleteFromForm => IsEditing` in the UI still not *referencing* the real rule — it just happened to no longer matter as much, since the backend would now reject a wrongful delete either way. Rather than leave that gap open (a disabled-looking button is much better UX than a click-then-error, and a UI-side copy of the rule is exactly the pattern that caused this whole gap), `PlannedBlockDto` gained a `HasEnded` field computed once by `GetPlannedBlocksForDayQueryHandler` via the same `PlannedBlock.HasEnded(now)` the validator calls, and `PlannerPageViewModel.CanDeleteFromForm` was rewritten to compose that referenced value with the live `ISessionStateService` comparison — never deriving the verdict itself. This is the general fix, not a one-off: enforcement lives in the Application layer; when the UI also needs to predict a rule for UX (disabling a button before the round-trip), it must reference the same computed answer, never maintain a second, independently-reasoned copy.

## Gap 10 — Where Should a Block-Spec DTO Shared by Two Slices Actually Live? *(closed, three attempts)*

**The gap:** Building the Extend slice, `SealNenContractBlockSpec` (a plain `{ PresetId, Start, End, IsFocus, Title? }` record used as a command field, not a `PlannedBlock` entity) needed to be reused by `ExtendNenContractCommand` too, rather than declaring an identical record twice. Where it should live took three attempts to get right.

**Attempt 1 — shared, wrong location:** Renamed to `NenContractBlockSpec` and moved into the parent `UseCases/NenContracts/` folder. Justified in the moment as "pure data, no behavior, no drift risk." Wrong because that justification was invented on the spot rather than checked against precedent, and it broke `MODULE_STANDARDS.md`'s "every use case lives in its own folder with exactly four files" for both `Seal/` and `Extend/` at once.

**Attempt 2 — duplicated, matching the four-file rule but nothing else:** Reverted to two independent copies, `SealNenContractBlockSpec` in `Seal/` and `ExtendNenContractBlockSpec` in `Extend/`. This restored "no shared base classes for commands or results... copy the pattern, don't abstract it" — but produced a different, equally visible problem: both slice folders now sat at *five* files instead of four, the opposite direction from Attempt 1's violation but still not matching the stated convention. Framed at the time as "vertical slices don't share command-adjacent types" — a rule this project had never actually stated that broadly.

**Attempt 3 — the actual precedent, found by checking rather than assuming:** `StartSessionCommand.BreakSettings` is typed as `BreakSettingsDto`, and that type lives in `NenFocus.Application/DTOs/BreakSettingsDto.cs` — a shared folder, not inside `UseCases/Sessions/StartSession/`. `PostSessionDto`, `SessionDto`, `PlannedBlockDto`, `RitualRequirementChange` all follow the same pattern: supporting shapes referenced by commands or queries live in `DTOs/`, kept out of any single slice's own four files. The "exactly four files" rule and "no `BaseCommand`" rule were never in tension with this — they're about not building an inheritance hierarchy for the CQRS scaffolding itself (Command/Handler/Result/Validator), not about forbidding a shared supporting DTO. `NenContractBlockSpec` moved to `NenFocus.Application/DTOs/NenContractBlockSpec.cs`; both per-slice copies deleted; both `Seal/` and `Extend/` are back to exactly four files each.

**Principle demonstrated:** Two lessons, not one. First (same as ever): ask what's actually being protected before choosing to share or not share — a business rule that could drift into disagreement is worth centralizing (see `DailyFloorPolicy.RestDayExceptions`/`PerDayExceptionsFrom`, built the same session, never reverted, because it centralizes real domain knowledge); a data-only DTO carries no such risk either way. Second, learned the hard way across two wrong attempts: when a codebase convention seems to force an awkward choice, look for existing precedent that already answers the question before inventing a resolution — `BreakSettingsDto` had been sitting in `DTOs/` the whole time, quietly demonstrating the exact pattern both earlier attempts were missing.

## Gap 11 — The 5-Minute Grace Period Was Documented, Never Implemented *(closed)*

**The gap:** Discovered while starting the deficit/completed-hours query slice (2026-07-08). `DOMAIN_DICTIONARY.md` and the Technical mapping table both describe `FocusBlockOutcomeClassifier.Classify` as treating a ritual completed within 5 minutes of `scheduledStart` as `CompletedOnTime`. The shipped code had no such window: `if (completedAt <= scheduledStart) return CompletedOnTime;` was a strict, zero-tolerance check — a ritual completed even one second late was already `StartedLate`. The existing test suite confirmed this wasn't an oversight in the tests either: no test exercised anything near the grace boundary. This was documented intent that was never built, sitting in an already-shipped domain service — unlike most gaps this session, which were caught *before* the code shipped, this one had been live (though not yet consumed by any Application-layer feature) with no test ever catching the discrepancy.

**The closure:** Added `FocusBlockOutcomeClassifier.GracePeriodMinutes` (`const int = 5`) and fixed `Classify` to check `completedAt <= scheduledStart.AddMinutes(GracePeriodMinutes)`. Also built the second half of the documented-but-missing behavior in the same pass: `IFocusBlockOutcomeClassifier` gained `CreditedFocusMinutes(scheduledStart, scheduledEnd, ritualCompletedAt, actualElapsedMinutes)` — the "completed-hours formula" the docs already described but that didn't exist as code anywhere. It returns the full scheduled duration when within grace, `actualElapsedMinutes` otherwise. Both methods share the one `GracePeriodMinutes` constant, so `Classify`'s outcome and `CreditedFocusMinutes`'s crediting can never disagree about what "within grace" means — a single source of truth for a rule now needed in two places, the same discipline as `PlannedBlock.HasEnded` and `NenContract.IsDueForActivation`/`IsDueForCompletion` earlier this session.

**Principle demonstrated:** A design gap doesn't stop being real just because the code compiles and the existing tests pass — `FocusBlockOutcomeClassifier` had shipped, with tests, missing a documented feature nobody had written a test to catch (because nobody had written the feature). Checking a domain service's actual behavior against its own documentation before building on top of it — not just before building it the first time — is what caught this. If the completed-hours query had been built against the classifier as it stood, either the grace period would have silently never applied to Daily Floor crediting, or the query would have needed to duplicate the "within grace" check itself, reintroducing the two-implementations-of-one-rule risk this session had already fixed twice elsewhere.

## Gap 12 — CreatePlannedBlock Crashed at Runtime: `INenContractRepository` Was Never Registered *(closed)*

**The gap:** The Work Hours guard (CreatePlannedBlock/UpdatePlannedBlock contract-guards slice, step 3) added `INenContractRepository` as a required constructor parameter on `CreatePlannedBlockValidator` and `UpdatePlannedBlockValidator`. At the time, this was assessed as "currently inert in the running app" — correct about behavior, wrong about reachability. `INenContractRepository` had no Infrastructure registration at all (Task #11, EF Core persistence, was and is still pending), and FluentValidation validators are constructed eagerly by DI when a command runs — every constructor parameter must resolve, whether or not the method that uses it is ever called. The result was a hard crash (`InvalidOperationException: Unable to resolve service for type 'INenContractRepository'`) on **every** `CreatePlannedBlockCommand`, including ordinary blocks with no `ContractId` at all — reported by the architect while trying to create a planned block through the running app, the first time any of this session's Nen Contract Application-layer work was actually exercised outside a test double.

**Why the earlier self-audit missed it:** "Inert" was the wrong word for what was actually true. The guard's *logic* was correctly inert (no contract ever has a non-null `WorkHoursPolicy`, so the check always passes when reached) — but *reachability* was never inert, because DI resolves the whole constructor graph up front. The distinction between "this branch never does anything" and "this dependency can never be constructed" wasn't tested, because this entire session's work had only ever been exercised through NSubstitute mocks, never through the live composition root.

**The closure:** Added `NullNenContractRepository` (`Infrastructure/Persistence/Repositories/`) — every lookup returns null/empty, every write is a no-op. This isn't a workaround masquerading as a fix: there is currently no reachable UI path that creates a `NenContract` at all, so "no contract exists" is simply true, and every caller of `INenContractRepository` across this session's work was already written to treat a missing contract as the correct non-blocking fallback (checked one by one before writing the stub, not assumed). Registered in `NenFocus.Infrastructure/DependencyInjection.cs` alongside the other repositories, with a doc comment marking it for deletion once Task #11 lands.

**Principle demonstrated:** "Inert" and "unreachable via DI" are not the same claim, and only one of them was actually verified. Application-layer work built and tested exclusively against mocks can still break the composition root the moment it's exercised for real — a gap the test suite structurally cannot catch, because the test suite never constructs the real `IServiceCollection`. This is the same category of risk `DESIGN_GAP_HISTORY.md` Gap 11 flagged for behavior ("shipped, passed tests, missing a documented feature") applied to wiring instead of logic.

## Gap 13 — Update Handlers Constructed Value Objects Unprotected; One Could Have Silently Committed Partial Mutations *(closed)*

**The gap:** Self-audit of the newly-built `CreateContractPresetCommandHandler`/`UpdateContractPresetCommandHandler` (Contract Preset CRUD slice) found both constructing `DailyFloor`/`WorkHours` and calling the entity factory/mutator unprotected — any out-of-range value would throw an uncaught `ArgumentException` instead of a clean `Result.Fail(...)`. The validators normally prevent this, but that's a runtime DI-composition guarantee, not one the type system proves; this codebase's own tests already call handlers directly, bypassing validation. Checking whether this was a new mistake or an inherited one found the same shape already present in `CreateBlockPresetCommandHandler` (unprotected `new BlockedApp(...)`/`new BlockedSite(...)` in a loop) and `DuplicateBlockPresetCommandHandler` (an explicit empty — not null — `NewName` skips the `??` default and reaches `BlockPreset.Create` unchanged). Both pre-date this session; `ContractPreset`'s handlers were written by deliberately mirroring `BlockPreset`'s CRUD shape, which is how the gap propagated forward into new code.

**The harder problem, found while designing the fix, not while looking for it:** `UpdateBlockPresetCommandHandler` couldn't be fixed with the same simple try/catch used for the three Create-shaped handlers. `TransactionalCommandHandler.HandleAsync` calls `_uow.CommitAsync(...)` **unconditionally** — it does not inspect the inner handler's `Result.Success` before committing. `UpdateBlockPresetCommandHandler`'s `preset` is loaded via `GetByIdAsync` and is therefore already tracked by the same `DbContext` instance *before* any mutation begins. The original code applied `Rename`, then looped removing and re-adding `BlockedApp`/`BlockedSite` entries — a sequence of separate mutating calls, not one atomic operation. Wrapping that whole sequence in one try/catch would not have been a fix: if entry 3 of 5 in a loop threw, entries 1 and 2 would already be mutated on the tracked entity, the handler would return `Fail`, and `CommitAsync` would persist the partial mutation anyway — turning "reports failure" into "silently corrupts data while reporting failure," strictly worse than the original uncaught crash (which at least unwound the stack before `CommitAsync` was ever reached).

**The closure:** For the three Create-shaped handlers (`CreateContractPreset`, `UpdateContractPreset` — whose `ContractPreset.Update` is a single atomic validate-then-assign method, not a sequence — `CreateBlockPreset`, `DuplicateBlockPreset`), nothing is added to the tracked `DbContext` until the final explicit `AddAsync` call, so a simple try/catch around construction is sufficient and safe. `UpdateBlockPresetCommandHandler` needed a real restructure: `BlockedApp`/`BlockedSite` instances are now constructed into local lists first, and `Rename` (itself already guard-then-assign, so safe to include) runs in the same try block — all before `preset` is touched at all. Only once every fallible construction has already succeeded do the guaranteed-safe mutations (`ChangeWebsiteFilterType`, `ChangePresetType`, the pre-validated add/remove loops) run. This mirrors a discipline `NenContract.Seal`/`Extend` already followed correctly — validate the entire operation first, mutate second, never interleaved — which turned out to be *why* their existing try/catch blocks were already safe, not an accident.

**Principle demonstrated:** A defensive try/catch around a mutating call is not automatically a fix — it can be actively worse than doing nothing, if anything under commit-on-completion semantics can partially mutate before throwing. The controlling question before wrapping any exception handler around entity mutation in this codebase is not "can this throw" but "has anything already been tracked or mutated by the time it does." Regression tests for the `Update` fix assert the entity is **completely unchanged** after a rejected command, not just that the result reports failure — asserting only `Success == false` would have let a partial-mutation regression pass silently.

## Gap 14 — SessionStateService (Singleton) Captured Scoped Repositories Directly *(closed)*

**The gap:** Found by `CompositionRootTests` (added proactively alongside Task #14, itself motivated by Gap 12's lesson that DI wiring needs to be checked against the real container, not assumed correct). Turning on `ValidateScopes = true` — a stricter check than Gap 12's fix required — failed immediately: `SessionStateService` (registered `AddSingleton`) took `ISessionRepository` and `IBlockPresetRepository` (both `AddScoped`) directly as constructor parameters. A Singleton resolves its dependencies exactly once, at first use, and holds them for the app's entire lifetime — so this would have pinned one `NenFocusDbContext` instance alive permanently, captured by a service that only ever needed it for one call (`InitializeAsync`, dispatched once at startup).

**Why this had shipped without anyone noticing:** the same reason Gap 12 did — every existing test for `SessionStateService` constructs it directly with NSubstitute mocks, never through the real `IServiceCollection`. Nothing before `CompositionRootTests` existed had ever attempted to build the real composition root at all, let alone with scope validation on.

**The closure:** `SessionStateService` already had two working siblings solving this exact problem correctly — `ActiveSessionMonitor` (`AutoEndAsync`/`AutoResumeBreakAsync`) and `ScheduledEnforcementService`'s heartbeat both take `IServiceScopeFactory` in their constructor and resolve their scoped dependencies from a fresh `CreateScope()` per operation, never capturing them directly. `SessionStateService` was the one service in this family that didn't follow its own codebase's already-established pattern. Fixed by bringing it in line: constructor now takes only `IServiceScopeFactory`; `InitializeAsync` creates one scope, resolves `ISessionRepository`, `IBlockPresetRepository`, and the sweep command handler from it, and disposes the scope when the method returns. `ISessionStateService`'s public interface — `InitializeAsync()`, `ActiveSession`, `SetActive`, `SetRitualRequired`, `Clear`, all three events — is completely unchanged; every calling ViewModel is unaffected. The test file was updated to build a real minimal `ServiceCollection`/`ServiceProvider` from the same NSubstitute mocks (registered as singleton instances) to obtain a genuine `IServiceScopeFactory`, rather than hand-mocking the `IServiceScope`/`IServiceProvider` resolution chain.

**Principle demonstrated:** When a lifetime mismatch is found, check whether the codebase has already solved it correctly somewhere else before designing a new fix — `ActiveSessionMonitor` and `ScheduledEnforcementService` had already established the right pattern; the fix was to make `SessionStateService` consistent with its own siblings, not to invent anything new. Also: `ValidateScopes = true` is a strictly stronger check than `ValidateOnBuild` alone, and costs nothing extra to enable in a smoke test — there is no reason to leave it off once nothing in the graph fails it.

The real work waiting to be done wasn't new domain modeling — it was two narrow, genuine gaps between an already-correct domain concept and a UI surface that hadn't been built to reach all of that concept's valid states yet.

## Gap 17 — Block Splitting for Sealed Daily-Flexibility Contracts *(built, 2026-08-19)*

**The task:** A user with a Daily Flexibility contract needs to split one sealed block into two, back-to-back, then drag the second half wherever they want on the same day. Handed off as a full interrogation-then-build task.

**The interrogation, compressed:** No split for a block a session has already touched (any session, not just active — eliminates session-migration complexity entirely). Delete-and-recreate, not resize-in-place: the original `PlannedBlock` is deleted, two new ones are created with new `Id`s, same `ContractId`/`BlockPresetId`, no parent-child relationship — "equal contract members," matching how a redemption block relates to nothing but the fact it covers. `SplitPlannedBlockCommand` takes both halves' explicit start/end rather than a single cut-point, deliberately staying ignorant of what happens after — dragging the second half to a new time is a completely separate `UpdatePlannedBlockCommand`, not a parameter of Split. Split is exclusively a sealed-contract feature (an ordinary uncommitted block has no strictness rule to check, so "splitting" it is just delete-and-recreate through commands that already exist) and exclusively Daily-Flexibility (Lockdown blocks are immutable full stop; the validator gates on `StrictnessRule == DailyFlexibility` directly rather than reusing `AllowsBlockTimeChange`, which also passes `PeriodTimeBudget` — the wrong scope for this feature).

**One real "is there an easier way" question, answered before writing code:** could the user just delete the block and create two new ones through the existing commands? No — `DeletePlannedBlockValidator` already unconditionally rejects deleting a block under any in-effect contract, a deliberate protection, and composing `DeletePlannedBlockCommandHandler` + `CreatePlannedBlockCommandHandler` as two separate commands would mean two separate commits (`TransactionalCommandHandler` wraps every command handler and commits once per call) — reopening exactly the non-atomicity risk Gap 7's `BreakNenContractCommandHandler` was built to avoid. `SplitPlannedBlockCommandHandler` deletes and re-adds directly against the repository in one handler, getting one commit for free.

**A domain-drift correction caught mid-build, not after:** the validator initially added a "does the contract meet its floor at Seal time" rule to `SealNenContractValidator`/`EditNenContractValidator` — duplicate logic. `NenContract.Seal`'s own constructor already throws `ArgumentException` for exactly this case (confirmed by a validator test that unexpectedly threw instead of failing cleanly). The duplicate rule was reverted rather than kept alongside the real one — two places enforcing one invariant is the exact failure mode Gap 10/11 already catalogued.

**Two exclusive-end midnight bugs found by hand-testing after Split shipped, both traced to the same root cause:** `DateOnly.FromDateTime(command.End.ToLocalTime())` reads a block ending exactly at midnight (e.g. 22:00–24:00) as belonging to the *next* calendar day, since `24:00` is represented as `00:00` the following day. This broke two things: moving a Daily Flexibility block to end at midnight was rejected as "crossing days" (`UpdatePlannedBlockValidator`'s same-day check), and splitting a block so the second half ends at midnight had the identical failure (`SplitPlannedBlockValidator`, which had copied the same pattern). Both fixed by resolving the end boundary one tick earlier (`command.End.ToLocalTime().AddTicks(-1)`) before taking `.Date` — mirrors the `[start, end)` exclusive-end semantics `PlannedBlock.IsActive` already uses everywhere else; a normal (non-midnight) end time is unaffected, since subtracting one tick never crosses a calendar-day boundary except at the exact boundary itself.

**A third, unrelated bug found the same session, same root cause class (stale enforcement-adjacent state read as still-live):** `PlannedBlockRepository.GetOverlappingAsync` never filtered out cancelled blocks (`CancelledAt.HasValue`, from Gap G's Break-cleanup redesign). A broken contract's cancelled-but-not-deleted blocks kept blocking new scheduling into their old time slot forever — reported as "A Focus block already exists here" when sealing a brand-new contract into a cancelled contract's old schedule. Fixed at the repository level (`.Where(b => ... && b.CancelledAt == null)`), which fixes every caller — Seal, Edit, Create, Update, Split — not just the path that surfaced it.

**Principle demonstrated:** The same three lessons this file keeps re-teaching, all triggered independently in one feature: check whether a domain invariant is already enforced somewhere before adding a second enforcement point (the Seal-time floor check); trace a boundary condition to its root cause before patching the symptom (both midnight bugs shared one fix, once diagnosed correctly, instead of two independent patches); and a bug found in one code path that reads from a shared repository method is very likely present in every other caller of that method too (`GetOverlappingAsync`'s fix silently repaired Create/Update/Seal/Split at once).

## Gap 18 — Daily Flexibility Floor-Protection, and Period Time Budget's `ContractFloor` *(built, 2026-08-19)*

**The gap:** Two related but separately-scoped pieces, both closing long-standing documented-but-unbuilt behavior. First: `ARCHITECT_GOVERNANCE.md` Open Gap F (Daily Flexibility's "total daily time conserved" intent, documented since Gap 15, never enforced). Second: `DOMAIN_DICTIONARY.md` had claimed since its first Nen Contract entry that "`PeriodTimeBudget`: Same as Daily Flexibility, but the budget is tracked across the full contract period instead of per day" — aspirational documentation with zero backing code; a `PeriodTimeBudget` contract went through the identical per-day `DailyFloorPolicy`/Day-Met machinery as `Locked`/`DailyFlexibility`, with the only real differences being "can move to any day in the period" and "redemption can land on any day." Both gaps surfaced in the same working session, starting from the architect asking to fix Gap F, then interrogating whether the daily-floor concept made sense for Period at all — which turned out to require reopening Period's core design, not just adding a guard.

**Gap F's resolution (Daily Flexibility):** its documented "total daily time conserved" intent (see Gap 15) had never been enforced, and the original open questions around it (what counts toward the day's total, Seal-time vs. pre-edit comparison, tolerance, Redemption interaction) turned out to answer themselves once the architect reframed the actual requirement mid-session: the guard was never meant to enforce *exact* conservation (a resize would always violate that unless paired with a compensating edit elsewhere — no such multi-block atomic mechanism exists). What's actually needed is **floor-protection** — a day's total may shrink freely as long as it never drops *below* that day's own resolved Daily Floor. That reframing dissolves every open question at once: "what counts toward the day's total" is Focus-only, matching `NenContract.IsDayMet`/`DailyFloor.IsSatisfiedBy`, which the guard reuses directly rather than re-deriving; "Seal-time total vs. pre-edit total" is moot, since the comparison is always against the floor, a fixed number, never a moving total; "tolerance" is moot for the same reason; and Redemption interaction needs no special case, since a redemption block is just additional Focus time on a day, which can only ever help a floor comparison, never hurt it. Built in `UpdatePlannedBlockValidator`: for a `DailyFlexibility` contract, shrinking a Focus block re-checks the edited day's total (via `ComputePlannedFocusHoursQuery` with the block excluded and the new range added back in) against `contract.IsDayMet(date, newTotal)` — the exact same domain rule Day-Met scoring already uses, not a re-derived comparison. `CreatePlannedBlock`/`DeletePlannedBlock` needed no equivalent guard: Delete is already unconditionally rejected for any in-effect contract, and a brand-new block can only ever add to a day's total, never shrink it below floor.

**Period Time Budget's resolution needed a real new domain concept, arrived at by interrogation, not assumption:** the architect's framing — a day's blocks can move anywhere, but the *whole period's total* must never drop below what was committed at Seal — doesn't fit `DailyFloorPolicy`'s shape at all (that value object resolves a floor *per day*; Period's model has no per-day obligation to resolve). Introduced `ContractFloor` (`NenFocus.Domain/ValueObjects/ContractFloor.cs`): same shape as `DailyFloor` (`Hours`, `IsSatisfiedBy(double)`) but deliberately a *different* type, not a reuse — `DailyFloor`'s constructor caps at 24 hours, correct for a single day and wrong for a period total that can easily exceed it (caught before writing any Application code, not after; the first draft of this design recommended reusing `DailyFloor` directly and was corrected once its constructor was actually read). `NenContract.ContractFloor (ContractFloor?)` is mutually exclusive with a real `DailyFloorPolicy` (a guard clause in `Seal` throws if both are set with real content), mirroring the same "illegal states unrepresentable via a runtime guard, not a type-system union" discipline `MODULE_STANDARDS.md`'s "no shared base classes" rule already implies for this codebase's value objects. `NenContract.IsPeriodMet(double)`/`ContractFloorHours` mirror `IsDayMet`/`FloorHoursFor`'s exact shape and purpose — the Application layer never reaches into `ContractFloor` directly, same discipline as every other `NenContract`-owned policy.

**Why a polymorphic `ContractFloor`/`DailyFloorPolicy` hierarchy was considered and rejected:** they answer genuinely different questions with genuinely different shapes (one resolves per date, one is a single whole-contract scalar) — forcing a shared interface would mean the period-mode side implements a per-day method that's always meaningless for it. This codebase's value objects are all flat records; only entities (`FocusBlock`/`BackgroundBlock`) use inheritance. Two nullable fields plus one guard clause in `Seal`, mirroring how `WorkHoursPolicy`'s both-or-neither check already lives in the Application-layer validator rather than the type system, was judged more consistent with house style than introducing the first polymorphic value object for what's fundamentally two optional fields.

**Wiring:** `SealNenContractCommandHandler`/`EditNenContractCommandHandler` derive `ContractFloor` from the sum of drafted Focus blocks when `StrictnessRule == PeriodTimeBudget && FixedDailyFloorHours is null` — the same "whatever was drafted becomes the committed target, trivially satisfied by construction" philosophy Simple contracts already use for their per-day floor, just totaled instead of per-day. A Period contract *with* a real fixed floor is untouched — that combination already worked (each day independently checked, blocks movable anywhere in the period) and still does. `GetActiveNenContractQueryHandler`: when `ContractFloorHours.HasValue`, the days-behind/Day-Met loop is left completely alone — it naturally yields zero for both, since `DailyFloorPolicy.None` makes `IsRestDay`/`IsDayMet` trivially resolve "rest"/"always met" for every day, nothing new to suppress. Per-day badges instead compare that day's completed hours against its own *currently planned* hours (dynamic, reflecting any post-seal moves) — reusing `ComputePlannedFocusHoursQuery`/`GetNenContractCompletedFocusHoursQuery`, both already built, no new query needed. No day is ever a rest day in this mode (confirmed with the architect: "if it's moved to another day then that day would not just turn into Rest" — every day is equally in-play when only the period total matters).

**The banner text was unified across every strictness rule in the same pass, not just Period:** the architect's own follow-up observation, mid-testing — the "days behind/days met" framing read as unnecessarily different between Period and everything else. `ActiveNenContractDto` gained `TotalFloorHours`/`TotalCompletedHours`, computed uniformly for every contract (`ContractFloorHours` when set, otherwise the sum of every day's resolved per-day floor — `dayStatuses.Sum(d => d.FloorHours)`, already computed for the badges, reused rather than re-derived); the banner text collapsed from two branches to one: `"Contract: [Name] — Day X/Y — Xh / Yh completed — Zh deficit"` for every strictness rule.

**The future-badge simplification (a Daily-Flexibility-only feature from an earlier pass this same day) was generalized to every strictness rule, then refined once more after a follow-up correction:** first pass — `ShowSimplifiedFuture` (single number, no `/floor`, on a sealed contract's future day) applied only to `DailyFlexibility` and `ContractFloor` mode, since those were the only cases provably always-safe at the time. Once the ordinary-Period per-day guard and Daily Flexibility's own guard were both confirmed correct, the condition generalized to *any* sealed contract (`ContractStrictnessRule.HasValue`) — a live drafting preview (where `ContractStrictnessRule` is null) is the only case still showing the two-number comparison, since that comparison is the actionable feedback drafting exists to give. **Then refined again** once the architect pointed out a real case the blanket simplification hid: a day scheduled with *more* than a real fixed floor requires (e.g. 2h planned against a 1h floor) has genuine surplus worth showing, not hiding behind a bare "2h." `ShowSimplifiedFuture` now also requires `CurrentHours <= RequiredFloorHours` — an exact match still collapses to one number (and collapses back the moment an edit brings a surplus day down to exactly the floor again), but a surplus day shows the full `"2h / 1h"` comparison. The color stays the same either way (`IsMet` is already true in both cases) — only the label format changes.

**Immediate badge/banner refresh, found while testing the above:** `MoveOrResizeBlockAsync` and the form's `SaveAsync` only called `LoadWeekAsync()` after a committed change, relying on a pre-existing 3-second poll timer (`_floorStatusPollTimer`, built for a different reason — keeping Today's badge live during an in-progress session) to eventually catch the banner up. Both now also call `RefreshActiveContractAsync()` directly, matching what `ConfirmSplitAsync` already did — the poll timer remains as a background fallback, not the primary update path for the user's own actions.

**Confirmed via `NenFocus.Tests`:** 953 of 956 passing (the 3 failures are the pre-existing, unrelated em-dash string-comparison cases tracked since Gap G's closure). New coverage: `ContractFloorTests` (value object), `NenContractTests` (mutual-exclusivity guard, `IsPeriodMet`/`ContractFloorHours`), `SealNenContractCommandHandlerTests`/`EditNenContractCommandHandlerTests` (derives `ContractFloor` from drafted totals), `UpdatePlannedBlockValidatorTests` (Daily Flexibility floor-protection, Period `ContractFloor` protection, ordinary Period per-day protection checking both the vacated and landing day), `GetActiveNenContractQueryHandlerTests` (`ContractFloor`-mode day-status computation, no rest days, `TotalFloorHours`/`TotalCompletedHours` for both modes).

**Principle demonstrated:** A documented-but-unbuilt behavior ("tracked across the full period instead of per day") can sit in the docs for weeks looking like a settled design when it's actually never been checked against the live code — the correction only surfaced because the architect asked a "does this even make sense" question about the *adjacent*, already-partially-built feature (Gap F), not because anyone was specifically auditing Period. Reuse the exact rule a related feature already established (`IsDayMet`'s shape, mirrored into `IsPeriodMet`) rather than inventing a parallel comparison — and when a proposed reuse turns out to carry an incompatible constraint (`DailyFloor`'s 24-hour cap), build the narrow sibling type instead of forcing the fit or duplicating validation logic ad hoc.

## Gap 19 — Daily Floor's Blank-vs-Zero Ambiguity Traced to a Silent Coercion, Not a UI Oversight *(closed, 2026-08-19)*

**The gap:** Manual testing surfaced a Lockdown contract's future-day badge reading `"2h / 0h"` for a day with 2 planned hours — a real floor of exactly zero, not "no floor." The architect's own diagnosis was immediately correct: they had typed `0` into the Advanced wizard's daily-floor field, believing it meant "no floor," when the actual "no floor" signal in this codebase has always been *leaving the field blank* (`ResolvedFixedDailyFloorHours` already returned `null` for an unparseable/empty string, feeding `DailyFloorPolicy.PerDay` — the per-day-derived mode — rather than `DailyFloorPolicy.Fixed(new DailyFloor(0), ...)`, a real zero-hour floor applied to every day). Two values that look nearly identical to a user (an empty field vs. typing `0`) meant two completely different, unrelated domain configurations.

**Root-caused, not just patched at the display layer:** the exact same 0-vs-blank confusion was independently found live in `ContractWizardViewModel`'s "Save as preset" path — `DailyFloorHours = fixedFloor ?? 0` silently coerced "no fixed floor was chosen" into "a real zero-hour floor" every time a no-floor Advanced contract was saved as a reusable preset. This was a second, independent occurrence of the identical mistake, not a duplicate report of the first — confirming the ambiguity was structural (the domain had no way to make "explicitly no floor" and "explicitly zero" visibly different choices), not a one-off typo.

**The closure, in three parts:**
1. **The wizard's floor field became a checkbox** ("Enforce a fixed daily floor"), mirroring the already-existing "Enforce work hours" pattern exactly — `IsDailyFloorEnabled` gates both the text field's visibility and `ResolvedFixedDailyFloorHours`'s resolution. There is no longer a blank-vs-zero distinction to confuse — the field simply doesn't exist when the floor isn't enabled.
2. **Zero was made an invalid value everywhere a floor can be set**, not just discouraged in the UI: `SealNenContractValidator`/`EditNenContractValidator`/`CreateContractPresetValidator`/`UpdateContractPresetValidator` all changed their range check from `InclusiveBetween(0, 24)` to `InclusiveBetween(1, 24)` plus a new whole-number check (`floor % 1 == 0`) — the architect's explicit ask ("whole number, minimum exactly 1," confirmed over the alternative of allowing fractional floors like 0.5h). A new cross-check was added in the same pass, also the architect's explicit ask: when both a fixed floor and work hours are enabled, the floor can't exceed the work-hours window's span (`floorHours <= (WorkHoursEnd - WorkHoursStart).TotalHours`) — a floor that could never be satisfied within the only hours blocks are allowed to exist in is a configuration error, not a valid edge case, checked in the wizard for immediate feedback and in all four validators as the real gate (this codebase's established "wizard is convenience, validator is the gate" two-tier pattern).
3. **`ContractPreset.DailyFloor` became nullable** (`DailyFloor? DailyFloor`, previously non-nullable) — a preset can now represent "no fixed floor" the same way a contract can, closing the coercion bug at its source rather than only at the wizard's call site. Confirmed as the more DDD-correct shape before building it (asked directly, answered "which is most DDD"): a boolean enabled-flag plus a sometimes-meaningless-when-off value is exactly the smell this codebase has independently rejected multiple times already (`SkippedOccurrence`'s no-`Resolved`-flag design in Open Gap E, `ContractFloor`'s mutual-exclusivity-over-polymorphism choice earlier the same session) — a nullable value object states "may or may not have one" without a redundant second field. New migration `MakeContractPresetDailyFloorNullable`.

**Principle demonstrated:** A confusing UI affordance is sometimes a symptom of a missing domain distinction, not a display bug fixable by rewording a label — here, "no floor" and "a floor of zero" were genuinely different configurations that the UI had no honest way to let the user choose between, so the fix had to reach into the command shape, both pairs of validators, and the preset entity itself, not just the wizard. And: when the same mistake is found independently in two unrelated code paths (the wizard's live validation and the preset-save coercion), that's a strong signal the underlying concept itself was ambiguous, not that two different people made two different errors.

## Gap 20 — Focus Block Outcome: Uncapped Late-Start Credit, No Planner Display for Anything But Missed *(closed, 2026-08-20)*

**The gap, found while manual-testing with the debug clock:** a block scheduled 12:00–15:00, ritual completed 19 minutes late, session ended (via a debug-clock skip) 3 hours after the late start — the Post-Session screen credited the full 3 hours, not the 2h41m actually available between the late start and the block's own scheduled end. Traced to `IFocusBlockOutcomeClassifier.CreditedFocusMinutes`: the `CompletedOnTime`/grace-period branch was already correctly capped (it credits a fixed `scheduledEnd − scheduledStart`, never more), but the `StartedLate` fallthrough branch returned raw `actualElapsedMinutes` with no cap at all — a session that ran (or was force-ended) past `scheduledEnd` earned unbounded bonus credit. Separately, the Planner tile had visual treatment for exactly one outcome, `Missed` (red background, strikethrough, "MISSED" label) — a `StartedLate` block rendered identically to a normal completed one, and the tile's `Start`/`End` always showed the raw scheduled window regardless of what actually happened.

**The closure, built incrementally with sign-off at each design point:**
1. **Credit cap:** `CreditedFocusMinutes`'s `StartedLate` branch now returns `Math.Min(actualElapsedMinutes, scheduledEnd − ritualCompletedAt)` — confirmed with the architect that actual elapsed time can never legitimately exceed the block's own scheduled window; the debug clock is a testing-only tool, not a case needing separate enforcement.
2. **`PlannedBlockDto.IsMissed (bool)` → `Outcome (FocusBlockOutcome?)`.** Chosen over a second boolean flag as more DDD-correct — the domain's own vocabulary (`FocusBlockOutcome`), not an ad-hoc bit, flows through the DTO. `GetPlannedBlocksForDayQueryHandler` now calls `IFocusBlockOutcomeClassifier.Classify(...)` directly instead of a hand-rolled `RitualCompletedAt is null && HasEnded` predicate — collapsing two independently-derived "was this missed" computations (Domain's `Classify`, Application's own re-derivation) into one, the same drift class flagged by Gap 6/11.
3. **Tile `Start`/`End` become the actual worked window**, not the raw scheduled one: `Start` pulls forward to `RitualCompletedAt` once past grace (left untrimmed within grace, matching the full credit given), `End` pulls back to `SessionEndedAt` for an early end (existing precedent from the `EndedEarly` work, Gap 22 below, now composed with the new Start-side trim) — both apply independently, so a block that's both `StartedLate` and `EndedEarly` shortens from both ends.
4. **Full color/badge scheme**, confirmed point-by-point: `CompletedOnTime` → green (`#3A9E6A`, reusing the existing "session active" color), no badge — color alone reads as "on time." `StartedLate`/`EndedEarly` → one shared amber (`#D97706`), labeled "STARTED LATE"/"ENDED EARLY," no strikethrough (the block genuinely happened). `Missed` → unchanged (red, struck through, "MISSED"). Badge/color switch live, the instant `Classify()` resolves — not gated on `HasEnded` — confirmed against the actual navigation code that this is a distinction without a difference in this app: the whole nav shell (Planner included) is hidden behind the Ritual overlay until the ritual completes, so "the moment it's knowable" and "the moment the user could possibly see it" are the same moment.

Corrected: `PlannedBlockTileViewModel` exposes only `Outcome`/`WasStartedLate` (semantic facts); the class-name/badge-text mapping moved into `PlannerPageView.axaml.cs`'s code-behind, which already owns the imperative tile-construction this View uses instead of XAML data templates.
6. **The dual-outcome case.** `Classify()` deliberately gives `EndedEarly` priority over `StartedLate` when a block is genuinely both (pre-existing behavior, confirmed intentional, not touched) — but the tile needed to say both. New `WasStartedLate (bool)`, independent of `Outcome`, added to the DTO/ViewModel. Building it surfaced that the underlying grace-period lateness check was already independently re-derived in **four** places by this point (`Classify`, `CreditedFocusMinutes`, `GetFocusBlockRitualContextQueryHandler`'s live ritual-page check, and the new tile Start-trim) — extracted `IFocusBlockOutcomeClassifier.IsLateStart(scheduledStart, momentToCheck) -> bool` as the one shared Domain method, all four call sites (plus the new `WasStartedLate` check) now delegate to it instead of re-deriving the comparison. Confirmed as more DDD-consistent than adding a fifth inline copy, matching `DailyFloor.IsSatisfiedBy`/`UsageCeiling.IsExhausted`'s "the rule belongs with its data, reused wherever it's checked" precedent.

New/updated coverage: `FocusBlockOutcomeClassifierTests` (credit cap, `IsLateStart` boundary cases), `GetPlannedBlocksForDayQueryHandlerTests` (`Outcome` for all four verdicts, display-start/end trim independently and combined, `WasStartedLate` independent of `Outcome`), `GetFocusBlockRitualContextQueryHandlerTests` (unchanged behavior after routing through the shared method).

**Principle demonstrated:** a business rule checked in more than one place is a standing invitation to drift — the fourth independent copy of the same grace-period comparison was the signal to finally extract it, not the first. And: catching your own architecture mistake mid-session (the CSS-string-on-ViewModel misstep) by checking against the codebase's own established precedent, rather than defending the shortcut, is exactly what "surface drift, don't fix silently" means in practice — including when the drift is something just introduced, not just something inherited.

## Gap 21 — Missed-Block Detection Was Edge-Triggered, Invisible to a Large Time Jump *(closed 2026-08-20; DB-only scope reversed same day; a TOCTOU race, a boundary-width mismatch, and finally a missing pre-Ritual guard all found and fixed in the same day's follow-up testing — see the three addenda below)*

**The gap, found while manual-testing:** a block created and then skipped over entirely via the debug clock — jumping past both its scheduled `Start` and `End` in one instantaneous jump — triggered neither the Ritual nor a `Missed` marking. Traced to an edge-detection/level-detection mismatch: `ScheduledEnforcementService`'s 5-second heartbeat (`Task.Delay`, real wall-clock, not the debug clock) samples `ISystemClock.UtcNow` once per tick and calls `SessionStateService.SetRitualRequired(true/false, ...)`, which only raises `RitualRequirementChanged` on an actual state *transition* (`SetRitualRequired(false)` when already `false` is a silent no-op). `ShellViewModel.TryMarkBlockMissed` — the only live path that marks a block `Missed` — fires exclusively off that event. Because the debug clock's jump was instantaneous but the heartbeat only samples "now" every 5 real seconds, its very next tick after the jump already saw `now` past the block's `End`; the block was never observed as "active, no session" at any tick, so the required→not-required transition that would trigger `TryMarkBlockMissed` never fired either. The same failure mode applies without any debug tooling: a laptop sleeping/suspending across a block's entire window produces an identical "large jump between heartbeat ticks."

**What already existed and was already correct:** `SweepMissedFocusBlocksCommandHandler`, a genuinely level-based detector (`IPlannedBlockRepository.GetUnresolvedFocusBlocksAsync`: any block with `End < now && RitualCompletedAt == null && CancelledAt == null`, no dependency on having previously observed the block as active) — but it was only ever invoked **once**, from `SessionStateService.InitializeAsync()` at app/session-service startup, never periodically.

**The closure:** `ScheduledEnforcementService.ExecuteAsync`'s existing 5-second loop now also resolves and calls `ICommandHandler<SweepMissedFocusBlocksCommand, SweepMissedFocusBlocksResult>` on every tick, inside the same `IServiceScopeFactory`-created scope it already uses for its policy computation. No new domain or application code — purely a new call site for an already-correct, already-unit-tested handler. A block can now never sit unresolved for longer than one heartbeat interval, regardless of whether any intermediate transition was ever witnessed.

**Scope interrogated before building, not assumed:** considered whether a newly-swept `Missed` session should also live-push a Post-Session popup straight into `ShellViewModel`'s pending-overlay queue, versus letting the database be correct immediately with the popup surfacing at the next app restart (today's existing catch-up path, via the one-time `GetUnacknowledgedPostSessionsQuery`). Decided against live-push, and asked directly which was "more DDD": `SessionMissedEvent` is already deliberately unhandled — `DOMAIN_DICTIONARY.md` documents this as intentional, the same "surfaced by query, not by an event handler chain" posture already established for `SkippedOccurrence` (Open Gap E). Wiring live surfacing would mean either `ScheduledEnforcementService` (Infrastructure) reaching directly into `ShellViewModel`'s (UI) queue — inverting Clean Architecture's dependency direction — or inventing a new cross-layer notification channel solely to contradict a standing, deliberate domain decision, for a rare edge case. The existing `TryMarkBlockMissed` comment ("the next cold-start sweep or heartbeat tick will pick it up again") already described the intended behavior this closure actually delivers.

**Confirmed via `NenFocus.Tests`:** 980 of 980 passing, unaffected — `SweepMissedFocusBlocksCommandHandlerTests` already covered the handler itself; `ScheduledEnforcementService` has no unit test harness, consistent with its pre-existing untested-shell status (mirrors `NenContractHeartbeatService`, also untested by design, per its own row in `DOMAIN_DICTIONARY.md`).

**Principle demonstrated:** an edge-triggered detector answers "did I see it happen," a level-based detector answers "is it true right now" — they are not interchangeable, and a system that needs to survive not being watched continuously (sleep, a large clock jump, or any other missed observation) needs the level-based one running on a loop, not the edge-triggered one made cleverer. When a rare-but-real failure mode is found, the fix is to run the already-correct check more often, not to invent new plumbing to patch around the detector that structurally can't see it.

### Revisited same day (2026-08-20): the DB-only scope was reversed after the architect hit the real gap firsthand

**What happened:** the architect manually tested the closure above — created a block, skipped time past it — and reported two things: the Planner tile stayed stale until an unrelated action (editing/navigating) happened to reload it, and no Post-Session popup ever appeared. The second was exactly the deliberate scope decision from this gap's original closure, working as designed. Reasoning about a scope decision in the abstract and then actually living with its consequence are different things — the "DB-only" tradeoff read as correctly-scoped restraint beforehand and as a real, felt UX gap afterward. Asked directly whether to reverse it, given the new firsthand information: **yes.**

**The tile-staleness half was a separate, independent bug, investigated first:** `PlannerPageViewModel`'s only periodic timer (`_floorStatusPollTimer`, 3s) refreshes the day-floor badges and active-contract banner only — it never calls `LoadWeekAsync()`, and it doesn't even run unless a Nen Contract is active. Every tile reload in the codebase was already exclusively action-triggered (edit/move/delete/split a block, week navigation, contract seal/cancel, session end) — this wasn't a regression from the heartbeat-sweep change, just a pre-existing gap the sweep change made newly visible (previously, nothing *could* change a block's status while the app kept running without the user's own action causing it).

**The live-push reversal, built to match this codebase's own established broadcast pattern, not a new invention:** `ISessionStateService` (the same Application-layer interface `ShellViewModel` already subscribes to for `RitualRequirementChanged`) gained two new members:
- `event EventHandler<IReadOnlyList<PostSessionDto>>? PostSessionsReady` / `void NotifyPostSessionsReady(...)` — `ScheduledEnforcementService`'s periodic sweep now passes its `SweepMissedFocusBlocksResult.MissedSessions` (previously discarded entirely) through this call. `ShellViewModel` subscribes exactly like `RitualRequirementChanged`, enqueuing each into the same `_pendingOverlays` queue the live edge-triggered path already uses — same triage batching, same everything, the only difference is where the `PostSessionDto` came from. The method itself no-ops on an empty list, so callers don't need to remember to check.
- `event EventHandler? PostSessionAcknowledged` / `void NotifyPostSessionAcknowledged()` — raised from `ShellViewModel.ExitPostSession()` (the existing "Done" dismissal handler). This is what closes the tile-staleness gap: rather than adding a new poll, `PlannerPageViewModel` subscribes to this event and reloads on dismissal — the exact moment a sweep-caught Missed block's data is known to have changed. `OnSessionChanged` (already subscribed, already reloading on session **end**) was also widened to reload on session **start** — a ritual completing stamps `RitualCompletedAt` immediately, changing the block's `Outcome`/tile display before the session has ended, and nothing was catching that transition either.

**Why event-triggered over a second poll timer, confirmed by the architect's own framing of the question:** every existing tile refresh in this codebase is already action/event-triggered; the only poll in the file exists narrowly to keep a continuously-changing number (today's floor badge, during a running session) live, not to catch a discrete state flip. Once live-push exists, every path that can change a block's resolved `Outcome` while the app is running already funnels through something `PlannerPageViewModel` can listen to — there was no remaining case only a timer could catch.

**Why this doesn't contradict the original "surfaced by query, not event" reasoning — it narrows it instead:** `SessionMissedEvent` itself is still unhandled, and the startup-only sweep (`SessionStateService.InitializeAsync`) still relies purely on `GetUnacknowledgedPostSessionsQuery`'s catch-up, with no live event — that reasoning was correct for the case it covered (a sweep result nobody could possibly be watching for, since the app had just started and nothing was subscribed yet). What changed is narrower: the *periodic* sweep runs inside a long-lived, already-running app where `ShellViewModel` unquestionably exists and is already wired for exactly this kind of live signal (`RitualRequirementChanged` is the identical shape, already crossing the same Infrastructure→Application-interface→UI boundary). Extending an established, already-crossed bridge is a different decision than building a new one from scratch — the Clean Architecture objection from the original closure applies to the latter, not the former.

**Confirmed via `NenFocus.Tests`:** 983 of 983 passing. New coverage: `SessionStateServiceTests` (`NotifyPostSessionsReady` raises with a non-empty list / no-ops on empty, `NotifyPostSessionAcknowledged` raises unconditionally).

**Principle demonstrated:** a scope decision reasoned through correctly in the abstract can still be wrong once its consequence is actually experienced — the fix in that situation is to revisit the decision with the new information, not to defend the original reasoning. And: "don't invent a new cross-layer channel" and "extend a channel that already crosses that exact boundary for the identical reason" are different judgments — the first objection doesn't automatically apply to the second just because both involve the same two layers.

### A second bug, found the same day testing the live-push closure above: a TOCTOU race the original sweep-in-the-heartbeat change (this gap's own first closure) introduced

**The gap:** running the app under a debugger, the architect got a Missed Post-Session popup for a block (correct — live-push above working as intended), immediately followed by the Ritual for the **same** block, which then rejected at Hatsu with "A session already exists for this focus block." Traced to a race this gap's own original closure introduced and never had, before today: `ScheduledEnforcementService` captures `now` once per heartbeat tick and passes it explicitly to `ComputeActivePolicySliceQuery(now)`, but `SweepMissedFocusBlocksCommandHandler` (added to that same tick earlier today) read its own independent `ISystemClock.UtcNow` internally rather than accepting the tick's already-captured value. Any real time elapsing between those two reads — debugger overhead, a breakpoint, DB I/O, anything — meant a block whose `End` fell inside that gap could get two disagreeing verdicts in one tick: the sweep (later, more current read) correctly saw it as past `End` and marked it `Missed`; `ComputeActivePolicySliceQueryHandler` (the earlier, now-stale `now`) still saw it inside `[Start, End]` and fired `SetRitualRequired(true, sameBlockId)`. Neither `PolicyEngine.ComputeSlice` nor `ShellViewModel.StartRitual` has (or should need) any check for "does this block already have a Session" — that's `StartSessionCommandHandler`'s job, which correctly rejected it, just too late in the flow to be a good user experience (a rejected Hatsu, not a ritual that was never offered).

**Why this couldn't have happened before today:** before this gap's original closure, the sweep only ever ran once, at startup, before `ScheduledEnforcementService`'s loop had ticked at all — there was no second clock read in the same operation for it to race against. The race is a direct, if unintended, consequence of composing two previously-separate operations (policy computation, missed-block sweep) into one heartbeat tick without also unifying what "now" means between them.

**The closure:** `SweepMissedFocusBlocksCommand` gained an optional `AsOf (DateTime?)` field. `ScheduledEnforcementService` now passes its own already-captured `now` explicitly (`new SweepMissedFocusBlocksCommand { AsOf = now }`); `SweepMissedFocusBlocksCommandHandler` uses `command.AsOf ?? _clock.UtcNow`, falling back to a fresh read only when no caller-supplied instant exists. The other call site, `SessionStateService.InitializeAsync()`'s startup sweep, is untouched — it's the only time-sensitive read in that method, so it has no sibling value to disagree with.

**Confirmed via `NenFocus.Tests`:** 984 of 984 passing. New coverage: `SweepMissedFocusBlocksCommandHandlerTests.HandleAsync_AsOfProvided_UsesItInsteadOfClock` — asserts the repository is queried with the supplied `AsOf`, not the mock clock's value.

**Principle demonstrated:** composing two independent operations into one orchestrated step (here, one heartbeat tick) is only safe once every time-dependent input they read is unified to one value — "now" is not a constant within a single method body unless something deliberately makes it one. A caller that already resolved "now" once should never let a callee re-resolve it independently; the callee should accept it as a parameter, exactly the same discipline `ComputeActivePolicySliceQuery(now)` already modeled correctly, and `SweepMissedFocusBlocksCommand` originally didn't.

### A third bug, found testing the second fix: unifying *which* "now" isn't enough if the two checks use different *boundary widths* around it

**The gap:** the identical symptom recurred — Missed popup, then Ritual for the same block, then "A session already exists for this focus block" at Hatsu — even after the `AsOf` fix above. Not stale data (ruled out: the mechanism below is sufficient to reproduce it live, on its own, regardless of database state). Traced one layer deeper: `AsOf`/`now` unification fixed *which instant* the sweep and the policy computation agree on, but not the *width of window* each one considers "still active" around that shared instant. `ComputeActivePolicySliceQueryHandler`'s block-fetching query deliberately over-fetches with a **±1-second buffer** (`query.At.AddSeconds(-1)` to `AddSeconds(1)`) — existing, unrelated slop tolerance for SQLite datetime comparison — while the sweep's `GetUnresolvedFocusBlocksAsync` uses a strict `End < asOf`, no buffer. A block whose `End` falls inside that 1-second gap (between `now-1s` and `now`) satisfies *both* conditions simultaneously: the sweep sees `End < now` → `true` → marks it `Missed`; the policy query's range-overlap predicate sees `End > now-1s` → `true` → still hands the block to `PolicyEngine`. And `PolicyEngine.ComputeSlice` — confirmed by reading it directly, not assumed — did no independent re-check of its own: every block the caller's (buffered) query returned was treated as unconditionally eligible to become `ActiveFocusBlockId`, re-triggering `SetRitualRequired(true, sameBlockId)` for a block the sweep had already resolved in the same tick.

**Why the architect's own proposed fallback ("shouldn't the Ritual be blocked if a session already exists") was directionally right but not the precise mechanism:** there was no *active* Session in play — a Missed session is created going straight from `NotStarted` to `Missed`, never through `Active` — so a check gated on "is there an active session" wouldn't have caught this case. What *was* already built and correct, and simply never got a chance to fire, is `ShellViewModel.HandleLiveRitualRelease`: it already closes the Ritual overlay live if the block it's showing gets released while mid-ritual. The bug wasn't a missing fallback at the UI layer — it was that `PolicyEngine` kept sending the *wrong signal upstream* (`SetRitualRequired(true)` instead of `false`) for a block that had already resolved, so the existing, correct fallback mechanism never had a reason to trigger.

**The closure:** `PlannedBlock.IsActive(DateTime atTime) => atTime >= Start && atTime < End` already existed in `NenFocus.Domain/Entities/PlannedBlock.cs` — built at some earlier point, unit-tested in isolation (`PlannedBlockTests.cs`), but never actually called from any production code path. `PolicyEngine.ComputeSlice` now filters through it directly: `blocks.Where(b => !b.CancelledAt.HasValue && b.IsActive(at))`. This makes `PolicyEngine` the sole, precise authority on "is this block active right now," independent of however loose or buffered the caller's own fetch was — `ComputeActivePolicySliceQueryHandler`'s ±1-second buffer is left completely untouched (it's presumably there for a legitimate SQLite precision reason, out of scope to verify or remove), because it's now harmless: over-fetching a candidate that isn't really active just means `PolicyEngine` correctly excludes it, rather than the caller needing to get its own boundary exactly right.

**Confirmed via `NenFocus.Tests`:** 985 of 985 passing. New coverage: `PolicyEngineTests.ComputeSlice_FocusBlockAlreadyEnded_ExcludedFromActiveFocusBlockId` — a Focus block ending 1 second before `at` must not become `ActiveFocusBlockId`/`ActiveBlockPresetType`, confirmed to fail before the fix (reproduces the exact bug at the Domain level, not just as an integration symptom) and pass after. Verified against the full existing `PolicyEngineTests` suite that every pre-existing test block is already constructed with `Start = At`, so none relied on the old, unfiltered behavior — the fix needed no test rewrites, only an addition.

**Principle demonstrated:** two checks agreeing on *which instant* "now" is are not the same as agreeing on *what counts as still active relative to it* — a shared timestamp with different boundary widths around it is still two different answers to "is this happening right now." And: a Deep Module (`PolicyEngine`, "sole owner of all merge rules" per its own documented charter) must be the actual, final authority on the question it owns — trusting a caller's upstream filtering to already be precise, just because it's *usually* close enough, is exactly the kind of implicit contract that breaks the moment two independently-evolving callers (a strict sweep, a buffered range query) stop agreeing on what "close enough" means.

### A fourth cause, found retesting after the third fix: the debug clock's own reset-on-restart behavior, exposing a guard that had never existed at all

**The gap:** the identical symptom recurred a third time — Ritual shown, then "A session already exists for this focus block" at Hatsu — after the boundary-width fix above. This time genuinely different, and not a code bug in anything built today: the architect's own diagnosis, confirmed correct. `SystemClock`'s debug-clock offset resets to zero on every app restart (a plain instance field, never persisted — confirmed, and correct/intended behavior for the debug tool). A block's `Start`/`End` are fixed calendar timestamps, entirely untouched by the debug clock. Sequence: skip time forward past a block's `End` (sweep correctly marks it `Missed`, a `Session` row is permanently saved) → restart the app → the debug offset is gone, real wall-clock time is back, and since only a few real minutes had actually passed, real `now` is still sitting *inside* the block's original real-time window → `PolicyEngine` (correctly, using real time) reports the block as active and re-triggers the Ritual — for a block that already has a resolved `Session` from the fake-time run.

**Confirmed structurally impossible without the debug clock, not just unlikely:** in real (non-debug) use, `now` only ever moves forward — verified no other code path moves it backward. Once real time has genuinely passed a block's `End` and it's been marked `Missed`, real time can never fall back inside `[Start, End)` again. This is a testing-tool artifact, not a fourth instance of the same class of production bug as the first three.

**What it exposed, though, was real and worth fixing regardless of the debug clock:** nothing anywhere in the Ritual-triggering path had ever checked "does a Session already exist for this block" *before* showing the Ritual. The only place that check existed in the entire app was `StartSessionCommandHandler`, at the very last step — after the user had already gone through the whole wizard. This is the general defense-in-depth the architect proposed all the way back at the first occurrence of this symptom ("shouldn't the Ritual be blocked if a session already exists") — imprecise in its original wording (there was never an *active* Session in any of the four occurrences; a Missed session goes straight from `NotStarted` to `Missed`, never through `Active`), but directionally correct every time, and finally worth building once a third independent mechanism had produced the identical failure mode.

**The closure:** `FocusBlockRitualContext` (returned by `GetFocusBlockRitualContextQueryHandler`, already called by `ShellViewModel.StartRitual` right before the Ritual UI opens) gained `AlreadyHasSession (bool)`, populated via `ISessionRepository.ExistsForOriginatingBlockAsync` (a repository the handler didn't previously depend on). `ShellViewModel.StartRitual` now checks it: if a session already exists for the block, the Ritual is never opened — it declines silently and drains whatever else is queued instead. This is a general guard, not scoped to this one mechanism: it now protects against *any* future cause that manages to send a stale ritual-required signal, not just the four already found and fixed today.

**Confirmed via `NenFocus.Tests`:** 986 of 986 passing. New coverage: `GetFocusBlockRitualContextQueryHandlerTests.HandleAsync_SessionAlreadyExistsForBlock_AlreadyHasSessionIsTrue`.

**Also confirmed directly against the live database, not inferred from symptoms alone** — a read-only query (via a throwaway scratch console project referencing the already-restored `Microsoft.Data.Sqlite` package, deleted after use) against `%AppData%\NenFocus\NenFocus.db` showed the block in question (`13:13–14:45 UTC`, the architect's local `15:13–16:45`) already had a `Session` with `Status = Missed` and a stamped `PostSessionAcknowledgedAt` — confirming both that the guard's premise held and that the block was already fully resolved from an earlier test round, not a new issue.

**Principle demonstrated:** when the same symptom recurs through a *third* independently-diagnosed mechanism, the right response shifts from "find and fix this one root cause" to "add the guard that makes the symptom itself unreachable, regardless of cause." Each of the first three fixes closed a real, specific hole — but none of them, individually or together, could promise there wasn't a fourth. A precise check at the one point that actually matters (does a session already exist, right before offering to create one) closes the whole class at once, and is cheaper than continuing to hunt for every way "now" can lie.

## Gap 22 — `EndedEarly` Focus Block Outcome & Deficit-Ledger Correctness *(closed, 2026-08-12)*

**The gap, found while verifying a doc-drift claim, not while looking for it:** `TECHNICAL_SPEC_INFRA.md` used to (wrongly) claim sessions can't be ended early. Fixing that led to reading `EndSessionCommandHandler`, which revealed `block.TrimEnd(endedAt)` — when a Planned session ends before its originating block's scheduled end, the block's own `End` field is **permanently overwritten** to match. Tracing what that actually breaks:

- **`TrimEnd`'s usual justification turns out to be redundant.** The assumed reason — stopping the block from re-triggering the Ritual or re-applying enforcement once the session's gone — is already handled by a *different*, purpose-built mechanism: `PolicyEngine.ComputeSlice()` already computes `FocusSessionCompleted` (`RitualCompletedAt != null && !activeSessions.Any()`), and `ScheduledEnforcementService` already checks it and calls `RemoveEnforcementAsync` + `SetRitualRequired(false)`. Confirmed in the live code — `TrimEnd` was never needed for enforcement safety at all.
- **Its one genuine remaining job is Planner display** — not leaving a tile that visually stretches to the original end time after the session's already over. But because `End` is the *same field* `IFocusBlockOutcomeClassifier.Classify(...)` and every deficit/credited-hours computation read as "scheduledEnd," fixing a display concern silently corrupts the historical record.
- **Concrete damage, verified against `GetNenContractDeficitsQueryHandler`/`GetNenContractCompletedFocusHoursQueryHandler`:**
  - A `StartedLate` block that also ends early: raw deficit (`scheduledMinutes − actualElapsedMinutes`) algebraically collapses to *only* the late-start gap — the "ended early" component vanishes entirely, however early the session actually stopped, because `scheduledMinutes` is computed from the already-trimmed `End`.
  - A `CompletedOnTime` block that ends early accidentally avoids over-crediting the Daily Floor (the grace-period "full scheduled duration" credit ends up equal to actual time worked, purely because `End` was already trimmed to match) — but this is a side effect of the bug, not a designed behavior, and fixing the bug properly needs to preserve this outcome deliberately rather than by accident.
  - There is no way today to distinguish "ran the full block" from "started on time but quit after five minutes" anywhere in the domain — both read as plain `CompletedOnTime`.

**The closure:**

| Concept | Shape |
|---|---|
| `FocusBlock.SessionEndedAt (DateTime?)` | Migration `AddFocusBlockSessionEndedAt`. Stamped via `MarkSessionEnded(DateTime endedAt)`, mirroring `RitualCompletedAt`/`MarkRitualCompleted`'s stamped-timestamp idiom. Only stamped when ending genuinely early (`endedAt < block.End`) — same condition `TrimEnd` used, just redirected to a non-destructive field. `block.End` is never mutated by session-ending again; `EndSessionCommandHandler`'s `TrimEnd` call is deleted. |
| `IFocusBlockOutcomeClassifier.Classify(...)` (widened) | Gains a `DateTime? sessionEndedAt` parameter. **Deliberately part of `Classify` itself, unlike `Cancelled`** — `Cancelled`'s cause (a `NenContract` breaking) is genuinely external to the block's own story, which is why it stayed a query-layered interpretation outside the classifier. `EndedEarly`'s cause is entirely intrinsic to the block+session pair — the same category of fact `ritualCompletedAt` already is — so it belongs inside the one function that already owns "what happened to this block." If the Ritual was completed (on time or late) and `sessionEndedAt.HasValue && sessionEndedAt.Value < scheduledEnd`, the verdict becomes **`EndedEarly`** instead of `CompletedOnTime`/`StartedLate`. |
| `FocusBlockOutcome` enum (widened) | Gains `EndedEarly` — a fourth value alongside `CompletedOnTime`/`StartedLate`/`Missed`. |
| `IFocusBlockOutcomeClassifier.CreditedFocusMinutes(...)` | For `EndedEarly`, credits `actualElapsedMinutes` — confirmed with the architect, not the grace-period full-scheduled-duration credit. That credit exists to forgive a late *start*; applying it to an early *end* was never a deliberate choice, just an accident of `TrimEnd` making the two numbers equal. |
| `GetNenContractDeficitsQueryHandler` | Outcome filter widened from `Missed or StartedLate` to `Missed or StartedLate or EndedEarly`; reordered to fetch the session before calling `Classify(...)` (needed for `session.EndedAt`). Raw deficit now computes correctly against the untouched original schedule. `RedemptionEntry` needed no changes — it already generalizes over whatever block IDs appear in the deficit result set. |
| `GetNenContractCompletedFocusHoursQueryHandler` | Same reorder-then-pass-`session.EndedAt` treatment; existing "outcome is null → still open, skip" logic is unaffected since `EndedEarly` is always a resolved (non-null) outcome. |
| Planner tile rendering | Visual end becomes `Min(End, SessionEndedAt ?? End)`, computed at query/display time (`GetPlannedBlocksForDayQueryHandler`), same "Application computes, UI only references" precedent used throughout this session's other designs. `End` itself is never touched, so this is purely cosmetic — same visual outcome as before the fix, correct underlying data now. |
| `PolicyEngine` | No changes needed — confirmed by checking why `CancelledAt` needed a new exclusion and `SessionEndedAt` doesn't: a cancelled-but-never-started block can have `RitualCompletedAt == null`, so `FocusSessionCompleted`'s existing check doesn't cover it, which is why `CancelledAt` needed its own `PolicyEngine.ComputeSlice()` filter. An early-ended block always has `RitualCompletedAt` set (a session had to exist to end early), so `FocusSessionCompleted` already covers its enforcement-safety case fully. The two mechanisms don't overlap and neither needs to do the other's job. |

**Cross-reference:** widens `GetNenContractDeficitsQueryHandler`/`GetNenContractCompletedFocusHoursQueryHandler`, both also touched by Gap 23's notification/recap work below — this gap is what makes their deficit/credited-hours output trustworthy for a block that ended early, contract or no contract. Independent of Gap 23 otherwise — this fixes a general Session/FocusBlock correctness issue, not something specific to Nen Contract lifecycle.

**Confirmed via `NenFocus.Tests`:** 759 passing, including new `EndedEarly` classification, credited-minutes, deficit, and Planner-display-trim cases. This also retroactively fixed the live wrong number on the Planner's active-contract banner (`GetActiveNenContractQueryHandler` composes both formerly-broken queries directly into `DaysBehind`/`DeficitHours`) and removed the correctness risk `ARCHITECT_GOVERNANCE.md` Open Gap C1/C2/C3 would otherwise have inherited from the same completed-hours query.

**Principle demonstrated:** a "fix the display" patch that reaches for the same field a correctness computation already reads from is not a safe shortcut — `TrimEnd` looked like a harmless cosmetic fix but silently corrupted the historical record every downstream query depended on. The fix was a new, non-destructive field, not a smarter way to mutate the old one.

## Gap 23 — Nen Contract Lifecycle Notifications & Break-Cleanup Redesign *(closed, notifications 2026-08-12, break-cleanup 2026-08-18)*

**The feature, in two independent parts, both now closed** (a third part, the Insights recap query itself, remains open — see `ARCHITECT_GOVERNANCE.md` Open Gap G):

1. **Start/end notifications.** A toast when a Nen Contract activates (`StartDate` arrives) and another when it completes (`EndDate` passes), same delivery mechanism as the existing session-start/session-end toasts.
2. **Break-cleanup redesign.** What happens to a broken contract's not-yet-elapsed blocks, revised mid-interrogation once the real requirement surfaced.

**Why event handlers are the right shape for Activate/Complete (contrast with Gap 7's rejection of a `NenContractBrokenEvent` handler):** `Break` was rejected as an event-handler case because it only ever fires from a direct, synchronous UI button click — the caller already has full context, so relaying it through an event is a pointless extra hop. Activate and Complete are structurally different: both fire from `SweepNenContractLifecycleCommandHandler`, dispatched by `NenContractHeartbeatService`'s unattended 1-minute background loop. Nothing in the UI necessarily knows the transition happened — the whole point of sealing a contract is not having to watch it. This is the same "fact needs to reach a consumer that doesn't share the calling context" shape that already justifies `SessionStartedEventHandler`/`SessionEndedEventHandler`.

**Notifications, closed 2026-08-12:** `NenContractActivatedEventHandler`/`NenContractCompletedEventHandler` mirror `SessionStartedEventHandler`'s pattern exactly — load the contract by `ContractId` via `INenContractRepository`, call `INotificationService` with a message built from `Name`. No new interfaces needed — both `NenContractActivatedEvent`/`NenContractCompletedEvent` already fired from `NenContract.Activate()`/`Complete()` and already carried `ContractId`.

**Break-cleanup redesign, interrogated 2026-08-12, built 2026-08-18.** Originally recorded as an accepted limitation (a future Insights recap couldn't show cancelled blocks because `BreakNenContractCommandHandler` deleted them), then interrogated properly once it became clear the limitation directly undercuts the point of that eventual recap. This reverses Gap 7's delete-only decision — deliberately, not by accident, and only for the reason Gap 7 itself flagged as the one case that would justify revisiting it.

**Revised mid-interrogation once the real requirement surfaced.** The first pass of this design (query-time-only "Cancelled" label, Background blocks unlinked) was correct for pure reporting, but insufficient once the architect confirmed a second requirement: a block that hasn't happened yet when its contract breaks must **stop enforcing**, not just be labeled differently in a report. A purely computed, unpersisted label can't do that — the enforcement heartbeat never runs a recap query, it only reads raw blocks. That requirement forced a real persisted fact, not a derived one.

- **`PlannedBlock` gains `CancelledAt (DateTime?)`** — on the shared base, not `FocusBlock` only, so it applies uniformly to both types. Set once via `MarkCancelled(DateTime cancelledAt)`, mirroring `FocusBlock.RitualCompletedAt`/`MarkRitualCompleted`'s existing stamped-timestamp idiom (throws if already cancelled, same double-call guard). **`PlannedBlock` also gained `: AggregateRoot`** — a prerequisite discovered during implementation, not called out in the original interrogation: `MarkCancelled` needed to raise `PlannedBlockCancelledEvent` (see below), which requires `Raise()`/`DomainEvents`, which only `AggregateRoot` provides. `FocusBlock`/`BackgroundBlock` previously had neither. Verified zero-touch for EF Core (the existing global `modelBuilder.Ignore<DomainEvent>()` already covers the new `DomainEvents` collection — confirmed via a clean migration diff containing only the `CancelledAt` column) and for `EfCoreUnitOfWork` (already generic over `AggregateRoot`, no changes needed). In hindsight this also closes a pre-existing modeling gap: `PlannedBlock` already behaved as an aggregate root in every other respect (own repository, own independent CRUD use cases, referenced by ID — never by object reference — from `Session` and `NenContract`).
- **`BreakNenContractCommandHandler` no longer deletes or unlinks anything.** It calls `MarkCancelled(now)` on every linked block (Focus or Background alike) for which `HasEnded(now)` is false, then saves each — one uniform loop, no per-type branching, nothing removed from the database. `IPlannedBlockRepository.DeleteAsync` is no longer called by this handler at all.
- **Enforcement stops via a combination of `ComputeActivePolicySliceQueryHandler` and `PolicyEngine.ComputeSlice()` — corrected during implementation from the original single-layer plan.** The original plan put the `CancelledAt` filter solely inside `PolicyEngine.ComputeSlice()`. Verified against the live code that this is insufficient: `ComputeSlice` receives `presets` as an already-flattened, pre-resolved list built by the query handler *before* `ComputeSlice` is ever called (`presetIds` is unioned from `blocks.Select(b => b.BlockPresetId)` and `sessions.Select(s => s.BlockPresetId)`), and `BlockedApps`/`BlockedSites`/`AllowedSites` are computed purely from that flat `activePresets` list — with zero cross-referencing back to which block contributed which preset. Filtering `activeBlocks` alone inside `ComputeSlice` would correctly stop the Ritual and shrink `SliceEnd`, but would leave a cancelled block's apps/sites enforced indefinitely, since its `BlockPresetId` was already folded into `presets` upstream. Building true preset↔block correlation into `PolicyEngine` was considered and rejected as out of scope — it would change `ComputeSlice`'s long-standing, deliberately-tested contract and ripple through most of `PolicyEngineTests.cs`. The actual fix: `ComputeActivePolicySliceQueryHandler` excludes `CancelledAt.HasValue` blocks *before* building `presetIds`, so a cancelled block's preset is never resolved or passed to `ComputeSlice` at all. `PolicyEngine.ComputeSlice()` *additionally* and independently filters `activeBlocks` by `CancelledAt` on its own inputs (defensive — it shouldn't assume callers pre-filter), which is what actually drives `ActiveBlockPresetType`/`ActiveFocusBlockId`/`FocusSessionCompleted`/`SliceEnd`.
- **Planner visibility:** `GetPlannedBlocksForDayQueryHandler` excludes any block with `CancelledAt.HasValue` from the calendar view — same "Application computes, UI only references" precedent as `IsUnderInEffectContract`.
- **Active session on a cancelled block — confirmed with the architect: force-end it too, not just the block.** Stamping `CancelledAt` alone does *not* stop a currently-running session, since `SessionStartedEventHandler` already applies enforcement from the Session itself, independent of the block from that point on. Real fix: `BreakNenContractCommandHandler` gains `ISessionRepository`, calls `GetActiveAsync()`, and if the active session's `OriginatingBlockId` matches one of this contract's blocks, calls `session.Complete(now)` directly on the loaded entity and saves it. **Deliberately not composed through `EndSessionCommandHandler`** — every command handler is wrapped by `TransactionalCommandHandler`, which commits once after it returns; nesting a second command call would trigger a second, separate commit, reopening the exact non-atomic risk Gap 7 eliminated. Mutating the `Session` entity directly and letting `EfCoreUnitOfWork.CommitAsync()` walk it alongside `NenContract`/`PlannedBlock` in the same commit mirrors `StartSessionCommandHandler`'s already-established precedent for atomic cross-aggregate mutation. No new `SessionStatus` value — reuses `Completed`; `SessionEndedEvent` publishes in the same commit and the already-built `SessionEndedEventHandler`/`ShellViewModel` Post-Session queuing pick it up with zero new code.
- **For symmetry with Gap 4's "domain events raised inside entities" rule**, `MarkCancelled` raises a `PlannedBlockCancelledEvent`, matching every other state-transition method in this codebase — even though nothing consumes it yet. Same "deliberately silent" posture already accepted for `SessionMissedEvent`.

**Confirmed via `NenFocus.Tests`:** 874 total, 871 passing (the only failures are 3 pre-existing, unrelated `BlockPresetRepositoryTests` cases involving em-dash string comparison, confirmed present on `dev` before this work via `git stash`). Migration `20260818201041_AddPlannedBlockCancelledAt` adds the column; diff contains only that column, confirming the `AggregateRoot` promotion needed no EF changes.

**Principle demonstrated:** a scope decision (Gap 7's delete-only cleanup) can be correct when it's made and still worth reversing later, once a *specific, concrete* new requirement — not just a vague "might be nice" — makes the original tradeoff wrong. And: when a query handler pre-filters its inputs before handing them to a Deep Module, verify the Deep Module doesn't also need its own independent filter — trusting a caller's upstream filtering to already be precise is an implicit contract that breaks the moment either side changes independently (the same lesson Gap 21's third addendum re-learned later, at the `PolicyEngine` boundary specifically).

## Gap 24 — `GetNenContractDeficitsQueryHandler` Used Raw Elapsed Minutes, Not Credited Minutes — a Late-Started Session Running Past the Block's Own End Could Silently Zero Out a Real Deficit *(closed, 2026-08-21)*

**The gap, found by the architect while testing the new "Incomplete Blocks" popup (Gap 22/23's sibling feature, built the same week) — reproduced against the live DB, not assumed:** a Daily Flexibility contract's 2-hour block, ritual completed 36 minutes late, session run to completion — the day's floor badge correctly showed ~1.4h/2h credited (via `GetNenContractCompletedFocusHoursQueryHandler`, which already goes through `CreditedFocusMinutes`), but the block never appeared in the Incomplete Blocks popup at all, despite a real ~0.6h remaining deficit. Traced directly against `%AppData%\NenFocus\NenFocus.db` (mirroring Gap 21's own DB-verification precedent): the session started at 15:36 (36 min late against a 15:00–17:00 block) and ran a fixed 120-minute duration to 17:36 — 36 minutes *past* the block's own 17:00 scheduled end. `GetNenContractDeficitsQueryHandler` computed `rawDeficit = scheduledMinutes(120) − actualElapsedMinutes(≈120)` using the session's raw, uncapped elapsed time (`Session.GetElapsedTime` = `EndedAt − StartedAt`) — since the late start was fully offset by running past the block's own end, `rawDeficit` collapsed to ≈0, and the block was filtered out of the deficit list entirely (`if (remainingDeficit <= 0) continue;`).

**Root cause, precisely:** `IFocusBlockOutcomeClassifier.CreditedFocusMinutes` already exists specifically to answer "how much of *this block's own scheduled window* was honored" — for a `StartedLate` verdict it correctly caps credit at `scheduledEnd − completedAt`, deliberately refusing to award extra credit for time worked past the block's own end (Gap 20's "no unbounded bonus credit" fix). `GetNenContractDeficitsQueryHandler` never called it — it re-derived its own, uncapped notion of "how much was completed" straight from the session's raw elapsed time, which has no relationship to the block's own scheduled window at all. Two different answers to "how much of this block did the user actually do," one correct (feeding the Daily Floor badge) and one wrong (feeding the deficit ledger and, by extension, the Incomplete Blocks popup) — the exact same class of drift Gap 6/11/20 already caught and fixed elsewhere in this codebase, just not caught here until a new UI feature (the Incomplete Blocks popup) finally exercised a combination of inputs (late start + session running past the block's own end) the existing test suite had never covered.

**The closure:** `GetNenContractDeficitsQueryHandler` now calls `_classifier.CreditedFocusMinutes(block.Start, block.End, block.RitualCompletedAt, session?.EndedAt, actualElapsedMinutes)` and computes `rawDeficit` from the credited result, not the raw one. `FocusBlockDeficitDto.CompletedMinutes` (added the same week for the Incomplete Blocks popup's "completed/planned" display) is populated from the same credited value, so the popup's numbers can never disagree with the day's floor badge. `_classifier` was already an injected dependency — no new constructor parameter.

**Confirmed via `NenFocus.Tests`:** new case `HandleAsync_StartedLateSessionRanPastBlocksScheduledEnd_DeficitUsesCreditedNotRawElapsed` reproduces the exact bug (asserted failing against the pre-fix handler — empty result — before the fix landed), then passes against the fix. Two pre-existing tests (`HandleAsync_StartedLateBlockWithPartialSession_...`, `HandleAsync_EndedEarlyBlock_...`) needed an explicit `CreditedFocusMinutes` stub added — they'd been passing only because those particular fixtures never happened to overflow the block's window, so raw and credited had always coincidentally agreed until this case.

**Principle demonstrated:** the same lesson Gap 6/11/20 already taught, learned again because a new consumer finally exercised the untested combination — when two different query handlers both need "how much of this block was completed," compute it once (`CreditedFocusMinutes`) and have both call it, never let a second handler re-derive its own version from more primitive inputs. A bug like this can sit correctly-looking in shipped, tested code for weeks — the existing deficit tests were all individually correct, just never combined "started late" with "ran past the block's own end" in one fixture.

**Note (2026-08-21):** the "Incomplete Blocks popup" referenced above as the triggering consumer was itself removed later the same session — see Gap 25. This gap's fix (`GetNenContractDeficitsQueryHandler` using credited, not raw elapsed, minutes) is independent of that popup's fate and remains correct/needed regardless of which UI reads the deficit ledger.

## Gap 25 — The Redemption Mechanism Gets Its First Real UI, After Two Discarded Shapes and Three Bugs Found Testing the Third *(closed, 2026-08-21)*

**The starting discovery — doc drift, not a design gap.** `DOMAIN_DICTIONARY.md` and `DESIGN_GAP_HISTORY.md` both described the Planner's "Redemption" form section as `*(built)*` since 2026-07-08. Handed a spec for a "Makeup Blocks" feature (arriving from a separate conversation) that assumed this was greenfield work, a check against the live code first — grepping the entire UI project for any reference to redemption entries — found **zero**. The Application-layer machinery (`GetNenContractDeficitsQuery`, `CheckRedemptionEntryQuery`, the Create/UpdatePlannedBlock guards) was real, fully built and tested since 2026-07-08 Slices 6–7. No UI had ever been wired to it. The originally-handed-off spec also proposed a `MakesUpForBlockId` (one-to-one) shape, incompatible with the already-built `RedemptionEntries` (one-to-many) domain shape — building it as specified would have meant either ignoring existing, tested code or running two parallel redemption mechanisms. Both problems were surfaced before any code was written, not fixed silently.

**First shape, built then fully removed: a day-level popup.** `GetIncompleteBlocksForDayQuery` (composing `GetNenContractDeficitsQuery`, filtered to one day), a day-header "N incomplete" badge, and a popup listing that day's incomplete blocks with a time-picker "Create Redemption" sub-form. This surfaced Gap 24 (above) while being tested. The architect then asked for a fundamentally different interaction — drag a block into position rather than type times into a form — making this whole shape obsolete rather than merely buggy. `GetIncompleteBlocksForDayQuery`, the popup, the day-header badge, and `PlannedBlockDto.RemainingDeficitMinutes` (added to drive the badge) were all deleted in the same pass that replaced them, including their tests — nothing was left half-built or commented out.

**Second shape, built then fully removed: a red "+" icon with a draggable in-memory draft.** Interrogated properly before building: state model (an in-memory `RedemptionDraftBlock`, deliberately **not** a reuse of `ContractDraftBlock` — that type is wired end-to-end into the whole-contract wizard flow, and forcing a single ad-hoc block through it would mean either a pile of irrelevant side effects or scattering "is this really a contract draft?" branches through it, the exact "one flag, two meanings" smell `SkippedOccurrence`/`ContractFloor` already rejected), trigger (icon on the incomplete tile), default placement (next 15-minute mark strictly after now), validation (live for past-date/contract-date-range, deferred to the server for Work Hours/overlap — matching what contract-drafting's own drag-move path already does, not a new standard), and a Confirm/Cancel `Popup` that re-anchored to the tile on every drag tick (reusing the existing `Tiles.CollectionChanged` → `RebuildTiles()` hook, no new wiring). Fully built, then the architect asked for it to be removed entirely: *"the way you create a make up block is now just by creating a new block tile on the planner instead."* `RedemptionDraftBlock`, the icon, the drag branch in `MoveOrResizeBlockAsync`, the popup, and every supporting method were deleted in one pass, confirmed via a full grep for zero remaining references before moving on.

**Third shape — what shipped.** Creating an ordinary new Focus Block, the form's preset dropdown gets a "Redemption" toggle whenever the selected preset + date combination is eligible to cover exactly one incomplete block (new `FindRedemptionEligibleBlockQuery`, composing `GetNenContractDeficitsQuery` + the existing `NenContract.CheckRedemptionEligibility` domain method — never re-derived). This resolved a live tension with Open Gap D along the way: an early version of this design would have auto-linked *any* new block sharing a preset with an incomplete block, silently, without the user confirming that's what it was for — the same "silently auto-allocating coverage" pattern Open Gap D already rejected for the dropped Spontaneous Redemption path. Flagged directly rather than built past; the architect chose the explicit-click toggle instead, which requires the user to be the one who decides a block counts as a redemption, consistent with Gap D's standard. Clicking the toggle suggests an End time and dispatches the same `CreatePlannedBlockCommand`/`RedemptionEntries` already built — no new command, no new validator beyond one added rule (below).

**Addendum 1 — the suggested End time silently truncated fractional minutes.** `TimeSpan.FromMinutes(remainingDeficit)` then reading `.Minutes` drops the fractional part — a real deficit of 53.177 minutes suggested exactly "53," not "53.18" or "54." Traced against the live database (same technique as Gap 21/24): a day's floor badge stayed amber instead of turning green by about 11 seconds, because the redemption block was sized to the truncated suggestion and the user completed it exactly as suggested. Fixed with `Math.Ceiling` — the suggestion now always rounds *up* to the next whole minute, so accepting it as-is can only meet-or-exceed the real deficit, never fall short.

**Addendum 2 — the ceiling fix immediately caused a different rejection.** `RedemptionEntries.MinutesCovered` had been set to the block's own scheduled duration `(endUtc − startUtc)`. Once that duration was rounded *up* (Addendum 1), it now routinely exceeded the real (fractional) remaining deficit, and `CheckRedemptionEntryQuery`'s existing "can't claim more than what's outstanding" guard correctly rejected it — "This covers more minutes than the referenced block still has outstanding," reported directly from a real "ended early" block. The fix: `MinutesCovered` and the block's own duration were never required to be the same number (domain Rule 6/7 already say surplus block time beyond the claimed amount is fine, it just isn't attributed to any specific missed block) — the ViewModel had conflated them. Decoupled: `MinutesCovered = Math.Min(blockDuration, remainingDeficit)`, so the block stays long enough to close the day's floor gap while the ledger claim never exceeds what's genuinely outstanding.

**Addendum 3 — the same suggestion could overflow past midnight.** A deficit larger than the remaining room in the day (e.g. 45 minutes owed starting at 23:30) produced a suggested End time like "24:28" — not just a display oddity: `TimeSpan.TryParse("24:28")` accepts it as *1 day + 28 minutes* rather than rejecting it, so saving it unmodified would have scheduled the block a full calendar day later than intended. Fixed by clamping the suggestion at 24:00 and showing an inline notice stating how much of the deficit that leaves uncovered. Work Hours was deliberately left out of the clamp — reasoned through explicitly as "most DDD": `NenContract.WorkHoursPolicy` is already the single source of truth, enforced server-side for every block-creation path in the app including this one; teaching the client that rule too, for one display suggestion, would mean either re-deriving a domain rule in a second place or widening `ActiveNenContractDto` with fields whose only consumer is a suggestion nicety, not an actual validation need. If Work Hours does reject the clamped suggestion at Save, the user gets the same `FormError` experience as any other Work-Hours-violating block today — no regression, no silently-wrong guess.

**Confirmed via `NenFocus.Tests`:** `FindRedemptionEligibleBlockQueryHandlerTests` (7 cases: contract not found, no matching preset, `DailyFlexibility` same-day-only, `PeriodTimeBudget` any-day, `Locked` never eligible, earliest-match tiebreak), plus the existing `GetNenContractDeficitsQueryHandlerTests`/`GetPlannedBlocksForDayQueryHandlerTests`/`CreatePlannedBlockValidatorTests` suites extended along the way. The three addenda are ViewModel-layer fixes (`PlannerPageViewModel.ToggleMarkAsRedemption`/`SaveAsync`) — this codebase does not unit-test the ViewModel layer, so these were verified by full-solution build + manual reasoning against the exact live-database numbers that reproduced each one, not by new automated tests. 998 tests passing throughout.

**Principle demonstrated:** two lessons stacked on top of each other. First, the same one Gap 16 already taught — check whether something is already built before treating a handoff as greenfield; the backend here was real and tested, only the UI was missing, and the missing half was the *entire* actual scope. Second: fixing a rounding bug by rounding the other direction is not automatically safe — Addendum 1's fix (round up) directly caused Addendum 2's bug (over-claiming), because two numbers (a block's own duration, and how much of a deficit it's allowed to claim) had been silently treated as one. A "safe" direction for one invariant (the day's floor total) can be an unsafe direction for a different invariant (the ledger's claim cap) computed from the same value — the actual fix was recognizing the two numbers never needed to be equal in the first place.

## Gap 26 — Redemption Becomes Automatic Attribution, Not a Toggle — Widened to Lockdown, Combined With a "Cover Deficit" Quick-Create *(closed, 2026-08-21)*

**The ask, same day Gap 25 shipped the toggle:** the architect wanted the whole mechanism to feel less like a manual step and more like a natural consequence of scheduling — any Focus Block placed on a day/period eligible to cover an outstanding deficit should just count, without a click. Widened during interrogation to also open **Lockdown** to redemption (previously the one `StrictnessRule` that hard-rejected it outright), and to add a banner-level "quickly create the tile I need" action alongside the passive detection.

**The Lockdown premise, checked against the live code before accepting it:** the architect's framing was "you can always insert new blocks under Lockdown, you just can't edit/delete/split an existing one." Verified directly against `CreatePlannedBlockValidator` — it has no `StrictnessRule` branch at all; only `NenContract.CheckRedemptionEligibility` (called solely when `RedemptionEntries` is non-empty) ever rejected `Locked`. So the premise was already true; the only real change needed was widening `CheckRedemptionEligibility` itself, not touching block-creation permissions.

**`NenContract.CheckRedemptionEligibility`, rewritten:** `Locked` and `DailyFlexibility` now share one same-day branch (Locked's redemption window is confined to the day it's owed, same as Daily Flex's whole rearrangement model). `PeriodTimeBudget` branches on whether the contract carries a real `ContractFloor` (any day in the period) or a real per-day floor instead — the Gap 18 hybrid — in which case it's same-day too, for the same "each day has its own obligation" reason. Every branch now returns `Allowed` or `WrongDay`; `RedemptionEligibility.NotAllowed` became unreachable and was deleted outright, following the Gap 15 precedent of removing an enum value once nothing distinguishes it rather than leaving it as dead code.

**The attribution/eligibility computation moved from two client-validated query types into one server-side Deep Module.** `CheckRedemptionEntryQuery`/`CheckRedemptionEntryQueryHandler`/`RedemptionEntryCheckResult`/`RedemptionEntryMessages` (validated a client-supplied `RedemptionEntries` list) and `FindRedemptionEligibleBlockQuery`/`Handler` (found one eligible target to drive the toggle) were both deleted. `ComputeRedemptionAttributionQuery`/`Handler` replaces both: given a preset, a block's `[Start, End)`, and either an explicit `ContractId` or `null` (auto-discover across every currently in-effect contract via `INenContractRepository.GetAllInEffectAsync`), it resolves which single contract's deficits apply, walks them oldest-first with spillover (`Math.Min(remainingBlockDuration, remainingDeficit)` per entry — Rule 5's multi-entry support finally has a real driver), and returns `{ ContractId, Entries }`. `CreatePlannedBlockCommand`/`UpdatePlannedBlockCommand` both dropped `RedemptionEntries` as client input entirely — there's nothing left for the client to choose. `CreatePlannedBlockCommandHandler`/`UpdatePlannedBlockCommandHandler` call the query themselves and use its result directly.

**A real design bug caught while writing the handler's own tests, before it shipped:** the first draft returned `ContractId: null` whenever no eligible deficit was found, regardless of whether the caller had passed an explicit `ContractId`. That's correct for auto-discovery (nothing to attach an ordinary new block to), but wrong for `UpdatePlannedBlockCommandHandler` recomputing an *already-contract-tied* block's coverage, or `SplitPlannedBlockCommandHandler` splitting one — either would have silently unlinked the block's contract the moment its deficit was fully covered or its date/preset changed. Fixed by echoing back an explicit `ContractId` on the empty-eligible path instead of always returning null; auto-discovery (`ContractId: null` in) still correctly stays null when nothing qualifies. `UpdatePlannedBlockCommandHandler` additionally never *calls* the query at all when the existing block has no contract — editing a standalone block does not auto-discover one for the first time, matching the existing "re-parenting isn't a designed operation" comment already on `UpdatePlannedBlockCommand`.

**A second real bug, pre-existing since Gap 17, found while fixing Split for the new model:** `SplitPlannedBlockCommandHandler` copied the *same* `RedemptionEntries` list onto both resulting halves verbatim — a genuine double-count (a 15-minute entry duplicated onto both halves would read as 30 minutes covered against a single missed block). Fixed by querying attribution once for the original block's whole combined span, then partitioning the returned entries across the two halves by each half's own duration — an entry entirely within one half's window goes only to that half; one straddling the cut point splits into two entries against the same missed block, proportioned by each half's share.

**Validator consequence, reasoned through rather than assumed:** `CreatePlannedBlockValidator`'s Work Hours check used to test `command.ContractId` directly, skipping the check whenever it was null. With attribution now server-computed and potentially auto-discovering a contract the command itself never named, that would have let a redemption block silently bypass Work Hours validation. Fixed by having the validator call the same `ComputeRedemptionAttributionQuery` the handler will call (for Focus blocks only) and checking `AllowsBlockPlacement` against whatever contract it resolves — accepting one extra query call per validation as a contained, already-precedented tradeoff (`CreatePlannedBlockValidator` already called a sibling query per `RedemptionEntries` item before this pass) rather than threading a computed result between validator and handler, which aren't otherwise wired to share state in this pipeline.

**UI, "Cover Deficit" banner button — the second half of the ask.** The old per-block "Redemption" toggle and its `EligibleRedemptionTarget`/`IsMarkedAsRedemption` state are gone entirely; the block-creation form now just shows a passive, non-interactive preview (`RedemptionSuggestionNotice`, refreshed on preset/date/**and now also time** changes) computed from the exact same `ComputeRedemptionAttributionQuery` the handler will call on Save — the preview can never drift from what actually happens, and there is nothing to click. Separately, the active-contract banner gained a "Cover Deficit" button, mirroring the existing Nen Contract button+`Popup` pattern exactly (named `Button` as `PlacementTarget`, `BottomEdgeAlignedRight`, light-dismiss). A new `GetSuggestedRedemptionPlacementsQuery` groups a contract's deficits coverable *today* by preset, sums each group's remaining minutes into one target duration, and computes a placement via a pure algorithm: snap forward to the next quarter-hour; shift earlier (never before `AsOf`) only if needed so the full duration still fits before the day's boundary (midnight, or the contract's Work Hours close, whichever binds); search past any conflicting Focus Block that day and retry. When even starting right now can't fit the whole amount, the suggestion starts at `AsOf` and ends at the boundary with `CanFullyCover: false` — the ViewModel shows a confirmation dialog ("won't fully cover — create anyway?") before dispatching a knowingly-partial tile, rather than silently under-covering or refusing outright. More than one preset owing opens the popover for the user to pick; exactly one skips straight to creating the tile.

**A revisited idea, explicitly parked rather than built:** the architect floated letting the user explicitly combine two same-preset incomplete blocks into one redemption tile via the picker, then asked "or should we drop it for now" — dropped after clarifying it would add real UI complexity (per-instance rows, multi-select state) for a case the automatic per-preset summing already handles invisibly (a preset's tile is already sized to its *total* outstanding deficit across every missed block, oldest-first). Revisit only if the automatic total ever proves to be the wrong default in practice, not before.

**Confirmed via `NenFocus.Tests`:** 997 passing. New coverage: `ComputeRedemptionAttributionQueryHandlerTests` (auto-discovery across multiple in-effect contracts, same-day vs any-day eligibility per strictness mode, oldest-first spillover, `ExcludeBlockId`, the explicit-`ContractId`-echoed-back-on-empty fix), `GetSuggestedRedemptionPlacementsQueryHandlerTests` (snap, boundary shift against both midnight and Work Hours close, overlap search, the can't-fully-cover fallback — including the exact 23:05/50-minute example worked through during design), `SplitPlannedBlockCommandHandlerTests` (the double-count fix, entry-straddling-the-cut-point split), updated `NenContractTests` for the widened `CheckRedemptionEligibility`, and updated Create/Update command handler and validator tests throughout.

**Principle demonstrated:** the same "check the live code before accepting a premise" discipline Gap 16/25 already established, applied to a *positive* claim this time ("Lockdown already allows new blocks") rather than a negative one ("this doesn't exist yet") — verifying it was true saved a needless validator change. And: writing the new query handler's own unit tests immediately surfaced a real correctness bug (the silent-unlink risk) that manual reasoning about the "happy path" auto-discovery case had missed entirely — the tests weren't just documentation of already-correct behavior here, they were how the bug got found.

## Gap 28 — Planner "Done Block" Snapshot View, Replacing the Greyed-Out Edit Form *(closed, 2026-08-21)*

**The ask:** clicking a finished block in the Planner opened the same edit form used for future blocks, just with every field disabled — functional but ugly, and gave no view of what actually happened (Zetsu goal, reflection, blocked attempts). The architect wanted a dedicated read-only "snapshot" instead, but only for genuinely done blocks — a block whose active session is still running must keep the existing locked-form behavior unchanged.

**Interrogated before any code:** the "done" trigger (Focus: `Outcome` resolved via the classifier, not merely `IsCompleted`; Background: no `Outcome` concept at all, so `HasEnded` is the only signal — confirmed directly against `FocusBlockOutcomeClassifier`, which never runs for a `BackgroundBlock`); content for a Focus block with no Session (Missed — Cancelled blocks never reach the Planner's tile list at all, filtered out by `GetPlannedBlocksForDayQueryHandler` already) versus one with a Session (full snapshot: goal, reflection, expandable blocked-attempts list, redemption coverage if any); a genuinely new dedicated view rather than reusing the edit-form modal; and — the largest fork — what "delete" should mean for a done block.

**The delete-rule reversal.** `DeletePlannedBlockValidator` had an unconditional rule since Gap 9: "this block has already ended and is kept as a historical record — it cannot be deleted." The architect wanted this reversed specifically for non-contract-linked blocks (their only remaining role once done is display in this new snapshot, and Gap 9's original worry — protecting Insights/Missed-Session historical accuracy — doesn't apply to a block nobody but the Planner ever reads again), while making contract-linkage protection **permanent** rather than scoped to `IsInEffect` (a block that was ever part of a Nen Contract can never be deleted, even after that contract concludes — protects the contract's historical Day-Met/completed-hours stats forever, not just while the contract is live). Net effect: `clock`/`contracts` (previously injected for the `HasEnded`/`IsInEffect` checks) became entirely unused and were dropped from the validator's constructor — a rule reversal that happened to also shrink the module's dependency surface.

**The closure:**

## Gap 29 — A Redemption Block Could Generate a Fresh Deficit of Its Own; Rule 13 Was Documented But Never Actually Enforced *(closed, 2026-08-21)*

**The report:** after starting a block late (creating a deficit), then using the "Cover Deficit" flow (Gap 26) to complete a redemption block covering it, the Cover Deficit button and active-contract banner still showed an outstanding deficit and offered a new redemption — despite the day's floor badge already reading green.

**Root cause, precisely — and a doc/code drift, not a fresh design question.** `DOMAIN_DICTIONARY.md`'s Redemption Rule 13 already stated: *"A redemption block that itself is missed does not create additional deficit. The original missed block's deficit simply remains uncovered. No 'redeem the redemption' chain."* But `GetNenContractDeficitsQueryHandler` never actually implemented this — it looped over every `FocusBlock` in the contract uniformly, including ones that were themselves redemption blocks (`RedemptionEntries.Count > 0`), classifying each by its own `Outcome` and adding it to the deficit list if `Missed`/`StartedLate`/`EndedEarly` — with nothing exempting a block that was itself already covering someone else's deficit. A redemption block whose own Ritual completion landed even slightly past its 5-minute grace period (very plausible: "Cover Deficit" sizes the suggested block's window to exactly the deficit owed, often starting at or near "now," leaving little margin for the Ten→Zetsu→Ren→Hatsu click-through itself) would generate a brand-new deficit entry for itself — one nothing was ever designed to redeem, matching every symptom reported. The rule existed in the dictionary since Gap 26 closed the same day; the code just never caught up to it.

**The closure — pushed onto the entity, not left as a query-handler-local check.** `FocusBlock.CanContributeOwnDeficit(FocusBlockOutcome? outcome)` (new Domain method) combines both conditions that decide "is this block's own outcome a deficit the ledger should track" — the outcome must be a genuine shortfall (`Missed`/`StartedLate`/`EndedEarly`), and the block must not itself already be a redemption (`RedemptionEntries.Count == 0`). `GetNenContractDeficitsQueryHandler` now asks `block.CanContributeOwnDeficit(outcome)` instead of separately re-deriving both conditions inline — Tell, Don't Ask, the same move as `IsAtLeastAsStrict` below (Gap 30), done first here.

**Confirmed via `NenFocus.Tests` (1000+ passing):** new Domain-level `FocusBlockTests`-style coverage in `PlannedBlockTests.cs` (`CanContributeOwnDeficit` exercised directly against the entity for all three shortfall outcomes, `CompletedOnTime`, still-open/`null`, and each shortfall outcome again while `RedemptionEntries` is non-empty) plus a handler-level regression test (`HandleAsync_RedemptionBlockItselfStartedLate_DoesNotAppearAsItsOwnDeficit`) reproducing the exact reported scenario end-to-end. Existing redemption-coverage tests had only ever stubbed the covering block's own `Classify` result as `null` (never late/early) — the untested combination that let this ship in the first place.

**Principle demonstrated:** a rule can be correctly written down in `DOMAIN_DICTIONARY.md` and still not exist in the code it describes — the dictionary documents intent, not a guarantee of implementation, and neither should be trusted without checking the other. Also: when a business rule is a combination of two conditions checked together at one call site, it belongs on the entity as one named question (`CanContributeOwnDeficit`), not as two separately-maintained `continue` guards a future second call site could easily replicate incompletely.

## Gap 30 — `BlockPreset` Lock Only Protected the Blocklist Direction; an Allowlist Preset Could Be Weakened Freely While Locked *(closed, 2026-08-21)*

**Surfaced while reasoning about redemption integrity, not while touching presets directly.** Discussing whether a user could game a redemption block's credit by weakening its preset mid-flow, the architect's first assumption — that no protection existed at all — was wrong and corrected against the live code: Gap 8's add-only lock (`UpdateBlockPresetValidator`) already exists, is tested, and is documented (`DOMAIN_DICTIONARY.md`'s Block Preset section). But auditing it for the redemption-specific question surfaced a real, separate, previously-untested bug in that existing mechanism.

**The bug:** `UpdateBlockPresetValidator`'s `IsAddOnlyChange` required the proposed `Websites` list to be a **superset** of the current one, unconditionally — correct for a `Blocklist` preset (removing a blocked site weakens it, so add-only keeps it at least as strict), backwards for an `Allowlist` preset (removing an *allowed* site **narrows** what's let through — the stricter direction — while *adding* one **widens** it — the weaker direction, even though it's technically an addition). A locked `Allowlist` preset could therefore only ever become more permissive, never less, exactly inverted from what "locked" is supposed to guarantee. Every existing test for the locked/add-only behavior (`UpdateBlockPresetValidatorTests`) used `WebsiteFilterType.Blocklist` — the Allowlist direction had no coverage at all since Gap 8 shipped it 2026-07-07.

**Confirmed against the entity before fixing:** `BlockPreset.WebsiteFilterType` applies only to `Websites` — `BlockedApps` has no allow-mode concept whatsoever (always a plain blocklist), so apps are unconditionally add-only regardless of the preset's filter type. `ChangeWebsiteFilterType` also destructively clears the whole site list on switch (`_websites.Clear()`) — already correctly blocked outright while locked (`WebsiteFilterType` must stay unchanged), not a new finding, just confirmed still true.

**The closure — pushed onto the entity, mirroring Gap 29's move the same day.** `BlockPreset.IsAtLeastAsStrict(IReadOnlySet<string> proposedApps, IReadOnlySet<string> proposedSites)` (new Domain method) encodes the direction rule once: apps always add-only; sites add-only under `Blocklist`, remove-only under `Allowlist`. `UpdateBlockPresetValidator.IsAddOnlyChange` now delegates to it for the app/site check instead of re-deriving the (previously wrong) direction inline — the validator still owns the separate "every other field must be unchanged" checks (`Name`/`WebsiteFilterType`/`PresetType`/`Tags`), which aren't domain strictness logic, just equality comparisons.

**Confirmed via `NenFocus.Tests` (1000+ passing):** 6 new `BlockPresetTests` cases exercising `IsAtLeastAsStrict` directly (Blocklist add/remove, Allowlist add/remove — the two previously-untested cases now explicit) plus 2 new `UpdateBlockPresetValidatorTests` cases reproducing the exact locked-Allowlist scenario end-to-end through the full validator.

**Principle demonstrated:** an existing, tested, documented protection mechanism can still have an untested branch with inverted logic — "it's already built and covered by tests" isn't the same claim as "every direction of the rule it enforces is covered by tests." Also, the same Tell-Don't-Ask move applied twice in one session (`CanContributeOwnDeficit` above, `IsAtLeastAsStrict` here) to two unrelated subsystems that happened to share the same underlying smell: a validator or query handler comparing an entity's raw collections/fields directly to compute a business rule the entity itself should be the one to answer.

## Gap 31 — A Planned Session Could Hang Forever at `00:00:00`: Unhandled Exceptions in a Fire-and-Forget Auto-End Call Vanished Silently *(closed, 2026-08-21)*

**The report:** finishing a planned Focus block under a Nen Contract, the countdown reached `00:00:00` and just stayed there — the session never ended, no Post-Session screen appeared, nothing.

**Root cause — a pre-existing structural gap, not a contract-specific regression.** `ActiveSessionMonitor.Recalculate()` (`NenFocus.Infrastructure/Services/ActiveSessionMonitor.cs`) detects timeout correctly (`remaining <= TimeSpan.Zero`) and is latched to fire only once per session (`_autoEndPending`), but the actual auto-end call — `_ = AutoEndAsync();` — is fire-and-forget with **zero exception handling**, and both the timer and the latch are already stopped/set *before* that call runs. `AutoEndAsync` resolves `ICommandHandler<EndSessionCommand, EndSessionResult>` and awaits it; that chain runs through `TransactionalCommandHandler` (which only catches `DbUpdateException` for the unique-constraint case, confirmed by reading it directly — anything else propagates unhandled) → `EfCoreUnitOfWork.CommitAsync()` → `SessionEndedEventHandler` (removes enforcement, cancels reminders, sends a notification). Any exception anywhere in that chain becomes an **unobserved task exception** on the fire-and-forget call — silently discarded, with nothing left to retry (timer already stopped, latch already set) and nothing logged anywhere, since this path had no logging at all before this fix. `EndSessionCommandHandler` itself was read in full and confirmed to have **no** contract/deficit-related code path — today's earlier Gap 29/30 changes are not implicated; this bug predates them and simply surfaces more often for Planned/contract sessions, which are the ones people actually let run to natural completion rather than clicking "End Session" manually (a separate, synchronous path that would have surfaced the error instead of swallowing it).

**The closure — mirrors `ScheduledEnforcementService`'s existing heartbeat resilience pattern exactly, not a new one invented for this.** `ActiveSessionMonitor` gained an `ILogger<ActiveSessionMonitor>` (same DI convention `ScheduledEnforcementService` already uses). Both `AutoEndAsync` and `AutoResumeBreakAsync` wrapped in try/catch: on failure, log the exception with the session ID, and — for auto-end specifically — re-arm (`_autoEndPending = false`) and restart the timer, so the *next* tick retries automatically instead of the failure being permanent. `AutoResumeBreakAsync`'s failure is logged but not retried (the timer was never stopped for that branch, and `_breakStartedAt` is already cleared beforehand, so there's no equivalent "stuck forever" failure mode to guard against — just a stale DB-vs-UI break state worth knowing about via the log).

**No test coverage added** — `ActiveSessionMonitor` has no existing unit tests (an Infrastructure-layer singleton wrapping a real `System.Timers.Timer` and DI scope resolution, same "don't unit-test the hosted-service shell directly" precedent already established for `NenContractHeartbeatService`/`ScheduledEnforcementService`). Verified via full-solution build (C# + Avalonia XAML) and the full `NenFocus.Tests` suite (1016 passing, unaffected).

**Explicitly evaluated and rejected: modeling this as a domain concept.** Asked directly whether this fix followed DDD principles — it does, but not via an entity-level move like Gap 29/30 the same day. Retry-on-transient-failure for a fire-and-forget background timer isn't a fact about a `Session`; it's a purely technical reliability concern (coping with a flaky DB commit or hosts-file I/O error), and `Domain` cannot depend on `ILogger` regardless. The fix stays entirely in Infrastructure, where `ActiveSessionMonitor` already lives, and doesn't touch or bypass the "commands don't call enforcement/notifications directly, event handlers do" rule — `AutoEndAsync` still only ever calls the same `ICommandHandler<EndSessionCommand,...>` it always did.

**Principle demonstrated:** a fire-and-forget async call (`_ = SomeAsync()`) with no exception handling is not merely a style nitpick — it's a silent failure mode waiting to happen, and one bad exception inside it can leave a user-facing feature (here, the entire active-session timer) stuck indefinitely with zero diagnostic trail. Also: not every bug is a missed domain-modeling opportunity — recognizing when a fix is correctly infrastructure-only, rather than reaching for an entity-level abstraction because the previous two fixes that session happened to be that shape, is itself the DDD-consistent judgment call.

## Gap 32 — A New Rule Written Down, Then Immediately Used to Audit and Fix Three More Instances of the Same Smell *(closed, 2026-08-21)*

**The ask:** after Gaps 29–31 (four bugs in one session, all sharing the same root shape — an Application handler re-deriving a business rule from raw entity fields instead of asking the entity a named question), the architect asked whether a more streamlined, DDD-aligned way to prevent this existed. The answer: write the pattern down as an explicit rule (`MODULE_STANDARDS.md`'s new "Application Handler Forbidden Zone," mirroring the existing ViewModel Forbidden Zone), then immediately use that rule's own criteria to audit the rest of the Application layer before more instances shipped as bugs.

**The audit turned up one genuine, high-confidence live bug and one lower-severity consistency issue** (a third, Infrastructure-layer finding — a one-tick boundary mismatch between `GetUnresolvedFocusBlocksAsync`'s SQL filter and `FocusBlockOutcomeClassifier.Classify`'s Missed branch — was flagged but deliberately left unfixed: out of the audited layer's scope, and no evidence it has actually bitten):

**Bug 1 (high confidence) — `CreatePlannedBlockCommandHandler`/`UpdatePlannedBlockCommandHandler`'s active-session overlap guard recomputed the session's end as `StartedAt + Duration` instead of using `Session.EndAt`.** For a **Planned** session, `StartSessionCommandHandler` pins `EndAt` to the originating block's own scheduled end (`session.Start(now, originatingBlock?.End)`), while `Duration` stays the block's full nominal length regardless of exactly when the Ritual completed — a documented invariant (`StartSessionCommandHandler`'s own comment: "Duration... is a fixed fact about the schedule... not 'time remaining from Ritual completion'"). A session started even slightly late (still within the 5-minute grace period) therefore makes `StartedAt + Duration` overshoot the session's real `EndAt` by exactly the lateness — the overlap guard could wrongly reject a new or edited Focus block that legitimately fits right after the session's actual end. `GetActiveSessionQueryHandler` already used `session.EndAt` correctly for the same fact, proving it was the intended accessor all along. Fixed by using `activeSession.EndAt` directly in both handlers.

**Bug 2 (lower severity, same shape) — `StartSessionCommandHandler` checked `now >= originatingBlock.End` inline instead of calling `PlannedBlock.HasEnded(now)`**, the codebase's one documented canonical "is this past" definition (`End < asOf`, strict). Only differs at the exact-equality instant (`now == End`), so unlikely to have caused a real reachable bug, but it's the identical anti-pattern and costs nothing to fix. Swapped to call `HasEnded` directly.

**Confirmed via `NenFocus.Tests` (1024 passing):** new regression test for Bug 1 in both `CreatePlannedBlockCommandHandlerTests`/`UpdatePlannedBlockCommandHandlerTests` (a Planned session started 5 minutes "late," `EndAt` pinned earlier than `StartedAt + Duration`, a new block scheduled to start exactly at the real `EndAt` must succeed) and one for Bug 2 in `StartSessionCommandHandlerTests` (originating block's `End` exactly equal to `now` must still allow starting).

**A follow-up question, answered precisely rather than reassured vaguely:** the architect asked whether using `EndAt` here could "take away from the grace period" or revive the Gap 20/24/25-era credited-minutes/rounding bugs. It doesn't: grace-period credit is computed entirely separately, by `IFocusBlockOutcomeClassifier.CreditedFocusMinutes`, from the **block's own** `Start`/`End`/`RitualCompletedAt`/`SessionEndedAt` — never from `Session.EndAt` or the `sessionEnd` local variable this fix touched. The two subsystems don't share an input at all; `EndAt` is, if anything, the *more* correct value here, since it's the same boundary (`originatingBlock.End`) `CreditedFocusMinutes` already caps a late start's credit against — a late-started Planned session was never going to run past that point regardless of this fix.

**Principle demonstrated:** writing a rule down doesn't just prevent the *next* instance — used immediately as an audit checklist, it found instances that already existed, unnoticed, in already-shipped code. Two of Bug 1/2's three call sites (`GetActiveSessionQueryHandler` correct, `CreatePlannedBlockCommandHandler`/`UpdatePlannedBlockCommandHandler`/`StartSessionCommandHandler` not) had silently disagreed about the same fact for a while — the exact "same fact, computed twice, one copy drifts" shape the new rule exists to catch before it ships as a bug report instead of an audit finding.

## Gap 33 — A Redemption Tile Could Fully Cover a Deficit and the Cover Deficit Button Would Still Stay Lit, From a One-Tick Rounding Loss — a Regression of Gap 25, Not a New Bug Shape *(closed, 2026-08-22)*

**The report:** ending a Focus block early under a Daily Flex contract, then using Cover Deficit to create a redemption tile sized to close the gap exactly — the tile visibly and functionally covered the deficit, but the Cover Deficit banner button never disappeared, and clicking it again offered to create a second, redundant tile.

**Root cause, verified against the live database, not assumed.** `GetSuggestedRedemptionPlacementsQueryHandler.FindPlacement` sized the suggested tile's duration to the live deficit as a raw fractional `double` — here, `31.896581196666666` minutes, from an `EndedEarly` session timestamped to the millisecond — and passed it straight to `DateTime.AddMinutes`, which rounds to the nearest 100ns tick. `ComputeRedemptionAttributionQueryHandler` then read the persisted block's actual span back out as `TotalMinutes` to compute `RedemptionEntry.MinutesCovered`, landing at `31.896581195` — about 1.7e-9 minutes short of the live figure, reproduced exactly with a standalone script against the real numbers before either fix was written. `GetNenContractDeficitsQueryHandler`'s "is this fully covered" check (`remainingDeficit <= 0`) could then never trigger: the deficit was permanently, imperceptibly `> 0`.

**Not a new bug shape — a regression of one already fixed once.** Gap 25 Addendum 1 (2026-08-21) hit this exact class of bug in its previous form (`TimeSpan.FromMinutes(remainingDeficit).Minutes` truncating the fractional part) and fixed it with `Math.Ceiling` — *"the suggestion now always rounds up to the next whole minute, so accepting it as-is can only meet-or-exceed the real deficit, never fall short."* That rounding did not survive Gap 26's same-day rewrite of the mechanism into automatic attribution — nothing in the replacement `GetSuggestedRedemptionPlacementsQueryHandler` rounded at all, and the guarantee silently disappeared until a live bug report rediscovered it a day later.

**The closure — fixed at the source, not patched at the comparison.** Two changes, deliberately not one:
- `GetSuggestedRedemptionPlacementsQueryHandler`: `neededMinutes = Math.Ceiling(group.Sum(d => d.RemainingDeficitMinutes))`, computed before the value ever reaches `AddMinutes`. A whole number of minutes converts to ticks with zero rounding loss, so a redemption tile's actual persisted span is always `>=` the deficit it was sized for, and `ComputeRedemptionAttributionQueryHandler`'s existing `Math.Min(remainingDuration, deficit)` resolves to the exact deficit every time — never a tick-short approximation of it.
- `GetNenContractDeficitsQueryHandler`: a `0.01`-minute tolerance on the "is this resolved" check, kept as ordinary defensive practice for any future float-comparison path (e.g. a manually-timed block landing near-exact by coincidence) — not relied on as the primary fix, since a tolerance alone can't distinguish "genuinely covered, tick-rounding noise" from "genuinely short by a real, tiny amount."

**An audit for other instances, done before considering this closed.** Grepped every `.AddMinutes(...)`/`.AddSeconds(...)`/`TimeSpan.FromMinutes(...)` call across Domain, Application, Infrastructure, and the UI project for the same shape (a fractional `double` — not a literal or `int` field — feeding a timestamp later compared against an "at least X" threshold). Found none. Every other call site uses a whole-number literal or an `int`-backed field (`SessionDuration.DurationMinutes`, `IFocusBlockOutcomeClassifier.GracePeriodMinutes`, `PlannerDragMath`'s snap constants). `SplitPlannedBlockCommandHandler`'s own fractional `RedemptionEntries` redistribution was checked specifically, since it also touches `MinutesCovered` — found safe: its duration comes from the split dialog's own typed, clean-grid Start/End (never a fraction), and its arithmetic is an exact complement (`toSecond = entry.MinutesCovered - toFirst`), never a new `DateTime` round-trip.

**A deliberate no — not building a shared rounding helper.** Asked directly whether a generic utility should be built now so any future call site (Open Gap A's Usage Ceiling, Open Gap E's Recurring Blocks — both plausible future homes for the same "fraction into a persisted timestamp" shape) automatically gets this right. Declined: with exactly one real call site and no second one yet in existence, a shared helper would be an abstraction with no second caller to prove its shape correct — the same "empty box, narrow lid" smell already rejected elsewhere in this codebase (Gap 27's contract-preset detour; Open Gap K's Split dialog, whose four time fields were deliberately left unlinked rather than generalized). Instead, following the exact precedent Gap 32 set the previous day: the general shape of the risk is written down as a standing rule in `MODULE_STANDARDS.md`'s Application Handler Forbidden Zone (sibling to Gap 29–32's "no re-deriving a business rule from raw fields" rule), and a regression test (`GetSuggestedRedemptionPlacementsQueryHandlerTests.HandleAsync_FractionalDeficit_SuggestionRoundsUpToWholeMinute`) encodes the guarantee directly in code. The test is the more durable of the two safeguards — documentation alone already failed to prevent this exact regression once, when Gap 26 silently dropped Gap 25's fix.

**Confirmed via `NenFocus.Tests` (1030 passing):** new tests for the ceiling fix and the degenerate-placement guard (`GetSuggestedRedemptionPlacementsQueryHandlerTests`), plus three new covering-block-outcome cases in `GetNenContractDeficitsQueryHandlerTests` found and fixed in the same investigation (a covering block that ends up Missed must reopen the original deficit in full; one that ends early must cap its contribution at what it actually credited, not its planned claim; one still scheduled ahead and not yet judged must keep optimistic full credit).

**Principle demonstrated:** a documented rule is not a permanent guarantee against a later rewrite — Gap 25's rounding guarantee was written down in exactly the right place and still got silently lost one gap later, because nothing *enforced* it once the code it lived in was replaced. Documentation records intent; a regression test is what actually survives a rewrite. And: "make this more streamlined for the future" does not always mean "build the abstraction now" — the DDD-consistent answer, per Gap 32's own precedent from the day before, is to name the smell as a standing rule, use it as an audit checklist, and wait for a second real caller before generalizing.

## Gap 34 — The Cover Deficit Button Could Fire Mid-Session, Sizing a Redemption Tile Against a Number That Hadn't Settled Yet — Redemption Rule 18 *(closed, 2026-08-22)*

**The report:** starting a Focus block late under a Daily Flexibility contract, the Cover Deficit button appeared on the Planner and could create a redemption tile **while the late-started session was still actively running** — before anyone could know whether it would finish on schedule (making the final deficit small) or end early (making it larger). Sizing a real, scheduled tile against a number that could still change was the actual problem, not a display glitch.

**Root cause, precisely.** `IFocusBlockOutcomeClassifier.Classify` returns `StartedLate` the instant the Ritual completes past its grace period — correctly, since that's its job (a live "what does this look like right now" read, the same mechanism Day Met's progress bar already relies on updating in real time as a session runs). `EndedEarly` is only ever reported once `SessionEndedAt` is actually set, and `Missed` only once the block's window has fully closed with no ritual — both already inherently final by construction. `StartedLate` was the one exception: nothing gated it on the session having actually finished, so `GetNenContractDeficitsQueryHandler` could compute a deficit from a `creditedMinutes` figure that was still changing minute by minute.

**Interrogated, not assumed — two real forks, both resolved with reasoning tied to existing precedent, not preference:**
- **Scope: change the shared classifier, or add a narrower, second gate?** Rejected changing `Classify`/`CreditedFocusMinutes` outright — that would also freeze Day Met's live progress number, Insights, and Planner badges until each block finishes, none of which had ever been reported as wrong. Precedent: Gap 29's `FocusBlock.CanContributeOwnDeficit(outcome)` already established the pattern of *composing* `Classify`'s answer as an input to a narrower, second question, rather than changing the shared primitive every consumer depends on. The deficit ledger's real question — "has this settled enough to spend a real tile on it" — is exactly that kind of second question, answered entirely inside `GetNenContractDeficitsQueryHandler` by substituting `null` for a not-yet-final outcome; `Classify` itself is untouched.
- **What decides "settled"?** First landed on `Session.PostSessionAcknowledgedAt` (the architect's own initial framing: wait for the user to click Done on the Post-Session screen), and a `Session.IsPostSessionAcknowledged` property was built and tested against it. Revisited immediately, on the architect's own second thought: acknowledgment exists for an unrelated reason (`GetUnacknowledgedPostSessionsQuery`'s crash-recovery replay, `ShellViewModel` catching a resolved session nobody has seen after a restart) — reusing it here would couple two independent subsystems, and would leave an already-final, already-correct deficit hidden indefinitely if the user never gets around to dismissing that screen. Replaced with `Session.HasEnded => EndedAt.HasValue` (mirroring `PlannedBlock.HasEnded`'s exact naming idiom) — the minimal, sufficient condition: once the session has genuinely ended, naturally or early, the number cannot change further, full stop. `IsPostSessionAcknowledged` was deleted rather than left as unused surface area once superseded.

**The closure — one new Domain fact, one substitution site.** `Session.HasEnded` is the only new Domain surface. Inside `GetNenContractDeficitsQueryHandler`'s existing per-block resolution pass (already computing `outcome`/`creditedMinutes` for every block, from the Gap 33 restructuring earlier the same day), the resolved outcome is now `hasEnded ? outcome : null` before being stored — reusing every downstream branch already built for a `null` outcome (excluded as a deficit source; trusted optimistically as a still-pending covering block) with no further changes needed. Redemption Rule 18 records the result: a block's outcome counts toward the deficit ledger — as a source or as a covering block's contribution — only once its session has actually ended.

**Confirmed via `NenFocus.Tests` (1032 passing):** new cases for a still-running late-started session (excluded), and — the check that would have caught choosing the wrong gate — a session that has ended but is deliberately left unacknowledged (`PostSessionAcknowledgedAt` never set), which must still count toward the deficit. Every pre-existing test in the file needed its stubbed session updated to actually reach `Complete()`/`Miss()` (i.e., to have genuinely ended) rather than relying on a bare `Classify` stub alone — a gap in the existing fixtures' realism that this change surfaced, not a new bug.

**Principle demonstrated:** the first answer to "when is this final" was plausible, buildable, and fully tested — and still wrong, because it reused a fact designed for a different question. Two facts that happen to usually coincide (a session ending, and the user acknowledging it) are not the same fact, and the moment that was checked explicitly (what does `PostSessionAcknowledgedAt` actually exist *for*), the coupling stopped looking clean. Composing an existing domain fact is only correct DDD when it's the *right* fact for the question being asked, not merely one that's already lying around and usually correlates.

## Gap 35 — Cross-Midnight Block Support, Part 1: A Domain-Wide UTC/Local Day-Boundary Bug Surfaced and Fixed Before the Feature It Blocked *(closed, 2026-08-25)*

**The task:** Open Gap K Part 1 — make a block spanning midnight (e.g. 22:00–01:00) representable and correctly handled everywhere, so Part 2 (the Planner Time Range Editor) has solid ground to build on. Domain/Application only — deliberately no UI this slice, since the Planner form's single shared `DatePicker` can't represent a cross-day End until Part 2 ships; verified entirely by tests.

**What was already correct, confirmed by reading the code before writing anything:** `PlannedFocusHoursCalculator` already split a range's hours across the days it occupies; `PlannedBlock.Reschedule`/`FocusBlock.Create` had no same-day constraint to remove; `PlannedBlockRepository.GetForDayAsync` already queried by overlap, not "starts on this day"; `PolicyEngine.ComputeSlice` was purely instant-based, never date-based. None of these needed to change.

**The detour that became the real prerequisite.** Tracing "which day does this credit belong to" surfaced that `PlannedFocusHoursCalculator`'s caller fed it raw UTC ranges with no local conversion — meaning its day-keyed dictionary was keyed by *UTC* calendar day, while every date-comparison elsewhere in the codebase explicitly converts to local first. Pulling that thread found the same missing-conversion mistake independently repeated in **six** places: both `AllowsBlockPlacement` call sites (Work Hours — not an edge case, this one misfired for *every* block under a Work-Hours contract for any non-UTC user), `GetNenContractCompletedFocusHoursQueryHandler` (both branches), `ComputeRedemptionAttributionQueryHandler` (redemption day-eligibility), `GetSessionSnapshotForBlockQueryHandler` (a display date), and `GetActiveNenContractQueryHandler` ("today," driving the contract banner's Day X/Y and every day-status badge). Two call sites — `SplitPlannedBlockValidator` and `UpdatePlannedBlockValidator`'s `AllowsBlockTimeChange` path — already did this correctly. The existing test suite could never have caught any of it: `WorkHoursTests.cs` built its `DateTime`s with plain `new DateTime(...)` (`Unspecified` kind, no real offset), so no test exercised a genuine UTC/local mismatch.

**Fix: one testable seam, not six independent patches.** `ISystemClock` gained `DateTime ToLocal(DateTime utc)`, plus a `ToLocalDate` extension — the same interface tests already substitute to control `UtcNow` now makes a non-UTC offset directly provable, closing the reason this went undetected in the first place. All eight call sites (six broken, two normalized for consistency) route through it. Two gained `ISystemClock` as a new constructor dependency.

**The feature itself, built on that corrected foundation:**
- `IFocusBlockOutcomeClassifier` gained `CreditedWindow(...)`, returning the real `(Start, End)?` window backing whatever `CreditedFocusMinutes` would return — every branch of the existing scalar turned out to already be secretly a duration of a real window. `CreditedFocusMinutes` was refactored to derive its number from `CreditedWindow`'s duration, so the two can never disagree.
- One new pure Domain primitive, `DayRangeSplitter.Split`, extracted from `PlannedFocusHoursCalculator`'s existing day-walk loop and reused by three call sites instead of being copied a third and fourth time — justified by precedent, not hypothetically: the exact-midnight tick-subtraction fix was already independently reimplemented twice (`SplitPlannedBlockValidator`, `UpdatePlannedBlockValidator`) before this gap.
- `NenContract.AllowsBlockPlacement` generalized from `(DateOnly date, DateTime start, DateTime end)` to `(DateTime localStart, DateTime localEnd)`, walking day-by-day and checking each day's segment against that day's own `WorkHoursPolicy`.
- `GetNenContractCompletedFocusHoursQueryHandler` rewritten to compose `CreditedWindow` with `PlannedFocusHoursCalculator` for the per-day split. Along the way, its existing `Classify` call turned out to be fully redundant once `CreditedWindow` existed — every case where `Classify` returns a resolved outcome exactly matches where `CreditedWindow` returns a non-null window (verified case by case, not assumed) — so it was dropped rather than kept as a second, independently-computed way of answering the same question.
- `SplitPlannedBlockValidator` generalized to let its two resulting pieces land on *either* day a cross-midnight original spans (each piece still resolving to a single day — no recursive crossing, matching Part 2's decision to leave the Split dialog's UI untouched), deliberately not floor-protected (matching Split's existing unprotected behavior for ordinary same-day splits — confirmed no floor check existed there before this gap either). **Split was also restricted to Focus blocks only**, removing Background block Split entirely (`PlannerPageViewModel.CanSplitBlock` had no type gate before this — Background Split was genuinely reachable in the live UI). This was a deliberate scope call, not a forced one: Background has no duration cap and could in principle span 3+ days, and restricting Split to Focus (capped at 12h once Part 2 lands, so at most 2 days) removes that case entirely rather than needing to guard against it. A defensive guard against a 3+ day original was added anyway, since Focus isn't actually capped yet until Part 2 ships — rejecting outright rather than letting the 2-day-only logic silently misapply.

**A second representational gap found by the tests written to prove the first fix, not anticipated in the design.** `DayRangeSplitter` always ends a non-final day-segment exactly at midnight, but `WorkHours.End` is a `TimeOnly`, which cannot represent "24:00" — so a segment ending exactly at midnight could never satisfy *any* Work Hours window, no matter how late it was configured, defeating the entire point of the per-day generalization for the night-shift case it exists for. Fixed the same way the codebase already resolves "exact midnight has no presence on the next day" for date extraction (`SplitPlannedBlockValidator`, `UpdatePlannedBlockValidator`): when a day-segment's end lands exactly at midnight, check `ContainsRange` against one tick earlier instead. Verified safe for every ordinary (non-midnight) boundary case — the adjustment only ever changes the outcome in the narrow gap between "exactly at midnight" and "one tick before midnight," which is exactly the gap `TimeOnly`'s representable range can't otherwise close.

**Known, deliberately out-of-scope UI-layer twin, flagged not fixed.** `PlannerPageViewModel.ValidateDraftPlacement` has its own separate, non-day-segmented Work Hours check for contract-drafting-mode blocks (no `NenContract` exists yet to delegate to during drafting). It shares the same "not yet cross-midnight-aware" gap `AllowsBlockPlacement` had — but since no UI path can create a cross-midnight block yet (this gap's own verification posture), it's unreachable today. Worth fixing when Part 2 ships the real editor, not before.

**Confirmed via `NenFocus.Tests` (1058 passing, up from 1032):** new cases throughout for cross-midnight blocks and sessions, the UTC/local fix (a deliberately non-UTC-offset mock at each of the eight call sites, not just identity), the Work Hours midnight-boundary fix, and Split's Focus-only/2-day/N-day-guard rules.

**Principle demonstrated:** the bug that mattered most here was never the one the task set out to fix. Tracing "which day does this belong to" one level deeper than the immediate feature required surfaced a domain-wide correctness bug — six independent instances of the same missing conversion — that existed before cross-midnight blocks were ever discussed, and that this feature would have silently inherited and made worse (cross-midnight times cluster exactly where local/UTC calendar days diverge). Verifying a claim against the live code, rather than trusting a plausible design write-up, is what turned "let's build the feature" into "let's fix the foundation, then build on it."

## Gap 38 — Open Gap L Closed: the Dropdown Never Had a Traversal Bug, It Had a Wrong Constant *(closed, 2026-08-26)*

**Approach, not another guess.** Three prior attempts (Gap 37, all now Open Gap L history) each landed a fix that looked correct — the last one even passed a real, repeated headless repro — and each still failed in the live app for an unexplained reason. A fourth "confident" fix built the same way risked the same outcome. Instead of reasoning from another isolated repro, temporary instrumentation was added directly to `ScrollDropdownToWindow` (`PlannerPageView.axaml.cs`): every attempt, popup/list/`ScrollViewer` lookup result, `Extent`/`Viewport`/`Offset` before and after the set, and several post-layout ticks were logged. Since Claude has no way to drive or observe the live GUI directly, the log was written to a plain temp file (`%TEMP%\nenfocus_dropdown_diag.log`) alongside `Debug.WriteLine`, so it could be read back directly after the architect reproduced the bug — no copy-paste, no debugger attached required.

**What the data actually showed:** the offset-setting mechanism from Gap 37's third attempt was never broken. Every attempt found the popup, the list, and the `ScrollViewer` on the first try (no retries ever needed), set `Offset` to its computed target, and that value stuck — confirmed unchanged across 8 repeated `LayoutUpdated` ticks per open, no later reset. The actual defect was the number being set: `ScrollDropdownToWindow` converted a target row index to pixels using a hardcoded `DropdownItemHeightPx = 33`, measured once via an isolated headless Avalonia layout pass. Live-app data told a different story — `scrollViewer.Extent.Height / list.ItemCount` came out to **exactly 38px per row**, not 33, reproduced identically for both Start's plain-string 97-item list (`3686 / 97`) and End's `TimeText`+`Duration`-templated 26-item list (`988 / 26`). The further into the list the target time was, the larger the resulting scroll error (`index × 5px`), which is exactly the "still broken, in a way nobody could pin down" symptom Open Gap L described. Presumably the headless layout pass simply doesn't reproduce whatever real Windows theme/DPI/font metrics the live app renders with — the same class of "a close approximation isn't the real thing" lesson Gap 37 already drew, just found this time in a measurement rather than a tree-traversal path.

**The fix:** `ScrollDropdownToWindow` now derives the row height at runtime — `scrollViewer.Extent.Height / list.ItemCount` — instead of trusting any hardcoded constant. This is self-correcting regardless of whatever theme, DPI, or font actually renders the popup; there is no longer a pixel number to keep in sync with the real control. `DropdownItemHeightPx` was deleted.

**A related, second bug found by the same fresh eyes, same session:** `MaxDropDownHeight="171"` (Gap 37, derived from the same wrong 33px figure: `5 × 33 + 6`) consequently didn't actually cap the popup at 5 rows — at the real 38px row height it showed either fewer than 5 rows or a visible sliver of the next one, depending on which box. Corrected to `196` (`5 × 38 + 6`), landing the `ScrollViewer`'s viewport at exactly 190px. Verified via 8 repeated `LayoutUpdated` ticks per open that `Viewport` holds rock-steady at that number the whole time — ruling out a "still-settling" theory before changing anything, the same discipline that found the first bug.

**Confirmed working in the real running app by the architect** — not an isolated repro. Both the centering fix and the height fix were validated live, in two separate manual passes, before the diagnostic instrumentation was removed. Full solution builds with 0 warnings, 0 errors.

**Principle demonstrated:** the fix for "a controlled experiment isn't a substitute for the real thing" (Gap 37's own stated lesson) isn't "try harder to build a better experiment" — it's to stop experimenting in a vacuum and instrument the real thing directly, then read back what it actually did. Three attempts reasoned about the live app from isolated approximations of it; the fourth read the live app's own numbers and found a bug none of the three were even looking for.

## Gap 40 — Every ViewModel Shared One `DbContext` for the App's Entire Runtime, Silently *(closed, 2026-08-30)*

**The report that started it:** manual QA of Gap 39's Planner badge/confirm-gate work turned up something unrelated — after completing a `StartedLate` Focus block under an active Nen Contract, the Planner's deficit banner kept showing 0h deficit and no Cover Deficit button, even though the block genuinely fell short of its floor. Reopening the app fixed it immediately.

**Root cause, chased down with real production handlers against a copy of the live database, not guessed at.** A throwaway console harness (referencing the real `NenFocus.Domain`/`Application`/`Infrastructure` projects) ran `GetNenContractDeficitsQueryHandler` and `GetActiveNenContractQueryHandler` directly against a copy of the architect's actual `%APPDATA%\NenFocus\NenFocus.db`. The math was exactly right — a real 0.21h deficit, matching the banner's own "1.8h/2h completed" figure to the decimal. So the bug wasn't in the Application layer at all; it was that the live UI never re-ran the query after the session ended.

**Tracing *that* surfaced the real architecture bug.** `App.axaml.cs` resolves the entire ViewModel tree with `Program.AppHost!.Services.GetRequiredService<ShellViewModel>()` — straight from the root DI container, no scope ever created. `NenFocusDbContext` is registered Scoped. Resolving a Scoped service from root is normally rejected by `ServiceProviderOptions.ValidateScopes`, but `Host.CreateDefaultBuilder` only turns that on automatically in the `"Development"` environment, and nothing in this app ever sets `DOTNET_ENVIRONMENT` — confirmed by grep, zero occurrences anywhere in the repo. So the resolution silently succeeded, and the single `DbContext` instance it produced lived for the rest of the process, shared by every repository behind every one of `ShellViewModel`'s 34 constructor-injected `IQueryHandler`/`ICommandHandler` fields — including the ~15 flowing down into `PlannerPageViewModel` alone. `PlannerPageViewModel`'s own 3-second `_floorStatusPollTimer`, its `SessionChanged`-triggered refresh, and ordinary user actions (Save, week navigation) all fire overlapping async operations against that one shared context, all via `Dispatcher.UIThread.Post(() => _ = SomeAsync())` — fire-and-forget, no `try/catch` anywhere in the chain. EF Core's `DbContext` isn't thread-safe; two overlapping operations throw `InvalidOperationException: A second operation was started on this context before a previous operation has completed`, and because every call site is fire-and-forget, that exception becomes an unobserved task exception — no crash, no error shown, the ViewModel just silently stops updating. Empirically reproduced by resolving `ShellViewModel` from a `ServiceCollection` built with `ValidateScopes: true`: `Cannot resolve 'NenFocus.ViewModels.ShellViewModel' from root provider because it requires scoped service 'NenFocus.Application.Interfaces.IBlockPresetRepository'.`

**Not a new mistake — a known one that stopped at the Application layer.** `InProcessDomainEventPublisher` already "creates a new DI scope per event handler to avoid `DbContext` concurrency issues" (`TECHNICAL_SPEC_INFRA.md`), and `SessionStateService`/`ActiveSessionMonitor` already resolve their own repositories from a fresh `IServiceScopeFactory.CreateScope()` per operation rather than holding constructor-injected ones. The UI layer's own query/command handlers, wired straight into long-lived ViewModels, were never brought under the same discipline.

**Interrogated before any code, per the architect's own request — the mechanism decision, made explicit:**
- **Rejected as a non-fix:** wrapping `ShellViewModel`'s own resolution in one explicit `IServiceScope` at startup. Still one `DbContext` shared by the whole tree — same bug, no throw.
- **Rejected: `IServiceScopeFactory` injected directly into every ViewModel, scope-management boilerplate repeated at every one of the ~50+ call sites.** No new abstraction, but leaks a raw DI-container primitive into the presentation layer — a composition-root concern crossing the "Dependencies only flow inward" boundary `ARCHITECT_GOVERNANCE.md` states as a rule — and scatters a cross-cutting concern that this codebase otherwise always centralizes once (`TransactionalCommandHandler`, `ValidatingCommandHandler`, `InProcessDomainEventPublisher`).
- **Settled: `IQueryDispatcher`/`ICommandDispatcher`.** Two new Application-layer interfaces (mirroring the existing `IQueryHandler`/`ICommandHandler` CQRS split — never one combined interface), each with exactly one generic method (`QueryAsync<TResult>(IQuery<TResult>)` / `DispatchAsync<TResult>(ICommand<TResult>)`, `TResult` inferred from the codebase's existing `IQuery<TResult>`/`ICommand<TResult>` markers — no second type parameter needed at call sites). Infrastructure implementations (`ScopedQueryDispatcher`/`ScopedCommandDispatcher`) hold only `IServiceScopeFactory`, registered `AddSingleton` (stateless, thread-safe), and internally do `using var scope = ...; var handler = scope.ServiceProvider.GetRequiredService(closedHandlerType); await handler.HandleAsync(...)` — one fresh scope, and therefore one fresh `DbContext`, per dispatch. The reflection needed to build the closed `IQueryHandler<,>`/`ICommandHandler<,>` type from `query.GetType()` isn't a new pattern either — `RegisterDecoratedCommandHandlers` already does the same `MakeGenericType`/`Activator.CreateInstance` work.
- **Scope granularity confirmed, not assumed:** one scope per individual dispatch, not per user action — `SaveAsync()`'s create-then-reload-then-refresh sequence becomes three independent scopes. Verified safe: SQLite is a real file, not an in-memory cache tied to one context, so a fresh `DbContext` in the next call always sees whatever the previous one just committed. A real end-to-end test proves this (`DispatcherIntegrationTests`: a command dispatched through one scope, a query dispatched through a different scope right after, sees the write).
- **Breadth, the architect's own call:** migrate every ViewModel in one pass rather than leaving the vulnerability live anywhere else, since it's identical everywhere `ShellViewModel`'s constructor-injected handlers reach.

**A second, independent bug found and fixed while building the dispatcher's own integration test, not part of the original report.** `DependencyInjection.cs` registered `AddDbContextFactory<NenFocusDbContext>` and `AddDbContext<NenFocusDbContext>` independently for the same context type — this alone (unrelated to the dispatcher) broke resolving `NenFocusDbContext` from *any* real DI scope under `ValidateScopes: true`, with a misleading "from root provider" message even when resolved from a real created scope. `CompositionRootTests` never caught it because it only builds the container, never resolves anything from it. Fixed with the Microsoft-documented pattern — register the factory once, derive the Scoped registration from it (`services.AddScoped<NenFocusDbContext>(sp => sp.GetRequiredService<IDbContextFactory<NenFocusDbContext>>().CreateDbContext())`) — verified empirically (resolves under strict validation; two different scopes get two different instances; the *same* scope resolving twice still gets the *same* instance, preserving the change-tracker-sharing a single command handler's multiple repository calls depend on; the factory itself still works unchanged for its existing singleton consumers). `CompositionRootTests` gained a test that actually resolves `NenFocusDbContext` from a scope, closing the exact hole that let this slip through originally.
